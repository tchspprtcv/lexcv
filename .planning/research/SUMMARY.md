## Executive Summary

Cross-entity global search is a well-understood, heavily-precedented UI/backend pattern (the "command palette," as popularized by Linear, Notion, GitHub, and Vercel): one debounced text input fans out across several data sources and returns grouped, click-to-navigate results behind a keyboard shortcut. What makes this instance notable is how little of it is actually new construction: LexCV already has every piece required and simply hasn't wired them together. The frontend already ships `cmdk@1.1.1` and shadcn's `CommandDialog`/`CommandGroup`/`CommandItem` primitives (installed in v2.13 Phase 107 for the `Combobox` component, unused as a top-level palette), and the header's "Pesquisar processos, entidades..." input is already sitting exactly where a palette trigger belongs — it is 100% decorative today (no `onChange`, no state). The backend needs no new dependency either: PostgreSQL 16 (the exact `postgres:16-alpine` image already deployed) ships `unaccent` and `pg_trgm` compiled in, and this codebase already has two working precedents for tenant-scoped `ILIKE` search (`ParecerSolicitacaoRepository.pesquisar()`, `NotificacaoRepository.buscarPorFiltros()`) to extend rather than reinvent. At LexCV's actual scale (a handful of institutional tenants, thousands not millions of rows each), plain `ILIKE` wrapped in `unaccent()` is the correct MVP technique — `pg_trgm` GIN indexing and `tsvector` full-text search are documented, real, and deliberately deferred until row counts or a relevance-ranking requirement actually justify them.

The recommended approach is a server-side merge into one new, dedicated `SearchController` (`GET /api/v1/search?q=`) that queries all 4 existing repositories itself and returns a single discriminated-union `SearchResultDto` list — the same "merge several entity types into one response" pattern this codebase already uses for `GET /processos/{id}/timeline`. This beats 4 parallel client-side calls on every measurable axis here: `GET /documentos` has no free-text filter today (client-merge isn't actually "no backend work"), each existing endpoint 403s independently per role so a client merge needs 4 defensive try/catch blocks, and a single endpoint can omit a whole entity category for a caller lacking that scope with zero extra logic. RBAC is the crux of the design: because all 4 seeded roles currently hold `view` on all 4 target entities, a single coarse `@PreAuthorize` would not visibly misbehave today — but it is still wrong, because roles are DB-managed and administrable, and because the real, current role differential in this system (`financeiro:view`, which ASSISTENTE lacks) can leak into search results indirectly, through `Honorario` data pulled in while enriching a `Processo` result preview. The correct shape — confirmed against Microsoft Graph Search API's own "gate before fetch, not after" authorization model — is to branch per entity type inside the handler, querying (not fetching-then-filtering) only the categories the caller's actual authorities permit.

The primary risks are security- and correctness-shaped, not UX-shaped, and every one of them has a direct, low-cost mitigation grounded in this exact codebase's own history: (1) tenant isolation must hold independently across all 4 branches, with special care for any entity or repository method lacking its own `tenant_id` — `Honorario` has none and must never be reached by this feature, and this project has already shipped this exact class of silent-filter bug twice (`GET /honorarios?processo_id=X`, `GET /documentos?processo_id=X`); (2) RBAC must be checked per entity-type branch, never as one blanket gate, and financial data must never opportunistically ride along in a `Processo` preview; (3) hydrating cross-entity breadcrumbs (a `Processo` hit's client name, a `Documento` hit's linked processo) must be batch-fetched (`findAllById` + `Map`), not looped per row — this exact N+1 anti-pattern already lives, uncorrected, in `ResourceController.listHonorarios()`; and (4) ranking must be explicit (exact/prefix structured-ID match before fuzzy substring) and, if `cmdk`/`Command` renders the results, `shouldFilter={false}` must be set explicitly (as `combobox.tsx` already had to do once) or cmdk's own default fuzzy scorer will silently re-sort or hide the server's correctly-ranked results. None of this requires new infrastructure, new libraries, or a new architectural concept — it requires disciplined reuse of patterns this codebase has already proven, applied correctly and independently to a genuinely new, tenant-isolation-and-RBAC-sensitive surface.

## Key Findings

### Recommended Stack

No new backend or frontend dependency is warranted. See `.planning/research/STACK.md` for full detail; the short version is that this codebase already has 100% of what it needs, and the actual decision is which SQL technique fits LexCV's real scale (thousands, not millions, of rows per tenant) — plain `ILIKE` wins for v1.

**Core technologies:**
- PostgreSQL `unaccent` (contrib extension, already compiled into the deployed `postgres:16-alpine` image) — strips diacritics before comparison, closing a real UX gap for Portuguese names ("Conceição" vs. "Conceicao"); enabled via a one-line `CREATE EXTENSION`, no Dockerfile/image change
- `ILIKE` inside native `@Query` (Spring Data JPA, already in `pom.xml`) — reuse the exact idiom already proven twice in this codebase (`ParecerSolicitacaoRepository.pesquisar()`, `NotificacaoRepository.buscarPorFiltros()`), not a new search paradigm
- `pg_trgm` (contrib extension) — enable now (free, already compiled in) but don't use its indexing/similarity capability until row counts genuinely justify it; this converts a future "provision a new extension" step into a future "add one index" step
- `cmdk@1.1.1` / shadcn `CommandDialog`/`CommandGroup`/`CommandItem`/`CommandEmpty` (already installed since v2.13 Phase 107, currently only used inside `Combobox`) — exact-fit primitive for "grouped by entity type, keyboard-triggered palette"; this is a wiring exercise, not new UI construction
- `@tanstack/react-query` (already installed) — a new `useGlobalSearch(query)` hook, same shape as every other `use-*.ts` hook

**Explicitly avoid:** Elasticsearch/OpenSearch/Meilisearch/Algolia/Typesense or Hibernate Search (wrong tool for a single-VPS deployment at this row count, and a second place tenant scoping would need re-implementing outside SQL); Apache Tika/OCR (a different, much larger feature — searching file *contents*, not metadata — not what's scoped); QueryDSL/jOOQ/Blaze-Persistence (no problem left for a query-builder to solve at 4 native `@Query` methods); a new debounce package (10-line local hook suffices); `tsvector`/full-text search and `pg_trgm` similarity/GIN indexing pre-emptively (real, documented, correct *next steps*, not v1 — see STACK.md's "Stack Patterns by Variant").

### Expected Features

See `.planning/research/FEATURES.md` for full detail, including a complete MVP/v1.x/v2+ breakdown and a feature-dependency graph.

**Must have (table stakes, P1):**
- One new unified backend endpoint searching Cliente, Processo, Documento, and ParecerSolicitacao for the caller's tenant — the literal ask ("endpoint novo")
- Structured-identifier-aware matching (`numero_cliente`, `numero_processo`, `nif`, `documento_numero`), not just free-text name/description — the domain-specific crux: institutional users type exact codes as often as names, and 2 of the 4 entities (Documento, ParecerSolicitacao) have no other reliable lookup path
- Exact/prefix matches on structured identifiers ranked at or above fuzzy substring matches
- Search-as-you-type with ~300ms debounce and a minimum query length (e.g. 2 chars) before firing
- Results grouped by entity type with a disambiguating subtitle per result (e.g. Cliente → `CLI-0001 · NIF 123456789`)
- Click a result → navigate to its existing detail route, palette closes (zero new routing — all 4 `/[id]` routes already exist)
- Visible trigger (convert the existing decorative header `<Input>`) **and** `Ctrl+K`/`⌘K` shortcut — PROJECT.md explicitly asks for both
- Per-entity-type RBAC gating inside the search itself (not one blanket check) and tenant isolation on every sub-query — both non-negotiable
- Empty / loading / no-results states (mostly free via `CommandEmpty`)

**Should have (differentiators, v1.x — deliberate include/defer call, not implied by literal scope):**
- "Ver todos os resultados de [Tipo]" overflow link per group, deep-linking into that entity's list page with the query pre-filled
- Recently-viewed **records** (not query strings) in the empty/pre-query state — client-side/session-local only, given the confidentiality reasoning below
- Matched-substring highlighting in result labels

**Defer (v2+, explicitly anti-features for this milestone):**
- Full-text/OCR search inside uploaded document contents — `Documento` stores only metadata today; a genuinely larger, separately-scoped feature
- Fuzzy/typo-tolerant matching (`pg_trgm` similarity) — unlikely to matter given how identifier-heavy this domain's queries are; revisit only with evidence
- Command-palette-as-action-launcher (create/navigate actions beyond record search) — roughly doubles scope, different feature class
- **Persisted search history / saved searches / search analytics** — actively avoid, not just defer: for a legal-practice tool, a visible list of recently-*typed* query strings on a shared workstation is a real confidentiality leak (e.g., exposing a colleague's search for a sensitive client name), and saved searches duplicate what Pareceres' existing advanced-search page and the new Processos estado filter already do

### Architecture Approach

See `.planning/research/ARCHITECTURE.md` for the full component/data-flow diagrams and 7 documented anti-patterns. The design is: one new, dedicated `SearchController` (never appended to the already-3,296-line `ResourceController`) that injects the 4 existing repositories directly (no new repository or service layer needed — all 4 already expose `findByTenantId(UUID)`), branches per entity type on the caller's actual `Authentication.getAuthorities()` (querying only categories the caller can see — never "fetch then hide"), and merges results into one flat `List<SearchResultDto>` (a plain Java `record`, mirroring the existing `TimelineItemDto` discriminated-union pattern exactly, deliberately avoiding the `Map<String,Object>` convention used by older list endpoints and its known camelCase/snake_case drift history). The frontend mirrors `NotificationBell`'s self-contained-shell shape: a new `GlobalSearchDialog` owns its own open-state and Cmd/Ctrl+K listener, backed by a `useGlobalSearch` TanStack Query hook and a small new `useDebouncedValue` hook, mounted once from `dashboard-shell.tsx` in place of the decorative input.

**Major components:**
1. `SearchController` (new, `backend/.../controllers/`) — owns `GET /api/v1/search`, resolves tenant + authorities once, branches per entity type, merges results (~80-120 lines)
2. `SearchResultDto` (new record, `backend/.../dtos/`) — unified discriminated shape across all 4 entity types, mirrors `TimelineItemDto`
3. `GlobalSearchDialog` (new, `web/src/components/shared/`) — Cmd/Ctrl+K listener, `CommandDialog` overlay, grouped rendering, click-to-navigate; mounted once, same relationship `dashboard-shell.tsx` already has with `NotificationBell`/`UserMenu`
4. `useGlobalSearch` + `useDebouncedValue` (new hooks, `web/src/hooks/` and `web/src/lib/`) — TanStack Query wrapper + a ~10-line debounce hook, zero new deps

**Build order (architecture's own explicit recommendation): backend before frontend.** This matches how every comparable cross-cutting feature in this codebase's history was sequenced (Pareceres backend in v2.5 then UI in v2.6; Notificações persistence/API in v2.10 Phases 85-88 before the bell/page UI in Phase 89) — there is no mock-API layer left in this project to build speculatively against. The backend contract (`SearchController` + `SearchResultDto`, with at least one test per RBAC branch) should exist and be stable before `GlobalSearchDialog`/`useGlobalSearch` wiring starts.

### Critical Pitfalls

See `.planning/research/PITFALLS.md` for full detail, including a "Looks Done But Isn't" checklist and a pitfall-to-phase mapping table this summary's roadmap section draws on directly.

1. **Tenant isolation leak via an entity with no `tenant_id` of its own, or an unscoped repository method reused because "it's already there."** `Honorario` has no own `tenant_id` (only a transitive `processo_id` FK) and must never be queried by text/ID match directly — join through `t_processo` or reuse the existing `findByProcessoIdIn` batch method against a pre-tenant-checked ID set. This exact bug shape (a filter defined but not actually wired into the query) has already shipped twice in this codebase (`GET /honorarios?processo_id=X`, `GET /documentos?processo_id=X`). **Avoid by:** one independently-tenant-scoped query per entity type, each starting from that table's own `tenant_id` (or a verified join for `Honorario`); a Testcontainers IT seeding 2 tenants with matching search tokens, asserting zero cross-tenant rows.
2. **A single coarse `@PreAuthorize` lets `financeiro` data leak into search results via hydration, even though all 4 *named* target entities currently share identical role access.** The real, current role gap in this system is `financeiro:view` (ASSISTENTE lacks it) — the risk isn't the 4 named entities misbehaving today, it's a `Processo` search-result preview opportunistically pulling in linked `Honorario.valorTotal`/status "since the join is natural" (this codebase already shipped exactly that join once, for `Termo de Honorários`, v2.9). **Avoid by:** minimal method-level `@PreAuthorize` (authenticate only), then 4 independent `hasAuthority(auth, "<scope>:view")` checks inside the handler body gating whether each repository is queried *at all*; never embed `Honorario`/`Pagamento` fields in a `Processo` result unless the caller separately holds `financeiro:view`.
3. **N+1 query explosion hydrating cross-entity breadcrumbs/labels** (a `Processo` hit needs its `Cliente.nome`, a `Documento` hit needs its linked `Cliente`/`Processo`, etc.) — none of the 5 entity models have JPA associations (every FK is a bare `UUID`), so nothing structural stops a per-row `findById()` loop. This is not hypothetical: `ResourceController.listHonorarios()`'s no-filter branch still does exactly this today, despite a batch-fetch method (`findByProcessoIdIn`) already existing elsewhere in the codebase specifically to fix it. **Avoid by:** collect all referenced IDs once across all 5 result lists, issue one `findAllById(...)` per referenced entity type, hydrate from in-memory `Map`s.
4. **Naive substring search buries exact structured-ID matches, and `cmdk`'s default client-side filter can silently undo the backend's ranking.** Neither existing search precedent in this codebase (`listClientes`'s in-memory filter, `ParecerSolicitacaoRepository.pesquisar()`) produces a relevance score; concatenating 4 unordered lists produces no meaningful order. Separately, `cmdk`'s `Command` defaults `shouldFilter` to `true` and a `command-score` of `0` **hides** an item entirely, not just deprioritizes it — this project's own `combobox.tsx` already had to explicitly disable this once. **Avoid by:** an explicit tiered ranking (exact ID match > prefix match > substring match, stable secondary sort by recency), computed server-side; and, if `Command`/`cmdk` renders results, `shouldFilter={false}` set explicitly, copying `combobox.tsx`'s pattern rather than reimplementing from scratch.

## Implications for Roadmap

Based on combined research, suggested phase structure for the full v2.14 milestone (5 targets). **Phases 1-3 map to target #1 and #2 (PROJECT.md's "fechar gaps de UX" clause) and are backed by all 4 deep-research files, HIGH confidence. Phases 4-5 map to targets #4, #3, #5 (PROJECT.md's "próximo passo na linguagem visual" clause) and are grounded only in PROJECT.md's own framing plus a light grounding check of this session (confirmed: `lucide-react@^0.543.0` already the established icon library, `Tooltip` primitive already installed since v2.13 Phase 108, `--radius` already a single isolated CSS custom property in `web/src/app/globals.css:75`) — not by dedicated research. Treat Phases 4-5's rationale as reasonable inference, not verified findings.**

### Phase 1: Backend — Cross-Entity Search API
**Rationale:** ARCHITECTURE.md's explicit recommendation is "build order: backend before frontend," matching this project's own established sequencing precedent (Pareceres, Notificações). All 4 critical pitfalls (tenant isolation, RBAC leak, N+1, ranking) live primarily at the data/API layer and must be correct and independently tested before any UI consumes the contract — nothing downstream can be trusted if this layer is wrong.
**Delivers:** New `SearchController` (`GET /api/v1/search?q=`) + `SearchResultDto` record; 4 tenant-scoped per-entity search branches (Cliente/Processo/Documento/ParecerSolicitacao) reusing existing repositories, each independently RBAC-branch-gated (query only if the caller holds that scope, never fetch-then-filter), plus a coarse `hasAnyAuthority` method-level fast-fail; structured-identifier-aware matching (`numero_cliente`, `numero_processo`, `nif`, `documento_numero`) with exact/prefix-first tiered ranking ahead of substring matches; batch cross-entity hydration (`findAllById` + `Map`, never per-row `findById` loops); `unaccent`/`pg_trgm` PostgreSQL extensions enabled via a new numbered `backend/migrations/*.sql` file (this project's established manual-migration convention, no Flyway/Liquibase); a Testcontainers IT (mirrors `NotificacaoRepositoryIT`) seeding 2 tenants with matching search tokens across every entity type including `Honorario`, asserting zero cross-tenant leakage; a per-role (ADMIN/ADVOGADO/TECNICO/ASSISTENTE) test matrix confirming zero `Honorario`-sourced fields ever appear in any response.
**Addresses:** FEATURES.md P1 items — unified backend endpoint, structured-identifier matching + exact-match-first ranking, per-entity RBAC gating + tenant isolation (all "essential, inseparable from the feature").
**Avoids:** PITFALLS.md Pitfall 1 (tenant isolation leak via `Honorario`/unscoped repo methods), Pitfall 2 (RBAC bypass via financeiro hydration), Pitfall 3 (N+1 hydration), Pitfall 4's backend half (unranked/buried exact-ID matches).

### Phase 2: Frontend — Global Search Command Palette
**Rationale:** Depends on Phase 1's stable, RBAC-tested backend contract. Reuses existing, currently-unused `cmdk`/shadcn `CommandDialog` primitives installed since v2.13 Phase 107 — this is substantially a wiring exercise, not new component construction, which is why FEATURES.md rates it LOW complexity across nearly every row.
**Delivers:** New `GlobalSearchDialog` component (self-contained, mirrors `NotificationBell`'s own-state pattern) wired into `dashboard-shell.tsx` in place of the decorative header `<Input>`; new global `Ctrl+K`/`⌘K` keydown listener (no existing pattern to reuse — genuinely new, ~10 lines); new `useDebouncedValue` (~300ms) + `useGlobalSearch` (TanStack Query) hooks; results grouped via `CommandGroup` by entity type with disambiguating subtitles; `shouldFilter={false}` explicitly set (copying `combobox.tsx`'s already-proven workaround); click-through navigation to the 4 existing detail routes, palette closes on select; empty/no-results states via `CommandEmpty`; entity-type-section rendering gated on `permissions.isFetched` (never `!permissions.isLoading` — a recurring bug class in this codebase per Phase 103/105/v2.13-audit history).
**Addresses:** FEATURES.md P1 items — `CommandDialog` palette wired to trigger, `Ctrl+K`/`⌘K` shortcut, debounce + minimum query length, grouped results with subtitles, click-through navigation.
**Avoids:** PITFALLS.md Pitfall 4's frontend half (cmdk `shouldFilter` gotcha), the Performance Trap of firing a full 4-entity fan-out on every keystroke without debounce, the UX Pitfall of rendering an empty section for a scope the caller lacks, the recurring `permissions.isFetched`-vs-`isLoading` race.

### Phase 3: Processos — Filtro por Estado
**Rationale:** Narrow, single-module, additive feature that completes PROJECT.md's "fechar gaps de UX" clause alongside Phases 1-2. `Processo.estado` already exists as a queryable field (confirmed in FEATURES.md's existing-search-fields inventory), and the `Select`-based filter pattern is already established precedent from v2.13 Phase 106 (Agenda's categoria/status filters). Sequenced before the visual-language phases so its own filter-toolbar controls exist before the app-wide icon/tooltip sweep (Phase 5) needs to cover them.
**Delivers:** New `estado` `Select` filter on the Processos list, following the existing filter-toolbar pattern already used elsewhere in the app.
**Note:** Not covered by dedicated research this pass (see Scope Note); low-risk given direct precedent already in this codebase.

### Phase 4: Visual Language Foundation — Cantos Arredondados (`--radius`)
**Rationale:** A single, already-isolated global CSS custom property (`--radius` in `web/src/app/globals.css:75`, feeding `--radius-sm/md/lg/xl/2xl/3xl/4xl` derived values) — the same low-risk, foundational shape as v2.13's own Phase 1 token work. PROJECT.md frames this as a deliberate, conscious reversal of the v2.13 "institutional document" identity (`--radius: 0` → rounded). Doing this before the icon sweep (Phase 5) avoids visually re-reviewing every touched screen twice.
**Delivers:** `--radius` value change + a full-app visual QA pass (every card/button/input/dialog corner) across `web/` (and `webpage/` if it shares the token).
**Note:** Not covered by dedicated research this pass; grounded only in a direct confirmation this session that the token is already fully isolated to one variable, making the change itself mechanically trivial — the actual work is the visual QA sweep, not the CSS change.

### Phase 5: Visual Language — Ícones em Todos os Botões + Filtros Ícone-Only
**Rationale:** Targets #3 ("ícones em todos os botões da aplicação") and #5 ("botões de ação de filtro ícone-only com tooltip, em todos os módulos") both touch the same button-bearing surfaces across every module and both depend on primitives already established in this codebase (`lucide-react@^0.543.0`, the app's existing icon library; the `Tooltip` primitive, already installed and in production use since v2.13 Phase 108) — combining avoids two separate passes over the same files. This phase is sequenced **last** deliberately: "icons on all buttons" must include the new search trigger (Phase 2) and the new estado-filter controls (Phase 3), so it cannot correctly run before those buttons exist.
**Delivers:** Icons added to all application buttons; filter action buttons (aplicar/limpar/exportar) across every module converted to icon-only with a hover tooltip, reusing the existing `Tooltip` primitive for the resulting accessibility requirement.
**Note:** Not covered by dedicated research this pass; PROJECT.md itself frames these as the "next step in the visual language," implying lower functional risk than Phase 1's security-sensitive search work, but the roadmapper should still verify actual file-count/surface-area scope during planning given how many modules this touches.

### Phase Ordering Rationale

- **Phases 1 and 2 must be sequential, not merged or reordered**, per ARCHITECTURE.md's explicit, codebase-precedented recommendation (Pareceres, Notificações) — the backend contract must be stable and independently RBAC/tenant-tested before the frontend consumes it, since there is no mock-API layer in this project to build against speculatively.
- **Within Phase 1, tenant isolation (Pitfall 1) must land and be tested before RBAC branching (Pitfall 2) and hydration (Pitfall 3) are layered on top** — PITFALLS.md is explicit that "nothing downstream can be trusted if this layer is wrong." A phase-planner splitting Phase 1 further should preserve this internal ordering.
- **Phase 3 (estado filter) is grouped with Phases 1-2** because PROJECT.md's own Goal statement pairs "pesquisa decorativa" and "sem filtro de estado" as the same class of gap ("Fechar gaps de UX deixados pela v2.13"), distinct from the visual-language clause that follows it.
- **Phases 4-5 (visual language) are grouped separately and run after Phases 1-3** because PROJECT.md's Goal statement itself separates "fechar gaps de UX" from "dar o próximo passo na linguagem visual" as two distinct clauses, and because Phase 5's app-wide icon sweep has a genuine (not merely narrative) dependency on every button added by the earlier phases already existing.
- **Whether Target #1 (Phases 1-2) ships as exactly two phases, or is combined into one, is explicitly called out by ARCHITECTURE.md as "a roadmap-granularity decision, not an architecture one"** — this summary recommends two phases given the security-critical, independently-testable nature of the backend contract, but a "standard" granularity roadmap could reasonably combine them if a single phase's task list stays manageable.
