## Scope Note

**This phase introduces zero new visual surface.** Per 78-CONTEXT.md: "É uma relocalização pura de JSX/estado existente, sem alteração de comportamento, campos ou dados." The "Documentos a Tratar" and "Deslocações" sections already exist, fully built and functional, inside the `tab === "dados"` branch of `web/src/app/(dashboard)/clientes/[id]/page.tsx` (introduced pre-Phase 76, kept there by explicit Phase 76 decision). This phase only moves that JSX into its own conditional branch (`tab === "documentosATratar"` / `tab === "deslocacoes"`), replacing the `PlaceholderEmBreve()` placeholder introduced in Phase 76 — same markup, same hooks, same state, same handlers, same copy, byte-for-byte.

Both source blocks were read in full from the current file (post-Phase 77, confirmed against 78-CONTEXT.md's line estimates):

- **"Documentos a Tratar"** — lines 890–939. State: `documentosATratar` (`DocumentoATratar[]`), `addDocATratarModal` (bool), `newDocATratar: { descricao: string }`, handler `confirmAddDocATratar()` (lines 275–280). Only field is `descricao` — confirmed no `data` field exists today, matching CONTEXT.md's explicit correction of the roadmap text ("NÃO se adiciona um campo `data` nesta fase").
- **"Deslocações"** — lines 941–1013. State: `deslocacoes` (`Deslocacao[]`), `addDeslocacaoModal` (bool), `newDeslocacao: { descricao: string; local: string; data: string }`, handler `confirmAddDeslocacao()` (lines 282–287).
- **Placeholder to remove** — `tab === "documentosATratar" ? <PlaceholderEmBreve /> : tab === "deslocacoes" ? <PlaceholderEmBreve /> : ...` (lines 1080–1083), replaced by the relocated JSX.
- **Dialog-reset `useEffect`** (Phase 76, CR-01 fix, lines 211–220) — currently resets `addDocATratarModal`/`addDeslocacaoModal`/`newDocATratar`/`newDeslocacao` whenever `tab !== "dados"`. Per CONTEXT.md, this must be extended so each dialog also resets when the *user's own tab* is no longer active (i.e. `addDocATratarModal` resets when `tab !== "documentosATratar"`, `addDeslocacaoModal` resets when `tab !== "deslocacoes"`) — not just when leaving "Dados" generically, since the dialogs move out of "Dados" entirely.

**No new component library additions, no new color/typography/spacing tokens, no new copy.** The only code change is *where* this JSX/state lives (which conditional tab branch), plus a small widening of an existing `useEffect`'s condition.

## Interaction Contract (the actual scope of Phase 78)

This is the real work of this phase. The checker/executor should validate against this section, not the boilerplate design-token sections above (which are unchanged by definition).

### 1. What moves, and where

- **"Documentos a Tratar"** JSX block (current lines ~890–939, the `<div className="space-y-2">...` containing the `h4`, `Dialog`, and `ul`/empty-state) moves out of the `tab === "dados"` branch and into a new conditional: `tab === "documentosATratar" ? (<Card><CardContent>...</CardContent></Card>) : ...`, replacing the current `<PlaceholderEmBreve />` at that position.
- **"Deslocações"** JSX block (current lines ~941–1013) moves the same way into `tab === "deslocacoes" ? (...) : ...`, replacing its `<PlaceholderEmBreve />`.
- Wrap each relocated block in a `Card`/`CardContent` (or an equivalent simple wrapper) consistent with how other tab-content branches render (`ClienteProcessosTab`, `ClienteParecerTab` render inside `Card`) — exact wrapper markup is Claude's/executor's discretion per CONTEXT.md, as long as visual output (spacing, headings, list styling) is unchanged from today's "Dados"-tab rendering.
- All React state (`documentosATratar`, `deslocacoes`, `newDocATratar`, `newDeslocacao`, `addDocATratarModal`, `addDeslocacaoModal`) and handlers (`confirmAddDocATratar`, `confirmAddDeslocacao`) stay declared at the same component scope (top of `ClientePage`) — only their *consumption site* (which JSX branch renders them) changes. This is required because both lists are staged locally and included in the "Guardar" payload regardless of which tab is active (per CONTEXT.md: "Ambas as listas continuam a fazer parte do payload de 'Guardar' do formulário principal").

### 2. Dialog-reset `useEffect` extension

Current effect (lines 211–220) resets all three intake dialogs (including Documentos Entregues, which stays in "Dados") whenever `tab !== "dados"`. Extend the condition so:
- `addDocATratarModal`/`newDocATratar` reset when `tab !== "documentosATratar"` (not `!== "dados"`).
- `addDeslocacaoModal`/`newDeslocacao` reset when `tab !== "deslocacoes"` (not `!== "dados"`).
- `addDocEntreModal`/`newDocEntre` (Documentos Entregues — out of this phase's scope, stays in "Dados" until Phase 79) keeps its existing `tab !== "dados"` condition, untouched.

This can be one `useEffect` with per-dialog conditionals, or split into per-tab effects — implementation detail left to the executor; the observable behavior (each dialog closes/clears when its own tab is no longer active) is the contract.

### 3. Gating — unchanged

- "Adicionar" button in both sections stays gated by `canEditClientes && editable` (same AND-gate as every other CRUD affordance since Phase 75) — this phase does not change the gating logic, only relocates the JSX that carries it.
- In read mode, both lists remain always visible; only "Adicionar" and the per-item "✕" remove button are hidden/inactive. No new empty-state-in-read-mode variant is introduced.

### 4. Guardar / persistence — unchanged

- Both lists remain part of the single form's staged local state, submitted via the existing "Guardar" flow in the page header, regardless of which tab is currently active. This phase does not add per-tab save buttons or change the submit payload shape.

### 5. Visual regression check (what "done" looks like)

Before/after screenshot of the "Documentos a Tratar" list and "Deslocações" list (in both read and edit mode) must be pixel-identical, modulo which tab button is highlighted — the content itself does not move, resize, or restyle; only its parent conditional branch changes.
