<objective>
Build `AlertasDiariosJob` — the codebase's first `@Scheduled` background job — and its Mockito test suite, test-first. The job scans every tenant daily for (1) prazos whose Processo has crossed into a risk level, (2) critical calendar eventos, and (3) honorarios overdue >=30 days without full payment, creating one edge-triggered notification per newly-reached level per recipient (Processo responsavel + each tenant ADMIN).

Purpose: Delivers NOTF-20 (prazo risk alerts), NOTF-21 (evento risk alerts) and NOTF-23 (honorario overdue alerts) as a daily verification, reusing the Phase 85 `RiscoPrazoService` (no 5th copy of threshold logic) and the Phase 86/87 `NotificacaoService.criar(...)` write choke point. This is the highest-risk phase in the milestone: it introduces the first non-request-driven thread, so tenant isolation, no-SecurityContext discipline, failure isolation, and edge-triggered idempotency are the whole point — hence TDD.

Output: `AlertasDiariosJob.java` (job) + `AlertasDiariosJobTest.java` (behavioral proof).
</objective>

- Recipient = the PROCESSO's responsavel, never the Prazo's own responsavelId. Prazo has its own `responsavelId` field — ignore it; resolve `processoPorId.get(prazo.getProcessoId()).getResponsavelId()` (CONTEXT.md line 46/48).
- Prazo filter: skip concluded prazos (`!Boolean.TRUE.equals(prazo.getConcluido())`) — matches the existing risco enrichment at ResourceController listProcessos (non-concluido prazos only). Do NOT read/write `Prazo.escalonado` (unrelated UI snapshot per PATTERNS.md line 204).
- Evento date field = `getDataInicio()` (not dataFim). Rationale: the existing notification-facing endpoint `/eventos/upcoming` (which feeds today's NotificationBell — the exact feature this job persists) computes evento risco from `dataInicio` (ResourceController:2378). The dashboard KPI helper uses `dataFim` for a different (counting) purpose; deliberately NOT copied here to keep the bell and the job semantically aligned. Evento concluded rows are excluded at the query via `findByTenantIdAndConcluido(tenantId, false)`.
- Evento with null processoId: no Processo -> responsavel is null -> only the ADMIN fan-out fires (null-safe, same pattern as null responsavelId). linkUrl for such an evento = "/agenda".
- categoria mapping: prazo PROXIMO->"PRAZO_PROXIMO", VENCIDO->"PRAZO_VENCIDO"; evento PROXIMO->"EVENTO_PROXIMO", VENCIDO->"EVENTO_VENCIDO"; honorario -> "HONORARIO_ATRASADO" (single level). OK -> no notification.
- entidadeTipo/entidadeId: prazo -> ("prazo", prazo.getId().toString()); evento -> ("evento", evento.getId().toString()); honorario -> ("honorario", honorario.getId().toString()). All ids stringified (entidadeId is String).
- Honorario rule (all must hold to notify): valorTotal != null AND dataAcordo != null AND (totalPago == null || totalPago.compareTo(valorTotal) < 0) AND ChronoUnit.DAYS.between(dataAcordo, hoje) >= 30. Any failed guard => skip that honorario silently.
- Idempotency dedup between responsavel and admins is handled naturally by the existence-check ordering (process responsavel first; an admin who is also the responsavel is then skipped because criar() has already persisted that row) — do not add extra dedup logic.
- Notification text (Portuguese, tone adjustable per CONTEXT.md discretion but ship these concrete defaults): PRAZO_PROXIMO titulo "Prazo a vencer" / PRAZO_VENCIDO titulo "Prazo vencido", mensagem referencing prazo.getDescricao() and the processo numero; EVENTO_PROXIMO "Evento a aproximar-se" / EVENTO_VENCIDO "Evento em atraso", mensagem referencing evento.getTitulo(); HONORARIO_ATRASADO titulo "Honorário em atraso", mensagem referencing the processo numero and the day count.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Spring scheduler thread → tenant data | The `@Scheduled` method runs on a background thread with NO HTTP request, NO JWT, NO `Authentication` in `SecurityContextHolder`. This is the first code path in the app that must resolve tenant without a security context. |
| Per-tenant iteration → cross-tenant data | One job run touches EVERY tenant's data in sequence. A single missing/incorrect tenant filter would let one tenant's users be notified about another tenant's entities. |
| Job → notification write path | All writes funnel through `NotificacaoService.criar(...)`, which independently re-validates that the destinatario belongs to the tenant. |

| T-88-02 | Information Disclosure (cross-tenant leak) | every repository call in the scan | mitigate | Tenant isolation is enforced by explicit `tenantId` threading at EVERY query, verified against the actual confirmed signatures (not assumed): `processoRepository.findByTenantId(tenantId)`, `prazoRepository.findByTenantId(tenantId)`, `eventoRepository.findByTenantIdAndConcluido(tenantId, false)`, `userRepository.findByTenantIdAndRoleName(tenantId, "ADMIN")`.
