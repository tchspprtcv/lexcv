<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client → `POST /processos/{id}/factos` | Untrusted payload may include a forged `ordem` value attempting to jump the sequence or collide with another Facto's position |
| Client → `PUT`/`DELETE /processos/{id}/factos/{factoId}` | Untrusted path variables; same cross-processo IDOR risk class as Decisão/Testemunha in `81-02` |
| Concurrent requests → `POST /processos/{id}/factos` | Two near-simultaneous creates on the same processo racing on the same max-lookup |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-81-09 | Tampering / IDOR | `PUT`/`DELETE /processos/{id}/factos/{factoId}` | mitigate | Double-check pattern (parent tenant + `facto.getProcessoId().equals(id)`) applied verbatim, matching Decisão/Testemunha in `81-02` and closing PITFALLS.md Pitfall 3 for the third and final new entity |
| T-81-10 | Tampering | `POST /processos/{id}/factos` — client-supplied `ordem` | mitigate | Server unconditionally recomputes `ordem` as `max(existing ordem for this processo_id) + 1` inside a `synchronized` block, discarding any client-supplied value — a forged `ordem: 999` (or a negative/duplicate value) in the create payload has zero effect on the persisted value |
| T-81-11 | Race Condition (Tampering-adjacent) | `POST /processos/{id}/factos` under concurrent requests | mitigate | `synchronized (FactoRepository.class)` wraps both the max-lookup query and the subsequent save, closing the read-then-write race window that would otherwise let two near-simultaneous creates both read the same max and persist a colliding `ordem` (matches the existing `createCliente`/`ParecerController` sequence-number precedent already relied on elsewhere in this codebase) |
| T-81-12 | Denial of Service | `synchronized (FactoRepository.class)` | accept | Class-level synchronization serializes Facto creation application-wide (across all tenants/processos), not just per-processo — an accepted trade-off matching the exact same pattern already in production for Cliente's `numeroSequencial` and `ParecerVersao`'s `numeroVersao`; at this project's current data volumes (tens of Factos per processo, not thousands of concurrent creates) this is not a realistic availability risk |

All Tampering/IDOR threats for this plan's write endpoints are mitigated identically to `81-02`'s pattern, completing PROC-17 for all three new entities across the two plans.
