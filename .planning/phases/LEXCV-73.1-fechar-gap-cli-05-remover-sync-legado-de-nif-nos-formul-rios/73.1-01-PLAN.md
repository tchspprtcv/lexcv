<objective>
Close the CLI-05 gap identified in the v2.7 milestone audit (BLOCKER 1 + BLOCKER 2). CLI-05 requires that every cliente (Particular or Empresa) carries a valid, mandatory NIF of exactly 9 numeric digits. Two defects currently break that guarantee:

1. **Frontend (BLOCKER 1):** Both the create and edit cliente forms retain a pre-milestone NIF-sync block that runs *after* the payload is built, silently overwriting the dedicated Zod-validated `nif` field with the unvalidated legacy `documento_numero` whenever `documento_tipo === "NIF"`.
2. **Backend (BLOCKER 2):** `createCliente`/`updateCliente` accept `@RequestBody Cliente` with no `@Valid`, and `Cliente.nif` has no Bean Validation — so NIF validity is a browser-only guarantee. Additionally, the controller itself re-derives `nif` from `documentoNumero` (the server-side twin of BLOCKER 1), which would defeat the new validation by overwriting the validated value with an unvalidated one.

Purpose: Make the dedicated `nif` field the single source of truth for NIF, enforced on both client and server, so the milestone's core requirement is a system-wide guarantee rather than a browser convention.

Output: Legacy NIF-sync removed from 2 frontend files and 2 backend code paths; Jakarta Bean Validation added to the model; `@Valid` added to both endpoints; build + typecheck gates green.
</objective>
