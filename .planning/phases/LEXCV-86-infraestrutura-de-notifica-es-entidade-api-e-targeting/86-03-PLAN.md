<objective>
Expose the notification REST API and wire the RBAC scope that gates it. Create `NotificacaoController` — a dedicated controller (not more lines in the ~2900-line `ResourceController`) — with the four endpoints from Success Criterion 1, every one scoped by BOTH tenant and the caller's own userId. Read endpoints query `NotificacaoRepository` directly; the two mutating endpoints (`marcarLida`, `marcarTodasLidas`) delegate to `NotificacaoService` (Plan 86-02) rather than calling `notificacaoRepository.save(...)`/`saveAll(...)` from the controller, preserving `NotificacaoService` as the sole write path for the whole subsystem. Seed the new `notificacoes:view` scope for all four roles in `DatabaseSeeder`, list it in `AdminController.getRbac()`'s `systemPermissions` (so it is visible/manageable on the Admin Settings RBAC screen), and register `notificacoes` in the frontend `KNOWN_SCOPES` registry.

Purpose: This is where the IDOR-adjacent risk this phase introduces is enforced at the API surface — every read and mutation must filter by `destinatario_id` as well as `tenant_id`, because notifications are this project's first per-recipient-private resource (every other resource is tenant-shared). Getting the dual scoping wrong here would leak one user's notifications to another user in the same tenant. This plan now also depends on Plan 86-02, since the write endpoints call into `NotificacaoService`.

Output: `NotificacaoController.java`, modified `DatabaseSeeder.java`, modified `AdminController.java`, modified `web/src/lib/permissions.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → NotificacaoController | Untrusted request inputs cross here: path var `{id}`, query params `categoria`/`lida`/`page`/`size`. Identity (tenantId, userId) comes only from the server-side `UserPrincipal`, never from the request body. |
| recipient A ↔ recipient B (same tenant) | The IDOR-adjacent boundary this phase introduces: a user must never read, count, or mark-read a notification owned by another user in the SAME tenant. This is NOT covered by the tenant-only checks every other endpoint uses. |
| NotificacaoController → NotificacaoService | The two write endpoints cross into Plan 86-02's service rather than touching the repository; the controller must always pass its own `getTenantId()`/`getUserId()` through, never a value derived from client input. |
