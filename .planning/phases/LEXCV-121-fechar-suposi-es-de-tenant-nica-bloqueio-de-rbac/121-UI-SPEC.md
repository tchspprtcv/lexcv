# Phase 121 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase covers ISOL-01, ISOL-02 and ISOL-03. Dedicated codebase research recorded in `121-CONTEXT.md` confirms exactly **one** UI-facing surface across all three: ISOL-01 (`PublicController.getBranding`) and ISOL-02 (the tenant-heuristic sweep) are backend/audit-record concerns with zero rendered UI. ISOL-03's frontend half is a single, small, additive change to one existing sub-component — `RbacTab` in `web/src/app/(dashboard)/settings/page.tsx` (function starts at line 760). No new screen, no new route, no new shadcn component install.

**The change:** the "Guardar Regras" button (currently unconditional, `:860-871`, live and clickable for every tenant ADMIN today) stops being exposed to a tenant ADMIN once the backend lock (method-level `@PreAuthorize("hasRole('PLATAFORMA_ADMIN')")` on `updateRbac`) ships — satisfying ROADMAP Phase 121 Success Criterion 4 verbatim:

> "A aba 'Controlo de Acesso (RBAC)' das Definições (`settings/page.tsx`, `RbacTab`) deixa de expor a ação de gravar a um `ADMIN` de tenant na interface, evitando um `403` confuso na UI."

`121-CONTEXT.md` locks the *mechanism* (a new condition on `me?.roles?.includes("PLATAFORMA_ADMIN")`, reusing the exact idiom from `dashboard-shell.tsx:91`/`plataforma/page.tsx:78-89`) but deliberately leaves **what renders in the button's place** as an open call for this contract to make. That call is resolved below: **a static, neutral `Badge` reading "Gerido pela Plataforma," with a `Lock` icon and an explanatory `Tooltip`** — not a bare empty gap, and not a disabled-but-visible button (see Copywriting Contract for the reasoning).

Everything else in `RbacTab` — the tab's own visibility (`hasRbacManage`), the permission matrix, the "Nota Importante" ADMIN-row-lock banner, `GET /admin/rbac`'s read path — is explicitly unchanged. `UserManagementTab` (the sibling tab, Phase 118) is untouched by this phase.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | "Guardar Regras" — pre-existing, unchanged. Now conditionally rendered only when `me?.roles?.includes("PLATAFORMA_ADMIN")` is true. Nobody can reach that branch today (`hasRbacManage` doesn't yet grant `PLATAFORMA_ADMIN` tab access — confirmed by 121-CONTEXT.md research), so in practice every current viewer sees the replacement state below. |
| Replacement state — Badge label | **"Gerido pela Plataforma"** (`variant="outline"`, `Lock` icon `h-3 w-3`, `gap-1`). This is the always-visible "why there's no Save button" signal required by Success Criterion 4 — legible without hovering, unlike a tooltip-only explanation. |
| Replacement state — Tooltip (on hover/focus) | "As regras de acesso por perfil (RBAC) passaram a ser uma configuração fixa e comum a toda a plataforma LexCV — já não podem ser alteradas a partir de um escritório individual." Gives the fuller "why" for a curious tenant ADMIN without cluttering the header row. |
| Empty state | Not applicable — no new list/table is introduced. The permission matrix always has rows (4 roles × N system permissions); it can never render zero. |
| Error state | Not applicable in practice. `handleSave`'s existing catch block (`setError(msg); toast.error(msg)`) is the only error path tied to this button, and its sole trigger (the Button) no longer renders for a tenant ADMIN — it becomes unreachable dead code for them, not a live error surface. No new error copy is introduced; do not rewrite `handleSave`. |
| Destructive confirmation | Not applicable — this phase introduces no destructive action. |

**Why a Badge+Tooltip rather than a bare gap or a disabled button:** Success Criterion 4's verb is "deixa de **expor**" (stops *exposing*) — a visible-but-disabled button would still be "exposed," just inert, and would misleadingly suggest a state-based block (like Phase 118's at-limit button or Phase 120's reserved-tenant guard) rather than a permanent, role-based one. A bare empty header slot satisfies the literal criterion but leaves the checkbox-toggling-with-no-save-path (see Interaction Notes, item 8) unexplained and looks like a rendering gap rather than a deliberate design. A static, self-explanatory Badge — reusing components already imported in this exact file, in the exact variant (`outline`) this same milestone already established for "this belongs to the platform, not this tenant" signals (120-UI-SPEC's "Plataforma" badge) — closes both gaps at zero new cost.

## Interaction Notes

Concrete implementation contract points — not covered by the tables above but load-bearing for the executor:

1. **Conditional expression.** Inside `RbacTab`, add:
   ```ts
   const me = useMe();
   const isPlatformAdmin = me.isFetched && (me.data?.roles?.includes("PLATAFORMA_ADMIN") ?? false);
   ```
   This mirrors `dashboard-shell.tsx:91`'s exact idiom (`me.data?.roles?.includes("PLATAFORMA_ADMIN") ?? false`) plus the `isFetched` gate `plataforma/page.tsx:78` uses — giving a single clean boolean with no loading-state flash (during the brief window before `me` resolves, the expression is `false`, so the Badge — the safe, non-exposing default — renders, never the Button).
2. **Self-fetch `useMe()` inside `RbacTab` itself, not prop-drilled from `SettingsPage`.** This matches the established self-fetching convention already used by the sibling `UserManagementTab` in this exact file (which calls its own `useMe()` per 118-UI-SPEC, rather than receiving `me` as a prop). TanStack Query dedupes on the shared `["auth", "me"]` cache key — this is not a second network fetch.
3. **Render swap, in place of the existing unconditional `<Button onClick={handleSave} ...>` at `:860-871`:**
   ```tsx
   {isPlatformAdmin ? (
     <Button
       onClick={handleSave}
       disabled={saving}
       className="bg-blue-600 hover:bg-blue-700 text-white shadow-sm flex items-center gap-2 self-start sm:self-auto"
     >
       {saving ? <Loader2 className="h-4 w-4 animate-spin" /> : <Save className="h-4 w-4" />}
       Guardar Regras
     </Button>
   ) : (
     <Tooltip>
       <TooltipTrigger asChild>
         <span tabIndex={0} className="self-start sm:self-auto">
           <Badge variant="outline" className="gap-1">
             <Lock className="h-3 w-3" />
             Gerido pela Plataforma
           </Badge>
         </span>
       </TooltipTrigger>
       <TooltipContent>
         As regras de acesso por perfil (RBAC) passaram a ser uma configuração fixa e comum a
         toda a plataforma LexCV — já não podem ser alteradas a partir de um escritório individual.
       </TooltipContent>
     </Tooltip>
   )}
   ```
   The Button's own JSX/styling is otherwise untouched — only the surrounding condition is new. `self-start sm:self-auto` (carried over from the Button) keeps the mobile stacking behavior identical on the `flex-col sm:flex-row` `CardHeader`.
4. **Badge is not natively focusable or disabled — the `<span tabIndex={0}>` wrapper is still required for keyboard parity**, even though this is a different reason than Phase 118/120's disabled-Button case (there, the wrapper works around `buttonVariants`' baked-in `disabled:pointer-events-none`; here, it's needed because a plain `Badge` `<span>` has no native tab stop at all). Same wrapper technique, different underlying cause — do not skip it.
5. **Zero new imports.** `Badge`, `Tooltip`/`TooltipTrigger`/`TooltipContent`, `Lock`, and `useMe` are already imported at the top of `settings/page.tsx` today (the first three are used elsewhere in this same file; `useMe` is already imported and used by `UserManagementTab`, a sibling function in the same file).
6. **`Role` already includes `"PLATAFORMA_ADMIN"`** (`web/src/types/auth.ts`, extended in Phase 120) — no type change needed this phase.
7. **Explicit non-goals — do not touch:**
   - The permission matrix's checkboxes stay exactly as interactive as they are today for every non-ADMIN role (`handleCheckboxChange`, `isDisabled = role === "ADMIN"`) — no new `disabled` styling is added anywhere in the matrix, even though a tenant ADMIN can no longer persist a toggle. `hasRbacManage` (tab visibility, `:58`) is unchanged.
   - The "Nota Importante" `ShieldAlert` banner (ADMIN-row-immutability explanation) is a different concern from the Save-button visibility — do not edit its copy or merge the new Tooltip explanation into it.
   - `GET /admin/rbac`'s frontend call path (`useAdminRbac()`) is unchanged — it already works for a tenant ADMIN and Success Criterion 4 only names the write action.
   - Do not delete or rewrite `handleSave`/`saving`/`success`/`error` state, or the `{success && ...}`/`{error && ...}` banners in `CardContent`. They remain correct as-is; they simply become unreachable via the UI for a tenant ADMIN (no button to trigger them), and stay fully live for the day a future phase grants `PLATAFORMA_ADMIN` access to this tab.
8. **Known, accepted limitation (flagged for visibility, not for action this phase):** a tenant ADMIN can still toggle a non-ADMIN role's checkbox in local state (`localRolePermissions`) with no way to persist it, since Save is gone for them. `121-CONTEXT.md` scopes this phase to hiding only the Save action, not to also disabling matrix interactivity — noted here so it isn't mistaken for an oversight.
9. **UI-facing verification checkpoint** (the backend 403 proof itself is a separate, non-UI test per `121-CONTEXT.md`): log in as an existing tenant ADMIN, open Definições → Controlo de Acesso (RBAC), confirm the header shows the "Gerido pela Plataforma" Badge (never the Button), confirm hover *and* keyboard focus both reveal the Tooltip explanation, and confirm the matrix below still renders with its non-ADMIN checkboxes clickable exactly as before.
