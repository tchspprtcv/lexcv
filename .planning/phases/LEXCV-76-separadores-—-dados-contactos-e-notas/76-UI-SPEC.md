## Scope Note

This phase introduces **one new visual pattern** (a 7-button tab row) to the clientes ficha, but that pattern is **not invented here** — it is a direct reuse of the button-toggle-row pattern already shipped in `web/src/app/(dashboard)/processos/[id]/page.tsx` (`type TabKey`, `useState<TabKey>`, `Button` row with `variant={tab === x ? "secondary" : "outline"}`, single conditionally-rendered `Card`/content region). Per 76-CONTEXT.md: "réplica exata do padrão já usado em processos." No shadcn `Tabs`/`TabsList`/`TabsContent` (Radix) — this project has never adopted that primitive and does not do so here.

Both source files were read in full:
- `web/src/app/(dashboard)/processos/[id]/page.tsx` (1447 lines) — tab row markup at lines 910–941 (`<div className="flex flex-wrap gap-2">` containing `Button` elements), tab-conditional rendering at lines 943–1440 (`{tab === "x" ? <Card>...</Card> : tab === "y" ? ... : null}`).
- `web/src/app/(dashboard)/clientes/[id]/page.tsx` (current, post-Phase 75, 1634 lines) — single flat page today: header with Editar/Guardar/Cancelar state machine (unchanged, Phase 75 scope), then `Dados` Card (dl/dd view + form edit, includes Tipo/Email/Telefone/Localidade/Morada — NOT identification), `Conta-corrente` Card, `Informações Adicionais` Card (documento_tipo/documento_numero/ramo_atividade/detalhes_adicionais — THIS is where identification currently lives, to be folded into "Dados" per CLI-19), `Intake do Caso` Card (descricao_caso + honorarios_propostos + 3 staged lists, edit-mode only today), `ClienteContactosCard`/`ClienteNotasCard` (2-col grid), `ProcuracaoCard`/`ResponsaveisCard`×2 (3-col grid).
- `web/src/lib/cliente-documento-tipo.ts` — `getDocumentoTipoOptions(tipo)` / `toDocumentoTipo(value, tipo)`, already filters by cliente tipo (Phase 74 deliverable, unchanged by this phase).

**No new component library additions, no new color/typography/spacing tokens.** The only genuinely new interaction surface is: (1) the 7-tab state machine wrapping existing content, (2) the "Em breve" placeholder card for 5 unbuilt tabs, (3) `overflow-x-auto` applied to a button row for the first time in this codebase (existing precedent for `overflow-x-auto` is tables/lists only — see Spacing Scale below), (4) folding identification fields into the "Dados" card as a distinct sub-section.

**Design System detected:** No `components.json` in `web/` — no shadcn CLI (unchanged since Phase 74/75). Hand-rolled Radix-based primitives under `web/src/components/ui/` (`Button`, `Card`, `Badge`, `Dialog`, `Input`, `Label`, `RadioGroup`, `Switch`). Shadcn initialization gate: **not applicable** — this phase adds zero new UI primitives, only new state/layout composition over existing primitives.

## Spacing Scale

No new spacing tokens introduced. Existing structure reused verbatim, with one new composition (tab row + `overflow-x-auto` wrapper):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inherited from existing `gap-x-4`/`gap-y-3` `dl` grids |
| sm | 8px | `gap-2` on the tab-button row (matches processos exactly: `flex ... gap-2`) |
| md | 16px | `gap-4` default grid/section gap (existing, e.g. `grid gap-4 lg:grid-cols-2`) |
| lg | 24px | `space-y-6` page-level rhythm (existing, unchanged wrapper) |

Exceptions (new to this phase, per 76-CONTEXT.md explicit decision):
- The 7-button tab row wraps in `overflow-x-auto` (horizontal scroll) instead of `flex flex-wrap` — this diverges from the processos precedent (which uses `flex flex-wrap` for its 4 buttons) because CONTEXT.md explicitly requires the v2.3-responsiveness `overflow-x-auto` convention for this specific row, given 7 buttons risk wrapping awkwardly on mobile. Exact markup: `<div className="overflow-x-auto"><div className="flex gap-2 w-max">{...7 Buttons...}</div></div>` — the inner `flex gap-2` mirrors processos' button row spacing (`gap-2`) exactly; `w-max` (or `flex-nowrap` equivalent) is required so buttons do not wrap and instead scroll, since `overflow-x-auto` alone does nothing without a non-wrapping flex child. This is the one deliberate divergence from "exact replica" and is explicitly sanctioned by CONTEXT.md's Mecanismo section.
- Touch target: no new touch-target exception — tab buttons use the existing `Button` component's default height (unchanged, matches processos).

## Typography

No new typography introduced. Reuses the exact declared set from Phase 75 (verified unchanged in the current `clientes/[id]/page.tsx` read in this session): exactly **2** distinct weight utility classes appear across the page's text-role hierarchy — `font-semibold` (600, used on H1 "Cliente" and the Conta-corrente saldo figure) and `font-medium` (500, used on emphasized `dd` values and section sub-headings like "Honorários Propostos", "Documentos Entregues"). Everything else (breadcrumb, `dt` labels, plain `dd` values, muted/secondary text) carries no weight class — inherits base/unstyled weight, which is the absence of a third declared weight, not a third weight.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Page H1 ("Cliente") | 24px (`text-2xl`) | 600 (`font-semibold`) | default (existing, unchanged) |
| Tab button label (new: 7-button row) | existing `Button` component default text size (`text-sm`, unchanged) | existing `Button` default — no new weight declared; active/inactive distinguished by `variant` (color/background), not by font-weight | default (existing `Button` line-height) |
| Section sub-heading ("Identificação", "Intake do Caso", "Honorários Propostos") | 14px (`text-sm`) or `CardTitle` default for card-level titles | 500 (`font-medium`) for inline `h4`-style sub-headings; existing `CardTitle` default for `Dados`/`Contactos e Notas` card titles | 1.5 (existing, unchanged) |
| Emphasized value (Nome `dd`, saldo figure) | 14px (`text-sm`) body / 24px (`text-2xl`) for saldo | 500 (`font-medium`) / 600 (`font-semibold`) respectively | 1.5 / default |
| Body / `dl`/`dd` plain values, breadcrumb, muted labels, "Em breve" placeholder copy | 14px (`text-sm`, `text-sm text-neutral-500`) | no weight class declared — inherits base/unstyled weight | 1.5 (existing, unchanged) |

Declared weights for this phase: **2** — `font-semibold` (600) and `font-medium` (500). No third weight is introduced. The tab row introduces no new weight: active vs. inactive tab state is communicated via `Button` `variant` (`secondary` vs `outline`, i.e. background/border color), exactly as in processos — never via bold/not-bold, which would be a hidden third "weight-as-state" signal this contract explicitly forbids.

## Interaction Contract (the actual new design surface)

This is the real scope of Phase 76's UI work. The checker/executor should validate against this section more than the boilerplate sections above.

### 1. Tab state machine

- State: `const [tab, setTab] = React.useState<TabKey>("dados")` where `TabKey` is a union of 7 string literals (exact key names at Claude's/executor's discretion per CONTEXT.md — e.g. `"dados" | "contactosNotas" | "processos" | "pareceres" | "documentosEntregues" | "documentosATratar" | "deslocacoes"`).
- Default tab on mount: `"dados"`.
- All 7 buttons are always rendered, always enabled (`disabled` is never set) — clicking any of the 5 not-yet-implemented tabs is fully functional navigation into a placeholder, per CONTEXT.md: "Os botões destes separadores ficam clicáveis (não `disabled`)."
- Button markup (exact replica of processos pattern, lines 910–941 of `processos/[id]/page.tsx`):
  ```tsx
  <Button type="button" variant={tab === "dados" ? "secondary" : "outline"} onClick={() => setTab("dados")}>
    Dados
  </Button>
  ```
  repeated for all 7 keys/labels, in the fixed order given above.
- Wrapper divergence (per CONTEXT.md, see Spacing Scale exception): `<div className="overflow-x-auto"><div className="flex gap-2 w-max">{...7 buttons...}</div></div>` instead of processos' bare `<div className="flex flex-wrap gap-2">`.
- Exactly one `Card` (or content block) is rendered per active tab, via `tab === "x" ? (...) : tab === "y" ? (...) : ...` — same conditional-chain style as processos lines 943–1440, not a lookup map or switch (matches existing precedent literally for consistency, though a lookup/switch is not forbidden if the executor prefers it — no CONTEXT.md decision pins the conditional style itself, only the overall Button-row + single-Card mechanism).

### 2. "Dados" tab content (composition, per CONTEXT.md)

Everything from today's flat page EXCEPT Contactos/Notas and the 3 staged lists (which get their own separators in Phases 76/78), reorganized as:
1. **Dados** card — existing fields (Nome/NIF-if-still-here/Tipo/Email/Telefone/Localidade/Morada/Avençado) PLUS a new **"Identificação"** sub-section containing NIF, Tipo de Documento, Número do Documento (NIF was already in this card; Tipo de Documento/Número de Documento move here from "Informações Adicionais"). Sub-section gets its own `text-sm font-medium` heading "Identificação", visually distinct (e.g. `pt-4 border-t` divider) from the fields above it — not run together with no separation.
2. **Conta-corrente** card — unchanged, unaffected by this phase.
3. **Informações Adicionais** card — retains Ramo de Atividade + Detalhes Adicionais only (documento_tipo/documento_numero removed to "Identificação" above).
4. **Intake do Caso** section — Descrição do Caso + Honorários Propostos, nested within "Dados" tab (per CONTEXT.md: no dedicated tab of the 7 exists for this, so it stays here). Currently only rendered in edit mode on the flat page (`isEditing ? <Card>...</Card> : null`, line 664) — this phase's tab restructuring does not change that visibility rule; it only changes where it's nested.
5. **Advogados** / **Administrativos** (`ResponsaveisCard`×2) — stay inside "Dados" tab, unchanged (no dedicated tab of the 7 exists for these either, per CONTEXT.md).
6. **Procuração** card — stays inside "Dados" tab (not explicitly named in CONTEXT.md's "Dados" composition list, but has no dedicated tab among the 7 and was part of "tudo o que existe hoje" prior to Phase 75 — retained here by elimination).

All view/edit toggling behavior (Phase 75's `isEditing`/`editable` prop chain) is preserved unchanged for every field/card moved into "Dados" — this phase does not alter the AND-gate (`canEditClientes && editable`) logic, only the surrounding tab chrome.

### 3. "Contactos e Notas" tab content

`ClienteContactosCard` + `ClienteNotasCard`, moved verbatim (same 2-col grid `grid gap-4 lg:grid-cols-2`, same props, same `editable={isEditing}` wiring) from the flat page into this tab's conditional render block. No markup changes to the cards themselves.

### 4. Placeholder tabs (5): Processos, Pareceres, Documentos Entregues, Documentos a Tratar, Deslocações

Each renders identically:
```tsx
<Card>
  <CardContent className="py-12 text-center">
    <p className="text-sm font-medium text-neutral-500 dark:text-neutral-400">Em breve</p>
    <p className="text-xs text-neutral-400 dark:text-neutral-500 mt-1">
      Esta funcionalidade estará disponível brevemente.
    </p>
  </CardContent>
</Card>
```
No `CardHeader`/`CardTitle`, no spinner, no `isLoading`/`isError` state, no API call of any kind (per CONTEXT.md: "sem spinner nem chamadas de API"). Visually consistent with the existing empty-state idiom already used elsewhere in the app (e.g. timeline's "Sem entradas na timeline" pattern in processos, `py-12 text-center` + two-tier text-size messaging) — reuses that established empty-state visual rhythm rather than inventing a new one.

### 5. Editar-triggers-tab-switch behavior

Per CONTEXT.md: "Ao clicar 'Editar' estando noutro separador (ex. 'Contactos e Notas'), a UI muda automaticamente para o separador 'Dados'." Implementation: the existing `onClick={() => setIsEditing(true)}` handler for the "Editar" header button must also call `setTab("dados")` (in either order, same event handler) before or alongside flipping `isEditing`. This applies only to entering edit mode — `Cancelar`/`Guardar` (exiting edit mode) do NOT force a tab switch back to any particular tab; the user stays on whichever tab they're viewing when they save/cancel.

### 6. Mobile responsiveness

Only the tab-button row gets the new `overflow-x-auto` treatment (see Spacing Scale exception above). No other new mobile-specific behavior is introduced by this phase — the underlying cards/forms already carry their Phase 55-era responsive classes (e.g. `max-sm:h-12 max-sm:text-base` on inputs), unchanged.
