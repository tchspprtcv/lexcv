<objective>
Deliver the entire backend for NOTF-26 snooze: a new nullable `Notificacao.snoozedUntil` column,
its manual migration, a read-side visibility predicate on the two "unread" queries (badge count and
mark-all-read), a `NotificacaoService.snooze(...)` write method, the `PATCH /notificacoes/{id}/snooze`
endpoint, and the Mockito unit tests that prove the write contract.

This is the last plan in this milestone that touches `NotificacaoService.java` /
`NotificacaoController.java` / `Notificacao.java` / `NotificacaoRepository.java` — the sequential
notification chain (93 → 94 → 95 → 96) closes here. Snooze is deliberately modeled as an orthogonal
visibility toggle on the *same, already-existing* row: it never interacts with `lida`, never widens
`uk_notificacao_dedup`, and requires zero change to `AlertasDiariosJob` (its existence-check ignores
`snoozedUntil`, so a snoozed row still counts as "exists" and is never recreated — Pitfall 4 resolved
by construction).

Purpose: NOTF-26 success criteria 1 (backend), 2 (backend read-side), 3 (reappearance invariant), 4
(job idempotency untouched).
Output: modified entity/repository/service/controller + new migration + new Mockito tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → NotificacaoController.snooze | New @PreAuthorize('notificacoes:view')-gated PATCH endpoint accepting a caller-supplied `id` (path) and `dias` (body); tenant + destinatario are NEVER caller-supplied (derived from JWT) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-96-01 | Tampering (IDOR) | snooze of another user's notification | mitigate | snooze() loads via `findByIdAndTenantIdAndDestinatarioId(id, getTenantId(), getUserId())`; a non-owned id yields empty -> 404, never a save on another recipient's row (Pitfall 10) |
| T-96-02 | Information Disclosure | existence of another recipient's notification | mitigate | Empty-Optional -> 404 (not 403); identical response whether the id doesn't exist or belongs to someone else — no existence leak across the recipient boundary |
| T-96-03 | Tampering (domain safety) | snoozing a PRAZO_VENCIDO to hide an overdue legal deadline | mitigate | `!isSilenciavelCategoria(n.getCategoria())` -> 400; reuses the NOTF-24 single source of truth (PRAZO_VENCIDO is silenciavel(false)) so an already-overdue prazo can never disappear from view |
| T-96-04 | Denial of Service | arbitrary/huge `dias` pushing snoozedUntil far into the future | mitigate | Server validates `dias ∈ {1,3,7}` BEFORE loading the row; any other value -> 400. The client cannot supply a raw datetime |
| T-96-05 | Tampering (cross-tenant query) | count/find visibility predicate leaking across tenants | mitigate | Both LidaFalse @Query methods keep the mandatory `tenantId` + `destinatarioId` predicates; the snooze clause is additive, never replaces the scoping predicates |
| T-96-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan (Java source + SQL migration only); Package Legitimacy Gate not applicable |
</threat_model>
