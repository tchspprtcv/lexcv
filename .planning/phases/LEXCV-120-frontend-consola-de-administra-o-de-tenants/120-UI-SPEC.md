# Phase 120 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase delivers one brand-new internal screen — `/plataforma`, role-gated to `PLATAFORMA_ADMIN` only, rendered inside the normal `DashboardShell` chrome — plus the frontend consumption of 3 new backend endpoints on the already-existing `PlatformAdminController` (Phase 119): list tenants (PROV-03), adjust `plano`/`limiteUtilizadores` (PROV-04), and suspend/reactivate (PROV-05). `POST /api/v1/platform/tenants` (PROV-02, list creation) already exists from Phase 119 and is consumed here for the first time by a real UI.

**Zero new shadcn installs.** Every primitive this phase needs — `Card`, `Button`, `Input`, `Label`, `Badge`, `Tooltip`, `Dialog`, `AlertDialog`, `NativeSelect`, `Table` (via the shared `DataTable`), `DropdownMenu` (via `DataTableViewOptions`) — already exists in `web/src/components/ui/`. No new registry, no new dependency.

**This contract reuses 3 established patterns verbatim rather than inventing new ones:**
1. The shared `DataTable` (`web/src/components/shared/data-table/`, v2.13 Phase 104) for the tenant list — same as Clientes/Processos/Pareceres/Financeiro/Documentos.
2. `UserManagementTab`'s inline create-panel toggle (`settings/page.tsx`) for "Criar Tenant" — the list Card swaps wholesale to a form Card, no modal.
3. The Tooltip + disabled-`<span tabIndex={0}>` composition (Phase 118, `118-UI-SPEC.md`) for the reserved-"LexCV"-tenant suspend guard.

| Role | Size | Weight | Line Height |

| Heading | 20px | 600 | 1.2 |

**New weights decided by this phase: 2 total — 400** (regular — table cell text, Dialog body/description text, Input values, tooltip content) **and 600** (semibold — page `<h1>`, Card/Dialog titles, `DataTableColumnHeader` labels, the "limite atingido" caption and any at-limit state text). **Exception (pre-existing, locked, not a new decision — same mechanism as the Spacing section's own "Exceptions" line above):** Display (30px/**700**) appears on this screen only because the page `<h1 className="text-3xl font-bold tracking-tight">` reuses the exact already-locked, app-wide Display convention verbatim from every other page (Clientes, Settings, Dashboard, Agenda, Processos, Pareceres — 8 confirmed sites). It is inherited unchanged, not re-decided here, and is excluded from this phase's own 2-weight budget the same way the Spacing section excludes pre-existing 12px/36px/48px values from its own 7-checkpoint scale. Badge internals (12px, `font-medium`/500, baked into `components/ui/badge.tsx`) are likewise an inherited shadcn-primitive weight this phase does not touch, override, or count against its budget.

Accent reserved for: "Criar Tenant" CTA, both Dialog "Guardar" buttons, the active nav-item state. Never applied to Plano badges (STARTER/STANDARD/ENTERPRISE — gray/purple/amber, informational tier labels, not actions) or to the Estado badge (green/red, a status signal, not an action).

A 5th color is used deliberately, following existing precedent (`processos/dashboard/page.tsx`, `dashboard/page.tsx` already use `Badge variant="green"` for positive-active state): **emerald** (`emerald-600`) for the Reativar direction — the row icon's hover color, and the Reativar `AlertDialogAction` confirm button (`bg-emerald-600 hover:bg-emerald-700 text-white`). This is not a 3rd "brand" color — emerald is this codebase's already-established "positive/active-state" semantic (the `Ativo` badge, the notification-preference toggle's `checked:bg-emerald-500`), reused here for symmetry with its opposite (Suspend = red/Lock, Reactivate = emerald/Unlock).

## Screen Layout & Component Reuse Map

### Route & navigation
- Route: `web/src/app/(dashboard)/plataforma/page.tsx` → `/plataforma`, rendered inside the existing `DashboardShell`.
- Page-level guard (defense in depth, matching `ClientesPage`'s exact pattern): `if (me.isFetched && !me.data?.roles?.includes("PLATAFORMA_ADMIN")) return <AccessDeniedState ... />`. Backend `@PreAuthorize("hasRole('PLATAFORMA_ADMIN')")` on `PlatformAdminController` is the authoritative layer; this is the UX mirror.
- New sidebar nav item appended to the end of `NAV` in `dashboard-shell.tsx` (after Pareceres): `{ href: "/plataforma", label: "Plataforma", icon: Building2 }`. Visible only to `PLATAFORMA_ADMIN` — since that role carries zero scoped permissions (Phase 119), the existing `requiredPermission`/`hasPermission` filter cannot gate it. Do not modify `SidebarNav`'s filter logic; instead splice the item into the array passed to `<SidebarNav nav={...} />` only when `isPlatformAdmin` is true (e.g. `const navItems = isPlatformAdmin ? [...NAV, platformNavItem] : NAV`). Icon choice `Building2` deliberately echoes its two existing uses in this codebase (`/setup`'s "Tenant Inicial" section, the topbar's tenant-identity fallback) — same semantic, a third consistent use.
- Emergent consequence (no new code required): every existing `requiredPermission`-gated nav item already renders hidden for a `PLATAFORMA_ADMIN` user (empty `permissions` array), so "Plataforma" is typically the only nav item such a user sees.
- Type-plumbing flag (not a visual decision, but load-bearing): `Role` in `web/src/types/auth.ts` is currently `"ADMIN" | "TECNICO" | "ADVOGADO" | "ASSISTENTE"` and does not include `"PLATAFORMA_ADMIN"` — extend the union for the role check above to type-check.

### Default view — Tenants list
**Primary visual anchor:** the "Criar Tenant" button (sole accent-colored element in the header row) is the deliberate focal point of the default screen — everything else (table rows, badges) uses neutral/status color only.

Single `Card` (`rounded-xl`, matching every other list Card in this app), containing:
- `CardHeader` (`flex flex-row items-center justify-between`): left = CardTitle + CardDescription (see Copywriting); right = "Criar Tenant" button.
- `CardContent`: search `Input` (see Copywriting) directly above the table, then the shared `DataTable`.
- No KPI hero row (unlike Clientes/Processos). `UserManagementTab` — CONTEXT.md's own named closest analog — has no KPI row either; this screen mirrors that simpler shape deliberately, not the heavier Clientes/Processos shell.

**DataTable columns** (`ColumnDef<TenantAdminSummary>[]`, mirrors `clientes/columns.tsx` structurally):
1. `nome` — `enableHiding: false`. Cell: rounded-md initials avatar (first 2 letters, uppercase — exact classes from `clientes/columns.tsx`'s nome cell: `h-10 w-10 rounded-md bg-blue-50 dark:bg-blue-500/10 text-blue-700 dark:text-blue-400 border border-blue-100 dark:border-blue-500/20`) + bold tenant name, **plain text, not a link** (deliberate deviation from Clientes: every action here happens via in-row Dialogs, there is no tenant detail page this phase). The row where `nome === "LexCV"` additionally renders a small `Badge variant="outline"` reading "Plataforma" immediately under the name, so the disabled suspend action is self-explanatory before the platform admin even hovers the tooltip.
2. `plano` — Badge, raw enum casing (matches the established convention: Clientes' `tipo` column renders raw `"PARTICULAR"`/`"EMPRESA"`, not a humanized label). `STARTER` → `variant="gray"`, `STANDARD` → `variant="purple"`, `ENTERPRISE` → `variant="amber"`, class `font-bold tracking-wide` (identical to the `tipo` column's badge class).
3. `utilizadores` — two-line stacked cell (`flex flex-col`, mirrors the `nif` column's stacked-caption treatment): line 1 = `"{X}/{Y}"` (or `"{X} · sem limite"` when `limiteUtilizadores` is null); when `X >= Y` (limit reached), line 1 switches to weight 600 + destructive color and a line 2 caption `"limite atingido"` appears using the already-declared 12px Label size (uppercase, destructive) — reusing Phase 118's exact at-limit visual language for cross-phase consistency, sized from this phase's own declared scale rather than introducing a 5th size value. Sortable on the numeric active-user count.
4. `estado` — Badge, humanized Title Case (matches the `ativo`/`Ativo`/`Inativo` boolean-status convention, distinct from the raw-enum `plano` column): `Ativo` → `variant="green"`, `Suspenso` → `variant="red"`.
5. `acoes` — `enableSorting: false`, `enableHiding: false`, right-aligned (matches Clientes exactly). Two icon buttons, `inline-flex items-center gap-1`, `h-9 w-9 p-0` desktop / `h-12 w-12 p-0` mobile, each Tooltip-wrapped:
   - **Editar** (`Pencil`, hover `text-emerald-600`) — always enabled, including for "LexCV". Opens the Editar Dialog.
   - **Suspender/Reativar** (single toggle slot: `Lock` icon + hover `text-red-600` + tooltip "Suspender" when `ativo=true`; `Unlock` icon + hover `text-emerald-600` + tooltip "Reativar" when `ativo=false`) — `disabled` + Phase 118 Tooltip+`<span tabIndex={0}>` composition for the row where `nome === "LexCV"` (tooltip copy overrides to the reserved-tenant guard message; see Copywriting). Opens the matching AlertDialog confirmation.

No "Eliminar" action exists for tenants in this phase — deliberately out of scope. Do not add one.

**Mobile (`<md`)**: stacked cards, `md:hidden`, one per tenant — mirrors `clientes/page.tsx`'s mobile card block structurally (initials avatar + name + Plano/Estado badges inline, action icons at `h-12 w-12` below). Desktop DataTable wrapped `hidden md:block`, matching the exact breakpoint convention used everywhere else in this app.

### Criar Tenant (inline panel, not a modal)
Clicking "Criar Tenant" swaps the entire Card content from [search + table] to a form Card — the exact `isFormOpen` toggle mechanic from `UserManagementTab`, not a `Dialog`. Rationale: the logo upload + preview needs generous 2-column width (mirroring `/setup`'s own layout treatment), and no "modal + file upload" precedent exists in this app to justify inventing one; an inline panel handles it more comfortably. Header carries an "X" close button (`aria-label="Fechar"`, matches `UserManagementTab` exactly); Footer carries "Cancelar" (outline) + "Criar Tenant" (blue, submit) — same label as the trigger, no third phrase invented.

Fields, in order (see Copywriting for exact label/placeholder/validation copy): Nome da Empresa/Cliente, Logo (opcional, file input with preview), Email do Administrador, Password, Confirmar Password. Zod schema mirrors `schemas/setup.ts`'s `setupSchema` rules exactly (reuse or re-export `strongPasswordPattern`, do not re-derive the regex).

On success: `queryClient.invalidateQueries` on the tenants-list query key, toast success, panel closes back to the list. **Do not** copy `UserManagementTab`'s `window.location.reload()` — that is a legacy mock-database-era artifact (its own comment says "reload to sync mock database"), superseded everywhere else in this app by the idiomatic `useMutation` + `queryClient.invalidateQueries` pattern already used consistently in `use-clientes.ts` (e.g. `invalidateQueries({ queryKey: ["clientes", "list"] })`). Follow that pattern, not the settings-page one.

### Editar Tenant (Dialog, modal)
A `Dialog` (not `AlertDialog` — this is a reversible form edit, not an immediate consequential action), default width, triggered by the row's Editar button. Exactly 2 fields: Plano (`NativeSelect`, 3 options, raw enum values as both `value` and visible option text — STARTER/STANDARD/ENTERPRISE) and Limite de Utilizadores (`Input type="number"`, empty = `null` = sem limite). Both fields commit together on "Guardar" (single PATCH/PUT, per CONTEXT.md's own discretion on combining vs. splitting — combined here since both edit the same `Tenant` row and neither needs the immediate-effect guarantee suspend does).

**Never** fold the suspend/reactivate toggle into this Dialog. Suspend's Success Criterion is "immediate effect," which is a direct, single-purpose action; the Editar Dialog is a deferred-until-"Guardar" form draft. Mixing the two would blur an instant action with a pending edit.

### Suspender/Reativar (AlertDialog, per row)
See column 5 above for the icon/tooltip/color contract. Confirmation copy and button styling in Copywriting/Color. On confirm: single PATCH toggling `ativo`, `queryClient.invalidateQueries`, success toast — no reload.

**Suspended tenant's own end users — no new UI needed.** When a tenant is suspended, `JwtAuthenticationFilter`'s existing per-request re-validation (extended in this phase to also check `Tenant.ativo`) means that tenant's users' very next request — including the existing 30–60s notification-bell poll, or their next navigation — silently receives a 401. `apiFetch` already excludes 401/403 from its automatic toast, and `DashboardShell`'s existing `me.isError` effect already redirects to `/login?returnUrl=...`. This is the exact same "session expired" UX already in place for user-level deactivation; do not build a bespoke "your organization was suspended" banner — it is out of scope and would leak information to a locked-out user.
