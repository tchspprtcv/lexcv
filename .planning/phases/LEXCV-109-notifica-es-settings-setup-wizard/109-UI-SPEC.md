# Phase 109 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 109 covers NTF-28 (`DropdownMenu` for the topbar/sidebar user menu), NTF-29 (`Badge` for the notification-bell unread counter), and NTF-30 (`Progress` for the `/setup` wizard). Per `109-CONTEXT.md`'s locked Phase Boundary, exactly 3 files are touched: `web/src/components/shared/dashboard-shell.tsx` (user menu, 3 call sites — see finding below), `web/src/components/shared/notification-bell.tsx` (unread badge only, lines 88-95), `web/src/app/setup/page.tsx` (Checklist card → Progress, lines ~261-270). This is the smallest module phase in the milestone — a pure component-identity swap, zero new business logic, zero new page.

**Explicitly out of scope (do not re-litigate):**
- The `Popover` composition in `notification-bell.tsx` (trigger/content, dropdown list, snooze control, mark-all/mark-one) — locked untouched by both `109-CONTEXT.md` and Roadmap Success Criterion 1 (converting it to `DropdownMenu` would be an accessibility anti-pattern for a list with multiple interactive controls per row).
- The `RBAC isFetched` pattern established in Phases 105-108 — none of this phase's 3 files use `usePermissions()`/`permissions.isFetched`; `dashboard-shell.tsx` uses `useMe()` + `hasPermission()` directly to filter nav items (line 89), a different, pre-existing pattern. Not touched.
- Adoption of the shadcn `Avatar`/`AvatarFallback` primitive (established for Clientes/Processos in Phase 105/CLP-04) for the topbar/sidebar user avatar — not requested by NTF-28/29/30 or `109-CONTEXT.md`. The avatar's existing custom markup (initials-fallback `<div>`/`<img>`, gradient-circle on topbar, square on sidebar) is preserved pixel-for-pixel; only a `DropdownMenu` wraps it.
- Adding a confirmation dialog to "Terminar sessão" — no such request exists; logout stays a direct action (see Copywriting Contract).
- `/setup`'s "Regras da Password" card (adjacent to the Checklist card) — unrelated, untouched.

**Verified-against-source findings (load-bearing for planning):**

1. **The user-menu migration touches 3 call sites in `dashboard-shell.tsx`, not 2** — confirmed by direct read of the current file (line numbers below are exact, current-source-verified, matching `109-CONTEXT.md`'s own citations where given):
   - **(a) Topbar header block, lines 294-311** — inside `<header>`'s `<div className="ml-auto flex items-center gap-3">`, the `<div className="flex items-center gap-3 pl-1">` sub-block: name+role text (`<Link href="/settings">`, hidden on `<sm`) + circular gradient avatar (`<Link href="/settings">`, `h-9 w-9 rounded-full bg-gradient-to-tr from-blue-600 to-indigo-500`). **No separate logout button exists here today** — this is the literal "avatar+nome, hoje um `<Link>` simples para `/settings`" described in `109-CONTEXT.md`'s Phase Boundary, and the one Roadmap Success Criterion 1 calls "o novo menu de utilizador na topbar." Always visible (both viewport sizes — the `<header>` itself is never hidden), currently the *only* place mobile users can reach anything settings/logout-adjacent without opening the hamburger drawer.
   - **(b) Desktop sidebar footer, lines 135-164** — inside `<aside className="hidden md:flex ...">`'s `mt-auto p-4` block: square avatar (`<Link href="/settings">`, `h-9 w-9 rounded-md bg-slate-800`) + name/role (`<Link href="/settings">` + `<div>`) + a **separate** `Tooltip`-wrapped `Button` (lines 155-162) with `LogOut` icon and `onClick={onLogout}`.
   - **(c) Mobile Sheet footer, lines 220-249** — structurally identical duplicate of (b), inside `<SheetContent side="left">`; its own Tooltip+Button portion at lines 240-247.
   - **All 3** currently navigate directly to `/settings` on avatar/name click and (for (b)/(c) only) expose logout via a structurally-independent adjacent button — matching `109-CONTEXT.md`'s general description "O bloco inteiro (avatar+nome) torna-se `DropdownMenuTrigger asChild`, deixando de navegar diretamente para `/settings` ao clicar." Building the shared `UserMenu` once and consuming it at all 3 sites (not just (b)/(c)) is the only reading that satisfies both the Roadmap's singular "topbar" framing and `109-CONTEXT.md`'s explicit line citations for all 3 locations — and avoids leaving the topbar's avatar block on the old direct-`Link` behavior while (b)/(c) move to `DropdownMenu`, a visibly inconsistent half-migration this milestone has consistently avoided (see Phase 105's Clientes+Processos combined-delivery rationale for the same principle).
2. **`/setup`'s Checklist block is at lines 261-270** (not 262-269 as `109-CONTEXT.md` approximates) — a `<div className="space-y-3 border ... p-5 ...">` containing a `text-xs font-semibold uppercase tracking-[0.22em]` label ("Checklist") and 3 `<p>` lines. `form.formState.isSubmitting`/`successMessage`/`serverError` are confirmed present exactly as `109-CONTEXT.md` describes (lines 31-32, 296-298 in the current file), so the phase-derivation logic needs no new state.
3. **`Progress` is not yet imported in `setup/page.tsx`** (confirmed — current imports are `Button`, `Card*`, `Input`, `Label`, `apiFetch`, `setupSchema`, types only) — a new `import { Progress } from "@/components/ui/progress"` is required. `Badge` is **already** imported in `notification-bell.tsx` (line 8, used for the category chip) — no new import needed there, only the markup at lines 88-95 changes.
4. **`cn()` is `twMerge(clsx(...))`** (`web/src/lib/utils.ts`) — confirmed Tailwind-class-conflict-aware. This matters for the Badge migration: passing `className="... bg-red-500 p-0 h-4 w-4 ..."` to `<Badge>` correctly overrides `badgeVariants`' own `bg-neutral-100`/`px-2.5 py-0.5` (same-property-group override, not a duplicate-class bug), exactly as `109-CONTEXT.md` requires ("via `className` override").

## Visual Hierarchy

No new page-level focal point anywhere. All 3 changes are in-place component-identity swaps over existing chrome:

- The 3 `UserMenu` call sites keep their exact existing position, size, and trigger appearance (circular gradient avatar + right-aligned text on the topbar; square avatar + left-aligned text on the sidebar/Sheet footers) — only click behavior changes (opens a menu instead of navigating directly), and (b)/(c) lose their separate always-visible logout icon button (folded into the menu, see Component Inventory).
- The unread-count `Badge` keeps the exact existing `absolute -top-0.5 -right-0.5 h-4 w-4` position/size on the `Bell` icon button — no layout shift.
- The `/setup` Checklist card keeps its exact existing container (`border-slate-200 bg-slate-50 p-5`, right column, `lg:pl-8` divider) — only its inner content changes from a static label+3-lines to a `Progress` bar + percentage + the same 3 lines as a legend below it.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|

Component-specific notes:

- `DropdownMenuItem` renders at its own shipped `text-sm` (14px), unweighted (400) — matches Body, zero new type treatment.
- The `Badge`'s `text-[10px] font-bold` is **reused verbatim** from the existing `<span>` it replaces (Verified-against-source, `109-CONTEXT.md` locked) — not a new violation; this project has a long-standing informal exception for sub-12px counter/chip micro-text (sidebar "Sistema" label at `text-[10px]`, avatar initials, timestamps), predating this milestone.
- The Progress section's "Progresso"/percentage label reuses the existing `text-xs font-semibold uppercase tracking-[0.22em]` treatment already on the Checklist label it replaces — no new weight/size.
- **Pre-existing, out-of-scope note (same class of issue every prior module UI-SPEC flagged):** the sidebar brand mark "LEXCV" (`text-[11px] font-bold tracking-widest`, both `<aside>` and `<Sheet>` copies) and the avatar-initials fallback text (`text-xs font-bold`, all 3 call sites) both carry a `font-bold` (700) weight — a 3rd weight value outside this project's declared 400/600 pair. Flagged here purely so the checker does not misattribute these as new violations this phase introduces.
