## Icon Vocabulary Contract

This resolves `115-CONTEXT.md`'s one open discretion item ("Mapeamento exato ícone↔ação... a decidir durante o planeamento/execução"). Two rules apply everywhere:

- **Icon size:** `h-4 w-4` on every icon inside a `Button`, with zero exceptions found across all 44 already-compliant instances. Locked.
- **Icon-only footprint:** `size="icon"` (resolves to `h-9 w-9` per `button.tsx`'s `buttonVariants`), matching the icon-only pattern already established at 15+ call sites (`clientes/columns.tsx`, `processos/[id]/documentos-columns.tsx`, `documentos/columns.tsx`, `data-table-view-options.tsx`, etc.). Some older call sites hand-roll `className="h-9 w-9 p-0"` or `h-8 w-8 p-0"` instead of the `size="icon"` prop — both render identically; **use the `size="icon"` prop for every new FICO-01/ICON-01 icon-only button** (cleaner, matches the newer/majority convention), do not retrofit the older hand-rolled instances (out of scope, they already work).

### Icon-only + Tooltip code pattern (FICO-01 — copy exactly, already proven at 15+ call sites)

```tsx
<Tooltip>
  <TooltipTrigger asChild>
    <Button type="submit" size="icon" aria-label="Aplicar filtros">
      <Check className="h-4 w-4" />
    </Button>
  </TooltipTrigger>
  <TooltipContent>Aplicar filtros</TooltipContent>
</Tooltip>
```

Rules, all confirmed by precedent (`clientes/columns.tsx`, `documentos/columns.tsx`, `data-table-view-options.tsx`):
- `aria-label` and `TooltipContent` carry **identical copy** — this satisfies FICO-01 AC4 (keyboard-only users get the same information as mouse users) automatically, no separate a11y pass needed.
- Do **not** also add a native `title` attribute — it's redundant with `Tooltip` and not used at any of the established icon-only+Tooltip call sites (two other files in this codebase, `notification-bell.tsx`/`notificacao-snooze-control.tsx`, do combine `title` with a manual (non-`Tooltip`-component) hover — that's a different, older pattern; do not mix the two on the same button).
- Keep each button's **existing `variant`** when converting to icon-only (Aplicar keeps its primary/default variant, Limpar keeps `ghost`, Exportar keeps `outline`) — preserves the current visual hierarchy (primary vs. secondary action) even without text.

## Scope Boundaries — read before planning tasks

1. **Pareceres and Notificações: ICON-01 applies, FICO-01 does not.** `115-CONTEXT.md` explicitly excludes these two modules from the icon-only+Tooltip conversion ("não expandir a Pareceres/Notificações mesmo que tenham padrões semelhantes"), but that exclusion is scoped to FICO-01 only — ICON-01 has no module exclusion in either the requirement text or `115-CONTEXT.md`. Concretely: `pareceres/page.tsx`'s Aplicar/Limpar buttons (L185/188/370/377) and `notificacoes/page.tsx`'s "Limpar filtros" (L211) should receive an icon **while keeping their visible text** (icon + text, not icon-only). Do not strip their labels or add `Tooltip` wraps to these five specific buttons.

2. **Do-not-touch list (44 already-compliant instances):** every button cited as "compliant" in the tables above already satisfies ICON-01 today. Re-touching them (swapping `Pencil`→`Edit` for consistency, adding a `Tooltip` where only `aria-label` exists, etc.) is explicitly out of scope per `115-CONTEXT.md`: *"não reaplicar/trocar ícones já corretos nos ficheiros que já os têm."* The one pre-existing inconsistency worth knowing about (not fixing): `settings/page.tsx` uses `Edit` where the rest of the app uses `Pencil` for the identical "Editar" action — both are already-correct, leave both alone.

3. **Native `<button>` elements and Sidebar-specific button primitives are outside this audit's bounded scope.** This entire inventory covers the `<Button>` component from `@/components/ui/button` (the same 208/48 scope `115-CONTEXT.md` itself scouted). Two known examples exist outside that count: the prazo-conclusion toggle in `processos/[id]/page.tsx:1154-1165` (a raw `<button>`, already icon-only with `CheckCircle2`/`Circle`) and the topbar/sidebar chrome (`dashboard-shell.tsx`, `sidebar-nav.tsx`, `bottom-nav.tsx`, `user-menu.tsx`, `global-search-dialog.tsx`, `file-drop-zone.tsx` — none import `Button` directly). If the planner wants full `ICON-01` literal coverage ("todos os botões"), these files would need a separate discovery pass; recommend treating them as out of scope for this phase unless the checker flags a specific instance, since `115-CONTEXT.md`'s own scope discovery never counted them either.

4. **Special-case a11y completions (4 instances) are optional, not blocking.** Processos' Exportar (folded into the FICO-01 table, effectively mandatory since it's one of the 5 named modules) aside, the other 3 (Agenda's 2 Chevrons, Settings' close-`X`) already have a correct icon — their only gap is a missing `aria-label`. Neither ICON-01 nor FICO-01's literal text requires this fix (both are about icon *presence*, not pre-existing icon-only buttons' accessibility completeness). Recommend including them since they're nearly free, but do not block phase completion on them.

5. **Destructive actions: no new confirmation UX.** This phase adds `Trash2`/similar icons to existing Remover/Apagar/Eliminar triggers — it does not add, remove, or change how each one confirms (some already use `AlertDialog`, e.g. `agenda/[id]/page.tsx`; others rely on a plain `window.confirm()` inside the handler, e.g. `documentos/page.tsx`'s `DocumentoMobileCard`; a few have no confirmation at all today). Preserve whatever each button already does — this phase is additive-visual only.
