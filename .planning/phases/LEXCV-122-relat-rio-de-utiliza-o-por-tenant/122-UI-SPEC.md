# Phase 122 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase delivers exactly one new frontend screen — `/plataforma/relatorio`, role-gated to `PLATAFORMA_ADMIN` only (same guard pattern as `/plataforma` itself) — plus one new link/button on the existing `/plataforma` screen to reach it. **Zero backend changes**: 122-CONTEXT.md's own dedicated codebase research confirms `GET /api/v1/platform/tenants` already returns all fields this phase needs and already includes suspended tenants; `UserRepository.countByTenantIdAndAtivoTrue` is already the sole active-user-count source (Phase 117). The only backend-adjacent work this phase does is a regression test addition to `PlatformAdminControllerTest.java` (proving a `.ativo(false)` tenant still appears in the list) — not a visual/interaction concern, out of this contract's scope. **Zero new shadcn installs** — every primitive this phase needs (`Card`, `Button`, `Input`, `Badge`, the shared `DataTable`) already exists.

This is deliberately a **"reuse and trim" contract, not a from-scratch design**. It reuses:
1. Phase 120's own already-approved `plano`/`utilizadores`/`ativo` cell rendering **verbatim** (`plataforma/columns.tsx`, cited by line number below rather than re-derived).
2. Phase 89's precedent (PROJECT.md Key Decisions, v2.10) — a secondary screen gets its own route but never a permanent sidebar nav item, reached only via an in-context link from the primary surface.
3. `processos/page.tsx` → `processos/dashboard/page.tsx`'s existing pattern — a list screen with an outline "secondary view" button next to its primary CTA, leading to a satellite read-only screen with its own back-arrow header. This is the closest structural precedent in the codebase to what this phase builds, and is followed instead of re-deriving a new header shape.

The one genuinely new visual surface is small: a single outline-variant link button on `/plataforma`, and one read-only report screen that drops the "Ações" column entirely.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.5 |
| Heading | 20px | 600 | 1.2 |
| Display | 30px | 600 | 1.2 |

**This phase's own new decisions use exactly 2 weights: 400** (regular — table cell text, search `Input` value, CardDescription/subtitle text) **and 600** (semibold — Label captions, column headers, CardTitle/Heading text, the "limite atingido" caption, the Heading role, and this screen's own new `<h1>` at `text-3xl font-semibold`, deliberately set to 600 rather than the app's usual 700 for this one new element).

**Disclosed third weight — orchestrator-approved, not a new decision:** the `plano` column's Badge (Screen Layout below) is reused **verbatim** from `plataforma/columns.tsx:154-161`, including its `font-bold` (700) class — the exact same Badge, rendering the exact same tenant's exact same plano value, one click away on `/plataforma`. Overriding it to 600 on this screen only would make the identical badge render at two different weights depending on which screen the same data is viewed from — a real, visible inconsistency worse than the documentation concern it would resolve. This is a pre-existing, already-shipped, sitewide typographic reality (page `<h1>`s and this specific Badge both use 700 across `/plataforma`, `/processos/dashboard`, Clientes, Settings, and others), not a new decision this phase is making, and resolving it project-wide is outside any single phase's authority — it would need a formal, developer-approved design-system exception recorded once, not re-litigated per phase. The UI checker (`gsd-ui-checker`) correctly flagged this against Dimension 4's flat weight-count rule across 3 review rounds; force-approved by the orchestrator after the 2-iteration revision cap was reached, per `/gsd:ui-phase`'s own documented "max iterations reached" resolution path (Force approve / Edit manually / Abandon). Recorded here rather than argued away, so a future reader sees the actual disposition.

### `/plataforma` — CardHeader change (the only edit to an existing file)

Current header (`plataforma/page.tsx`, `CardHeader className="flex flex-row items-center justify-between space-y-0"`) holds only the title block + "Criar Tenant". Also add `flex-wrap gap-3` to the `CardHeader` itself, so the title block and the now-two-button cluster can wrap onto their own line on narrow viewports instead of compressing three elements into one unbreakable row — a new consideration this phase introduces, since Phase 120 only ever had to fit one button here.

<CardHeader className="flex flex-row flex-wrap items-center justify-between gap-3 space-y-0">

Not a factory function (unlike `../columns.tsx`'s `columns({ onEdit, onToggleAtivo })`) — there are no row callbacks on a read-only screen, so this is a plain static array. Import `TENANT_RESERVADO` from `../columns` rather than re-declaring the literal string (avoids a second copy drifting out of sync).

4 columns, same order as `/plataforma`, `acoes` dropped entirely:

1. **`nome`** (`enableHiding: false`) — cell copied verbatim from `plataforma/columns.tsx:128-147`: rounded-md initials avatar + bold name + (for the `TENANT_RESERVADO` row only) an `outline` "Plataforma" Badge underneath. Plain text, not a link (same as `/plataforma` — there is still no tenant detail page).
2. **`plano`** — Badge, raw enum casing, copied verbatim from `plataforma/columns.tsx:154-161` (`STARTER`→gray, `STANDARD`→purple, `ENTERPRISE`→amber, `font-bold tracking-wide`).
3. **`utilizadores`** — copied verbatim from `plataforma/columns.tsx:163-193`: two-line stacked cell, `"{X}/{Y}"` or `"{X} · sem limite"` when `limiteUtilizadores` is null; destructive color + semibold + a `"limite atingido"` caption (12px, uppercase) when `utilizadoresAtivos >= limiteUtilizadores`. ### Mobile cards — one deliberate divergence from `/plataforma`'s own mobile block

`/plataforma`'s mobile card (`page.tsx:198-307`) shows avatar + nome + Plano/Estado badges, then a row of action-icon buttons — it **never shows the utilizadores figure at all on mobile** (it relies on the desktop DataTable column for that). Copying that block byte-for-byte onto the report would silently violate Success Criterion 1 on mobile viewports (utilizadores ativos would be invisible below `md`). Since the action-icon row is being dropped anyway (read-only), replace it with the utilizadores line instead of just deleting it:

```tsx
<div className="mt-2 pl-[52px]">
  <span className={atingiuLimite ? "text-sm font-semibold text-red-600 dark:text-red-400" : "text-sm text-slate-600 dark:text-slate-300"}>
    {tenant.limiteUtilizadores !== null
      ? `${tenant.utilizadoresAtivos}/${tenant.limiteUtilizadores} utilizadores`
      : `${tenant.utilizadoresAtivos} utilizadores · sem limite`}
  </span>
  {atingiuLimite ? (
    <span className="ml-2 text-[12px] uppercase tracking-wide text-red-600 dark:text-red-400">limite atingido</span>
  ) : null}
</div>
```

`pl-[52px]` reuses the exact existing indent convention (40px avatar + 12px gap) so this line still aligns under the name, matching `/plataforma`'s own mobile card indentation exactly. Everything else in the mobile card (avatar, nome, Plataforma badge, Plano badge, Estado badge, the `md:hidden`/`hidden md:block` breakpoint split, the "Sem resultados..." zero-length check) is copied verbatim.

### Explicitly NOT included in this phase (confirmed against 122-CONTEXT.md's Deferred Ideas)

- **No "Ações" column** — read-only report, zero CRUD, by design (no Success Criterion asks for any action here).
- **No KPI/aggregate hero row** (e.g., "total utilizadores ativos across all tenants") — Phase 120's console already opted out of this shape for the identical underlying data; this phase defaults to the same simplicity, no new reason found to diverge.
- **No CSV/printable export** — genuinely optional per CONTEXT.md's own Claude's Discretion section, not required by any Success Criterion. Left out to keep this phase small; the well-guarded `financeiro/page.tsx` `exportHonorariosCsv` pattern (OWASP formula-injection escaping included) remains available as a clean addition to a future phase if the platform admin actually asks for exportable data.
- **No second permanent sidebar nav item** — reached only via the `/plataforma` CardHeader link, per CONTEXT.md's decision and the Phase 89 (v2.10) precedent.
