# Phase 113 — UI Design Contract

> Visual and interaction contract for promoting the existing Estado filter to the always-visible main filter bar on Processos. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Grounded in:** `113-CONTEXT.md` (locked decisions, smart-discuss autonomous), `REQUIREMENTS.md` (PEST-01), `ROADMAP.md` (Phase 113 goal + 3 success criteria), a direct read of `web/src/app/(dashboard)/processos/page.tsx` (current main filter bar, lines 202-320, including the existing Estado `NativeSelect` block at lines 251-270), `web/src/components/ui/native-select.tsx`, `web/components.json`, `web/src/app/globals.css`, and `112-UI-SPEC.md` (this repo's most recently approved UI-SPEC, confirming the current shadcn preset/design-token baseline). No open design questions required user interaction — `113-CONTEXT.md` already locked every visual decision this phase needs; every field below is pre-populated from these sources or a clearly-marked researcher default.

**Scope reminder (explicit, per the orchestrator's own framing of this phase):** this is a relocation, not a redesign. The Estado control already exists, is already fully functional, and is already correctly styled. The only change is its position in the DOM/JSX — from inside the collapsed `advancedOpen` panel to the always-visible main filter bar. This document is deliberately short because the visual surface being touched is deliberately small.

**Non-goals for this phase (explicit, to prevent scope creep):**
- Does NOT introduce any new component — `NativeSelect` (`web/src/components/ui/native-select.tsx`) is reused byte-for-byte: same props, same 6 `<option>` values, same `size="default"`.
- Does NOT change `draftEstado` / `onApply` / `onClear` logic — zero lines of state or handler code change; only the JSX's position in the tree moves.
- Does NOT touch `--radius` (Phase 114's job) or add an icon to the Estado field (Phase 115's job, ICON-01/FICO-01) — this page's existing icons (`Filter`, `Search`, `Download`, `Plus`) are untouched.
- Does NOT promote Tribunal, Área jurídica, or Cliente — they remain inside the collapsed `advancedOpen` panel, per `113-CONTEXT.md`'s explicit "O que NÃO promover" list.
- Does NOT add an active-filter-count badge to the "Filtros" button, does NOT add a totalAtivos/totalSuspensos count near the promoted dropdown (that KPI already exists elsewhere on this page and is explicitly out of scope per `113-CONTEXT.md`), and introduces zero new copy.

## Spacing Scale

Declared values (must be multiples of 4) — standard scale, already the app-wide convention. No new spacing tokens introduced by this phase:

| Token | Value | Usage on this page |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps inside buttons (`gap-1`/inline icon offsets) |
| sm | 8px | `gap-2` between the search field / promoted Estado field / "Filtros" button in the main bar |
| md | 16px | `p-4` filter-bar Card padding, `p-5` KPI card padding |
| lg | 24px | `gap-6` page header row |
| xl | 32px | Not used by the touched region |
| 2xl | 48px | Not used by the touched region |
| 3xl | 64px | Not used by the touched region |

**Exceptions:**
- One new **fixed width**, not a spacing token: `w-40` (160px = 4×40, 8-point-grid compliant) for the promoted Estado field's wrapper `<div>`. This is a researcher default (no existing precedent for an always-visible dropdown in this app's main filter bars — Clientes' own filter bar, built in the same Phase 105 batch, also keeps its Estado/Tipo selects inside its collapsed panel). 160px comfortably fits the longest option label ("Em triagem", "Encerrado", "Concluído") without truncation while staying visually compact next to the 320px search field. Do not use `w-full`/`flex-1` here — the wrapper sits inside a `flex flex-wrap` row (not a grid column), so an unconstrained width would fight the search field and the "Filtros" button for space.
- One **consequential layout adjustment**, not a new value: removing the Estado child from the 4-item `advancedOpen` grid (`lg:grid-cols-12`, each child `lg:col-span-3`, 4×3=12) leaves 3 children. To keep the row filling exactly 12 columns with no dangling gap, the 3 remaining fields (Tribunal, Área jurídica, Cliente) must change from `lg:col-span-3` to `lg:col-span-4` (3×4=12). See Relocation Detail below.

## Relocation Detail

*(Supplementary to the template's required sections — this is the concrete, line-level contract the planner/executor need for a JSX-move phase; the checker maps it to Dimensions 2/5 "Visuals"/"Spacing".)*

**Source (remove):** the entire Estado block currently at `processos/page.tsx:251-270` — the `<div className="lg:col-span-3">` wrapping the "Estado" label + `NativeSelect`, currently the first child inside `{advancedOpen ? (...) : null}` (`page.tsx:249-250`).

**Destination (insert):** as a new sibling `<div>` inside the existing `<div className="flex flex-wrap items-end gap-2">` (`page.tsx:205-229`), positioned between the Pesquisar field's closing `</div>` (`page.tsx:219`) and the "Filtros" `<Button>` (`page.tsx:220`) — matching `113-CONTEXT.md`'s locked position ("logo a seguir ao campo de pesquisa, antes do botão 'Filtros'").

**New wrapper markup** (only the outer `<div>`'s width class changes; the `NativeSelect` and everything inside it is byte-for-byte identical to the current lines 256-268):

```tsx
<div className="w-40 max-w-full">
  <div className="text-[11px] font-bold tracking-wider uppercase text-slate-500 dark:text-slate-400">
    Estado
  </div>
  <div className="mt-2">
    <NativeSelect
      value={draftEstado}
      onChange={(e) => setDraftEstado(e.target.value)}
      size="default"
      className="w-full"
    >
      <option value="">Todos</option>
      <option value="TRIAGEM">Em triagem</option>
      <option value="ATIVO">Ativo</option>
      <option value="SUSPENSO">Suspenso</option>
      <option value="ENCERRADO">Encerrado</option>
      <option value="CONCLUIDO">Concluído</option>
    </NativeSelect>
  </div>
</div>
```

**Required consequential edit (not optional):** after Estado's block is removed, the `advancedOpen` grid (`page.tsx:250`, `lg:grid-cols-12`) has only 3 children left (Tribunal, Área jurídica, Cliente). Each must change from `lg:col-span-3` to `lg:col-span-4` (3×4=12) so the row continues to fill exactly 12 columns. Leaving them at `col-span-3` would leave a dangling empty 3-column gap on the right on large screens — a visual defect directly caused by this relocation, not a pre-existing issue.

**Apply-behavior (resolves `113-CONTEXT.md`'s "Claude's Discretion" item):** keep the existing draft + "Aplicar" submission pattern unchanged. Do **not** add an `onChange`-triggered immediate-apply behavior exclusively for the promoted Estado field.
- Rationale: `113-CONTEXT.md`'s own domain framing is explicit — "uma mudança de layout, não de lógica" (a layout change, not a logic change). Special-casing Estado to auto-apply while Tribunal/Área/Cliente still require a manual "Aplicar" click would make the same form behave under two different submission models, a bigger behavioral change than this phase's proportionate scope calls for, and would touch `onApply`/state-handling code this phase does not need to touch.
- This still fully satisfies all 3 ROADMAP success criteria: "Aplicar" and "Limpar" already live in the always-visible main bar today (`page.tsx:234-239`), not inside `advancedOpen`. Once Estado sits next to the search field, the entire select → Aplicar loop is visible without opening any panel — the actual gap being closed (Estado's *invisibility*, not its logic) is fully fixed by the relocation alone.
- The search field's own 300ms-debounce auto-apply (`page.tsx:99-104`) is a distinct, pre-existing exception justified by free-text input, not a precedent to extend to discrete single-select filters.

**Accepted consequence — tab order:** relocating Estado earlier in the DOM changes tab order from `Search → Filtros → (Tribunal → Área → Cliente, if open) → Estado` to `Search → Estado → Filtros → Download → Aplicar → Limpar → Novo Processo → (Tribunal → Área → Cliente, if open)`. This is intended — Estado is now visually and functionally earlier in the flow — not a defect to fix.

**Accepted, pre-existing pattern — not a gap to fix here:** none of this page's filter labels (Pesquisar/Estado/Tribunal/Área jurídica/Cliente) use a `<label htmlFor>`/`id` association today; each is a plain `<div>` of text. This is a codebase-wide, pre-existing convention (present before this phase, present after it). Do not retrofit proper label association as part of this relocation-only phase — that is a separate, broader accessibility improvement out of this phase's scope.
