## From 108-04 human-verify checkpoint (Browser-pane environment issue, not a code defect)

## Follow-up on the Browser-pane environment issue (after goal-backward verification flagged `human_needed`)

Made a second recovery attempt. The environment DID partially recover — `/pareceres` (list) rendered with a single `<main>` and full click-interactivity (Filtros toggle opened correctly, 4 comboboxes rendered) in a reused tab. However, navigating from there to `/pareceres/{id}` (either real parecer ID) immediately reverted to the broken double-`<main>`/zero-interactivity state. Isolated further: a brand-new tab's *first-ever* navigation straight to `/pareceres/{id}` reproduced the same break (ruling out same-tab navigation history as the trigger); a nonexistent parecer ID reproduced the identical break (ruling out a data-dependent code path — the break happens before/regardless of `parecer.data` resolving); a full `.next` cache clear + dev-server restart did not resolve it (ruling out stale Turbopack incremental-cache corruption). Server-side logs stayed clean (`200`) throughout every attempt. This narrows the issue to something specific to the `pareceres/[id]/page.tsx` dynamic route's client bundle in this Browser-pane session specifically — plausible given `pnpm build` only type-checks/compiles dynamic `[id]` routes (marked `ƒ` Dynamic in the build output) without ever executing them against real data, so a dev-mode-only client runtime issue here would not be caught by the build gate the way a static route's issue would be. Not resolved this session; both items remain `human_needed` per `108-VERIFICATION.md`, consistent with how Phase 105 handled an analogous residual live-check gap (routed to `human_needed`, requirements still marked Complete, milestone proceeded).
