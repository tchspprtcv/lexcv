# Phase 108 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 108 covers PARC-18 (`Select`/`NativeSelect` for the Pareceres forms), PARC-19 (`Tooltip` on the "Histórico de Versões" timeline markers), and PARC-20 (`Accordion` collapsing old versions in that same timeline). Per `108-CONTEXT.md`'s locked scope, three files are touched: `pareceres/page.tsx` (list + quick filters + advanced search), `pareceres/nova/page.tsx` (creation form), `pareceres/[id]/page.tsx` (detail: `NovaVersaoForm`, `EntregarParecerDialog`, "Histórico de Versões" timeline).

**This phase is the first `Accordion` consumer in the entire project (confirmed by grep: zero prior imports outside `accordion.tsx` itself) and the first Timeline+Tooltip pairing** — `Tooltip` itself has been established since Phase 102/DSR-03 (icon-only row-action buttons, e.g. `pareceres/columns.tsx`'s "Ver detalhes"), but never yet on a timeline/version-history marker. Both patterns get the same prescriptive, no-precedent-to-inherit treatment Phase 106 gave `DatePickerField` and Phase 107 gave `Combobox`.

**Explicitly out of scope (per `108-CONTEXT.md`, do not re-litigate):**
- The `aprovado`/`aprovadoPorId`/`aprovadoEm` fields on `ParecerVersao` (approval UI) — deferred to a future milestone as PARC-17 since v2.6. No new UI is built around them this phase.
- Pagination/limit on `useParecerVersoes` — the `Accordion` solves the "many versions" UX without a backend change; out of scope.
- RBAC `isFetched` fix (7 sites across the 3 files) — a functional, non-visual correction bundled into this phase's execution but not part of this visual contract, flagged here only so the checker doesn't expect a UI-SPEC entry for it.
- `isResponsavelOuAdmin` instance-level RBAC logic (`pareceres/[id]/page.tsx:153-155`) — pre-existing v2.6 logic, unrelated to this migration, not touched.

**Verified-against-source findings (load-bearing for planning):**

1. **All 6 native `<select>` filter fields in `pareceres/page.tsx` use an empty-string `""` sentinel** (`draftStatus`/`draftAdvogadoId`/`draftClienteId` for the quick filters, lines 178-226; `pesquisaClienteId`/`pesquisaAdvogadoId`/`pesquisaStatus` for the advanced search, lines 259-307 — all `useState("")`, all first `<option value="">Todos</option>`). Radix `Select.Item` cannot take `value=""` (throws at runtime, the same restriction every prior module phase — 105/106/107 — has documented). All 6 need a non-empty sentinel (e.g. `"todos"`). The quick-filter `onApply` currently passes `draftStatus.trim()` etc. straight into `setFilters` with no truthy/sentinel check at all (the hook's own `buildParecerSearch`/`buildParecerPesquisaSearch` already do `filters.x?.trim()` before adding to the querystring, so an empty string is already silently dropped server-side) — switching the sentinel to `"todos"` requires `onApply`/`onClear` to translate `"todos"` back to `""`/omit-the-key before calling `setFilters`/`setPesquisaFilters`, otherwise the literal string `"todos"` would be sent as a real filter value. `onPesquisar`'s existing `if (status) next.status = status` (etc.) checks must become `if (status && status !== "todos") next.status = status`.
2. **`pareceres/page.tsx`'s 6 selects render at `h-10` (40px), not this project's established `h-9` (36px) shipped `Select`/`NativeSelect` default.** Every other module phase (105/106/107) that touched a legacy off-scale control height resolved it by accepting the primitive's own shipped default rather than preserving the legacy value (Phase 106 Scope note #3 did this for Agenda's `font-bold` filters; the same "primitive default wins" resolution applies here to height). All 6 `Select` filters in this phase render at the shipped `h-9`, a deliberate 4px reduction from today's `h-10` — not a regression, matching the height every other migrated `Select`/`NativeSelect` in the app already uses.
3. **`pareceres/page.tsx` and `pareceres/nova/page.tsx`'s native `<select>`s already carry a literal `rounded-none` class** (embedded directly in each inline `className`, and in `nova/page.tsx`'s local `selectClassName` const, line 26) — matching the literal-class convention already on every `Button` in the same files (e.g. `pareceres/page.tsx:134,144,153,164,167,340,344`, `nova/page.tsx:114,215,225`, all explicit `rounded-none`). `--radius: 0rem` is confirmed project-wide at `globals.css:75` (unchanged since Phase 107's finding), so this is visually redundant either way, but the new `SelectTrigger`/`NativeSelect` instances in these two files should carry an explicit `rounded-none` className addendum to match that file-local literal-class convention — same treatment Phase 107 gave its 2 Combobox call sites inside the Processo/Cliente ficha Dialogs.
4. **`EntregarParecerDialog`'s `<select id="versaoFinalId">` (`pareceres/[id]/page.tsx:492-504`) is the one exception** — its inline className (`"flex h-9 w-full rounded-md border border-neutral-200 bg-transparent px-3 py-1 text-sm shadow-sm dark:border-neutral-800"`) already uses `h-9` and `rounded-md` (not `rounded-none`), and neither sibling element in that `AlertDialogContent` (`AlertDialogCancel`, `AlertDialogAction`) carries a literal `rounded-none` override either. This one control needs **no** `rounded-none` addendum and **no** height correction — it already matches `NativeSelect`'s own shipped defaults almost exactly; only the component identity swap (raw `<select>` → `NativeSelect`) is needed here.
5. **`ParecerVersao` has no client-visible "is current"/"is delivered" flag** — this must be derived client-side from data already fetched: the most-recent version is `[...versoes].sort((a,b) => b.numeroVersao - a.numeroVersao)[0]`, and the delivered version is `versoes.find(v => v.id === parecer.data.versaoFinalId)` (only meaningful when `parecer.data.status === "CONCLUIDO"`). Both are already computable from data the page already holds (`versoes.data`, `parecer.data.versaoFinalId`, the existing `isConcluido` boolean) — no new fetch needed.
6. **The marker `<span>` in the current timeline design (`pareceres/[id]/page.tsx:271`) is a plain decorative dot, not a button/link** — it has no native focusability. Wrapping it in `<TooltipTrigger asChild>` without adding `tabIndex={0}` would make the new tooltip mouse-only, unreachable by keyboard — a real accessibility regression this phase must not introduce, since every other `Tooltip` consumer in this app (`pareceres/columns.tsx`'s icon-only `Button`, the sidebar `LogOut` button, Phase 102/DSR-03's icon-only row actions) wraps an already-focusable element.
7. **`AccordionItem`'s own shipped `not-last:border-b` divider (`accordion.tsx:29`) will not fire in the composition this phase requires**, because each `AccordionItem` must sit inside its own per-version marker-wrapper `<div>` (to keep the dot+connecting-line column visually paired with its version), making it the sole child of that wrapper rather than a direct sibling of the next `AccordionItem`. This is intentional and requires no override className — it naturally avoids stacking a redundant divider line next to the timeline's own vertical connecting line (`pareceres/[id]/page.tsx:273`, unchanged).

### Tooltip + Accordion — PARC-19 + PARC-20, "Histórico de Versões" timeline (`pareceres/[id]/page.tsx:240-308`)

**Both requirements land in the same block and are interdependent (the Accordion's default-open state and the Tooltip's copy both depend on the same "is this the current/delivered version" computation) — treat as one composition, not two independent edits.**

**Shared data derivation (compute once, reuse for both Tooltip copy and Accordion default-open state):**

```
const sorted = [...versoes.data].sort((a, b) => b.numeroVersao - a.numeroVersao);
const defaultOpenVersaoId = isConcluido
  ? (parecer.data.versaoFinalId ?? sorted[0]?.id)   // fallback to most-recent if versaoFinalId somehow doesn't match any loaded versao
  : sorted[0]?.id;

function versaoTooltipLabel(versao: ParecerVersao, index: number): string {
  if (isConcluido) return versao.id === defaultOpenVersaoId ? "Versão entregue" : "Versão anterior";
  return index === 0 ? "Versão atual" : "Versão anterior";
}
```

## Typography

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`/`105-UI-SPEC.md`/`106-UI-SPEC.md`/`107-UI-SPEC.md`, unchanged base scale. No new type role introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`) | 600 semibold | 1.4 |
| Heading | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display | 30px (`text-3xl`) | 600 semibold | 1.2 |

Component-specific notes:

- `SelectTrigger`/`SelectItem`/`NativeSelect` all render at `text-sm` (14px), unweighted (inherits 400) — a like-for-like match with the legacy raw `<select>` styling they replace (all 6 filter selects and all 5 form selects already had `text-sm` with no weight override), zero visible type-scale change. Unlike Agenda's `font-bold` (700) filter selects, this migration corrects nothing typography-wise — it is purely a component-identity swap plus the height correction noted above.
- `AccordionTrigger`'s children (`Versão N` / timestamp) keep their existing `text-sm font-medium` / `text-xs text-slate-500` styling verbatim — the primitive's own trigger wrapper is `text-sm font-medium` by default, which already matches "Versão N"'s existing weight; no new weight value introduced.
- `TooltipContent` renders at its own shipped `text-xs` (12px), inheriting `text-background`-on-`bg-foreground` (inverted) — identical to the existing "Ver detalhes" tooltip already live in `pareceres/columns.tsx`, no new type treatment.
- **Pre-existing, out-of-scope note (same class of issue every prior module UI-SPEC flagged):** the h1 headings in `pareceres/page.tsx` ("Pareceres Jurídicos") and `pareceres/[id]/page.tsx` ("Parecer Jurídico") use `text-3xl font-bold` (700), and `nova/page.tsx`'s h1 uses `text-2xl font-bold` (700) — a 3rd weight value outside this project's declared 400/600 pair, the same violation Phase 105 fixed for Clientes/Processos' h1s but which was never extended to Pareceres. Several CTA `Button`s in these same files (`"Nova Solicitação"`, `"Aplicar"`, `"Criar Solicitação"`, `"Pesquisar"`) also carry an explicit `font-bold` override. None of this is touched by PARC-18/19/20 (headings and CTAs are out of this phase's scope entirely) — flagged here purely so the checker does not misattribute these as new violations this phase introduces.

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`/`105-UI-SPEC.md`/`106-UI-SPEC.md`/`107-UI-SPEC.md`. This phase adds **zero** new accent-reservation entries — unlike Phase 107 (which added the upload `Progress` bar fill), Pareceres' new `Select`/`NativeSelect`/`Tooltip`/`Accordion` all reuse existing muted/popover/foreground-scale tokens with no new `--primary` usage.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background`/`--foreground` | Page background + default text |
| Secondary (30%) | `--card`/`--popover`/`--muted` (reconciled Phase 102) | `SelectContent`'s `bg-popover`; `TooltipContent`'s `bg-foreground`/`text-background` (inverted, primitive default); `AccordionTrigger`'s hover/focus uses `border-ring`/`ring-ring/50`, not a surface color |
| Accent (10%) | `--primary` | Reserved for the closed list already established (sidebar active-nav-item indicator/icon/label tint, user-avatar gradient badge, global search input focus ring, Dashboard KPI positive/urgent number highlight, `Calendar`'s selected-day fill since Phase 106, the upload `Progress` bar fill since Phase 107). **Neither `Select`, `NativeSelect`, `Tooltip`, nor `Accordion` join this list this phase** — the timeline's current/delivered marker deliberately stays `bg-slate-400 dark:bg-slate-500` (unchanged), not `bg-primary`; see Component Inventory for the rationale (the Accordion's default-open state is already the primary visual signal, a marker color would be redundant new scope) |
| Destructive | `--destructive` | Destructive actions only — this phase introduces no new destructive action. `EntregarParecerDialog`'s existing `bg-destructive`-styled "Entregar Parecer"/"Confirmar Entrega" buttons are unchanged; only that dialog's internal `<select>` migrates |
| `--radius` | `0rem` (confirmed at `globals.css:75`, project-wide, unchanged since Phase 107) | `SelectTrigger`/`SelectContent`, `NativeSelect`, `AccordionTrigger`, `TooltipContent` all resolve `rounded-md`/`rounded-sm` classes to a visual `0` already; the explicit `rounded-none` addendum on the 6 `Select`s and 4 `nova/page.tsx` `NativeSelect`s (see Component Inventory) is for literal-class source-consistency only, zero visual difference |

**Explicit rule for this phase:** the filter `Card`'s own container styling (`border-slate-200 dark:border-slate-800 bg-slate-50/50 dark:bg-slate-900/20`) and the "Histórico de Versões" `Card`'s own chrome are not retokenized — they continue to sit, unchanged, around the newly-migrated controls, same acceptable mid-milestone pattern every prior module phase established.
