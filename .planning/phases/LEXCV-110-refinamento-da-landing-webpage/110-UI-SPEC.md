## Divergence Notes — `webpage/` vs `web/` design tokens

Direct comparison of `webpage/src/app/globals.css` against `web/src/app/globals.css` and the 2 existing shared primitives:

1. **Token values (`:root`/`.dark` blocks): IDENTICAL.** All semantic tokens (`--background`, `--foreground`, `--primary`, `--card`, `--popover`, `--muted`, `--accent`, `--destructive`, `--border`, `--input`, `--ring`, `--radius`, sidebar/chart tokens) have byte-identical values in both apps. `--primary` resolves to `#2563eb` light / `#3b82f6` dark in both — this is the actual accent blue used app-wide.
2. **One real omission:** `web/globals.css` has an extra `@import "shadcn/tailwind.css";` (line 3) that `webpage/globals.css` lacks. Verified harmless for this phase — that file only defines `accordion-*` keyframes and `data-open`/`data-closed`/`scroll-fade`/`shimmer` utilities, none of which `Sheet` or `Badge` depend on (`Sheet`'s open/close animation uses Tailwind's native `data-[state=open]:animate-in` syntax + `tw-animate-css`, already imported in both apps). **No action needed** — do not add this import as part of Phase 110.
3. **`card.tsx` has diverged and this is intentional, not a bug:** `web/`'s reconciled Card (Phase 102-02) uses `rounded-lg` + token-based `bg-card`/`dark:bg-card`. `webpage/`'s Card is still the pre-reconciliation hand-rolled version: `rounded-none border ... bg-white ... dark:bg-[#020617]` (hardcoded hex, flat corners). **Do not reconcile `webpage/card.tsx` against `web/`'s version in this phase** — 110-CONTEXT.md explicitly locks in replicating "o padrão já idiomático do `TrustSection`" (which already uses this exact flat/hardcoded Card). The new Hero/Contacto `Card`s must look identical to `TrustSection`'s and `FeaturesSection`'s existing cards, not to `web/`'s newer rounded/tokenized look.
   - Side-effect worth knowing (not a defect to fix): in dark mode, `webpage/`'s Card background hex (`#020617`) is literally identical to `--background`'s dark value (`#020617`) — elevation comes entirely from the `border-slate-800` ring + `shadow-sm`, not from a background-fill contrast. This is the existing, already-shipped `TrustSection`/`FeaturesSection` look; Phase 110 inherits it unchanged.
4. **`button.tsx` has a trivial divergence, irrelevant to this phase:** `web/`'s reconciled Button additionally exports `buttonVariants` standalone (Phase 102-01 fix for IN-05); `webpage/`'s does not. Colors/variants/sizes are otherwise identical. Phase 110 does not need `buttonVariants` composition — no action needed.
5. **`Badge` is being introduced to `webpage/` for the first time this phase**, copied verbatim from `web/`'s current `badge.tsx`. `web/`'s Badge was a "Rule-C identity" component in Phase 102 — reconciled but deliberately kept on hardcoded `neutral-*`/`blue-*`/`emerald-*` etc. Tailwind literals (not tokens), so it carries zero risk of token mismatch when copied into `webpage/`.
6. **Net effect:** `Sheet` (token-based: `bg-popover`, `text-popover-foreground`) will render with correct light/dark colors in `webpage/` because the underlying `--popover`/`--popover-foreground` values are present and identical — confirmed in step 1. `Badge` (hardcoded-color based) will also render identically to `web/`'s. **Both primitives can be copied with zero visual adjustment.** Only `Card`'s pre-existing divergence is relevant, and it is explicitly the desired look for this phase (do not touch `card.tsx`).

## Spacing Scale

Declared values (must be multiples of 4) — confirmed against existing `webpage/` section conventions, no new scale introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps inside Button (`gap-2` uses 8px actually; 4px reserved for tightest icon padding) |
| sm | 8px | `px-3 py-1` Badge/eyebrow padding, tight inline spacing |
| md | 16px | `gap-4`, `mt-4` — default element spacing (Hero CTAs row, Trust/Features eyebrow-to-heading gap) |
| lg | 24px | `px-6` container padding, `gap-6`, `mt-6` — section content spacing |
| xl | 32px | `mt-8` — heading-to-grid/CTA-block spacing |
| 2xl | 48px | `py-12` — section vertical padding (mobile) |
| 3xl | 64px | `py-16` (`md:`/`lg:`), header `h-16` — section vertical padding (desktop), header height |

**Exceptions:**
- Icon-only hamburger trigger: **36px (`h-9 w-9`)**, not the 44px touch-target default — this matches the *existing* app-wide convention already used by `ThemeToggle` (`h-9 w-9`) in this same header, and by `web/`'s own mobile-drawer trigger in `dashboard-shell.tsx`. Introducing 44px here would look visually inconsistent sitting directly next to the 36px `ThemeToggle` button in the same header row. Keep 36px.
- Sheet drawer width: **`w-72`** (288px = 72 × 4, a valid multiple of 4 even though not one of the named scale tokens) — a fixed component dimension, not a spacing token. `web/`'s analogous app-shell drawer uses `w-[270px]` for its full sidebar replica; this phase's drawer is a much shorter 4-item nav list, so `w-72 sm:max-w-sm` is the prescribed size (does not need to match `web/`'s sidebar width, different composition).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Eyebrow / Badge label | 14px (`text-sm`) | 600 (semibold) | 1.2 (uppercase, `tracking-[0.2em]`) |
| Body | 16px (`text-base`) | 400 (regular) | 1.5 |
| Heading (H2) | 24px (`text-2xl`) | 600 (semibold) | 1.2 |
| Display (H1) | 48px (`text-5xl`) | 600 (semibold) | 1.2 |

**Exactly 4 sizes, exactly 2 weights** — matches the pre-existing typographic scale already used across `Hero`/`Trust`/`Features`/`Contact` sections; Phase 110 introduces zero new sizes/weights.

- **Eyebrow migration to `Badge` — explicit prescription (not left to discretion):** the current manual eyebrow span (`text-sm font-semibold uppercase tracking-[0.2em] text-slate-500`) must be preserved at **the same 14px/600/uppercase/tracking-wide visual size** when migrated to `Badge`. `Badge`'s own base classes default to `text-xs font-medium` (12px/500) — override both via `className` on the two `Badge` instances (Hero + Contacto) so only the shape/color changes (manual bordered span → `Badge variant="secondary"` pill), not the type scale. Do **not** silently accept Badge's smaller default size.
- **Pre-existing primitive weights not part of this phase's budget:** `Button`'s baked-in `font-medium` (500) and `Badge`'s own un-overridden base `font-medium` (500, overridden per above) are inherited component internals, not phase-introduced typography — they do not count against the "exactly 2 weights" rule for this phase's content decisions.
- **Heading semantics — critical correctness note for the executor:** `TrustSection`/`FeaturesSection`'s `Card` composition uses the `CardTitle` sub-component, which renders an `<h3>`. The Hero's `<h1>` and Contacto's `<h2>` are page-level headings, not repeated card-grid item titles — **do not swap them for `CardTitle`** (that would silently demote the page's H1 to an H3, a real accessibility/SEO regression, and would also inherit `CardTitle`'s baked-in `leading-none` which conflicts with the 1.2 heading line-height target above). Use `Card`/`CardHeader`/`CardContent` purely for layout/spacing; keep the raw `<h1>`/`<h2>` tags with their existing classes untouched inside them.
- **Scoped inconsistency, accepted by design:** `FeaturesSection`'s "MÓDULOS" eyebrow and `TrustSection`'s "CONFIANÇA INSTITUCIONAL" eyebrow are **not** migrated to `Badge` in this phase (LDG-18 only names Hero + Contacto). This leaves 2 of 4 landing sections still on the manual span pattern — a deliberate, phase-scoped boundary per 110-CONTEXT.md, not a missed inconsistency for the ui-checker to flag.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f8fafc` light / `#020617` dark (`--background`) | Page background, all section backgrounds |
| Secondary (30%) | `#ffffff` light / `#020617` dark (Card's hardcoded bg, see Divergence Notes §3) | Card surfaces (Hero, Contacto, Trust, Features) |
| Accent (10%) | `#2563eb` light / `#3b82f6` dark (`--primary` token, applied via direct `blue-600`/`blue-400` utility classes) | Reserved for: (1) the small horizontal accent rule under `BrandMark` in Hero, (2) nav link hover states (`hover:text-blue-600`), (3) feature icon color in `FeaturesSection` (`text-blue-600 dark:text-blue-400`) — **not** used as any Button's fill (Buttons use `neutral-900`/`neutral-100`, not `--primary`, per Phase 102's decision not to wire Button's default variant to the primary token) |
| Destructive | n/a | Not applicable — Phase 110 introduces no destructive actions (110-CONTEXT.md confirms none; nav links and CTAs are all non-destructive navigation/contact actions) |

**Accent reserved for:** the Hero's blue accent underline rule, hover states on the 3 desktop nav links (unchanged), and the module icons in `FeaturesSection` (unchanged, out of this phase's scope). Do not introduce new blue-accented elements (e.g., do not make the Sheet trigger icon blue, do not make Badge blue-tinted) — `Badge` stays on `secondary` variant (neutral gray tones) per 110-CONTEXT.md's explicit lock.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (Contacto) | "Pedir Demonstração" — pre-existing, unchanged by this phase |
| Hero CTAs | "Entrar" (secondary) / "Ver Funcionalidades" (ghost) — pre-existing, unchanged |
| Mobile nav trigger `aria-label` | `"Abrir menu"` — mirrors the exact string already used in `web/src/components/shared/dashboard-shell.tsx`'s hamburger button, per 110-CONTEXT.md's explicit instruction to match that convention |
| Sheet accessibility title (new requirement) | Radix `Dialog` (which `Sheet` wraps) requires a `Title` element for `aria-labelledby`, or React throws a console a11y warning. Add a visually-hidden `<SheetTitle className="sr-only">Menu</SheetTitle>` (or `"Navegação"`) as the first child of `SheetContent` — not visible, but required for correctness. No existing precedent in `webpage/` for this since it has no Sheet yet; `web/`'s own sidebar-replica Sheet uses a visible header block instead, which doesn't apply here (this drawer has no visible heading by design) |
| NAV_LINKS labels (reused, not new) | "Funcionalidades" (`#funcionalidades`), "Confiança" (`#confianca`), "Contacto" (`#contacto`), "Entrar" (`/login`) — identical strings already in `site-header.tsx`, only extracted into a shared array per 110-CONTEXT.md |
| Empty state | n/a — static marketing content, no data-fetch empty states in scope |
| Error state | n/a — no new error-prone interaction introduced (anchor-link navigation and a `mailto:` link cannot fail client-side) |
| Destructive confirmation | n/a — no destructive actions in this phase |

**Header layout resolution (explicit prescription, not left ambiguous):** 110-CONTEXT.md lists "Entrar" as one of the Sheet's contents but does not resolve whether the header's existing always-visible "Entrar" button also stays visible on mobile (today it is not gated behind `md:`, unlike the 3 anchor links). To avoid a duplicate "Entrar" appearing twice on small screens once it's also inside the Sheet:
- Header-level "Entrar" `Button` → add `hidden md:inline-flex` (desktop-only from now on).
- `ThemeToggle` → stays visible at all breakpoints, both inside and outside the Sheet trigger group (it is not part of `NAV_LINKS`, 110-CONTEXT.md never lists it as a Sheet item).
- Mobile header right-side group becomes: `ThemeToggle` + hamburger trigger. Desktop header right-side group is unchanged: nav links + `ThemeToggle` + "Entrar".
- Sheet `side="right"` (slides from the same side as its trigger), width `w-72 sm:max-w-sm` (see Spacing Scale exceptions).

**Hero/Contacto Card composition boundary (explicit prescription):** 110-CONTEXT.md names only "Badge+H1+parágrafo+2 botões CTA" (Hero) / "Badge+H1+parágrafo+CTA" (Contacto, note: H2 not H1 for Contacto) as moving inside the `Card`. `BrandMark` and the standalone blue accent `hr` (`h-px w-12 bg-blue-600`) currently preceding the Hero's eyebrow are **not** named — keep them outside/above the `Card`, unchanged, exactly as they render today. Only the 4 (Hero) / 4 (Contacto) explicitly-named elements move into `Card`/`CardHeader`/`CardContent`.
