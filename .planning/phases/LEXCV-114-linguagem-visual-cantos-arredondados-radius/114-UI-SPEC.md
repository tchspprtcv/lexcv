# Phase 114 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this phase (locked by `114-CONTEXT.md`):** flip one CSS custom property, `--radius`, from `0rem` to `0.5rem`, identically in `web/src/app/globals.css` and `webpage/src/app/globals.css`. No new component, no new copy, no new color, no new spacing value. The only genuinely open design question this phase raises is **what "done" looks like** — which is why this contract's weight sits almost entirely in the Radius Token Contract and the Verification/QA Plan below, not in re-litigating tokens that already exist and aren't changing.

**Read this first:** codebase research (Step 2 below) found that the token flip alone will **not** visually reach most of the app. See "Critical Scope Finding" — it is evidence, not a proposal to redesign anything, and it directly determines whether this phase's own Success Criteria 2 and 3 can be true.

## Radius Token Contract

### The change

| File | Line | Before | After |
|------|------|--------|-------|
| `web/src/app/globals.css` | 75 (`:root`) | `--radius: 0rem;` | `--radius: 0.5rem;` |
| `webpage/src/app/globals.css` | 74 (`:root`) | `--radius: 0rem;` | `--radius: 0.5rem;` |

Both files define `--radius` **only** inside `:root` — the `.dark` block never redefines it. This means dark mode already inherits whatever `:root` declares, with zero extra edits required for theme parity: light and dark get **exactly the same corner geometry**, the only thing that differs between themes is color. Verification does not need to hunt for a second `--radius` declaration in `.dark` — there isn't one, by design, in both files.

Both files also declare identical derived tokens in `@theme inline` (lines 42-48 in `web/`, 41-47 in `webpage/`), one single calc-chain off the base variable — no per-derived-token edits needed, they all cascade automatically:

| Token | Formula | Old (`--radius: 0rem`) | New (`--radius: 0.5rem`) |
|-------|---------|------------------------|--------------------------|
| `--radius-sm` | `calc(var(--radius) * 0.6)` | 0px | 0.3rem (4.8px) |
| `--radius-md` | `calc(var(--radius) * 0.8)` | 0px | 0.4rem (6.4px) |
| `--radius-lg` | `var(--radius)` | 0px | 0.5rem (8px) |
| `--radius-xl` | `calc(var(--radius) * 1.4)` | 0px | 0.7rem (11.2px) |
| `--radius-2xl` | `calc(var(--radius) * 1.8)` | 0px | 0.9rem (14.4px) |
| `--radius-3xl` | `calc(var(--radius) * 2.2)` | 0px | 1.1rem (17.6px) |
| `--radius-4xl` | `calc(var(--radius) * 2.6)` | 0px | 1.3rem (20.8px) |

`0.5rem` is shadcn's own "Default" preset radius — this is not an arbitrary number, it matches upstream convention (per `114-CONTEXT.md`, "o meio-termo mais comum em shadcn/ui").

No adjustment needed; the shell will pick up the new radius automatically. This item is closed, not just deferred.

## Critical Scope Finding — Hardcoded `rounded-none` Overrides Outside the Token

**This is the substantive content of this contract.** Read it before planning tasks for this phase.

### What was found

`web/src/lib/utils.ts`'s `cn()` helper uses `tailwind-merge` (`twMerge(clsx(inputs))`), confirmed by direct read. This means: whenever a page passes a `className` prop containing `rounded-none` into a shadcn primitive, that literal utility **wins** over the primitive's own token-derived default for the same class group — deterministically, not a maybe. A codebase-wide scan for the literal string `rounded-none` found:

| App | Occurrences | Files |
|-----|-------------|-------|
| `web/src` | 271 | 28 |
| `webpage/src` | 7 | 5 |

**Consequence:** editing only the two `globals.css` files will make the token itself correct, but it will be **visually invisible** on every element that carries its own `rounded-none` override — which, per the counts above, is most of the interactive surface of `web/`, including 3 of the 5 representative screens `114-CONTEXT.md` itself names for verification (Dashboard, Clientes, Processos). If Phase 114 ships as literally "edit two files," Success Criteria 2 ("Cartões, botões, inputs, badges, diálogos... mostram cantos arredondados... de forma visualmente consistente") and 3 ("sem exceções visuais nem cantos retos remanescentes") will not be true, and this will surface at verification/audit time instead of now.

This is not new design invention — the fix is mechanical: remove the literal `rounded-none` override so the element falls back to the primitive's own already-correct, already-token-derived default (documented in the tier table above). No new radius value, no new component, no new decision beyond "let the existing default show through." Recommend folding this remediation into Phase 114's plan rather than treating the phase as closed after the two-file edit; that scope call belongs to the planner/user, not to this contract, but the contract cannot responsibly omit the evidence.

### Legitimate exceptions — do NOT touch these

A minority of `rounded-none` occurrences are intentional and unrelated to the "reto" institutional look. Removing them would be a regression, not a fix:

| File : line | Why it's legitimate |
|---|---|
| `web/src/components/ui/calendar.tsx:124` (`range_middle`) | Date-range middle cells stay flat so a multi-day selection reads as one continuous shape; only `range_start`/`range_end` round |
| `web/src/components/ui/calendar.tsx:130` (`today`, `data-[selected=true]:rounded-none`) | Same range-continuity logic |
| `web/src/components/ui/calendar.tsx:238` (`data-[range-middle=true]:rounded-none`) | Same range-continuity logic, `CalendarDayButton` |
| `web/src/components/ui/input-group.tsx:125, 141` | Inner `Input`/`Textarea` is deliberately flush/borderless — the parent `InputGroup` wrapper carries the visible border+radius |
| `web/src/components/ui/tabs.tsx:28` (`data-[variant=line]:rounded-none`) | The "line" Tabs variant is an underline style with a transparent background by design (vanilla shadcn behavior); the `default` variant already correctly uses `rounded-lg` |
| `web/src/app/(dashboard)/processos/[id]/page.tsx:1030, 1177` — **only** the `max-sm:rounded-b-none` part | Mobile bottom-sheet pattern: flat only on the edge flush with the viewport bottom, paired with `max-sm:rounded-t-xl`. The **base** (non-prefixed) `rounded-none` earlier in the same className on both lines is **not** legitimate — it flattens the whole dialog at desktop/tablet widths and must be removed |
| `web/src/components/ui/checkbox.tsx:17` | Not actually `rounded-none` — uses a fixed `rounded-[4px]`, unrelated to this scan, unrelated to `--radius`. Listed here only so it isn't mistaken for a gap during QA |

### Inert (harmless) occurrences — no visual effect, fix optional/cosmetic only

`NativeSelect`'s `className` prop (see `native-select.tsx:16-20`) is applied only to the outer wrapper `<div>`, which has no visible border or background of its own — the actual bordered/rounded `<select>` element (line 27) uses a literal, non-parameterized `rounded-md` that no consumer `className` can reach. Every `<NativeSelect className="...rounded-none...">` call site (e.g. `pareceres/nova/page.tsx` ×4) is therefore a no-op today and will **not** block Success Criterion 2/3 — the visible control already renders `rounded-md` regardless. Removing these is cosmetic cleanup, not a visual fix; do not spend verification effort here.
