## Placement Clarification (read before implementing)

CONTEXT.md states the "Reatribuir" button belongs "junto ao campo Responsável no card **Dados**." Codebase inspection found this is not quite accurate as written:

- The **"Dados" card** (`processos/[id]/page.tsx` ~line 704–779) does **not** currently render a Responsável field at all.
- The **"Workflow" card** (~line 864–910) is where Responsável actually renders today, sourced from a *different* query (`useWorkflow(processoId)` → `workflow.data.responsavelNome`, not `processo.data.responsavel_nome` directly), styled as:
  ```
  <dt>Responsável</dt>
  <dd className="col-span-2 font-medium flex items-center gap-1">
    <User className="h-[14px] w-[14px] text-slate-400" />
    {workflow.data.responsavelNome ?? <span className="text-slate-400 dark:text-slate-500 italic">Não atribuído</span>}
  </dd>
  ```

**Resolution:** place the "Reatribuir" trigger inside this existing `dd` cell in the **Workflow card**, immediately after the name/"Não atribuído" text — this is the literal, only place the field renders today, satisfying "junto ao campo Responsável" exactly. Do not duplicate a second Responsável row inside the Dados card.

The button is visible **regardless of whether a responsável is currently assigned** — it doubles as the first-ever assignment path (today only `createProcesso` can set `responsavelId`, and the intake/edit forms do not expose it) and as the reassignment path. The label stays "**Reatribuir**" in both cases (no conditional "Atribuir" vs "Reatribuir" label — keeps logic simple, matches CONTEXT.md's literal locked wording).

**New hook recommendation (naming only — implementation is planner/executor's call):** `useReatribuirResponsavel(processoId)`, matching the existing verb-based mutation-hook convention (`useFormalizarProcesso`, `useExecutarTransicao`) in `web/src/hooks/use-processos.ts`.

**Cache invalidation (critical, easy to under-scope):** on success, invalidate/update at minimum:
- `["processos", "workflow", id]` — TanStack Query key for `useWorkflow`, the actual source of the rendered Responsável name
- `["processos", "detail", id]` — the main processo record also carries `responsavel_id`/`responsavel_nome`
- `["processos", "list"]` — list/dashboard views group backlog by `responsavel_id` (see `ResourceController` dashboard backlog logic); stale data here would misreport ownership until next refetch

Missing the `workflow` key specifically would make the UI appear to silently fail (success toast fires, but the displayed name doesn't change until an unrelated refetch) — this is the single most likely integration bug for this control.

## Interaction Flow (supplementary)

1. **Trigger:** "Reatribuir" button renders inside the existing Responsável `dd`, visible only when `canManageProcessos` is true.
2. **Step 1 — Dialog (selection):** Opens with the helper line showing the current responsável, a "Novo Responsável" `<select>` pre-populated from `useAdminUsers()`, defaulting to the **current** `responsavelId` if one exists (else the disabled placeholder). Footer: "Cancelar" / "Reatribuir" (submit disabled per the no-op/loading guards above).
3. Clicking "Reatribuir" in step 1 **does not call the API**. It closes the Dialog and opens the Step 2 AlertDialog, carrying the selected user id in local state (mirrors `EntregarParecerDialog`'s `selectedVersaoIdState` pattern — only one modal visible at a time).
4. **Step 2 — AlertDialog (confirmation):** Shows the consequence sentence naming the new responsável and processo número. Footer: "Cancelar" (discards the pending change; user must reopen step 1 to retry) / "Confirmar Reatribuição" (calls the mutation).
5. **On success:** close AlertDialog, run the cache invalidation above, `toast.success(...)`.
6. **On error:** keep the AlertDialog open, show the inline error line, also fire `toast.error(...)`, re-enable the confirm button (mirrors `EntregarParecerDialog`'s `entregaError` handling exactly).

## Known Gaps & Discretion Resolutions (supplementary)

- **Mobile dialog treatment:** the "Novo Prazo" dialog on this same page uses `max-sm:` bottom-sheet overrides (full-width, slides from bottom on small screens), but the dialogs CONTEXT.md explicitly names as the mirror target (Adicionar Parte/Fase/Decisão/Facto/Testemunha) use a **plain, centered `DialogContent`** with no such overrides. Resolution: follow the plain centered pattern (matches the named precedent literally); the bottom-sheet variant is a different, not-referenced precedent on the same page.
- **Tab deep-linking (relevant to NOTF-15's "link direto para a aba Fases," not to this phase's own UI):** codebase inspection found the ficha do processo's tab state (`const [tab, setTab] = React.useState<TabKey>("timeline")`, `processos/[id]/page.tsx:205`) is **plain local React state**, not synced to the URL (no query param, no hash). CONTEXT.md's assumption that "a UI da ficha já suporta" a deep-link-by-tab pattern does **not** hold today. This does not block Phase 87 (no visual component needed here — the notification's `link` field is backend copy), but the planner should be aware that constructing a working `?tab=fases`-style link requires **adding** query-param-driven tab state to this page (e.g., initialize `tab` from `useSearchParams()` on mount), which is a small but real code change, not a reuse of existing support.
- **"Dados" vs "Workflow" card naming:** see Placement Clarification above — resolved by anchoring to where the field concretely renders today.
