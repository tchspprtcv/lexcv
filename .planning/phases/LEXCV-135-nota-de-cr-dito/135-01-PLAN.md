<objective>
Lay the persistence foundation of the Nota de Crédito: the `MotivoNotaCredito` enum, three new immutable columns on `DocumentoFiscal`, and the narrow tenant-scoped finders the NC service and the read side need.

Purpose: every later plan (composition, service, read side, migration) builds on these exact names.
Output: enum + converter + test, entity columns, repository finders, updated pinned-structure tests and repository IT cases.

**Design resolution recorded here (orchestrator finding 1, applies to the whole phase):** `t_documento_fiscal.pagamento_id` stays `NOT NULL` + `UNIQUE`. For an NC, `pagamento_id` = the id of the NC's OWN negative estorno `Pagamento`; `documento_origem_id` → the FR; `tipo = NC` distinguishes it. There is NO `pagamento_estorno_id` column. Consequences (CONTEXT intent preserved): the estorno is identifiable (document with `tipo = NC` and `pagamento_id = estorno.id`), it can never be re-invoiced (`uk_documento_fiscal_pagamento` already forbids a second document for that payment), and it is "faturado", so the existing `existeParaPagamento` delete guard already blocks deleting it. No column relaxation is needed, which matters because `ddl-auto=update` never relaxes NOT NULL on existing installs.
</objective>
