# Phase 79 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

This phase replaces the placeholder tab (`tab === "documentosEntregues"`, currently `<PlaceholderEmBreve />`, `web/src/app/(dashboard)/clientes/[id]/page.tsx` line 957–958) with a real upload+listing flow, and **deletes** the old text-based "Documentos Entregues" section that still lives inside the `tab === "dados"` branch (lines ~826–896: the `Dialog`+`ul` block keyed on local state `documentosEntregues`/`newDocEntre`/`addDocEntreModal`).

Per 79-CONTEXT.md, this phase reuses **three already-built visual patterns verbatim**, combined into one tab:

1. **The Dialog "Adicionar" shape** already established for Documentos a Tratar / Deslocações (Phase 78) — `Dialog`/`DialogTrigger`/`DialogContent`/`DialogHeader`/`DialogTitle`/`DialogFooter`, `Button variant="outline" size="sm"` trigger, `Cancelar`/`Confirmar` footer actions.
2. **The upload mechanics** from `web/src/app/(dashboard)/documentos/novo/page.tsx` — `FileDropZone` (`web/src/components/shared/file-drop-zone.tsx`, unmodified), `useUploadDocumentoComProgresso` progress bar (`bg-blue-600` fill on `bg-neutral-200`/`dark:bg-neutral-700` track), inline `text-red-600` error line.
3. **The listing/download/delete mechanics** from `web/src/app/(dashboard)/documentos/page.tsx` — direct `<a href="/api/v1/documentos/{id}/download">` link, `window.confirm("Apagar este documento?")` + `useDeleteDocumento`, `toast.success`/`toast.error` on delete.

**Net-new visual decision in this phase:** the "tipo" field changes from a free-text `Input` (as in `/documentos/novo`) to a native `<input list="..."> + <datalist>` combobox, sourced client-side from the distinct `tipo` values already present in this client's own document list (no new endpoint for "tipos", per CONTEXT.md).

**Design System detected:** No `components.json` in `web/` (unchanged since Phase 74). Hand-rolled Radix-based primitives under `web/src/components/ui/` (`Button`, `Card`, `Dialog`, `Input`, `Label`). Shadcn initialization gate: **not applicable** — this phase adds zero new UI primitives; the native `<datalist>` is plain HTML, not a component-library addition.

## Interaction Contract (the actual new design surface)

This is the real scope of Phase 79's UI work. The checker/executor should validate against this section more than the boilerplate design-token sections above (most of which are declared-unchanged reuse).

### 1. What is deleted

- The entire old "Documentos Entregues" block currently inside `tab === "dados"` (JSX ~lines 826–896: the `h4`/`Dialog`/`ul` for `documentosEntregues`), including:
  - Local state: `documentosEntregues`, `addDocEntreModal`, `newDocEntre`.
  - Handler: `confirmAddDocEntre()`.
  - The dialog-reset `useEffect` branch for `addDocEntreModal`/`newDocEntre` (currently keyed on `tab !== "dados"`).
  - The `documentosEntregues: documentosEntregues` line from the `onSubmit` payload (`ClienteUpdateRequest`), and the corresponding `setDocumentosEntregues(cliente.data.documentos_entregues ?? [])` calls in the load-effect, `onCancel`, and post-submit reset.
- Per CLI-29/CONTEXT.md: this field is no longer sent to the backend at all from this UI. The old `documentos_entregues` column/field on `Cliente` becomes orphaned data (same clean-cut pattern as `dados_tipo` in v2.7) — no migration, no read-only display of old records anywhere in the new UI.

### 2. What is added — new tab content for `tab === "documentosEntregues"`

Replaces `tab === "documentosEntregues" ? <PlaceholderEmBreve /> : ...` with a new sub-component (naming is executor's discretion, e.g. `ClienteDocumentosEntreguesTab`), structured as:

- **Data source:** `useDocumentos({ cliente_id: id })` from `web/src/hooks/use-documentos.ts` — reused as-is (hook signature unchanged). The **queryFn inside the hook** must be repointed to call `GET /clientes/{id}/documentos` (new backend endpoint, per CONTEXT.md) instead of the generic `GET /documentos` (which ignores `cliente_id`/`processo_id` query params server-side, confirmed by CONTEXT.md's direct reading of `ResourceController.listDocumentos()`). This is a data-layer change, not a visual one, but it directly determines what this tab is capable of rendering — the UI contract assumes the hook, once fixed, returns exactly this client's documents.
- **Lazy fetch:** consistent with the Phase 77 precedent for Processos/Pareceres tabs, this tab's data fetch should only be "live" while the tab is active. Given `useDocumentos` has the same internal-only `enabled` computation gap flagged in 77-UI-SPEC.md (no external `enabled` override param), the executor should apply the same resolution options documented there (extend the hook to accept an external `enabled` flag, or scope the hook call to a sub-component that only renders/mounts while `tab === "documentosEntregues"`).
- **Card wrapper:** a single `Card`/`CardContent`, matching the `ClienteProcessosTab`/`ClienteParecerTab` precedent (`<CardContent className="p-0 bg-white dark:bg-[#020617]">` for the list portion) OR the simpler `Card`/`CardContent className="space-y-2 pt-6"` idiom used by Documentos a Tratar/Deslocações (Phase 78) — since this tab combines an "Adicionar" trigger row + a compact list (not a full `Table`), the Phase 78 `Card`/`CardContent` wrapper is the closer visual match and is the prescribed choice: a single `Card` containing (1) a header row with tab title implicit (no `h4` needed since the tab button itself already labels it — optional `h4` "Documentos Entregues" only if the executor judges it improves scan-ability, consistent with Documentos a Tratar's own internal `h4`) and an `Adicionar` trigger button, then (2) the list or empty-state below.
- **Gating:** the "Adicionar" trigger is visible/enabled only when `editable && permissions.can.edit("documentos")` per CONTEXT.md (NOT `clientes:edit` — this is a deliberate scope difference from every other "Adicionar" button on this ficha, which gate on `canEditClientes`). The list itself (view) is gated by `permissions.can.view("documentos")` — if the user lacks `documentos:view`, render `AccessDeniedState` for this tab, matching the `canViewProcessos`/`canViewPareceres` precedent from Phase 77 (`tab === "processos" ? (canViewProcessos ? <ClienteProcessosTab .../> : <AccessDeniedState .../>) : ...`).
- **Upload Dialog:** `Dialog`/`DialogTrigger asChild` (`<Button type="button" variant="outline" size="sm">Adicionar</Button>`) / `DialogContent` containing, in order:
  1. `FileDropZone` (label `Ficheiro`, same `accept` allowlist as `documentos/novo`: `"image/*,application/pdf,application/msword,application/vnd.openxmlformats-officedocument.wordprocessingml.document,.txt"`), with the same selected-file preview idiom (`FileDropZone`'s own internal emerald "file selected" card — no separate `<img>`/`<iframe>` preview needs to be re-implemented here; the full-page `preVisualizacao` image/PDF preview from `documentos/novo` is optional/discretionary for this compact Dialog context and may be omitted to keep the Dialog small, since CONTEXT.md doesn't require it).
  2. Tipo combobox: `<input list="tipo-documento-entregue-{clienteId}" placeholder="Selecione ou escreva um tipo" />` + `<datalist id="tipo-documento-entregue-{clienteId}">` populated with `Array.from(new Set(documentos.map(d => d.tipo).filter(Boolean)))` — distinct, already-used tipo values for this client's own documents, sourced from the same `useDocumentos` list already fetched for this tab (no separate request). Empty by default; no default value pre-filled.
  3. Upload progress bar (`useUploadDocumentoComProgresso({ onProgress })`), shown only while `progresso !== null`, identical visual structure to `documentos/novo` (label row `"A enviar..." / {pct}%` + `bg-blue-600` fill on `bg-neutral-200 dark:bg-neutral-700` track).
  4. Inline error line (`text-sm text-red-600`) if the upload fails.
  5. `DialogFooter`: `Cancelar` (`variant="outline"`, closes dialog without submitting) / `Confirmar` (default variant, triggers upload) — note this differs slightly from `documentos/novo`'s standalone-page `Enviar`/`Cancelar` labels; inside a Dialog on this ficha, `Confirmar` is the established convention (matches every other "Adicionar X" Dialog in this file) and is prescribed here for consistency, even though the action is "upload" not "add to local list".
  - On successful upload: `toast.success("Documento enviado com sucesso.")`, close the Dialog, clear the file/tipo fields, and rely on `useUploadDocumentoComProgresso`'s existing `onSuccess` query invalidation (`["documentos", "list"]`) to refresh the list — no manual local-state append needed (this differs from the Documentos a Tratar/Deslocações pattern, which stages entries in local React state; here, the document is already persisted server-side by the time the dialog closes, so the list refetches from the server, it does not get appended to a local staging array).
- **Uploaded-documents list:** compact `ul`/`li`, one row per document, each showing: file name (`font-medium`), tipo (if present, else `—`), formatted size + formatted created-at date, a download link, and a delete control — mirroring the Phase 78 `<li className="flex items-center justify-between border ... px-3 py-2 text-sm">` container shape but with richer per-row content than the plain-text Documentos a Tratar/Deslocações rows (since this list now carries file metadata, not just a description string). Not the full dual desktop-table/mobile-card layout from the standalone `/documentos` page — CONTEXT.md is explicit this is a "lista compacta", not the full listing UI.
  - **Download:** `<a href={`/api/v1/documentos/${d.id}/download`} target="_blank" rel="noreferrer" className="text-blue-600 dark:text-blue-400 hover:underline text-xs font-medium">Download</a>` — exact pattern from `documentos/page.tsx`'s mobile-card download link (direct href, not the presigned-URL `useDownloadDocumento` mutation hook, per CONTEXT.md's explicit "download por link direto" decision).
  - **Delete:** icon/button + `window.confirm("Apagar este documento?")` + `useDeleteDocumento(d.id)` + `toast.success("Documento apagado com sucesso.")` on success / `toast.error(msg)` on failure, gated by `permissions.can.edit("documentos")` (not `canEditClientes`) — matches CONTEXT.md's RBAC decision. Visual treatment: either the bare "✕" icon-button idiom from Phase 78 (`text-neutral-500 hover:text-red-600`, `aria-label="Remover"`) for visual consistency with the rest of this ficha, or the labeled `text-red-600 border-red-200 ...` outline button from `documentos/page.tsx`'s mobile card — executor's discretion, but must pick ONE and apply it consistently to every row; the "✕" idiom is the closer visual match to this ficha's established convention and is the prescribed default.
- **States:**
  - Loading → `A carregar...` (`text-sm text-neutral-500 dark:text-neutral-400`, matching this ficha's own loading idiom rather than the slate-based `/processos`/`pareceres` tab idiom, since this tab lives closer in spirit to Documentos a Tratar/Deslocações than to the Table-based tabs).
  - Error → `text-sm text-red-600`, message from `list.error instanceof Error ? list.error.message : "Não foi possível carregar os documentos entregues deste cliente."`.
  - Empty → `Nenhum documento entregue registado.` (`text-sm text-neutral-500 dark:text-neutral-400`).

### 3. Read-mode behavior

Unlike Documentos a Tratar/Deslocações (which render nothing at all in read mode per the corrected 78-UI-SPEC.md), this tab's **list is informational, not an edit-only intake field** — the uploaded documents are real persisted files relevant to view regardless of `isEditing`. Per CONTEXT.md's framing ("gere ficheiros carregados de facto"), the prescribed behavior is:

- The **list** (uploaded documents + download links) is visible in BOTH read and edit mode — this is a genuine content tab, not a form-staging area like the other intake sections.
- The **"Adicionar" trigger and delete controls** are gated by `editable && permissions.can.edit("documentos")` (hidden/inactive in read mode or without the `documentos:edit` scope), consistent with CLI-13's global rule that edit affordances are inactive/hidden in read mode.
- This is a deliberate, CONTEXT.md-justified divergence from Phase 78's "whole section hidden in read mode" pattern, because this tab's data is no longer client-side staged form state (like `documentosATratar`/`deslocacoes` are) — it is server-persisted `Documento` records fetched independently of the cliente "Guardar" flow. The checker should not flag this as an inconsistency with Phase 78; it is intentional given the data-model change (staged-array-in-form-payload vs. independently-persisted-and-fetched entity).

### 4. No "Guardar" payload involvement

Uploads and deletes in this tab are immediate, independent mutations (`useUploadDocumentoComProgresso`, `useDeleteDocumento`) — they do not go through the cliente-level `onSubmit`/"Guardar" flow at all, unlike every other intake section on this ficha. This tab has zero interaction with `ClienteUpdateRequest`.

### 5. Visual regression / consistency check (what "done" looks like)

- Dialog visually matches the Phase 78 Dialog shape (title, `Cancelar`/`Confirmar` footer, `space-y-4` field stack) with the two upload-specific additions (`FileDropZone`, progress bar) inserted in place of the plain `Input` fields Phase 78 uses.
- List rows visually match the Phase 78 `li` container idiom (border, `px-3 py-2`, flex justify-between) extended with 2 extra pieces of metadata (tipo, size/date) and 2 action affordances (download, delete) instead of Phase 78's single "✕" remove-only affordance.
- No accent-colored (`bg-blue-600`) element appears anywhere except the upload progress bar fill — the "Adicionar" trigger stays `outline`, matching every sibling "Adicionar" button on this ficha.
