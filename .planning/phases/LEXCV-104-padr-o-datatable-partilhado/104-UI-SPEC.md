# Phase 104 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 104 builds one shared DataTable pattern (`web/src/components/shared/data-table/`) on top of the already-reconciled `Table` primitive (Phase 102) and adopts it on the desktop (`hidden md:block`) branch of 5 list screens — Clientes, Processos, Pareceres, Financeiro, Documentos — plus swaps `/notificacoes`'s hand-rolled pager for the official `Pagination` component. Covers DTB-01, DTB-02, DTB-03. Mobile card views are unchanged. No row-selection/bulk actions (explicit `REQUIREMENTS.md` Out of Scope).

**Verified-against-source corrections to the roadmap/context framing (load-bearing for planning):**

1. **The 5 screens are NOT equally "already on `Table`."** Clientes, Processos, and Pareceres already render via the shadcn `Table`/`TableHeader`/`TableRow`/`TableHead`/`TableCell` primitives (Phase 102-reconciled). **Financeiro and Documentos do not use `Table` at all today** — their desktop branch is a raw hand-written `<table>`/`<thead>`/`<tr>`/`<th>`/`<tbody>`/`<td>` with ad hoc classes (`py-2 pr-4 font-medium`, `border-b border-neutral-200`), bypassing the primitive entirely. For these 2 screens, Phase 104 is simultaneously their *first* adoption of `Table` semantics and their DataTable adoption — a strictly larger migration than "layer DataTable on an existing Table," not a smaller one. Plan effort accordingly.
2. **Status/type indicators are inconsistent across the 5 screens today, independent of DataTable.** Clientes/Processos/Pareceres already render status-like columns with the real `Badge` component (`variant="blue"|"green"|"amber"|"gray"|"purple"`). **Financeiro's "Estado" column uses a hand-rolled `<span className={statusBadgeClass[status]}>`, not `Badge` at all.** Documentos already imports and uses `Badge` elsewhere in the same file (mobile cards, confidencialidade) but this needs re-verification per-column when its rows are rebuilt as `columns.tsx` cell renderers. **Mandatory for this phase:** when a screen's status/type column becomes a DataTable column, its cell renderer must use the real `Badge` component with an existing variant from `badge.tsx` (`blue`/`green`/`amber`/`red`/`purple`/`gray`) — never a new hand-rolled `<span className=...>` — closing Financeiro's gap as a natural side effect of the rewrite, the same way Phase 102 normalized Card dark-mode tokens as an intended side effect of reconciliation.
3. **The existing "pagination" footer on Clientes and Processos is 100% decorative and non-functional today** — verified by reading both files: the page-number buttons (`<button>1</button>`, `<button>2</button>`, `<button>3</button>`) have no `onClick` handlers at all, and both screens' hooks (`useClientes`, confirmed in `use-clientes.ts`; `useProcessos`, same shape) fetch the **entire filtered array in one request** — there is no `page`/`size` param anywhere in either hook. Clicking "2" today does nothing. This confirms Roadmap Success Criteria 1's `DataTablePagination` is a real functional fix, not cosmetic polish, for these 2 screens — and that TanStack Table's **client-side** `getPaginationRowModel()` (paginating the already-fully-fetched, already-server-filtered array in the browser) is the correct mechanism, not a new server param.
4. **`/notificacoes` is the ONLY genuinely server-paginated list in `web/` today** — verified via a repo-wide search for `totalPages` (2 files: `types/notificacoes.ts` and `notificacoes/page.tsx`). No other screen, including Clientes/Processos/Pareceres/Financeiro/Documentos, has a real backend `page`/`size`/`totalPages` contract. **DTB-03's "e qualquer outra lista paginada no servidor" resolves to zero additional screens** — its full scope is `/notificacoes` alone. Do not go looking for a second server-paginated screen to satisfy this requirement; there isn't one.
5. **The shadcn `Pagination` primitive is NOT yet installed** (confirmed: no `web/src/components/ui/pagination.tsx`) — unlike `Skeleton`/`Empty` (added Phase 101, first consumed Phase 103), `Pagination` was never added during Foundation. This phase must run `pnpm dlx shadcn@latest add pagination --diff` (official registry, zero name collision, no new npm dependency — pure Tailwind/`cn()` composition, not Radix-based) before DTB-03 work starts.
6. **`@tanstack/react-table` is a genuinely new npm dependency** (confirmed absent from `web/package.json` — only `@tanstack/react-query` exists today). Per `104-CONTEXT.md`'s locked decision, this requires the same package-legitimacy gate established in Phase 101 (`npm view` probe + blocking human sign-off) **before** `pnpm add`. This is a different gate from the shadcn third-party-registry vetting gate below — it applies because this is a plain npm library addition, not a `shadcn add <component> --registry <url>` call.

This correction does not change `104-CONTEXT.md`'s locked architecture decisions (shared directory location, no client-side re-filtering, build+adopt in one phase, no row-selection) — it only sharpens exactly what "already exists" vs. "must be built new" per screen, so planning isn't blocked assuming false parity between the 5 screens.

## Visual Hierarchy

No new page-level focal point. On all 5 screens, the DataTable occupies the exact same visual slot the raw `Table`/`<table>` already occupies today: inside the existing `Card`/`CardContent` desktop branch (`hidden md:block`), below the existing filter Card that stays completely untouched. Reading order is unchanged: page header → KPI/stat cards (where present) → filter Card (untouched, still hand-built per screen, still driving `use-*` hooks' server-side query params) → DataTable (new: sortable headers + column-visibility toggle + client-side pagination footer, replacing the old static/decorative table+pager). The DataTable introduces exactly one new small-scale visual element per screen: a `DataTableViewOptions` trigger (column show/hide), which sits at the toolbar row's trailing edge, `variant="outline"` `size="sm"`, never accent-colored (see Color section).

## Component Inventory — `web/src/components/shared/data-table/`

Prescriptive default shape (per `104-CONTEXT.md`, exact file names are Claude's discretion at the executor level, but this is the contract the planner should assume unless it deviates for a stated reason):

| File | Responsibility |
|------|-----------------|
| `data-table.tsx` | Generic `<DataTable columns={} data={} />`. Wraps `useReactTable` with `getCoreRowModel()`, `getSortedRowModel()`, `getPaginationRowModel()` only — **never `getFilteredRowModel()`** (filtering stays server-side via each screen's existing `use-*` hook + `useState` filters, per the locked decision in `104-CONTEXT.md`). Renders the existing `Table`/`TableHeader`/`TableBody`/`TableRow`/`TableHead`/`TableCell` primitives — never raw `<table>` tags, including for Financeiro/Documentos (see Scope note #1). Includes a defensive "no rows" `<TableRow><TableCell colSpan={columns.length}>` fallback per the official recipe (see Copywriting Contract) — expected to rarely render in practice since every screen already gates the whole table block behind its own outer `data.length === 0` check. |
| `data-table-column-header.tsx` | Sortable header cell: a `Button variant="ghost" size="sm"` wrapping the column label + a trailing icon (`ChevronsUpDown` when unsorted, `ArrowUp`/`ArrowDown` when active), calling `column.toggleSorting(column.getIsSorted() === "asc")` on click — simple 3-state cycle, no dropdown menu. Non-sortable columns (see per-screen table below) render as a plain `TableHead`, no button/icon. |
| `data-table-pagination.tsx` | Client-side pagination footer: rows-per-page `Select` (options `10`/`20`/`50`, default `10`) + "Página X de Y" text + `Anterior`/`Seguinte` buttons (`Button variant="outline" size="sm"`, disabled at bounds) — replaces the decorative fake page-number buttons on Clientes/Processos and the total-absence of any pager on Pareceres/Financeiro/Documentos. No numbered page links (see Color section — avoids introducing an "active page number" element that would need an accent-vs-neutral decision). |
| `data-table-view-options.tsx` | `DropdownMenu` (already installed) triggered by an icon `Button variant="outline" size="sm"` (`SlidersHorizontal`), listing every `column.getCanHide()`-eligible column as a `DropdownMenuCheckboxItem` bound to `column.getIsVisible()`/`column.toggleVisibility()`. Actions column and any primary identity column (e.g. Clientes' "Nome") should set `enableHiding: false` so the table can never be hidden down to zero useful columns. |

Explicitly **not** part of this inventory: no row-selection column, no `Checkbox` import in any `columns.tsx` (per `REQUIREMENTS.md` Out of Scope — "Row-selection/ações em massa em qualquer DataTable"), no `getFilteredRowModel()`/toolbar search-input duplication (existing filter Cards are reused as-is, not rebuilt as a TanStack "faceted filter" toolbar).

| Surface | Component | Data source | Copy |
|---------|-----------|--------------|------|
| DataTable footer (all 5 list screens) | `DataTablePagination` (shared, client-side, part of the `data-table/` inventory above) | `table.getPageCount()` over the already-fetched, already-server-filtered full array — no new network request per page turn | Rows-per-page label: **"Linhas por página"** · page indicator: **"Página {n} de {total}"** · buttons: **"Anterior"** / **"Seguinte"** (matches `/notificacoes`'s existing Portuguese convention) |

## Typography

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`, unchanged base scale. Included here to resolve a **real, pre-existing, three-way inconsistency in column-header styling across the 5 screens** that this phase's `DataTableColumnHeader` rewrite must close, not perpetuate:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`) | 600 semibold | 1.4 |
| Heading | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display | 30px (`text-3xl`) | 600 semibold | 1.2 |

**Verified-against-source finding:** today, Clientes/Processos/Pareceres override `TableHead` with `text-[10px] font-bold uppercase tracking-wider text-slate-500` — a 10px size that is **off the declared scale** (below Label's 12px floor). Financeiro/Documentos, being raw `<table>` (see Scope note #1), use plain `<th className="py-2 pr-4 font-medium">` with no explicit size (inherits 14px from the parent `<table className="text-sm">`, but at `font-medium`/500 weight — a 3rd weight value, over this project's 2-weight cap).

**Mandatory for `data-table-column-header.tsx` (applies uniformly across all 5 screens, closing this 3-way split in one pass):**

```tsx
<span className="text-xs font-semibold uppercase tracking-wider text-muted-foreground">
  {label}
</span>
```

This resolves to 12px/600 (the Label role exactly), preserving the uppercase/tracking-wider *treatment* the majority (3 of 5) of today's screens already use, while fixing the off-scale 10px value and eliminating Financeiro/Documentos' unrelated 3rd weight. Do not ship `data-table-column-header.tsx` with the raw shipped-default `TableHead` typography, and do not preserve either off-scale value "for continuity" — this is a deliberate, one-time close of a pre-existing inconsistency, matching the precedent Phase 102 set for Card dark-mode tokens (an intended improvement flagged in the contract, not a silent scope drift).

## Color

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`, unchanged — this phase adds zero new colors and zero new accent-reserved elements.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background`/`--foreground` | Page background + default text |
| Secondary (30%) | `--card`/`--popover` (Card/Dialog/Table chrome, reconciled Phase 102) | Card chrome every DataTable instance renders inside; sidebar/topbar (unchanged, not tokenized yet, out of scope) |
| Accent (10%) | `--primary` | Reserved exclusively for the closed list already established: sidebar active-nav-item indicator/icon/label tint, user-avatar gradient badge, global search input focus ring, Dashboard KPI positive/urgent number highlight. **DataTable does not join this list.** |
| Destructive | `--destructive` | Destructive actions only — each screen's existing per-row delete button (`Trash2` icon + `window.confirm()`) is unchanged by this phase, not migrated to `AlertDialog` (that would be scope expansion beyond DTB-01/02/03) |
| `--radius` | `0rem` | Sharp corners — `DataTablePagination`'s `Select`/`Button` and the new `Pagination` component all resolve to `0` automatically via the existing `--radius` token, no override needed |

**Explicit rule for this phase:** sort-state icons (`ArrowUp`/`ArrowDown`/`ChevronsUpDown`) and any pagination "current state" indicator render in `text-foreground`/`text-muted-foreground` — **never** `--primary`/accent blue. This is a deliberate correction, not an oversight: today's decorative fake pager on Clientes/Processos colors its (non-functional) active-page button `bg-blue-600` — that specific precedent is not carried forward, both because it was never a real interactive state and because extending the accent-reserved list is out of scope for a phase whose own requirements (DTB-01–03) don't ask for it.

Existing hardcoded `slate-*`/`blue-*` utility classes surrounding each DataTable (page headers, filter Cards, stat cards) are **out of scope for retokenization this phase** — preserving the "not a redesign" boundary established since Phase 101. Only the new `data-table/` files and the specific cells identified in the Per-Screen Adoption Contract (Badge migrations) are touched.
