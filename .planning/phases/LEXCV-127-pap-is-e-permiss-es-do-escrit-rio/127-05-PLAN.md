<objective>
Close the collision 127-CONTEXT.md Decisão 6 identified between two changes nobody had connected.

`AdminController.createUser`/`updateUser` resolve role assignment by **global role name**
(`roleRepository.findByNome`), then map to the tenant's homonymous `TenantRole`. Phase 126's review
made `resolverPapeisDeEscritorio` throw on partial mapping — the right fix for the bug it closed.
Put those two together with the renaming this phase ships: an office renames "ADVOGADO" to "Advogado
Sénior", and from that moment assigning that role resolves the global name, finds no homonymous
`TenantRole`, and returns **409**. User management breaks because of a rename made on a different
screen, with an error message pointing the administrator at the platform's molde catalogue for a
problem they created themselves and can fix themselves.

Assignment moves to office role **ids**. That is the correct model now anyway: an administrator picks
from the roles of their own office, which is literally what PAPEL-01 and PAPEL-06 describe. The
global-name path stops being used for assignment.

One thing must not be lost in the move. `t_user_role` is still read by
`UserRepository.findByTenantIdAndRoleName`, `findByTenantIdAndRoleNameIn` and
`findByTenantIdAndRoleNameAndAtivoTrue`, which drive `NotificacaoService`'s ADMIN fan-out and
`AlertasDiariosJob`. Phase 126 deliberately kept that table populated for reversibility, and dropping
its column is explicitly deferred past this milestone. So assignment keeps writing a **derived**
global-role mirror, computed from the selected roles' provenance — never from a name the user typed.

Purpose: PAPEL-06 without a rename-shaped trapdoor.
Output: an id-based assignment path, the dead name-based wrapper removed, and a rewritten test that
proves a renamed role assigns cleanly.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → `POST/PUT /api/v1/admin/users` | an office administrator submits the set of roles another user will hold — the highest-leverage write in the office surface |
| office tenant A → office tenant B | assignment ids are resolved only within the caller's tenant |
| office surface → `PLATAFORMA_ADMIN` | the third door onto the reserved role, after the RBAC read and write |
