## Scope Recap (from CONTEXT.md / ROADMAP.md / REQUIREMENTS.md)

- Audience: a law-office administrator (tenant `rbac:manage`), not a platform operator. This is a **customer-facing** surface — hold it to a higher bar than `/plataforma/moldes` (Phase 125's internal analog): nobody is available to explain confusion away.

- Reuse mandate (design brief + CONTEXT.md "Reusable Assets"): the permission × role matrix shape, its accessibility corrections, its typography table, its spacing exceptions, and its unsaved-edit merge behavior all come from Phase 125's `/plataforma/moldes` (`web/src/app/(dashboard)/plataforma/moldes/page.tsx`, `merge-local-permissoes.ts`, `criar-molde-panel.tsx`, and `125-UI-SPEC.md`). ## Screen Structure

### Focal point

**The permission matrix is the primary visual anchor of this tab.** It occupies the bulk of `CardContent` and it is what an administrator came here to read and change; everything else — the note box above it, the per-column badges, the kebab menus, the save button — is supporting apparatus around it. When a layout decision forces a trade-off, the matrix stays legible and the apparatus yields.

The secondary anchor is the **state of "Guardar Alterações"**: whether there are unsaved changes is the one piece of status an administrator must never have to guess at, because this tab now lets them lose work by navigating away.

### 0. Implementation note carried over from Decision 2b (CONTEXT.md) — not a visual requirement, but constrains how the component below is assembled

All hooks this tab needs (role list query, permission-catalog data, `useMe()` if still needed, mutations for save/create/rename/delete, and local dialog state) must be called **unconditionally, before the first early return** (loading/error branches) — the same Rules-of-Hooks discipline the current `RbacTab` already follows (`settings/page.tsx:756-763`) and that the `verify:bloqueio-rbac` gate's `A02` assertion checks for. This holds regardless of whether `useMe()` itself is still needed once the `isPlatformAdmin` branch is removed (§1 below) — the ordering discipline, not the specific hook, is what must survive the rewrite.

### 1. What is removed from the current `RbacTab` — say the inversion once, in the removal, not in a banner

Per Decision 1 (CONTEXT.md), delete:
- The `isPlatformAdmin` computation and every branch keyed on it (`settings/page.tsx:763`, `:808-810`, `:863-887`, `:907-916`, `:957-977`).
- The `Badge` + `Tooltip` reading "Gerido pela Plataforma" (`:876-886`).
- The duplicated "IN-01" paragraph inside the blue note box explaining the platform-lock (`:907-916`).
- The `ADMIN`-row-is-always-checked-and-locked special case keyed on the literal string `"ADMIN"` (`:809`, `:956`, `:964`) — replaced in §3 below by a provenance-based lock that survives renaming.

**No dedicated "this used to be locked, now it's yours" banner is added.** The design brief asks whether the reversal needs to be said out loud once, or whether silence is better; the answer chosen here is neither a permanent banner nor total silence — it is stated exactly once, permanently, as plain fact in the `CardDescription` (§3) and repurposed note box (§4), phrased the same way for a first-time reader and a returning one ("this is yours, here is what protects you"), rather than as a "look what changed" callout that would read as noise to anyone who never saw the old locked state. A locked-vs-unlocked narrative ages badly; an ownership statement does not.

### 2. `UserManagementTab` — role picker becomes dynamic (PAPEL-06)

Minimum necessary change, not a redesign of that tab. Today `UserManagementTab` toggles a hardcoded 4-item union (`MockRole[]`, `settings/page.tsx:664-682`) as a `grid-cols-2 sm:grid-cols-4` button grid. Office roles are now an unbounded, tenant-owned list, so:

- Replace the button-grid toggle with a scrollable checkbox list, reusing the **exact visual pattern already shipped two sections below it in the same file** — the "Permissões Customizadas" picker (`settings/page.tsx:697-724`: `max-h-56 overflow-y-auto` bordered container, one row per item, click-to-toggle div wrapping a `pointer-events-none` checkbox). Each row shows the role's name plus its provenance `Badge` (§3) so an assigner can tell a molde-instantiated role from a custom one at assignment time too, not only on the RBAC tab.
- Section label changes from "Funções / Perfis de Acesso" to **"Papéis do Escritório"** — matches the domain language this milestone introduces everywhere else (REQUIREMENTS.md, ROADMAP.md use "papéis", not "funções" or "roles").
- Keep the existing guard verbatim: a user must always have at least one role (`settings/page.tsx:320`, `if (selectedRoles.length > 1)` before removing) — generalize from comparing `MockRole` string literals to comparing role ids, since names are no longer stable identifiers once renaming exists.
- No new color: this list reuses the existing amber-accented "Permissões Customizadas" picker's neutral hover states (`hover:bg-slate-100/50`), not the RBAC tab's blue.

### 3. Main card — the role list becomes the permission × role matrix (default state)

Same shape as `RbacTab` today, generalized from a hardcoded 4-role array to the fetched tenant role list, and restructured following `/plataforma/moldes`'s more complete matrix (`moldes/page.tsx:329-410`) since that version already solved the accessibility gaps `RbacTab` itself never had:

```
CardHeader (flex-row, justify-between)
  ├─ CardTitle "Papéis do Escritório"
  ├─ CardDescription "Crie, edite, renomeie e atribua os papéis do seu
  │   escritório. Estas definições pertencem apenas ao seu escritório —
  │   não afetam outros escritórios da plataforma."
  └─ [ Criar Papel ]  [ Guardar Alterações ]
       outline, Plus     solid blue, Save — disabled until the matrix has
                          unsaved local edits (dirty-check against
                          fetched state, same pattern as RbacTab's
                          localRolePermissions vs. fetched rolePermissions,
                          generalized to role ids)

CardContent
  ├─ Repurposed note box (§4 — was the "Nota Importante" ADMIN-lock box)
  └─ Permission × role matrix table (below)
```

**Loading / error / empty states** — identical recipe to the current `RbacTab` (`settings/page.tsx:774-803`) for loading/error; empty state added defensively (a tenant should never reach zero roles after migration, but the pattern already exists in `/plataforma/moldes`, `moldes/page.tsx:308-327`, so it is reused rather than left unhandled): `Empty`/`EmptyHeader`/`EmptyTitle`/`EmptyDescription`/`EmptyContent` with title "Nenhum papel definido", body "Crie o primeiro papel do seu escritório para poder atribuí-lo a utilizadores.", and a "Criar Papel" button inside `EmptyContent`.

**Column header** — every role gets a two-row header: name row (with a lock icon prefix only for the protected admin-provenance role, and a kebab menu trailing it), then a badge row:

```tsx
<th key={role.id} scope="col" className="p-3 font-bold text-center text-slate-700 dark:text-slate-300 text-xs tracking-wider min-w-[140px]">
  <div className="flex flex-col items-center gap-1">
    <div className="flex items-center gap-1">
      {role.protegido && (
        <Tooltip>
          <TooltipTrigger asChild>
            <Lock className="h-3 w-3 text-slate-400" aria-label="Papel protegido" />
          </TooltipTrigger>
          <TooltipContent>
            Este é o papel de administrador do escritório. Não pode ser apagado nem
            perder as permissões que o tornam administrador.
          </TooltipContent>
        </Tooltip>
      )}
      <span>{role.nome}</span>
      <RolePapelMenu role={role} /> {/* DropdownMenu, see below */}
    </div>
    <div className="flex flex-wrap items-center justify-center gap-1">
      <Badge variant={role.sistema ? "gray" : "outline"}>
        {role.sistema ? "Predefinido" : "Criado por si"}
      </Badge>
      <Badge variant="gray">
        {role.utilizadoresAtribuidos} utilizador{role.utilizadoresAtribuidos === 1 ? "" : "es"}
      </Badge>
    </div>
  </div>
</th>
```

**Why two badges, not one, and why neutral (§ Color).** The design brief asks for the sistema/custom distinction to be *visible*, not just enforced. A single badge trying to carry both "where this role came from" and "why you can/can't delete it" would conflate two independent facts: provenance (informational, does not by itself restrict anything — a molde-instantiated `ADVOGADO` role is exactly as editable/deletable as a custom one, *unless* it also happens to be the protected admin role) and assignment count (the actual, load-bearing reason a delete can be refused, for *any* role regardless of provenance). Keeping them as two separate, neutral badges lets each answer one question. The **only** role that is unconditionally protected is the one flagged `protegido` (provenance = the ADMIN molde) — that fact gets its own distinct signal (the lock icon, not a badge), because it is a stronger, different kind of rule than "0 vs N users."

**No row is a hardcoded, name-matched lock.** `RbacTab` today special-cases the literal string `"ADMIN"`. This matrix instead locks by the `role.protegido` flag (provenance, survives renaming), and only locks the *currently-assigned* permission cells for that one role — see the floor-lock rule below. Every other role's row is fully editable, sistema or not.

**Floor-lock rule for the protected role (Decision 4 / PAPEL-08).** "Não pode ser despojado das permissões que o tornam administrador" is interpreted here as: for the `protegido` role only, any permission **currently checked** is locked checked (checkbox disabled, `checked` forced true); any permission **currently unchecked** remains freely toggleable, so the office can still grant its own admin role additional permissions, just never remove the ones it already has. This keeps the rule mechanically simple (no second "which permissions are load-bearing" list from the backend) and is self-consistent: since the protected role already carries `rbac:manage` by construction (it is the office's admin role), the floor rule alone prevents ever locking the office out of this very screen.

**Matrix body** — module-grouped rows, reused **verbatim** from `RbacTab` (`settings/page.tsx:934-988`) for the row structure, upgraded with `/plataforma/moldes`'s accessibility corrections (`moldes/page.tsx:373-404`) since this is a customer-facing screen and inherits the higher bar, not `RbacTab`'s original gaps:

```tsx
<th scope="row" className="p-3 text-left">
  <div className="font-medium text-slate-900 dark:text-slate-100">{permissao.nome}</div>
  <div className="text-[11px] text-slate-500 dark:text-slate-400 mt-0.5">{permissao.descricao}</div>
</th>
{roles.map((role) => {
  const isChecked = localPermissoes[role.id]?.has(permissao.key) ?? false;
  const isLockedFloor = role.protegido && (role.permissoesOriginais?.has(permissao.key) ?? false);
  return (
    <td key={role.id} className="p-3 text-center">
      <label className="inline-flex items-center justify-center cursor-pointer p-2">
        <input
          type="checkbox"
          checked={isChecked || isLockedFloor}
          disabled={isLockedFloor}
          onChange={() => handleToggle(role.id, permissao.key)}
          aria-label={`${permissao.nome} — ${role.nome}`}
          className={`h-4 w-4 text-blue-600 focus:ring-blue-500 border-slate-300 dark:border-slate-800 rounded transition-all ${
            isLockedFloor ? "cursor-not-allowed text-blue-500/55 opacity-60" : "cursor-pointer"
          }`}
        />
      </label>
    </td>
  );
})}
```

Accessibility contract, reused verbatim from `/plataforma/moldes` (`125-UI-SPEC.md` §5, `moldes/page.tsx:334-343,378,396`): every column `<th>` has `scope="col"`; the row's leading cell is `<th scope="row">` with explicit `text-left` (a `<th>` defaults to centered text, unlike a `<td>` — omitting this would silently center the permission name/description); every checkbox carries an explicit `aria-label` combining permission and role name, since the surrounding `<label>` padding wrapper has no visible text. No custom roving-tabindex grid widget — native Tab order and native checkbox Space-toggle, exactly as `RbacTab` and `/plataforma/moldes` already behave.

### 4. Repurposed note box — was "Gerido pela Plataforma" framing, now explains the two rules that remain

```tsx
    <strong>O papel de administrador do escritório</strong> mantém sempre as permissões

    alterações a qualquer papel aplicam-se de imediato às sessões já abertas dos
```

The second sentence directly surfaces PAPEL-03's live-effect guarantee (success criterion 2), which the old copy never had reason to mention.

### 5. Save flow — no confirmation dialog, unlike `/plataforma/moldes`

Clicking "Guardar Alterações" calls the mutation directly and shows a `toast.success("Permissões atualizadas com sucesso.")` on completion (`apiFetch`'s shared error toast handles failure automatically — no inline success/error `<div>` banner, which modernizes `RbacTab`'s current inline-banner pattern to match the toast-only convention `/plataforma/moldes` and `criar-molde-panel.tsx` already established as the more recent precedent in this codebase).

**Why no `AlertDialog`, unlike moldes' save flow.** Phase 125's confirmation dialog exists specifically to make a delayed, easy-to-misread cross-tenant non-effect visible before saving. Nothing analogous exists here: every permission change on this screen affects only this office, takes effect immediately, and PAPEL-07's isolation guarantee is a backend property proven by a dedicated test (Decision 5, CONTEXT.md), not something this screen needs to caveat to the person using it. Adding a confirmation step here would be friction with no corresponding risk to justify it.

The "Guardar Alterações" button stays disabled whenever there is no local diff against the last-fetched state (dirty-check, same technique as `RbacTab`'s `localRolePermissions` comparison, generalized to a `Record<roleId, Set<permissionKey>>` — see §6 for the merge behavior that keeps this diff correct across creates/renames/deletes).

### 6. Unsaved-edit merge behavior — reused from `/plataforma/moldes`, generalized

Reuse `mesclarEstadoLocal` / `LocalPermissoes` (`web/src/app/(dashboard)/plataforma/moldes/merge-local-permissoes.ts`) **by pattern**, not by literal import (that file is keyed on `moldeId: number`; this screen needs the same merge logic keyed on the tenant role's id). The contract that must hold, restated for this screen's extra mutations beyond moldes' create-only case:

- A role's local, unsaved permission edits survive **creating** a new role (exactly as in moldes — `mesclarEstadoLocal`'s doc comment at `merge-local-permissoes.ts:19-51` already covers this case verbatim).
- A role's local, unsaved permission edits survive **renaming a different role** — renaming changes a `nome` field the merge never keys on (it keys on id), so this holds automatically as long as the merge stays id-keyed and never re-derives keys from `nome`. Call this out explicitly in the plan: it is the one new failure mode this screen introduces relative to moldes (which had no rename), and it is trivially satisfied only if nobody "optimizes" the merge to use `nome` as the map key.
- A role's local, unsaved permission edits survive **deleting** a *different* role — same reasoning as create, generalized: the touched-ids set for the deleted role is simply dropped, all others are untouched.
- Deleting or renaming the role the operator is *currently* editing in the matrix should not throw — a deleted role's column and touched-id entry are both dropped together in the same reconciliation pass; a renamed role's column keeps its (now stale, about-to-refresh) checkbox state until the next fetch, exactly as any other untouched-vs-touched cell already behaves.

### 7. Rename — a `Dialog`, not inline, not the create panel

**Where it lives.** Not inline in the column header (too little width for a text input beside a two-badge-and-kebab-laden header, see §3's `min-w-[140px]` exception — adding an editable input there would force it wider still). Not the create panel (that panel's job is composing a *new* role's full permission set; reusing it for rename would force an irrelevant permission checklist onto a single-field edit and would visually suggest permissions are being redefined, which they are not). A focused, single-field `Dialog` — the first use of this exact "one field, Cancel/Save" idiom in this codebase for RBAC, but `Dialog` itself is already used elsewhere in the app (`components/ui/dialog.tsx`, used e.g. in `clientes/[id]/page.tsx`) for comparable focused edits.

**What it says about scope** (design brief's explicit ask — what a rename does and does not affect):

```tsx
<Dialog open={isRenameOpen} onOpenChange={setIsRenameOpen}>
  <DialogContent>
    <DialogHeader>
      <DialogTitle>Renomear papel</DialogTitle>
      <DialogDescription>
        Isto altera apenas o nome apresentado — não muda as permissões nem os
        utilizadores atualmente atribuídos a este papel. O novo nome fica visível de
        imediato em toda a aplicação.
      </DialogDescription>
    </DialogHeader>
    <div className="space-y-2">
      <Label htmlFor="roleRename">Novo nome</Label>
      <Input id="roleRename" defaultValue={role.nome} className="bg-slate-50 dark:bg-slate-950" />
      <p className="text-xs text-slate-500 dark:text-slate-400">Nome atual: {role.nome}</p>
    </div>
    <DialogFooter>
      <DialogClose asChild><Button variant="outline">Cancelar</Button></DialogClose>
      <Button className="bg-blue-600 hover:bg-blue-700 text-white" disabled={isPending}>
        {isPending ? "A gravar..." : "Guardar Nome"}
      </Button>
    </DialogFooter>
  </DialogContent>
</Dialog>
```

Validation mirrors the create panel's reserved-name check (§8): non-empty, trimmed, rejects `"PLATAFORMA_ADMIN"` case-insensitively. Unlike moldes' create flow, **no forced-uppercase transform** — office role names are free text chosen by the admin for their own team (e.g. "Recepção", "Financeiro Sénior"), not platform-reserved tokens like `ADMIN`/`ADVOGADO`, so there is no existing-name casing convention to match. Duplicate-name rejection is server-side; the shared `apiFetch` toast surfaces it and the dialog stays open with the input intact.

No warning about any backend consequence of renaming (e.g. the `ParecerController` name-matching debt in Decision 2a) belongs on this dialog — that debt is resolved *by this same phase*, at the backend, before renaming ships (Decision 2a, CONTEXT.md: `UserPrincipal` gains `moldeId`-based resolution precisely so renaming is safe). The UI does not need to caveat a risk the phase's own backend work already closes.

Trigger: a kebab (`MoreVertical`, lucide) `Button` (`variant="ghost" size="icon" className="h-6 w-6"`, `aria-label="Mais ações para o papel {nome}"`) trailing the role name in the column header, opening a `DropdownMenu`:

```tsx
<DropdownMenuContent align="end">
  <DropdownMenuItem onSelect={() => openRename(role)}>
    <Pencil className="h-4 w-4" /> Renomear
  </DropdownMenuItem>
  <DropdownMenuSeparator />
  {role.podeApagar ? (
    <DropdownMenuItem variant="destructive" onSelect={() => openDelete(role)}>
      <Trash2 className="h-4 w-4" /> Apagar Papel
    </DropdownMenuItem>
  ) : (
    <div className="px-2 py-1.5 text-xs text-slate-500 dark:text-slate-400 flex items-start gap-2">
      <Lock className="h-3.5 w-3.5 mt-0.5 flex-shrink-0" />
      <span>
        {role.protegido
          ? "Papel protegido: administrador do escritório."
          : `Atribuído a ${role.utilizadoresAtribuidos} utilizador${role.utilizadoresAtribuidos === 1 ? "" : "es"}. Remova-o(s) em Gestão de Utilizadores para poder apagar.`}
      </span>
    </div>
  )}
</DropdownMenuContent>
```

**Why the refusal reason lives inline in the menu, not in a `Tooltip` on a disabled item.** A hover-only `Tooltip` on a disabled menu item is not reliably reachable by keyboard/screen-reader users navigating an already-open `DropdownMenu` overlay (nested-overlay focus handling), and this is exactly the "real refusal state," not a decoration, that the design brief asks for. A static, always-visible explanatory row inside the already-open menu is unconditionally accessible and states the "path to act" (where to go) directly in text, without relying on a second interactive affordance layered on top of a disabled one.

### 8. Create role — inline panel, reusing `CriarMoldePanel`'s structure

Structural parent: `criar-molde-panel.tsx` (itself modeled on `criar-tenant-panel.tsx`) — swaps in place of the matrix `Card` when "Criar Papel" is clicked, same `isFormOpen` boolean pattern already used by `PlataformaPageContent` and reusable verbatim here.

```
Card
  CardHeader (flex-row, justify-between)
    ├─ CardTitle "Criar Papel"
    ├─ CardDescription "Defina o nome e as permissões iniciais deste papel.
    │   Fica disponível de imediato para atribuir a utilizadores do seu
```

On success: `toast.success('Papel "{NOME}" criado com sucesso.')`, close the panel, invalidate the roles query. On failure (e.g. duplicate name in this tenant): the shared `apiFetch` toast fires and the panel stays open with input intact — same recovery convention as `CriarMoldePanel`.

### 9. Delete — `AlertDialog`, only reachable when `podeApagar` is true

```tsx
<AlertDialog open={isDeleteOpen} onOpenChange={setIsDeleteOpen}>
  <AlertDialogContent>
    <AlertDialogHeader>
      <AlertDialogTitle>Apagar o papel "{role.nome}"?</AlertDialogTitle>
      <AlertDialogDescription>
        Esta ação não pode ser desfeita. O papel deixa de existir e as suas permissões
        deixam de estar disponíveis para atribuição. Nenhum utilizador tem este papel
        atribuído atualmente, por isso é seguro apagá-lo.
      </AlertDialogDescription>
    </AlertDialogHeader>
    <AlertDialogFooter>
      <AlertDialogCancel disabled={isPending}>Cancelar</AlertDialogCancel>
      <AlertDialogAction
        disabled={isPending}
        className="bg-red-600 hover:bg-red-700 text-white"
        onClick={(e) => { e.preventDefault(); void handleConfirmDelete(); }}
      >
        {isPending ? "A apagar..." : "Apagar Papel"}
      </AlertDialogAction>
    </AlertDialogFooter>
  </AlertDialogContent>
</AlertDialog>
```

On success: `toast.success('Papel "{NOME}" apagado.')`, close dialog, invalidate the roles query (dropping the deleted role's id from any touched-ids set per §6). On failure: keep the dialog open, same recovery convention as every other destructive confirm already in this codebase (e.g. `plataforma/page.tsx`'s tenant-status `AlertDialog`).

This dialog is **only ever opened** from the `podeApagar === true` branch of §7's dropdown — the disabled-with-explanation branch never renders a trigger for it, so there is no dead/disabled "Apagar" button anywhere on this screen; the refusal state (§7) and the confirmation state (§9) are two different, mutually exclusive UI paths, not one control that sometimes does nothing.

## Visual-QA Watch Items (non-blocking — flag for implementer, not a contract defect)

1. **Two-row role column headers under `min-w-[140px]`.** With a long role name (e.g. a custom "Assistente Jurídico Sénior") plus two badges plus a kebab trigger stacked in ~140px, wrapping is expected and acceptable (`flex-wrap` is already specified on the badge row); do not widen the column indiscriminately for one long name at the expense of every other column's alignment — truncate the name with `title={role.nome}` for the tooltip-on-hover full text instead, if a specific name overflows badly.

## Open Discretion Notes (Claude's Discretion, recorded per `<design_contract_questions>`)

1. **No permanent "this changed" banner (design brief Q1)** — resolved by stating the ownership fact permanently in `CardDescription` + the repurposed note box (§1, §4), not as a dismissible or time-limited callout. Reasoning: a "look, you can do this now" framing only makes sense to someone who remembers the old locked state; every office admin who onboards after this phase ships never saw it, and a stale "what's new" banner reads as noise to them forever. An ownership statement ("estas definições pertencem apenas ao seu escritório") reads correctly to both audiences on day one and on day one-thousand.
2. **Provenance shown as two small badges, not a section split or a single combined badge (design brief Q2)** — a section split (e.g. "Papéis Predefinidos" vs "Papéis Criados por Si" as two separate tables) would fragment the single matrix's column-comparison value (an admin comparing permissions across roles needs them side by side) for a distinction that, examined closely, only actually restricts one specific role (the protected admin role), not "all sistema roles." Two neutral badges plus one distinct lock icon communicate the real rule (provenance is informational; only one specific role is protected) more precisely than a section split would (which would visually imply *all* sistema roles are somehow less free to edit than custom ones, which is false).
3. **Rename as a `Dialog`, not inline or reusing the create panel (design brief Q3)** — reasoned in §7. A `Dialog` is the smallest primitive already in this codebase that fits "one field, explicit Save/Cancel, explains scope" without repurposing a component (the create panel) whose entire visual weight is a permission checklist that has nothing to do with a rename.
4. **Delete refusal as static in-menu text, not a `Tooltip` on a disabled item (design brief Q4)** — reasoned in §7, on accessibility grounds specific to nested overlays, not aesthetic preference.
5. **No amber/caution color this phase** — reasoned in the Color section: nothing on this screen has the delayed, easy-to-misread cross-tenant effect that justified amber in Phase 125's analog.
6. **User role picker becomes a checkbox list, not a bigger button grid (§2)** — an unbounded role count cannot scale in a fixed `grid-cols-4` layout the way four hardcoded roles could; reusing the already-shipped "Permissões Customizadas" checklist pattern in the same file avoids introducing a third distinct list-picker visual idiom into one component.
