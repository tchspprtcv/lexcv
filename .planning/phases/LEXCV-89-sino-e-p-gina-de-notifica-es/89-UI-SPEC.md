# Phase 89 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** Phase 89 is 100% frontend — it consumes the API already shipped in Phase 86 (`GET /notificacoes`, `GET /notificacoes/unread-count`, `PATCH /notificacoes/{id}/lida`, `POST /notificacoes/ler-todas`). No backend endpoint is created or changed. Two surfaces are in scope: (1) a full rewrite of the existing sino (`web/src/components/shared/notification-bell.tsx`, today driven by `useUpcomingEventos`) to consume real `Notificacao` records instead, and (2) a brand-new page at `/notificacoes` (App Router, `(dashboard)` route group) — the first frontend touchpoint for this entity, no prior art to preserve.

## Component & Placement Contract (supplementary)

### API contract (verified directly from backend source — do not re-derive)

```
GET  /notificacoes?categoria=&lida=&page=0&size=20
  -> { content: Notificacao[], totalElements: number, totalPages: number, page: number, size: number }
GET  /notificacoes/unread-count
  -> { count: number }
PATCH /notificacoes/{id}/lida
  -> Notificacao (the updated row)
POST /notificacoes/ler-todas
  -> { marcadas: number }
```

`Notificacao` shape (verified against `backend/src/main/java/com/lexcv/models/Notificacao.java` — Lombok `@Getter`-derived, **plain camelCase JSON, no snake_case, no naming-strategy override**):

```ts
type NotificacaoCategoria =
  | "FASE_ENTRADA" | "DOCUMENTO_NOVO" | "PROCESSO_ATRIBUIDO" | "PARECER_ATRIBUIDO"
  | "PRAZO_PROXIMO" | "PRAZO_VENCIDO" | "EVENTO_PROXIMO" | "EVENTO_VENCIDO" | "HONORARIO_ATRASADO";

type Notificacao = {
  id: string;              // UUID, serializes as string
  categoria: NotificacaoCategoria;
  entidadeTipo: string;    // "processo" | "documento" | "parecer_solicitacao" | "honorario" — not used for rendering, informational only
  entidadeId: string;
  titulo: string;           // backend-authored, e.g. "Nova fase"
  mensagem: string;         // backend-authored, e.g. "O processo 123/2026 entrou na fase Instrução"
  linkUrl: string | null;   // always a same-origin relative path when present, e.g. "/processos/{id}" or "/agenda" — never external
  lida: boolean;
  createdAt: string;        // ISO-8601 LocalDateTime string (Spring Boot default jsr310 serialization, NOT a timestamp array) — parse via `new Date(createdAt)`
};
```

**Important, verified fact for the executor:** unlike this project's recurring camelCase/snake_case DTO-mapping bug (seen 4x in `Processo`/`Cliente` create/update payloads), `Notificacao` GET responses need **no** `normalize*`/`toApiPayload` translation function — the Java field names and the JSON keys are identical camelCase strings, confirmed by reading the entity source directly. This phase only ever reads this entity (mark-read/mark-all mutations send no body), so this class of bug has no surface here at all.

### Query behavior contract (critical — this is the part most likely to be under-scoped)

| Query | Polling | `refetchOnWindowFocus` | Notes |
|-------|---------|--------------------------|-------|
| `useNotificacoesUnreadCount()` | `refetchInterval: 30_000` | `true` (explicit override — global default in `web/src/app/providers.tsx` is `false`) | Powers the bell's badge number |
| Dropdown's list query (`useNotificacoes({ size: 10 })`, no `lida` filter — most-recent-10 regardless of read state, per CONTEXT.md) | `refetchInterval: 30_000` | `true` (same override, same reasoning — a stale badge count next to a stale list is a worse, more confusing bug than a stale badge alone) | Powers the dropdown body |

**Cache invalidation on mark-read / mark-all (must satisfy CONTEXT.md's "contador do sino atualiza-se de imediato, sem esperar pelo próximo ciclo de polling"):** both mutations must, on success, invalidate **all** of: `["notificacoes", "unread-count"]`, `["notificacoes", "list", ...]` (broad prefix match — covers both the dropdown's 10-item query and the page's paginated query simultaneously). A prefix-level `queryClient.invalidateQueries({ queryKey: ["notificacoes"] })` after either mutation is the simplest correct approach and satisfies the "immediate" requirement without manual optimistic cache writes, since TanStack Query refetches any currently-mounted query matching an invalidated key immediately, not on the next poll tick.

## Interaction Flow (supplementary)

**Sino (bell):**
1. Badge shows `unreadCount` (capped display `"9+"` above 9), refreshed every 30s and immediately on window refocus.
2. Opening the popover shows: header row (**"Notificações"** + **"Marcar todas como lidas"**, disabled if `unreadCount === 0`), then up to 10 most-recent notifications (any read state), then footer (**"Ver todas as notificações"** → `/notificacoes`).
3. Clicking a notification row: fires `markAsRead.mutate(id)` (fire-and-forget, not awaited) **and** navigates via the row's `<Link href={n.linkUrl}>` in the same click — no confirmation step (CONTEXT.md locked). If `linkUrl` is null/empty, the row renders as plain non-navigating text (mirrors today's `ev.processoId ? <Link>... : <NotificationItem>` fallback pattern) but a null `linkUrl` should still allow marking as read via a small inline affordance, since the row otherwise has no click target.
4. Clicking "Marcar todas como lidas": calls the mutation, invalidates per the table above, shows `toast.success(...)`; button shows "A marcar..." while pending.

**`/notificacoes` page:**
1. Loads with defaults: `categoria = "Todas as categorias"`, lida-filter = **"Todas"**, `page = 0`, `size = 20`.
2. Changing either filter resets `page` to `0` and refetches.
3. Each row: unread rows show the blue dot + semibold title; clicking the title/row marks-as-read and navigates (same fused behavior as the dropdown, for consistency) **unless** the row is already read, in which case it's a plain navigation (no redundant mutation call). A separate small `Check` icon-button (outside the `<Link>`, not nested inside it — avoids invalid nested-interactive-element HTML) lets the user mark a single row as read **without** navigating away, satisfying NOTF-10 as a standalone action distinct from "open it."
4. "Marcar todas como lidas" (page header) behaves identically to the dropdown's version.
5. Pagination: "Anterior"/"Seguinte" + "Página {page+1} de {totalPages}", disabled at the respective boundary (`page === 0` / `page + 1 >= totalPages`).

## Known Gaps & Discretion Resolutions (supplementary)

- **3-way chip toggle vs. a single `Switch` for lida/não-lida:** CONTEXT.md says "toggle lida/não-lida" (singular), which could read as a binary on/off. Resolved in favor of a **3-way chip toggle** (Todas / Não lidas / Lidas) because: (a) the backend's own filter param is a nullable `Boolean` — a real 3-state contract Phase 86 deliberately built, and NOTF-13's "filtra... por estado lida/não-lida" reads more naturally as choosing among states than flipping one bit; (b) it reuses an exact, already-shipping codebase pattern (`aria-pressed` chip buttons, verbatim classNames) rather than introducing a new interaction paradigm; (c) a plain `Switch` would make "show only read items" structurally impossible, which is a real regression against what the API already supports for no interaction-cost savings.
- **Stacked-list instead of `Table` for the page/dropdown:** Per this project's own responsiveness convention (v2.3, "Cards empilhados em listas simples e scroll horizontal em tabelas complexas"), a notification is conceptually a list item (title + message + meta), not tabular data with meaningful columns — forcing it into `<Table>` would produce an awkwardly wide "message" column. A single stacked-row layout (like `DocumentoMobileCard`) used at all breakpoints avoids maintaining a separate desktop-table/mobile-card fork for content that was never tabular to begin with.
- **"neutral" vs. "slate" color family:** `documentos/page.tsx` (older) uses the `neutral-*` Tailwind family; `processos/[id]/page.tsx` and the sino itself (newer, and directly adjacent to this phase's work) use `slate-*`. This phase standardizes on **slate**, matching the bell it's visually/functionally paired with, deliberately diverging from the older `documentos` page's convention.
- **No relative-time formatting ("há 2 horas"):** No such helper or library (date-fns, dayjs) exists anywhere in this codebase; every one of the 15 pages using dates formats them absolutely via `toLocaleDateString`/`toLocaleString("pt-CV", ...)`. This phase follows that convention rather than introducing new date-math logic.
- **Mark-as-read-without-navigating affordance:** CONTEXT.md's dropdown behavior (click = read + navigate, fused) is explicit, but NOTF-10 ("Utilizador marca uma notificação individual como lida") reads as a standalone action. Resolved by adding a small secondary `Check` icon-button on the **page** (not the dropdown, which stays exactly as CONTEXT.md describes) so a user can clear an item's unread state without leaving the history view.
- **`linkUrl` can be `null` in the DB schema** (`@Column(name = "link_url")`, no `nullable = false`) even though every current caller (`ResourceController`, `ParecerController`, `AlertasDiariosJob`) always passes a real path today. The UI must not assume non-null — fall back to non-navigating plain text, matching the existing bell's defensive pattern for `ev.processoId`.
