# Phase 105 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 105 migrates the Ficha de Cliente (`clientes/[id]/page.tsx`) and Ficha de Processo (`processos/[id]/page.tsx`) from manual `Button`-toggle tab bars to real `Tabs`, replaces every native `<select>` in both modules with `NativeSelect`, introduces `Avatar` for Advogados/Administrativos/Testemunhas, and replaces the ad hoc `<div>+Link+"/"` header nav with `Breadcrumb` across 6 pages. Delivered as a single phase (never split) because the milestone's own stated risk is a visible inconsistency window between the two fichas. Covers CLP-01 through CLP-05. Per `105-CONTEXT.md`'s explicit scope expansion, this phase also touches: the Documentos tab of the Ficha de Processo (new `DataTable` adoption, Phase 104 pattern) and the Partes/Fases tabs (`<table>` → reconciled `Table` primitives, no full DataTable). No row-selection/bulk actions (project-wide Out of Scope).

**Verified-against-source findings (load-bearing for planning):**

1. **The two fichas' tab bars are structurally identical today** (`variant={tab === "x" ? "secondary" : "outline"}` `Button` array) but differ in exactly the two responsive treatments `105-CONTEXT.md` already locks as "keep as-is": Clientes wraps its bar in `overflow-x-auto` (single-row horizontal scroll), Processos uses `flex flex-wrap` (wraps to multiple rows). Do not unify these two behaviors — preserve each verbatim inside the new `TabsList`.
2. **`Tabs`/`TabsList`/`TabsTrigger`/`TabsContent` (`web/src/components/ui/tabs.tsx`) already ship a `variant="default"|"line"` prop.** `default` renders an `bg-muted` pill container with `data-active:bg-background data-active:shadow-sm` triggers — visually the closest existing primitive to today's `secondary`/`outline` `Button` pair (locked in CONTEXT.md as the variant to use). Do not use `variant="line"` (underline style, not requested).
3. **Neither ficha's header today is a `Breadcrumb`-shaped component** — it is a plain `<h1>` + `<div className="text-sm text-neutral-500..."><Link>{Módulo}</Link> / <span>{identificador}</span></div>`, structurally identical between the two fichas (only the module name/identifier differ). This is the pattern CLP-05 replaces on all 6 pages. **However, only 2 of the 6 target pages (`clientes/[id]`, `processos/[id]`) actually have this 2-level div-nav today.** The other 4 pages have a *different* existing header shape — this phase is a net-new addition of navigational structure on those, not a like-for-like swap:
   - `clientes/novo/page.tsx`, `processos/novo/page.tsx`, `clientes/merge/page.tsx`: plain `<h1>` + subtitle `<p>`, **no breadcrumb-shaped element exists at all** today — only a separate `Button asChild variant="outline"><Link>Voltar</Link></Button>` sitting to the right of the header. The new `Breadcrumb` is additive here; the existing "Voltar" button is unchanged (not requested for removal by CLP-05, stays as a redundant-but-harmless secondary affordance).
   - `processos/[id]/editar/page.tsx`: `<h1>Editar processo</h1>` + a **single**-level `<Link href={.../id}>Voltar ao detalhe</Link>` (no "/" separator, no module-root link) — the new `Breadcrumb` here should be 3-level (`Processos` → `{processo.data?.numero}` linking back to the ficha → `Editar`, current page), since `useProcesso(id)` is already loaded on this page and exposes `numero`.
4. **A pre-existing `<h1>` font-weight inconsistency is wider than the 2 fichas CONTEXT.md names.** Confirmed by direct read: `clientes/[id]` (`font-semibold`), `clientes/novo` (`font-semibold`), `clientes/merge` (`font-semibold`) are internally consistent within Clientes; `processos/[id]` (`font-bold`) and `processos/novo` (`font-bold`, plus stray `text-slate-900 dark:text-white` not used elsewhere) are consistent with each other — **but `processos/[id]/editar` uses `font-semibold`, breaking consistency within its own module.** `105-CONTEXT.md` explicitly authorizes reconciling to `font-bold` only for "ambas as fichas" (the 2 detail pages). This UI-SPEC recommends extending the identical fix, by direct analogy, to `processos/[id]/editar`'s `<h1>` (→ `font-bold`, drop the page's own unrelated `text-slate-900 dark:text-white` override if present) purely because this page's header is already being touched for its `Breadcrumb` addition — flagged explicitly here as a recommendation extending an authorized fix, not a silent scope expansion; planner/checker may override if a narrower reading is preferred.
5. **`<select>` styling divergence is wider than the two variants CONTEXT.md names.** A full grep of the 8 in-scope files (12 occurrences in Clientes, 15 in Processos — 27 total) surfaces **four**, not two, distinct hardcoded stylings, all collapsing into the same `NativeSelect` target regardless of origin:
   - Clientes RHF-bound forms (`clientes/[id]`, `clientes/novo`): `rounded-none border-neutral-200 ... focus-visible:ring-neutral-950`
   - Processos RHF-bound forms (`processos/[id]`, `processos/[id]/editar`, `processos/novo`): `rounded-md border-neutral-200 ... focus-visible:ring-neutral-950`
   - List-filter / dialog controlled selects (`clientes/page.tsx` ×2, `processos/page.tsx` ×2, `ReatribuirResponsavelControl` in `processos/[id]/page.tsx`): `h-10 bg-white dark:bg-[#020617] rounded-none border-slate-300 ... focus-visible:ring-blue-500` — note the stray `slate`/blue-500 ring, unrelated to either RHF variant
   - `clientes/merge/page.tsx` (×2, controlled): `h-10 bg-white dark:bg-neutral-950 rounded-md border-neutral-200 ... focus-visible:ring-neutral-950`

   This does not change CONTEXT.md's locked resolution ("`NativeSelect`'s own styling becomes the single source of truth") — it only confirms the cleanup surface is 4-way, not 2-way, so the planner should not stop after finding the two `const selectClassName` declarations; the list-filter and merge-page inline variants must be swept too.
6. **Testemunhas is a raw `<table>`, Partes/Fases are raw `<table>`, and the processo Documentos tab is not even a table** — confirmed by direct read: `ProcessoDocumentosTab` renders an `<ul><li>` list (`ProcessoDocumentoRow`), the same shape `documentos/page.tsx` had *before* Phase 104's migration. This means the new processo-scoped Documentos `columns.tsx` is a first-time `Table`/`DataTable` adoption for this tab specifically — model it directly on `web/src/app/(dashboard)/documentos/columns.tsx` (Phase 104, already migrated), reusing its `confidencialidadeVariant()` mapping and `DocumentoAcoesCell` pattern, filtered to the current `processoId` via the existing `useDocumentos({ processo_id: processoId })` hook (already used today) — no new hook needed, only new `columns.tsx` + swap `<ul>` for `<DataTable columns={columns(...)} data={documentos} getRowId={(d) => d.id} />`.
7. **The "Nome" cell chip on the Clientes list (`clientes/columns.tsx`, Phase 104) is NOT the real `Avatar` component** — it is a hand-rolled `div` (`h-10 w-10 rounded-none bg-blue-50 ... text-blue-700`) that happens to show initials. CLP-04 does not touch this chip (different requirement, different phase) — only its **initials-derivation logic** (`split(" ").filter(Boolean).slice(0,2).map(p=>p[0]).join("").toUpperCase()`) is reused verbatim inside the new, real `Avatar`/`AvatarFallback` instances this phase adds to `ResponsaveisCard` and the Testemunhas table. Do not retrofit real `Avatar` onto the Clientes list chip as a "consistency" side effect — that chip is out of scope.

## Visual Hierarchy

No new page-level focal point on either ficha. The `Tabs`/`TabsList` occupies the exact same slot in the DOM the `Button` array occupies today — directly below the header block, above the tab-content `Card`(s) — and at `variant="default"` renders at essentially the same visual weight (pill container, active tab lifted with `shadow-sm`) as today's `secondary`/`outline` button pair, so this is a semantics/accessibility upgrade (`role="tablist"`, `aria-selected`, keyboard arrow-navigation for free), not a visual redesign. `Breadcrumb` occupies the same slot the `<div className="text-sm text-neutral-500...">` nav row occupies today (or is added net-new directly below the `<h1>` where no such row exists yet — see Scope note #3). `Avatar` is inserted as a small leading element inside two already-existing row layouts (`ResponsaveisCard`'s list rows, the Testemunhas table's "Nome" cell) — it does not change row height beyond what `size="sm"` (24px, `size-6`) already accommodates inside the current `p-2`/`py-2` row padding. `NativeSelect` is a drop-in replacement inside existing form-field slots — no layout change beyond each of the 4 identified stylings (see Scope note #5) converging on the same visual shape.

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`, unchanged. No new spacing value introduced.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding — `Avatar`+name `gap-2` in Testemunhas/ResponsaveisCard rows rounds to this scale via Tailwind's `gap-2` (8px, see `sm` below — not `xs`) |

| lg | 24px | Section padding |

## Typography

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`, unchanged base scale. No new type role introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`) | 600 semibold | 1.4 |
| Heading | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display | 30px (`text-3xl`) | 600 semibold | 1.2 |

Component-specific notes (all already-shipped primitive defaults, not new choices this phase makes):

- `TabsTrigger` renders at `text-sm font-medium` (14px/500) — a pre-existing primitive weight distinct from both Body (400) and Label (600). This is `tabs.tsx`'s own shipped default from Phase 101/102 and is out of scope to change here (same treatment Phase 102 gave to primitive-internal typography it didn't re-litigate).
- `BreadcrumbList`/`BreadcrumbLink`/`BreadcrumbPage` render at `text-sm` (14px, Body) with `text-muted-foreground` (list/links) / `text-foreground` (current page) — matches the existing div-nav's `text-sm text-neutral-500` almost exactly, a semantically-equivalent token swap, not a size change.
- `AvatarFallback` at `size="sm"` renders at `text-xs` (12px, Label size, `group-data-[size=sm]/avatar:text-xs` in `avatar.tsx`) — correct for 2-letter initials at 24px diameter.
- The `<h1>` font-weight fix (Scope note #4) moves `clientes/[id]`/`processos/[id]` to a uniform `font-bold` (600 — Tailwind's `font-bold` is weight 700, actually; verify at implementation this doesn't silently introduce a 3rd weight value beyond the declared 400/600 pair — if so, prefer `font-semibold` project-wide instead of `font-bold` and flag the deviation from CONTEXT.md's literal "font-bold" wording at the checker step).

## Color

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`, unchanged — this phase adds zero new colors and zero new accent-reserved elements.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background`/`--foreground` | Page background + default text |
| Secondary (30%) | `--card`/`--popover`/`--muted` (reconciled Phase 102) | `TabsList`'s `bg-muted` container; `Table`/`Card` chrome around Partes/Fases/Documentos; `AvatarFallback`'s `bg-muted` |
| Accent (10%) | `--primary` | Reserved exclusively for the closed list already established: sidebar active-nav-item indicator/icon/label tint, user-avatar gradient badge, global search input focus ring, Dashboard KPI positive/urgent number highlight. **Neither `Tabs`, `Breadcrumb`, `Avatar`, nor `NativeSelect` join this list this phase.** |
| Destructive | `--destructive` | Destructive actions only — existing per-row delete (`window.confirm()`) on Partes/Fases/Testemunhas/Documentos is unchanged by this phase, not migrated to `AlertDialog` (scope expansion beyond CLP-01–05) |
| `--radius` | `0rem` | Sharp corners — `Tabs`/`TabsList`/`TabsTrigger`, `Avatar`, `NativeSelect`, `Breadcrumb` all resolve to `0` automatically via the existing `--radius` token except where the primitive is deliberately round by identity (`Avatar` is always `rounded-full`, a Radix `Avatar` convention independent of `--radius` — do not attempt to square it, that would break the fallback-initials circular affordance every other app in this ecosystem uses) |

**Explicit rule for this phase:** `AvatarFallback` uses its shipped default `bg-muted text-muted-foreground` — never the Clientes-list chip's `bg-blue-50 text-blue-700` accent-tinted treatment (see Component Inventory, CLP-04). This is deliberate: extending an accent tint to a second, unrelated surface (ResponsaveisCard/Testemunhas) is exactly the kind of silent accent-reservation-list growth the project's Color contract exists to prevent.

The list-filter/dialog select's stray `focus-visible:ring-blue-500` (Scope note #5, 3rd variant) is **not** carried into `NativeSelect` — `NativeSelect`'s own shipped focus ring (`focus-visible:ring-ring/50`, resolving to the neutral `--ring` token, not blue-500) is correct and matches the two RHF-bound variants' `ring-neutral-950`/`ring-neutral-300` intent far more closely than the outlier blue ring did. Losing that one outlier blue focus ring is an intentional side effect of the `NativeSelect` migration, not a regression to flag.
