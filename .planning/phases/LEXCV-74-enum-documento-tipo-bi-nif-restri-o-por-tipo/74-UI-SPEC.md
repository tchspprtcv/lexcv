## Scope Note

This phase is **not** a UI phase in the normal sense. Per 74-CONTEXT.md (`<specifics>`: "Nenhuma referência visual específica — esta é uma fase de modelo de dados + validação, sem mudança de layout"), the entire frontend surface is:

1. Removing 1 `<option value="NIF">NIF</option>` and adding 1 `<option value="BI">BI</option>` inside two **existing** native `<select>` elements (`documento_tipo` field) in `web/src/app/(dashboard)/clientes/novo/page.tsx` and `web/src/app/(dashboard)/clientes/[id]/editar/page.tsx`.
2. Filtering which of those `<option>` elements render, based on the already-selected `tipo` (Particular/Empresa) radio value.
3. Reusing the **already-existing** `Dialog` confirmation component (the `pendingTipo` swap-warning dialog already present in both files) to also clear `documento_tipo`/`documento_numero` when a switch of `tipo` invalidates the current selection — no new dialog, no new copy variant, no new visual state.

No new screens, no new components, no new layout, no new color usage, no new typography, no new spacing decisions. The `select`/`Input`/`Label`/`Dialog` styling already in the codebase (`selectClassName`, `rounded-none` inputs, existing `Dialog`/`DialogContent`/`DialogFooter` primitives) is reused unchanged.

**Design System detected:** No `components.json` found in `web/` — this project does not use the shadcn CLI. It uses hand-rolled Radix-based primitives under `web/src/components/ui/` (`Button`, `Card`, `Dialog`, `Input`, `Label`, `RadioGroup`, `Switch`, `Badge`) following a consistent flat/`rounded-none` visual language, plus a shared `selectClassName`/`textareaClassName` string constant for native `<select>`/`<textarea>` elements (both forms already define these identically). Because this phase introduces zero new components and zero new visual states, the shadcn initialization gate is **not applicable** — there is nothing new to scaffold, and forcing shadcn init here would be out of scope for a backend-enum phase.

## Interaction Contract (in place of new visual states)

Since this phase has no new visual states, the interaction contract below is the actual design surface the checker/executor should validate against:

1. **Option list filtering** — `getDocumentoTipoOptions(tipo)` (per 74-CONTEXT.md shared module decision) returns:
   - `tipo === "PARTICULAR"` → `[{value: "", label: "Nenhum"}, {value: "CNI", label: "CNI"}, {value: "BI", label: "BI"}, {value: "PASSAPORTE", label: "Passaporte"}]`
   - `tipo === "EMPRESA"` → `[{value: "", label: "Nenhum"}, {value: "REG_COMERCIAL", label: "Registo Comercial"}]`
   - `tipo === undefined` (not yet selected) → same behavior as today: render the full "Nenhum" + all options, or reasonably fall back to the Particular set — Claude's Discretion per CONTEXT.md, executor should pick whichever avoids an empty/broken select before `tipo` is chosen. Recommendation: fall back to `PARTICULAR` set (superset minus REG_COMERCIAL) to avoid showing an empty dropdown.
   - Option order matches existing order convention (Nenhum first, then document types in the same order currently hardcoded).
2. **Auto-clear on tipo switch** — no new UI. The existing `pendingTipo` Dialog confirm handler (`confirmTipoChange`) gains a side effect: when confirmed, if the current `documento_tipo` value is no longer valid for the new `tipo`, reset `documento_tipo` and `documento_numero` to `""` via `form.setValue`. No visual change to the dialog itself.
3. **Select element itself** — no className, sizing, or focus-state change. `selectClassName` constant stays identical in both files (already deduplicated at the style level, only the `<option>` list source moves to the shared module).
