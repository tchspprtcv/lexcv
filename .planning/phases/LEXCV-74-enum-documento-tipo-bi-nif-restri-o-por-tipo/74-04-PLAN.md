<objective>
Close the single verification gap in Phase 74 (Truth #10 / CR-01): a cliente loaded with a legacy/invalid `documento_tipo` for its `tipo` cannot be saved because the shared Zod schema unconditionally rejects the value before react-hook-form's `handleSubmit` ever reaches the `legacyDocumentoTipo` carve-out in `editar/page.tsx`'s `onSubmit`. That carve-out is dead code, and the on-screen banner promises a save path that does not work.

Fix by parameterizing the shared schema: introduce `buildClienteFormSchema(allowedLegacyDocumentoTipo?)`. When a legacy value is supplied, the per-tipo membership check in `superRefine` exempts exactly that one value; when omitted (the novo/create path), behavior is identical to today. `editar/page.tsx` rebuilds the resolver with the loaded legacy value so validation lets the untouched legacy value through while still rejecting any genuinely new invalid selection.

Purpose: Make the shipped legacy-preservation UX (banner + carve-out) actually reachable, satisfying CLI-24's "validated in frontend" clause for the editing flow without regressing new-record validation.

Output: Parameterized schema factory, updated editar resolver wiring, and a regression test covering both the legacy-pass and new-invalid-reject cases.
</objective>
