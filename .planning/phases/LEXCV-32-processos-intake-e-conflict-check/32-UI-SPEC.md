### Conflict-Level Badge Color Mapping

This phase introduces four semantically distinct badge variants that map to existing badge colors:

| Conflict Level | Badge Variant | Visual Signal |
|----------------|---------------|---------------|
| `sem_conflito` | `green` | No conflict detected — safe to proceed |
| `potencial` | `amber` | Conflict flagged — review required before override |
| `sanavel` | `blue` | Conflict present but resolvable — override with justification |
| `impeditivo` | `red` | Hard block — cannot be overridden, abertura impossible |

Source: badge variants defined in `web/src/components/ui/badge.tsx` (green, amber, blue, red already exist).

## Spacing & Layout: Multi-Step Intake Flow

The "Novo Processo" page (`/processos/novo`) is replaced by a 3-step wizard. No new routing — same path, stepper rendered within the page.

### Step Indicator (top of page, horizontal)

- 3 steps: `1 Intake` / `2 Conflict Check` / `3 Abertura`
- Active step: filled circle (blue-600, 32px diameter), label bold 14px
- Completed step: filled circle (emerald-600), with checkmark icon (lucide `Check` 14px)
- Upcoming step: circle outline (slate-300/slate-700), label 14px font-400
- Connector line between steps: 1px solid slate-200/slate-700
- Step indicator block spacing: `px-6 py-6` from page edges, `gap-4` between steps
- Sharp corners throughout (`rounded-none` on all interactive elements per Anti-Safe Harbor)

### Step 1: Intake

Form card with `CardHeader` ("Dados de Intake") + `CardContent`. Fields presented in a responsive grid:

- Row 1 (2 cols): `Cliente` (Select — potencial lead, tipo `lead`) / `Tipo de Processo` (Select — drives mandatory fields)
- Row 2 (2 cols): `Número` (Input, placeholder "Ex.: 123/2026") / `Área Jurídica` (Input, placeholder "Ex.: Cível")
- Row 3 (1 col full): `Tribunal` (Input, placeholder "Ex.: Tribunal da Comarca da Praia")
- Row 4 (2 cols): `Data de Início` (date Input) / `Data de Fim` (date Input, optional)
- Row 5 (1 col full): `Descrição` (Textarea, min-h-24, optional)
- Row 6 (full): Campos mínimos obrigatórios por tipo (dynamically rendered based on `tipo_processo` value — shown as additional labeled inputs)

CTA bar at bottom: `Continuar para Conflict Check` (primary, blue-600, rounded-none, font-bold) + `Cancelar` (ghost, link to `/processos`).

### Step 2: Conflict Check

Two-panel layout within a Card:

**Panel A — Conflict Check Trigger**
- Informational copy block: "O sistema vai verificar conflitos de interesse para o cliente, partes relacionadas e parte contrária declaradas no intake."
- `Executar Conflict Check` button (primary) — requires `processos:create` permission; shown disabled if permission absent.
- Loading state: button replaced by spinner + "A verificar conflitos..." text (14px, slate-500).

**Panel B — Match Results List** (rendered after check completes)
- Each match rendered as a bordered row (`border border-slate-200 dark:border-slate-800`, `rounded-none`, `p-4`):
  - Left: conflict level badge (`sem_conflito`/`potencial`/`sanavel`/`impeditivo`) + entity name + entity type (cliente/parte) + link to the record
  - Right: inline decision action (only when `processos:manage` permission present)
- Decision section (below match list or inline per match):
  - `Nível final` (Select: sem conflito / potencial / sanavel / impeditivo)
  - `Justificativa` (Textarea, required when level is `potencial` or `sanavel` for override; required always for `impeditivo` is a no-op — block is enforced)
  - `Decisor` (read-only, pre-filled from current user)
  - `Data` (read-only, pre-filled from today)
  - `Referência a evidência` (Input, optional)
  - `Registar Decisão` button (primary, `processos:manage` required)

**Blocking state for `impeditivo`:**
- `Continuar para Abertura` button is rendered but `disabled` with `opacity-50 cursor-not-allowed`
- Below the button: amber callout card (`bg-amber-50 dark:bg-amber-500/10 border border-amber-200 dark:border-amber-500/30 rounded-none p-4`) with text: "Conflito impeditivo registado. A abertura formal do processo está bloqueada até esta decisão ser revista por um utilizador com permissão de gestão."

**No matches state:** single row with `green` badge "Sem conflito detectado" and copy "Nenhuma correspondência encontrada para os critérios do intake."

### Step 3: Abertura

Summary card (read-only `dl` grid) showing intake fields and conflict check decision.

CTA bar: `Formalizar Processo` (primary) — disabled + reason shown when conflict is `impeditivo` or no decision registered.

Disabled state appearance: `opacity-50 cursor-not-allowed` on the button; immediately below it a `text-sm text-red-600` message: "Não é possível formalizar: existe um conflito impeditivo registado." or "Não é possível formalizar: o conflict check ainda não tem uma decisão registada."

On success: redirect to `/processos/{id}` (the newly created processo in estado `ativo`).

## Processo Detail: Conflict Check Section

On `/processos/{id}`, a new card section is rendered between the "Dados" card and the tab panel (partes/fases/movimentações). It is always visible when `processo.estado === 'TRIAGEM'` or when a conflict decision record exists.

Card layout:
- `CardHeader`: title "Conflict Check" + conflict level badge (right-aligned)
- `CardContent`:
  - Decision metadata row: decisor name, data, referência (if present) — `dl` grid, same pattern as existing dados card
  - Justification block: `p` with label "Justificativa" + value
  - Match list: same bordered row pattern as Step 2 (level badge + entity name + link)
  - If estado is `TRIAGEM` and user has `processos:manage`: inline "Formalizar Processo" button (primary, `rounded-none`, `font-bold`) with disabled state and reason message as described above

If no conflict decision exists yet (processo is `TRIAGEM`, check not yet run): card body shows `text-sm text-slate-500 dark:text-slate-400` "O conflict check ainda não foi executado para este processo."
