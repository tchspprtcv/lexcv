# Phase 102 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 102 reconciles the 13 pre-existing hand-rolled components (`button`, `dialog`, `alert-dialog`, `card`, `table`, `sheet`, `badge`, `input`, `label`, `popover`, `radio-group`, `switch`, `textarea` — ROADMAP.md's phase goal text says "14"; that figure is stale from before Phase 101 removed `toast.tsx`/`toaster.tsx`, the actual enumerated list in both ROADMAP.md and REQUIREMENTS.md DSR-01 has exactly 13 names, confirmed by direct file inventory of `web/src/components/ui/`) against the official shadcn registry, and adds `Tooltip` to icon-only interactive elements app-wide. Unlike Phase 101 (pure infrastructure, zero visible change), this phase **does** produce visible, intentional changes to already-shipped, heavily-used surfaces — CONTEXT.md itself requires a mandatory human visual checkpoint (light+dark) for exactly this reason. Consequently every section below is load-bearing this time, not "not exercised."

The single highest-risk decision this phase makes is **which existing colors change and which don't**. Getting this wrong in either direction is bad: silently keeping a stale hardcoded value when the registry now offers a token regresses the milestone's own consistency goal; silently adopting a token whose resolved value differs from today's rendered color (e.g. accidentally turning every default `Button` blue) is an unrequested redesign of the entire app. The **Color** section below states the exact rule and the exact per-component outcome expected, precisely to remove that ambiguity before planning/execution starts.

## Color

This is the section that governs the actual reconciliation work. All values below are sourced directly from reading the current 13 files (`web/src/components/ui/{button,badge,dialog,alert-dialog,card,sheet,input,label,popover,radio-group,switch,textarea,table}.tsx`) plus `globals.css` — not invented.

### Standing identity (unchanged from Phase 101 — do not touch)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background`/`--foreground` (`#f8fafc`/`#020617` light, `#020617`/`#f8fafc` dark) | Page background + default text |
| Accent (10%) | `--primary: #2563eb` light / `#3b82f6` dark | Reserved **exclusively** for: sidebar active-nav-item indicator/icon/label tint, user-avatar gradient badge, global search input focus ring, Dashboard KPI positive/urgent number highlight — all in `dashboard-shell.tsx`/`dashboard/page.tsx`, **none of the 13 reconciled files**. Phase 102 does **not** add `button`/`badge` default styling to this list |
| Destructive | `--destructive` (`oklch(0.577 0.245 27.325)` light / `oklch(0.704 0.191 22.216)` dark ≈ Tailwind `red-600`/`red-400`) | Destructive actions only |
| `--radius` | `0rem` | Sharp corners — institutional identity |

### Reconciliation rule (applies to all 13 components)

For every component, run `add <component> --diff`, then classify every color/radius delta the diff surfaces into exactly one of three buckets — never apply a diff wholesale:

- **Rule A — identical-value substitution (always apply).** The hardcoded literal and the token's resolved value render the same pixel in both themes. Example already decided in CONTEXT.md: `rounded-none` → `rounded-lg` (resolves to `0` via `--radius: 0rem` — visually identical today, but now propagates automatically if `--radius` ever changes). Apply these without further sign-off.
- **Rule B — convergent-but-different value (apply deliberately, flag at checkpoint).** The literal and the token render *visibly different* pixels, but adopting the token produces the semantically-correct, standard shadcn behavior the token exists for. See the concrete case below (card/dialog/alert-dialog/popover dark surfaces) — apply this, but call it out explicitly at the mandatory human visual checkpoint as an intentional, expected change, not a bug to revert.
- **Rule C — component identity (never substitute this phase).** The color *is* the component's visual identity, not an incidental surface color — `button`'s 5 variants, `badge`'s 9 variants (3 base + 6 custom color), `input`/`textarea`/`label`/`radio-group`/`switch`'s neutral-scale styling. Preserve every value byte-for-byte. **Do not** let any of these adopt `bg-primary`/`text-primary-foreground` even though the CLI's current registry `button.tsx` default variant now ships that way upstream — this repo's default button stays `bg-neutral-900`/`hover:bg-neutral-900/90` (and dark `bg-neutral-50`/`text-neutral-900`, matching what's there today), because `--primary` institutional blue is reserved for the closed list above, and swapping every "Guardar"/"Criar" button in the app to blue is an unrequested redesign, not a reconciliation.

### Concrete per-component outcome

| Component | Bucket | What changes | What must NOT change |
|-----------|--------|---------------|------------------------|
| `button` | C | Structural/a11y additions only if the diff reveals a genuinely missing feature (audit for any dropped prop before accepting) | All 5 variant colors (`default`/`secondary`/`outline`/`ghost`/`link`) and 4 sizes stay exactly as today — do **not** adopt the upstream registry's `bg-primary`-based default or its new `destructive` variant/`xs` size unless a future phase explicitly asks for them |
| `badge` | C (all 9) + A (radius, n/a — badge is already `rounded-full`, untouched) | none beyond structural | `default`/`secondary`/`outline` neutral values AND all 6 custom color variants (`blue`, `green`, `amber`, `red`, `purple`, `gray`) preserved verbatim — `gray` has 3 known call sites (`notificacoes/page.tsx`, `dashboard/page.tsx`, `processos/page.tsx`), grep-verify all 3 still compile post-reconciliation |
| `dialog` | A (radius) + B (dark surface) | `rounded-none`→`rounded-lg`; `dark:bg-[#020617]`→`dark:bg-popover` (see note below) | `sr-only` "Fechar" close-button label (verbatim Portuguese text); whether to adopt the registry's new `showCloseButton` prop is **not** decided by CONTEXT.md — default to keeping the close button always-visible (today's behavior) unless a grep of call sites shows one manually renders its own close affordance inside `DialogContent` |
| `alert-dialog` | A (radius) + B (dark surface) + C (Action/Cancel button colors) | `rounded-none`→`rounded-lg`; `dark:bg-[#020617]`→`dark:bg-popover` | `AlertDialogAction`'s hardcoded `bg-neutral-900` and `AlertDialogCancel`'s hardcoded outline styling are Rule-C (same reasoning as `button` default/outline) — do not retarget either to `--primary`/`--destructive` as part of this phase; any call site that needs a destructive-red confirm button already passes its own override `className` today, unaffected by this reconciliation |
| `card` | A (radius) + B (dark surface) | `rounded-none`→`rounded-lg`; `bg-white`/`dark:bg-[#020617]`→`bg-card` (light `--card` = `oklch(1 0 0)` = white, exact match; dark `--card` = `oklch(0.205 0 0)`, a visibly lighter gray than `#020617`) | `hover:shadow-md` transition, border treatment |
| `popover` | B (dark surface) | `dark:bg-slate-950`(=`#020617`, confirmed identical to `--background` dark)→`dark:bg-popover` | border/shadow/animation classes |
| `table` | B, optional (Claude's Discretion) | `bg-neutral-50`/`dark:bg-neutral-900/30` (footer, row-hover) may optionally converge to `bg-muted`/`hover:bg-muted/50` if verified visually close enough at the checkpoint — low risk, not required | `TableCaption`/`TableHead`/`TableCell` neutral-scale text colors (Rule C — no accent tint on table chrome) |
| `sheet` | Left structurally as-is per CONTEXT.md — B, cosmetic only "se aplicável" | `bg-white`→`bg-popover` is an exact match (light `--popover` = white); `dark:bg-neutral-950` is a **third**, distinct value from both `--background` (`#020617`) and `--card`/`--popover` (`oklch(0.205 0 0)`) — Claude's Discretion whether to converge it to `bg-popover` (recommended, for consistency with `dialog`/`card`'s newly-adopted elevated surface) or leave the literal; confirm the final choice visually at the checkpoint either way | `sr-only` "Fechar" label; do not re-scaffold the file via `add sheet --overwrite`, only hand-edit the color literals |
| `input`, `textarea`, `label`, `radio-group`, `switch` | C | none — Rule-C group, same reasoning as `button` | All current neutral-scale values (border, placeholder, focus ring, checked-state fill) preserved exactly |

**Why Rule B on card/dialog/alert-dialog/popover is a real, expected change, not a bug:** confirmed by direct reading — `card.tsx`'s `dark:bg-[#020617]`, `dialog.tsx`/`alert-dialog.tsx`'s `dark:bg-[#020617]`, and `popover.tsx`'s `dark:bg-slate-950` (Tailwind `slate-950` hex is literally `#020617`) are **all four already set to the exact same value as `--background` dark**. This means, today, cards/dialogs/alert-dialogs/popovers render with **zero visual elevation contrast from the page background** in dark mode — a pre-existing flatness, not a deliberate design choice recorded anywhere in `PROJECT.md`. Adopting `--card`/`--popover` (`oklch(0.205 0 0)`, a genuinely lighter gray) is the correct, semantically-intended fix and should be treated as an expected improvement — but because it changes rendered pixels, it must be part of what the mandatory human visual checkpoint (light+dark) explicitly signs off on, not something silently applied and never re-verified.

### Tooltip copy (DSR-03 — the one real copy surface this phase owns)

Icon-only buttons across the app currently ship with **zero accessible label** (confirmed via grep: `Eye`/`Pencil`/`Trash2` row-action buttons in `clientes/page.tsx`, `processos/page.tsx`, `pareceres/page.tsx`, `documentos/page.tsx` carry no `aria-label`, no visible text, no tooltip today). Scope per CONTEXT.md: sidebar icon-only elements + row actions only — do not extend to every icon in the app.

| Icon-only element | Tooltip copy (pt-PT/pt-CV, matching existing app conventions) |
|--------------------|------------------------------------------------------------|
| `Eye` (row action: view/detail) | "Ver detalhes" |
| `Pencil` (row action: edit) | "Editar" |
| `Trash2` (row action: delete) | "Eliminar" |
| `Printer` (row action: print) | "Imprimir" |
| Sidebar footer `LogOut` icon button (`dashboard-shell.tsx:154,234`) | "Terminar sessão" |
| Mobile hamburger `Menu` toggle (`dashboard-shell.tsx:244-251`, already has `aria-label="Abrir menu"`) | Optional — already accessible via `aria-label`; add `Tooltip` only for desktop-pointer consistency if the executor finds an equivalent desktop-only icon trigger, otherwise leave as-is (it's mobile-only/touch-first, a Tooltip adds little value there) |

Every Tooltip added should pair with (or confirm the presence of) an `aria-label` on the trigger element itself — `Tooltip` alone is not a substitute for an accessible name on elements screen readers may reach outside hover/focus context; DSR-03's own text only requires the visual `Tooltip`, but pairing it with `aria-label` is the correct, low-cost accessibility completion and should not be skipped when touching these call sites anyway.

**`TooltipProvider` mount (must be added, does not exist yet):** mount once in `web/src/app/providers.tsx` (the existing single client-side providers wrapper, alongside `QueryClientProvider`/`NextThemesProvider`), with `delayDuration` **explicitly set to `700`**:

```tsx
<TooltipProvider delayDuration={700}>
  {children}
</TooltipProvider>
```

This explicit prop is required, not optional — `web/src/components/ui/tooltip.tsx:9` (installed by Phase 101) defaults `TooltipProvider`'s own `delayDuration` prop to `0` (instant), which is **not** the `700ms` CONTEXT.md decided on ("default do shadcn (700ms)"). Omitting the prop at mount time would silently ship instant tooltips instead of the decided behavior.
