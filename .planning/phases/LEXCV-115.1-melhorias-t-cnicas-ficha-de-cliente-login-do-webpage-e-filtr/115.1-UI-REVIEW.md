## Top 3 Priority Fixes

1. **Raw UUID exposed, unstyled, in the "Advogado Responsável" table column** (`web/src/app/(dashboard)/clientes/[id]/page.tsx:1278`) — Non-ADMIN users viewing a cliente's Pareceres tab see a bare 36-character UUID (e.g. `a15704e5-0bbc-4885-8db3-0e789e38c7dd`) sitting in a table cell next to human-readable status badges and dates, with zero explanation that it's an id-only fallback. This reads as broken/unfinished to a legal-practice user. **Fix:** don't render the raw id at all — render a muted placeholder (e.g. `<span className="text-slate-400 italic">Não identificável</span>`) or, better, resolve advogado names via an endpoint scoped to `pareceres:view` rather than `hasRole('ADMIN')` (the code review's own suggested proper fix) so all viewers get real names.

2. **Inconsistent messaging for the identical "advogados list unavailable" failure across 3 surfaces this same phase shipped** — `clientes/[id]/page.tsx:1278` shows a raw id with **no message at all**; `pareceres/nova/page.tsx:266-270` shows *"Não foi possível carregar a lista de advogados — pode atribuir mais tarde a partir do parecer."*; `pareceres/page.tsx:228-232` and `:307-311` show the shorter *"Lista de advogados indisponível."` — all three are the same WR-01 fix batch (commit `c4b8733`) for the same root cause (`/api/v1/admin/users` 403s for non-ADMIN roles), but a non-admin user gets three different signals depending which screen they're on. **Fix:** extract one shared copy string/component for this degraded state and reuse it at all 3 call sites.

3. **Non-privileged-role rendering was never live-verified** — `115.1-VERIFICATION.md`'s own frontmatter records `human_verification` item 6 (non-ADMIN advogado degradation) and half of item 1 (button absence for non-privileged roles) as `BLOCKED (test environment, not code)` because the seeded `assistente@lexcv.cv` password no longer matches the dev database. Both remain source-verified only — the actual rendered experience for the majority of real-world users (ADVOGADO/ASSISTENTE, not ADMIN) has not been visually confirmed for this phase. **Fix:** rotate/reset the seeded non-admin dev credentials (or document a working one) and complete the live visual pass before treating Experience Design as fully closed for this phase.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

**What matches the contract exactly (verified against `115.1-UI-SPEC.md`'s Copywriting Contract table):**
- `Novo Processo` / `Novo Parecer` — present exactly once each, verbatim (`clientes/[id]/page.tsx:1112`, `:1231`).
- Locked-field helper — *"Cliente pré-preenchido a partir da ficha de cliente — não pode ser alterado aqui."* — present verbatim, identical in both `processos/novo/page.tsx:376-378` and `pareceres/nova/page.tsx:198-200` (em-dash and accents intact).
- `Entrar` unchanged at all 4 webpage call sites; Aplicar/Limpar/Pesquisar/Limpar Filtros unchanged in Pareceres — both confirmed via `git diff 1daafb3..HEAD`.

**Findings not covered by the approved contract:**
- The UI-SPEC's Copywriting Contract table (approved 2026-07-22) lists only the locked-field helper and the 4 CTAs. It does **not** list the recovery-message copy (*"O cliente associado a este link já não está disponível. Selecione um cliente na lista abaixo ou volte à ficha do cliente."* — `processos/novo/page.tsx:371-373`, `pareceres/nova/page.tsx:193-195`) or the advogado-degradation copy discussed in Finding #2 above. All of this text was written during the post-approval code-review/live-UAT fix cycle and never routed back through a copywriting-dimension check. The copy itself reads fine in isolation; the gap is that the approved design contract no longer fully describes what's shipped.
- Minor terminology drift: *"já não está disponível"* (cliente message) vs. *"indisponível"* (advogado message) — different phrasing for the same "unavailable" concept, in copy shipped by the same fix batch.

### Pillar 2: Visuals (3/4)

**What's correct:** Both new buttons (`clientes/[id]/page.tsx:1109-1114`, `:1228-1233`) are a byte-for-byte match of the locked reference pattern at `:1380-1383` (`variant="outline" size="sm"` + `Plus`) — confirmed via direct comparison, not just parameter inspection. Correctly de-emphasized vs. the bold list-page CTA style, exactly as the contract mandates. The header row renders independent of the tab's own loading/empty state (only gated on RBAC), which is good synergy with the empty-state copy ("Nenhum processo associado a este cliente.") — a user landing on an empty tab has an immediate, visible path to create one. No new icon-only buttons were introduced (all new buttons carry visible text), so no missing-aria-label risk. Área 2's 4 call sites are visually unchanged (confirmed byte-identical diff apart from the `href` line). Área 3's `Select→NativeSelect` swap matches the documented, intentional visual delta (native OS dropdown, unchanged height/focus-ring) with no unintended regressions.

**What's not:** The raw-UUID fallback described in Top Fix #1 is a genuine, visible defect in the shipped table — a 36-character opaque string with no visual treatment (no monospace, no truncation, no muted/italic styling to signal "this is a fallback"), sitting in a column otherwise populated with clean human names. It's the one place this phase's own new/touched code produces something that looks unfinished.

**Minor, pre-existing-but-visible-here inconsistency (not a regression introduced by this phase, but real on this page today):** the "Filtros" panel's Estado/Advogado/Cliente fields (`pareceres/page.tsx:202-249`) still use bare `<div>` micro-labels with no `htmlFor`/`id`, while the sibling "Pesquisa Avançada" panel's Cliente/Advogado/Estado fields (same page, same 3 field types) now have proper `Label htmlFor` + `NativeSelect id` pairing (`:280-327`) as a result of this phase's own bonus a11y fix. The UI-SPEC explicitly scoped the recommendation to the Pesquisa Avançada panel only (mirroring Processos, which has the same asymmetry), so this isn't a phase defect — but it does mean the same page now visibly treats two structurally-identical field trios differently.

### Pillar 3: Color (4/4)

Confirmed via `git diff 1daafb3..HEAD` (not whole-file grep, to avoid conflating pre-existing usage with this phase's actual delta): zero `text-primary`/`bg-primary`/`border-primary` and zero new `blue-*` class introduced by any of the 9 files' diffs. The Área 3 `Input` overrides' `focus-visible:ring-blue-500` (`pareceres/page.tsx:275,340,350`) is a byte-for-byte carry-over of the class the raw `<input>` already had before conversion — not a new accent introduction, confirmed by the diff hunk showing the old raw-input className string already contained it. The two new `variant="outline"` buttons use `Button`'s neutral base classes (`border-neutral-200 bg-white ... dark:border-neutral-800 dark:bg-neutral-950`, confirmed in `web/src/components/ui/button.tsx:14-15`) — no accent color anywhere on them, matching the contract's explicit "Accent explicitly NOT used" declaration. `#020617` hardcoded hex appears once per touched file, but it is the established app-wide dark-surface token already used identically dozens of times elsewhere (not a new introduction by this phase).

### Pillar 4: Typography (4/4)

Confirmed via diff inspection: every new string in this phase's delta reuses an already-in-use size/weight pair — `text-sm text-red-600` (error/recovery messages, matches the existing `clientes.isError` pattern exactly), `text-sm text-slate-500 dark:text-slate-400` (locked-field helper, matches existing muted-copy convention), `text-xs text-slate-500 dark:text-slate-400` (advogado-unavailable notes in `pareceres/page.tsx`), and the `Button size="sm"` default (`text-xs`/`font-medium`, inherited unmodified from `button.tsx:21`) for both new CTAs. No new size or weight token was introduced anywhere in the 9-file diff — the UI-SPEC's own claim ("No new font sizes are introduced") holds up under direct verification.

### Pillar 5: Spacing (4/4)

The new `<div className="space-y-2">` wrapper (`clientes/[id]/page.tsx:1106`, `:1225`) produces an 8px header-to-card gap, matching the contract's declared `sm` token exactly — verified structurally: when `canCreate*` is false the div has a single child (no phantom gap), when true the button row and Card get exactly one 8px gap. Área 3's conversion preserves the pre-existing `p-4`/`gap-4`/`gap-3` container spacing untouched (confirmed via diff — no spacing classes appear in the Task 1/Task 2 diff hunks at all, only primitive swaps). No new arbitrary bracket spacing value (`[...px]`/`[...rem]`) appears anywhere in the 9-file diff; the `text-[11px]`/`text-[10px]` micro-label sizes visible in whole-file greps all predate this phase and are untouched by it.

### Pillar 6: Experience Design (3/4)

**Genuine strength:** this phase demonstrates unusually rigorous state coverage for its "locked cliente field" pattern — loading (`clientes.isPending` → "A carregar..."), error (`clientes.isError`), not-found/recovery (`lockedClienteMissing`/`lockedClienteMissingUnresolved`, added across 3 review rounds), and a real runtime race (RHF `watch()` on an uncontrolled field never observing a browser-only visual fallback) that was caught only by live UAT and fixed same-day (commit `ccd1b80`). Submit-in-flight states use `Loader2` spinners with "A criar..."/"A guardar..." copy consistently. This is materially more defensive than a typical phase of this size.

**Why not 4/4:** (a) the advogado-degradation UX is inconsistent across 3 surfaces (detailed in Copywriting/Top Fix #2) — the *same* anticipated failure mode gets 3 different treatments, one of which (raw UUID, no message) is materially worse than the other two; (b) per `115.1-VERIFICATION.md`'s own frontmatter, 2 of 6 `human_verification` items remain `BLOCKED`/source-verified-only — specifically the actual rendered experience for non-privileged roles (button absence + advogado degradation) was never confirmed in a live browser session, only traced through source. Given Experience Design is specifically about verified state/interaction coverage, an admitted, still-open gap in verifying the majority-of-users code path keeps this below a clean pass.
