### Warnings

#### WR-01: "Cliente já não está disponível" recovery message never clears once the user picks a valid replacement

**File:** `web/src/app/(dashboard)/processos/novo/page.tsx:122-126,333-337,347-355`
**Also affects:** `web/src/app/(dashboard)/pareceres/nova/page.tsx:89-93,156-160,170-178` (identical pattern)

**Issue:**

The most recent fix (WR-01 round 2, commit `4b13f96`) correctly re-enables the locked `<NativeSelect>` and shows a red recovery message once `lockedClienteId` is confirmed absent from the loaded `clientes.data`:

```tsx
// processos/novo/page.tsx:122-126
const lockedClienteMissing =
  Boolean(lockedClienteId) &&
  !clientes.isPending &&
  !clientes.isError &&
  !clientes.data?.some((c) => c.id === lockedClienteId);
```

```tsx
// processos/novo/page.tsx:333-337 (disabled) and 347-355 (message)
disabled={
  clientes.isPending ||
  clientes.isError ||
  (Boolean(lockedClienteId) && !lockedClienteMissing)
}
...
{lockedClienteMissing ? (
  <p className="text-sm text-red-600">
    O cliente associado a este link já não está disponível. Selecione um cliente na lista abaixo ou volte à ficha do cliente.
  </p>
) : lockedClienteId ? (
  <p className="text-sm text-slate-500 dark:text-slate-400">
    Cliente pré-preenchido a partir da ficha de cliente — não pode ser alterado aqui.
  </p>
) : null}
```

`lockedClienteMissing` is derived only from `lockedClienteId` (the immutable URL search param — nothing in either component ever clears or rewrites it) and the `clientes` query's own state (`isPending`/`isError`/`data`). None of those four inputs change when the user interacts with the now-enabled `<select>` and picks a replacement client — `register("cliente_id")` is an *uncontrolled* RHF field, so choosing an option mutates only the DOM node's `.value`, not `lockedClienteId` or `clientes.data`. Concretely: once `lockedClienteMissing` becomes `true` on a given mount, it is mathematically impossible for it to become `false` again for the rest of that mount's lifetime — every one of its four conjuncts is either permanently fixed (`lockedClienteId`, once `clientes` has settled: `isPending`/`isError`) or already excludes the very id the user picked (the `.some((c) => c.id === lockedClienteId)` check always tests the *original*, still-missing id, never the user's new selection).

Net effect: a user who lands on `/processos/novo?clienteId=<deleted-id>` (or `/pareceres/nova?clienteId=<deleted-id>`) — precisely the scenario this fix was built for — sees the field re-enable as intended, correctly picks a valid replacement client from the dropdown, and then continues to see, indefinitely:

> "O cliente associado a este link já não está disponível. Selecione um cliente na lista abaixo ou volte à ficha do cliente."

directly beneath a `<select>` that now correctly shows their valid selection. The underlying form value is fine (Step 3 in `processos/novo/page.tsx` and the eventual POST body both read the select's live DOM value, which is correctly the user's chosen replacement), so this doesn't lose data or block submission — but a legal-practice user staring at a red "this client isn't available" error directly under their own valid, deliberate selection is a textbook trust-eroding contradiction, and is very likely to trigger hesitation, repeated re-selection, or a support ticket, in exactly the recovery flow this fix was written to make usable. The fix's own commit message ("add recovery path") is only half-delivered: the *control* recovers, the *messaging* does not.

**Fix:** Don't let `lockedClienteMissing` (as-is) drive the message directly — it must stay as-is for the `disabled` calculation (that part is correct: once truly missing, the field must never re-lock itself). Add a second, narrower condition for the message only, gated on whether the user has actually picked something yet. `pareceres/nova/page.tsx` already computes exactly this value (`clienteIdValue = form.watch("clienteId")`, used to filter the Processo dropdown) — reuse it there; add the equivalent `watch()` call in `processos/novo/page.tsx`:

```tsx
// processos/novo/page.tsx — add near the other locked-cliente derivations
const currentClienteId = intakeForm.watch("cliente_id");
const lockedClienteMissingUnresolved = lockedClienteMissing && !currentClienteId;
```
```tsx
// pareceres/nova/page.tsx — clienteIdValue already exists above; just derive from it
const lockedClienteMissingUnresolved = lockedClienteMissing && !clienteIdValue;
```
and in both files' JSX:
```tsx
{lockedClienteMissingUnresolved ? (
  <p className="text-sm text-red-600">
    O cliente associado a este link já não está disponível. Selecione um cliente na lista abaixo ou volte à ficha do cliente.
  </p>
) : lockedClienteId && !lockedClienteMissing ? (
  <p className="text-sm text-slate-500 dark:text-slate-400">
    Cliente pré-preenchido a partir da ficha de cliente — não pode ser alterado aqui.
  </p>
) : null}
```
(note the second branch also gains `&& !lockedClienteMissing`, so the "não pode ser alterado" copy — which is equally wrong once the field has genuinely recovered and become editable — doesn't reappear once the red message clears). Leave the `disabled={...}` expression exactly as-is; it must keep reading the original `lockedClienteMissing`, not the new `*Unresolved` variant, or the field will re-disable itself the instant the user picks a valid replacement.

#### IN-01: Conflict-check match links still omit `encodeURIComponent` (carried over, not yet fixed)

**File:** `web/src/app/(dashboard)/processos/novo/page.tsx:581-590`
**Issue:** Raised in the first review iteration and explicitly excluded from every fix pass since (`fix_scope: critical_warning`). Still present, unchanged, at its current line numbers:
```tsx
<Link
  href={
    match.entidadeTipo === "cliente"
      ? `/clientes/${match.entidadeId}`
      : `/processos/${processoId}`
  }
  className="text-xs text-blue-600 hover:underline shrink-0"
>
  Ver registo
</Link>
```
Every other dynamic link in these reviewed files wraps route params with `encodeURIComponent` (including both of this phase's own new links in `clientes/[id]/page.tsx`). Low practical risk since `entidadeId`/`processoId` are backend-generated, tenant-scoped UUIDs, not free-form user input.
**Fix:** `` `/clientes/${encodeURIComponent(match.entidadeId)}` `` / `` `/processos/${encodeURIComponent(processoId ?? "")}` ``.
