## Cross-Phase Integration Findings

### BLOCKER 1 — Mandatory NIF field silently overwritten by legacy documento_numero
**Requirement:** CLI-05
**Files:** `web/src/app/(dashboard)/clientes/novo/page.tsx:90-106`, `web/src/app/(dashboard)/clientes/[id]/editar/page.tsx:181-202`

Both forms retain pre-milestone "NIF sync" logic (`if (values.documento_tipo === "NIF" && values.documento_numero) { payload.nif = values.documento_numero; }`) that runs *after* the payload is built from the new dedicated, Zod-validated `nif` field. If a user fills the mandatory NIF input and also selects "NIF" in the legacy "Tipo de Documento" dropdown with a different "Número do Documento", the validated NIF is silently discarded in favor of the unvalidated legacy value. This is a reachable, user-facing data-integrity defect directly contradicting CLI-05's guarantee.

### BLOCKER 2 — CLI-05 not enforced server-side
**Requirement:** CLI-05
**Files:** `backend/src/main/java/com/lexcv/controllers/ResourceController.java:220,259`, `backend/src/main/java/com/lexcv/models/Cliente.java:35`

`createCliente`/`updateCliente` accept `@RequestBody Cliente` with no `@Valid`; `Cliente.nif` has no `@NotBlank`/`@Pattern`/`nullable=false`. NIF validity is a browser-only guarantee — any direct API caller can persist an invalid/missing NIF.

### WARNING — Raw enum value shown instead of translated label
**Requirement:** CLI-09, CLI-11 (partial)
**Files:** `web/src/app/(dashboard)/clientes/[id]/page.tsx:210`, `web/src/app/(dashboard)/clientes/[id]/ficha/page.tsx:184`

`documento_tipo` renders as literal "REG_COMERCIAL" instead of "Registo Comercial" on the detail page and printed ficha. Non-blocking but inconsistent with the milestone's UX-label work elsewhere, and inappropriate on a printable legal document.

## Confirmed Clean

- Zero remaining `dados_tipo`/`DadosTipo` references anywhere in `backend/` or `web/` (Phase 70 + 71-02 cleanup fully complete).
- REG_COMERCIAL wired end-to-end (backend enum → seed data → frontend type → both form selects → payload → persistence) aside from the cosmetic display warning above.
- Both create and edit E2E flows are structurally wired (form → API → backend → detail page) — only data-correctness for the NIF field is broken, not the wiring itself.

## Recommendation

Gap closure recommended before completing the milestone: this is the core requirement (CLI-05) of a milestone literally named "Melhoria Gestão de Clientes" whose stated goal includes simplifying client identification — shipping with a silent data-corruption path in that exact mechanism undermines the milestone's purpose. Both fixes are small and well-scoped:
1. Remove the now-redundant legacy NIF-sync block from both forms (the dedicated `nif` field is the sole source of truth per CLI-05/CLI-06).
2. Add `@NotBlank`/`@Pattern(regexp = "^\\d{9}$")` to `Cliente.nif` and `@Valid` to both controller endpoints.
