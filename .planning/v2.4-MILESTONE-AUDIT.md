# Milestone v2.4 "Ficha de Cliente" — Audit Report

**Audited:** 2026-06-30
**Status:** ⚠ GAPS FOUND
**Score:** 9/19 requirements satisfied (10 unsatisfied/partial)

## Summary

All 4 phases (57, 58, 59, 60) passed their individual goal verification, security audit, and code review gates. However, the milestone-level integration check uncovered a **systemic field-naming contract mismatch** between the backend (Spring Boot, default Jackson camelCase serialization, no naming-strategy override anywhere in `backend/`) and the frontend (TypeScript types and page reads/writes using snake_case for nearly every field introduced in this milestone).

This bug was invisible to phase-level verification because:
- Phase 57's verification was a human-run curl test directly against the backend API — it confirmed the backend behavior in isolation, never traced the frontend's actual JSON key reads.
- Phases 58–60's verifications confirmed the *presence* of UI code (badges, conditional sections, form fields) via direct file reads and grep, and confirmed `pnpm build`/`tsc --noEmit` succeed — but TypeScript's structural typing doesn't catch "the key exists in the type but is always undefined at runtime because the real API response uses a different key." Build success and field reachability were mistaken for end-to-end data flow.

A second, independent finding: the two new Phase 59 endpoints (`GET /clientes/{id}/advogados`, `GET /clientes/{id}/administrativos`) return raw `User` JPA entities, including the bcrypt `passwordHash` field (no `@JsonIgnore`), leaking credential hashes to any user with `clientes:view` permission.

## What Works

- Backend logic for all 4 phases is correct: CLI-0001 generation, tenant isolation on all 11 new endpoints, procuração upload/download/delete, advogados/administrativos CRUD, JSON column persistence for intake lists.
- `PUT /clientes/{id}` correctly accepts and persists all new fields when sent in the (correct) camelCase shape the editar/intake forms already use for the *write* path — the **write-side honorários/documentos/deslocações round-trip is fully correct**, just invisible on the read side.
- Advogados/administrativos display in the ficha page works end-to-end (their field names happen to already match between frontend and backend).
- Tipo/avençado (single-word fields) work correctly — unaffected by the casing bug.
- Print mechanics (FICH-02): `window.print()`, `@media print`, A4 `@page` sizing all function correctly, independent of the data bugs.
- All security gates passed cleanly (13/13 + 7/7 threats closed across phases 59/60) — the password-hash leak was not part of either threat register, a genuine miss in scope, not a registered-then-ignored risk.

## Critical Gaps (Blockers)

10 of 19 requirements are unsatisfied or partial, all traceable to one of two root causes:

1. **Field-naming mismatch** (affects PERF-02, PART-01, EMP-01, PROC-02, INT-01, INT-04, INT-05, INT-07, FICH-01) — see `gaps.integration[0]` above for the full mechanism.
2. **Password hash leak** (affects data exposure on INT-02/INT-03's underlying endpoints, not the requirement's functional behavior, but is a hard security blocker).

## Recommended Remediation

This is a well-scoped, mechanical fix — not a redesign:

1. Add `spring.jackson.property-naming-strategy: SNAKE_CASE` to `backend/src/main/resources/application.yml` (aligns the backend with the frontend's existing snake_case convention, which is already correct for most other fields in the app).
2. Fix `DadosTipo.java`: rename `cargoRepresentante` → `cargo` (or update frontend to match) to remove the residual name mismatch.
3. Add `@JsonIgnore` to `User.passwordHash`.
4. Re-run `mvn -DskipTests package` + `pnpm build`, then manually re-verify the 5 broken E2E flows listed in `gaps.flows` against live JSON responses (not just code presence).
5. Re-run phase-level VERIFICATION for 57, 58, 59, 60 with explicit JSON-shape tracing (request/response key names), not just code-presence checks.
