# Milestone v2.5 Audit: Módulo de Parecer Jurídico

## Summary

All 4 phases (61-64) passed individual verification with 0 open Critical/Warning findings after code review fix iterations (Phase 61: 2 iterations; Phase 62: 1; Phase 63: 1; Phase 64: 1). Backend-to-backend cross-phase wiring is solid — entity chains, tenant isolation, RBAC scope consistency, and audit-log coverage all check out with no blockers at that layer.

**One systemic, milestone-wide finding: this milestone shipped backend-only.** No frontend UI exists for the parecer module. This was a **deliberate, explicit decision** made and accepted during `/gsd:autonomous`'s smart-discuss step for all 4 phases (each phase's `*-CONTEXT.md` states "Esta fase entrega apenas API backend — sem rota `/pareceres` no frontend ainda"), not a planning oversight. However, `REQUIREMENTS.md` phrases nearly every requirement as "Utilizador pode..." (User can...), which — taken literally — is not yet true for an actual end user of the LexCV web app. It is true only for a direct API caller.

## Cross-Phase Integration

**Connected:** 13/17 requirements fully wired end-to-end at the backend layer.
**Wiring verified:** Phase 63's `/aprovar`/`/entregar` correctly reference `ParecerVersao` rows created by Phase 62. Phase 64's `pesquisar()` correctly joins `t_parecer_versao`. All 12 endpoints carry `@PreAuthorize` matching the `pareceres:view/create/edit/manage` scope convention seeded in Phase 61. Tenant isolation is enforced consistently across every new entity and endpoint added in Phases 62-64. All 5 audit-log write points (create, atribuir, versão-criar, aprovar, entregar) are present and correctly source `autorId`/`tenantId` from `SecurityContext`.

**Gap (non-blocking):** `versaoFinalId` is set correctly by `/entregar` but only surfaced as a raw field in generic JSON responses — no dedicated "parecer entregue" summary/view exists. Affects PARC-09 (warning, not blocker — the API contract is sound; no UI consumes it yet regardless).

**Missing layer (systemic, not a wiring bug):** 0 of 12 `/api/v1/pareceres/*` endpoints have a frontend consumer. No `web/src/app/(dashboard)/pareceres/` route, no `use-pareceres*.ts` hooks, no forms. This is consistent across the entire milestone — every phase deliberately scoped itself as backend-only.

## E2E Flow

**Backend chain (verified working):** solicitação criar → atribuir advogado → criar versões sucessivas → aprovar (opcional) → entregar → pesquisar/auditar. All 5 transition points chain correctly through repository lookups with tenant + parent-ownership guards.

**Product-level flow (not yet possible):** A user cannot click through the LexCV web app to create, track, or deliver a parecer — there is no UI entry point. This is the expected state of a backend-only milestone.

## Nyquist Compliance

No VALIDATION.md files exist for phases 61-64 (Nyquist validation was skipped per plan-phase's no-research path — `research_enabled: false` and no `--research` flag was used for any of the 4 phases). This is consistent, expected behavior for well-understood CRUD phases, not a gap.

## Scope Note (for milestone owner decision)

This finding is presented as `tech_debt`, not `gaps_found`, because:
1. Every phase passed its own goal-backward verification — the goal each phase set for itself (documented in ROADMAP.md + confirmed via interactive discuss) was fully achieved.
2. The backend-only scope was a **locked, user-approved decision**, repeated identically across 4 separate discuss sessions, not a silent omission.
3. No requirement is technically "unsatisfied" — every one has a working, tested, reviewed backend implementation.

However, the practical value delivered to an actual LexCV user is currently **zero** — nothing in this milestone is usable through the product yet. The REQUIREMENTS.md wording ("Utilizador pode...") implies otherwise. Two paths forward:

**A. Complete milestone v2.5 as backend-only, plan a v2.6 "Módulo de Parecer Jurídico — UI" milestone** for the frontend layer (recommended — keeps this milestone's git history clean and matches how prior milestones like v2.2 Document Storage split backend/frontend across versions).

**B. Insert a frontend phase (65) into this milestone before completing**, delaying completion but delivering an end-to-end usable feature in one milestone.
