# Phase 128 — UI Design Contract

> Visual and interaction contract for a new **read-only** "Auditoria" tab inside `web/src/app/(dashboard)/settings/page.tsx` (Definições), consulting the RBAC events written by Phase 127's write paths. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Recap (from CONTEXT.md / ROADMAP.md / REQUIREMENTS.md)

- Audience: a law-office administrator (`rbac:manage`), the same audience and same gate as Phase 127's `RbacTab`. Customer-facing.
- The screen must answer one concrete question fast (CONTEXT.md Specific Ideas): **"quem deu a esta pessoa acesso a X, e quando?"** A reverse-chronological list with no way to narrow it fails that test — AUDT-01/02/03 require filtering by target user and by role at minimum, plus paging (Decision 5: "o registo cresce sem limite").
- Events read as **human sentences in PT-CV** ("Maria Silva retirou o papel Advogado a João Pires"), never as raw `acao`/`entidade_tipo` codes. This is a deliberate correction against the existing analog (`processos/[id]/page.tsx:2360-2369`, the closest UI precedent), which renders `entry.acao` as a literal-code `Badge` (e.g. `"transicao_estado"`) — that pattern is the thing this spec exists to avoid repeating.
- **Read-only by construction (AUDT-04).** No edit, delete, or "clear log" affordance anywhere on this screen, not even disabled/hidden-behind-a-flag. See the dedicated Read-Only Guarantee section below.
- Lives inside Definições as a new tab in the existing tab strip (`settings/page.tsx:79` `TabId` union, `:109-170` tab strip), not a new route — matches CONTEXT.md's Integration Point ("nova secção ou separador de consulta").
- Out of scope this phase: export (Out of Scope in REQUIREMENTS.md), a unified processos+RBAC history screen (Deferred Idea).

## Read-Only Guarantee (AUDT-04) — binding on the implementer

This screen renders **query results only**. The following are explicitly **forbidden** anywhere on this tab, including in a disabled or hidden state:

- No edit affordance on any row (no pencil icon, no inline-editable field, no dialog that would `PUT`/`PATCH` an audit entry).
- No delete affordance on any row or on the list as a whole (no trash icon, no "limpar registo", no bulk-select-and-delete).
- No `DropdownMenu`/kebab menu on a row — unlike `RbacTab`'s role rows (`127-UI-SPEC.md` §7), an audit row has **no actions menu at all**. Its only interactive surface is the two filter controls and the pager above the list.
- The "Limpar filtros" button (§ Screen Structure) resets the **filter state**, not the log — it must not be visually or semantically confusable with a "clear log" action. Its label and icon (`X`, ghost variant) match the existing "Limpar filtros" convention already shipped in `notificacoes/page.tsx:210-213`, which resets that screen's filters for the exact same reason.
- The frontend must not call, import, or reference any mutation hook against the audit endpoint. `use-admin.ts`'s new hook for this screen (§ Data Contract Assumptions) is a `useQuery` only — no `useMutation` is added for audit entries, ever, in this file.

## Screen Structure

### Focal point

**The sentence list is the primary content.** An administrator opens this tab already holding a question ("who gave X access, and when?") — the two filters above the list exist to let them answer it without reading the whole log, and the pager exists so the list never becomes unusably long. Nothing on this screen competes visually with reading a row.

### 1. New tab in the Definições strip

Add `"auditoria"` to the `TabId` union (`settings/page.tsx:79`) and a new tab button, gated by the **same** boolean already computed for the RBAC tab — `hasRbacManage` (`can.manage("rbac")`, `settings/page.tsx:94`) — per Decision 5 (CONTEXT.md): the query endpoint sits under `rbac:manage`, the same authority that governs the write side, so the tab's visibility gate must match it exactly, not introduce a separate `audit:view`-style permission this milestone never defines.

```tsx
{hasRbacManage && (
  <button
    onClick={() => setActiveTab("auditoria")}
    className={`flex items-center gap-2 px-4 py-2.5 border-b-2 text-sm font-medium transition-all ${activeTab === "auditoria"
        ? "border-blue-600 text-blue-600 dark:border-blue-500 dark:text-blue-400"
        : "border-transparent text-slate-500 hover:text-slate-700 dark:text-slate-400 dark:hover:text-slate-200"
      }`}
  >
    <History className="h-4 w-4" />
    Auditoria
  </button>
)}
```

Placed immediately after the "Controlo de Acesso (RBAC)" tab button (`settings/page.tsx:145-156`), before "Notificações" — grouping the two `rbac:manage`-gated tabs together. Tab panel rendering follows the exact same `{activeTab === "auditoria" && hasRbacManage && (...)}` pattern already used for every other conditional tab (`settings/page.tsx:186-202`).

### 2. `AuditoriaTab` component — Filtros card + Resultados card + pager

**Page size: 20 rows**, sent as `size: 20`, matching the literal value `notificacoes/page.tsx` already uses. Changing either filter resets to the first page. An empty page past the end (for example after entries are filtered out) shows the empty state, never a blank card.

Structure reused **verbatim in shape** from `notificacoes/page.tsx` (`:121-273`) — the closest existing precedent in this codebase for "filterable, server-paginated, read-only list inside a settings-adjacent screen":

```
<div className="space-y-6">

      │   novamente." (text-sm text-red-600)
```

Filter state resets `page` to 0 on change (same clamp-on-shrink and reset-on-filter-change pattern as `notificacoes/page.tsx:80-107`, generalized to two filters — `utilizadorAlvoId` and `papel` — instead of one).

### 3. Audit row — human sentence, not a code

```tsx
<div className="flex items-start gap-3 py-3 border-b border-slate-100 dark:border-slate-800">
  <span className="text-xs text-slate-500 dark:text-slate-400 w-40 shrink-0 pt-0.5">
    {formatDateTime(entry.timestamp)}
  </span>
  <div className="flex-1 min-w-0 space-y-1">
    <p className="text-sm text-slate-900 dark:text-slate-100">
      {auditoriaEventoToSentence(entry)}
    </p>
    {entry.permissoesAdicionadas?.length || entry.permissoesRemovidas?.length ? (
      <p className="text-xs text-slate-500 dark:text-slate-400">
        {entry.permissoesAdicionadas?.length ? `Acrescentou: ${entry.permissoesAdicionadas.join(", ")}` : null}
        {entry.permissoesAdicionadas?.length && entry.permissoesRemovidas?.length ? " · " : null}
        {entry.permissoesRemovidas?.length ? `Retirou: ${entry.permissoesRemovidas.join(", ")}` : null}
      </p>
    ) : null}
  </div>
  <Badge variant="outline" className="shrink-0">
    {entry.categoria === "papel" ? "Papel" : "Atribuição"}
  </Badge>
</div>
```

`formatDateTime` reused verbatim from `processos/[id]/page.tsx:190-195` (`toLocaleString("pt-CV")`).

`auditoriaEventoToSentence` is a **new** pure function in a **new** file `web/src/lib/auditoria-rbac.ts`, following the exact `*ToLabel(value): string` convention already established for domain-code→PT-CV-copy mapping in this codebase (`lib/tipo-decisao.ts:5-13`, `lib/origem-processo.ts:3-11`) — a `Record`-keyed switch, not inline JSX conditionals in the page component. Sentence templates (actor and target names rendered `font-semibold`, per Typography):

| Event category (proposed, see Data Contract Assumptions) | PT-CV sentence template |
|---|---|
| Papel criado | "**{autor}** criou o papel **{papel}**." |
| Papel renomeado | "**{autor}** renomeou o papel **{nomeAntigo}** para **{nomeNovo}**." |
| Papel apagado | "**{autor}** apagou o papel **{papel}**." |
| Permissões de um papel alteradas | "**{autor}** alterou as permissões do papel **{papel}**." (detail sub-line above carries the added/removed list) |
| Papel atribuído a um utilizador | "**{autor}** atribuiu o papel **{papel}** a **{alvo}**." |
| Papel retirado a um utilizador | "**{autor}** retirou o papel **{papel}** a **{alvo}**." — this is the literal example from CONTEXT.md's Specific Ideas |
| Papel retirado por eliminação do utilizador (Decision 3) | "**{autor}** retirou o papel **{papel}** a **{alvo}** — utilizador eliminado." |
| Papel atribuído no provisionamento do escritório (Decision 4, conditional — only if the executor implements this event) | "A plataforma atribuiu o papel **{papel}** a **{alvo}** na criação do escritório." — `autor` here is a system actor, not a person; phrased without a person-subject accordingly |

**Null-name fallback (binding).** `auditoriaEventoToSentence` must never render `null`, `undefined` or a raw id. Events written by this phase always carry the snapshotted names, so a null name only occurs for data written outside this phase's path. When it happens, `{autor}` renders as **"um administrador removido"** and `{alvo}` as **"um utilizador removido"**, in the same weight as a real name. `{papel}` likewise falls back to **"um papel removido"**.

A sentence template this table does not cover must not silently fall back to printing a raw `acao` string — `auditoriaEventoToSentence` should throw or return a clearly-marked "evento desconhecido" placeholder in development, so a future new `acao` value is caught at the mapping function rather than leaking a code onto this screen (the exact failure this spec exists to prevent).

### 4. Two-column filter layout, matching `notificacoes/page.tsx:140` exactly

`CardContent className="grid gap-4 sm:grid-cols-2"` — identical breakpoint and gap to the reused precedent, not invented.

## Data Contract Assumptions This UI-SPEC Imposes On The API

Flagged to the planner as **assumptions for the backend design, not asserted facts** — CONTEXT.md leaves the exact `acao`/`entidade_tipo` values and the shape of `detalhe` to the executor's discretion. What follows is what the frontend in §3 needs in order to build a sentence and to filter, phrased as requirements the backend read endpoint must satisfy, however it names its internal `acao` codes:

| Field (per resolved entry) | Type | Load-bearing for |
|---|---|---|
| `id` | number | React key |
| `timestamp` | ISO datetime string | Row ordering, timestamp column |
| `categoria` | `"papel" \| "atribuicao"` (or equivalent, resolved server-side from `entidade_tipo`) | Category `Badge` (§3), lets the frontend pick the right sentence template family without parsing raw `acao` strings itself |
| `autorNome` | string, **snapshotted into `detalhe` at write time** (the actor's display name only — `User.nome`, never email). Read-time resolution from `autor_id` via the `resolveAutorNome` pattern (`ResourceController.java:148-152`) is NOT sufficient on its own: `deleteUser` is a hard delete (`AdminController.java:570-593`), so an actor who is later deleted would resolve to `null` and the log would forget who acted — the one fact an accountability log exists to keep. | Sentence subject |
| `alvoNome` | string, present only on `atribuicao`-category entries, **snapshotted into `detalhe` at write time** (display name only, never email), with `entidade_id` still carrying the user id. Same reason as `autorNome`: the target of a removal is often deleted afterwards, and that is exactly the person an investigation is about. | Sentence object, and the field the "Utilizador alvo" filter matches against server-side |
| `papelNome` | string (from `detalhe`, since Decision 2 says `detalhe` stores role names as configuration) | Sentence subject/object for every papel-related template, and the field the "Papel" filter matches against |
| `nomeAntigo` / `nomeNovo` | string, present only on rename events | Rename sentence template |
| `permissoesAdicionadas` / `permissoesRemovidas` | string[] (permission labels or keys, from `detalhe`) | Permission-change sentence's detail sub-line (AUDT-01's "o que mudou") |

**Filtering.** `utilizadorAlvoId` (matched server-side against the resolved target user, not client-side against a fetched page) and `papel` (matched server-side by name, exact match) are both requested as query parameters on the paginated read endpoint, consistent with Decision 5's "tem de ser paginado" requirement — filtering must happen before pagination, not after, or the page-size/filter combination would silently under-fill or empty a page.

**Known limitation to record, not solve, this phase:** the "Papel" filter's option list is sourced from the office's **currently live** roles (`useOfficeRbac().papeis`, the same query `RbacTab` already uses), for simplicity. A role later renamed keeps its old name in already-written audit sentences (the log is immutable, per AUDT-04), but the filter dropdown only offers the role's *current* name — an event about a role's *former* name is still visible in the unfiltered list, just not reachable via this specific filter control until/unless a future phase adds a "distinct historical role names" endpoint. This is recorded as a known, accepted v1 gap, not asserted as solved.

**Pagination envelope** — reused verbatim from the existing `NotificacoesPageResponse` shape (`types/notificacoes.ts:32-38`), the only precedent for a paginated read endpoint already in this codebase:

```ts
interface AuditoriaRbacPageResponse {
  content: AuditoriaRbacEntry[];
  totalElements: number;
  totalPages: number;
  page: number;
  size: number;
}
```

**Endpoint path (recommendation, not a decision):** `GET /admin/rbac/audit?page&size&utilizadorAlvoId&papel`, nested under the existing `/admin/rbac` prefix (`AdminController`), gated `hasAuthority('rbac:manage')` per Decision 5. The planner may place this differently (e.g. a new controller) as long as the gate and the tenant-scoping (AUDT-03) hold.

**Hook location** (per CONTEXT.md Integration Points, explicit): a new `useOfficeRbacAuditoria(filters)` query hook in `web/src/hooks/use-admin.ts`, following the exact `useQuery` shape of `useOfficeRbac` (`use-admin.ts:70-79`) and the filter/pagination query-key convention of `useNotificacoes` (`hooks/use-notificacoes.ts:21-40`). No `useEffect` — filters are plain `useState`, refetch happens automatically through the TanStack Query key, matching every other list hook in this codebase.

## Open Discretion Notes (Claude's Discretion, recorded per `<design_contract_questions>`)

1. **New tab vs. a sub-section inside the existing RBAC tab.** Chosen: a new top-level "Auditoria" tab, gated identically to "Controlo de Acesso (RBAC)". Reasoning: the RBAC tab is already a dense editing surface (matrix + create panel + two dialogs, per `127-UI-SPEC.md`); a filterable, paginated, read-only log is a different task shape (consult, not edit) and a different visual rhythm (a scrolling sentence list vs. a fixed matrix). Keeping them as siblings in the tab strip, both gated by the same authority, mirrors how "Gestão de Utilizadores" and "Controlo de Acesso" are already two separate tabs behind two related-but-distinct gates rather than one overloaded screen.
2. **Sentence composition on the frontend (`lib/auditoria-rbac.ts`) vs. backend-composed prose.** Chosen: frontend composition from resolved structured fields, mirroring the established `*ToLabel` lib convention already used for `tipoDecisaoToLabel`/`origemProcessoToLabel`. Reasoning: copy iteration (wording, punctuation, PT-CV phrasing) is cheaper to correct in a small frontend pure function than in Java string-building, and this keeps the backend's job limited to resolving ids to names — which it must do anyway for `alvoNome`/`autorNome` — rather than also owning sentence grammar.
3. **Role filter as a plain `<select>` vs. `Combobox`.** Chosen: plain `<select>`, matching the `notificacoes/page.tsx` categoria-filter precedent, because an office's role list is small and closed (unlike the potentially large client/processo lists that justify `Combobox`'s search box elsewhere in this codebase). The target-user filter uses `Combobox` instead because a tenant's user list can be long enough to need search, matching the `documentos/page.tsx` precedent for the same reason.
4. **"Papel" filter sourced from live roles, not a historical-names endpoint.** Recorded as a known v1 limitation in Data Contract Assumptions rather than solved — building a "distinct role names ever seen in the log" endpoint is a bigger backend lift than this phase's scope (a single new read endpoint plus a `detalhe` column) justifies, and the unfiltered list plus the target-user filter still surface every event regardless.
5. **Provisioning-event sentence (Decision 4) included but marked conditional.** Since CONTEXT.md leaves whether provisioning is audited to the executor, the sentence template table includes a template for it so the copy contract does not need a follow-up UI-SPEC revision if the executor chooses "yes" — but it is explicitly marked conditional, not asserted as shipped.
