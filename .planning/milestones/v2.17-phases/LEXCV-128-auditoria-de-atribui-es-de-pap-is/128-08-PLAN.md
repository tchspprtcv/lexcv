Reconciliation with the UI-SPEC "Data Contract Assumptions" (which the spec itself flagged as assumptions, not facts):
  - `papel` filter by NAME → implemented as `papelId` (by id). Stronger: an event about a role that was later renamed is still found. The UI-SPEC "known limitation" about renamed roles therefore no longer applies to renames; it still applies to DELETED roles, which are absent from the dropdown.
  - `categoria` resolved server-side: as assumed.
  - `autorNome`/`alvoNome`/`papelNome` snapshotted in detalhe: as assumed. They are null only for events written outside this phase's path; for the provisioning event autorNome is null BY DESIGN (system actor).
  - `acao` is also returned, so the composer can distinguish criar/apagar/etc. inside a categoria. It maps codes through a Record and never displays them.
  - permission lists are KEYS; labels come from useOfficeRbac().data.permissoes (key → nome), falling back to the key.

Existing (web/src/hooks/use-admin.ts): OFFICE_RBAC_KEY = ["admin", "rbac"] as const; useOfficeRbac(); useAdminSaveUser(id?); useAdminDeleteUser(id);
  useSaveOfficeRbac / useCreateOfficeRole / useRenameOfficeRole / useDeleteOfficeRole already invalidate OFFICE_RBAC_KEY. TanStack prefix matching then ALSO invalidates ["admin","rbac","auditoria",...], so only the two user mutations need an explicit invalidation.
Existing lib convention: web/src/lib/tipo-decisao.ts, web/src/lib/origem-processo.ts (*ToLabel with a Record).
Pagination precedent: web/src/hooks/use-notificacoes.ts (buildNotificacoesSearch + queryKey over every filter), web/src/types/notificacoes.ts.
