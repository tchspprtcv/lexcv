## Per-Seam Verdicts

### Seam 1 -- Authority-resolution spine (Phase 126 ResolucaoPapeisService)
**Verdict: WIRED**

- JwtAuthenticationFilter.doFilterInternal calls resolucaoPapeisService.resolverNomesPapeis, resolverPermissoesEfectivas, resolverMoldeIds on every authenticated request (no caching), feeding UserPrincipal.create.
- AuthController (getMe/login/refresh/updateMe) -- all call sites of resolucaoPapeisService confirmed by grep; the one remaining principal.getRoles() read (getMe) is a read of the already-resolved principal, not a bypass.
- AdminController.createUser/updateUser write path calls resolucaoPapeisService.resolverPapeisDeEscritorio to populate tenantRoles.
- Repo-wide grep for getRoles() across backend main sources returns exactly the expected set: internal reads inside ResolucaoPapeisService/VerificacaoDerivaPapeisService/MigracaoPapeisEscritorioService plus AuthController getMe. No unaccounted site.
- PLATAFORMA_ADMIN path: ResolucaoPapeisService.usaPapeisDeEscritorio falls back to global roles whenever tenantRoles is empty -- the platform admin has zero TenantRole rows and always resolves via this fallback, failing to the safe side.
- Repo-wide grep for hasRole( in controllers shows only ONE live annotation: PlatformAdminController class gate. All other hasRole hits are comments/history. AdminController/OfficeRolesController/AuditoriaRbacController are gated by hasAuthority, never hasRole.

### Seam 2 -- Provenance vs. name (Phase 127 closing the Phase 126 debt)
**Verdict: WIRED**

- ParecerController (deliver-parecer and create-version guards) calls resolucaoPapeisService.temPapelDeMolde(principal, NOME_MOLDE_ADMIN), not a name-equality check.
- ResourceController -- same pattern for ADVOGADO/ASSISTENTE/TECNICO via temPapelDeMolde(user, ...).
- AdminController and OfficeRolesController -- all ADMIN-literal occurrences resolve to roleRepository.findByNome(ADMIN).map(Role::getId), i.e. looking up the global moldes id for a moldeId-based provenance comparison, never a TenantRole.nome/principal-role-set string comparison.
- Targeted grep for the anti-pattern (name.equals literal comparisons against ADMIN, ADVOGADO, TECNICO, ASSISTENTE on TenantRole or principal role sets) across the backend main sources returns zero matches.
- OfficeRolesController.createRole/renameRole both reject the reserved literal names (PLATAFORMA_ADMIN and its ROLE_-prefixed form) via validarNome (case-insensitive), independent of the moldeId provenance check used elsewhere -- this is a name-based guard by deliberate design (defense-in-depth for a reserved name), not a provenance regression, and is layered on top of, not instead of, the moldeId checks in updateRbac/deleteRole.

### Seam 3 -- 124-to-127 catalogue seam (reserved-permission filtering)
**Verdict: WIRED**

- AdminController.getRbac (permissoesDoCatalogo), AdminController.updateRbac (catalogoPorChave), OfficeRolesController.createRole (catalogoPorChave), and PlatformAdminController (moldes console list/create/update, 4 call sites) all resolve the permission catalogue exclusively via permissionRepository.findAllByReservadaPlataformaFalse() -- confirmed by direct grep across all four controllers; no findAll() call on PermissionRepository exists anywhere in the write or read paths.
- Cannot silently drop a permission the UI never showed -- traced the full write path: updateRbac does a full-replace per role (setPermissions call), so the frontend must submit the complete permission set per touched role. Frontend merge-local-papeis.ts initializes localPermissoes per papelId from the unfiltered papel.permissoes array returned by getRbac (the true persisted set, not filtered by catalogue/label), and mesclarEstadoLocal preserves untouched roles local edits by id (never by name) across reconciliation with fresh server payloads. Toggling one checkbox only adds/removes that one key from the Set -- it can never silently drop a permission the matrix never rendered, because that permission was already present in the Set from initialization and is never removed unless explicitly toggled. If a submitted key is genuinely reserved/unknown, updateRbac rejects with 400 (Permissao desconhecida) rather than silently dropping it.

### Seam 6 -- Phase 128 transactional coupling (audit and mutation)
**Verdict: WIRED, with one disclosed test-coverage WARNING**

- OfficeRolesController.createRole/renameRole/deleteRole and AdminController.updateRbac/createUser/updateUser/deleteUser -- all 7 handlers confirmed Transactional by direct grep.
- Every non-2xx return path in these 7 handlers routes through RecusaTransacional.recusar, which marks the current transaction rollback-only -- read the full implementation; the mechanism is sound (documented in-file: a ResponseEntity return is a normal method return from Spring perspective and would otherwise commit).
- Audit calls (registar* methods on AuditoriaRbacService) are placed strictly after the successful entity write in each handler, inside the same transactional method -- confirmed by reading all 7 call sites.
- AuditoriaRbacService methods are Transactional with MANDATORY propagation -- a refused/failed audit write cannot silently commit its own sub-transaction independent of the caller.
- One residual, honestly-disclosed coverage gap (not a wiring break) inherited from 128-VERIFICATION.md and independently re-confirmed still present at current HEAD: no dedicated runtime test proves that a thrown exception from registarAtribuicoes during provisionTenant actually rolls back the tenant, user and role writes (the MANDATORY-propagation mechanism is standard, sound Spring behavior, structurally correct, but untested end-to-end because Testcontainers/Docker is unavailable in this environment). Two related regression tests were added after the phase own verification specifically to close half of this gap (MigracaoPapeisEscritorioService non-audit is now proven; the provisionTenant propagation-on-failure test proves propagation out of the method, still not full rollback via a real transaction manager). This is a WARNING, not a BLOCKER -- the runtime mechanism is real and correctly wired, but is asserted by design and reasoning for the full-rollback case rather than by an executed integration test.

### Seam 7 -- E2E flows
**Verdict: All 3 traced flows WIRED, no break found**

(a) Provision a new office, then the admin logs in and sees/edits own roles.
PlatformAdminController (authenticated PLATAFORMA_ADMIN console) calls setupService.provisionTenant, which calls instanciarMoldesEAtribuirAdminFundador -> instanciarMoldes (copies the current moldes into the new tenant) and immediately assigns the TenantRole ADMIN to the founding admin user, inside the same transactional method, before provisionTenant returns -- this closes the documented race where a freshly-provisioned admin could have empty tenantRoles for one boot cycle. registarAtribuicoes records this with autor null (correctly not attributing the founder own assignment to the invoking platform admin). On first login, JwtAuthenticationFilter resolves via tenantRoles (already populated), reaching getRbac and seeing only its own office roles, per Seam 1/3. The separate public first-run wizard (SetupController -> initializeSystem) deliberately does not call registarAtribuicoes (no principal to attribute to) -- confirmed structurally by the class-level absence of the dependency, and by a Mockito verifyNoInteractions test.

(b) Office admin renames its own admin role, then still reaches /api/v1/admin and can still deliver a parecer.
OfficeRolesController.renameRole mutates only the role nome field -- no touch to permissions or moldeId. Reachability of /api/v1/admin/* is gated by hasAuthority checks on users:manage/rbac:manage, computed from TenantRole permissions via ResolucaoPapeisService.resolverPermissoesEfectivas, which is unaffected by the name change. Parecer delivery in ParecerController checks temPapelDeMolde(principal, NOME_MOLDE_ADMIN), which compares moldeId -- also unaffected by rename. Self-lockout is additionally impossible at the permission-editing layer because updateRbac floor-lock (superset rule plus explicit rbac:manage/users:manage presence check, keyed by moldeId-provenance protegido flag, not by name) blocks stripping those two authorities from the protected role even via hand-edited state.

(c) Office admin assigns a role to a user, the user effective permissions change, and the event appears in the Auditoria tab scoped to that office only.
AdminController.updateUser (tenantRoleIds branch) resolves ids against the caller tenant, sets the user tenantRoles, then calls auditoriaRbacService.registarAtribuicoes inside the same transactional method. On the affected user next request (no re-login needed, per the filter explicit per-request re-resolution with no memoization), JwtAuthenticationFilter re-reads tenantRoles (EAGER, same query) and produces a fresh UserPrincipal with the new permission set. AuditoriaTab (wired in settings/page.tsx behind hasRbacManage) calls useOfficeRbacAuditoria -> GET /admin/rbac/auditoria -> AuditoriaRbacController.listar, which takes tenant only from UserPrincipal (no request parameter to bypass) and AuditLogRepository.buscarEventosRbac filters by tenant_id in both the select and paired count query (native SQL, both branches). AUDT-04 immutability holds structurally: AuditLogRepository extends the bare Spring Data Repository marker interface (not JpaRepository), exposing only save and two finder methods -- no delete or update methods exist as callable Java methods anywhere in the compiled API, pinned by AuditLogImutabilidadeTest.
