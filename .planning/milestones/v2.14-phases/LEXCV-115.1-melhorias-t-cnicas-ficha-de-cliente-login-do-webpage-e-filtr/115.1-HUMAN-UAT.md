### 3. Missing-cliente recovery flow (WR-01, iter2+iter3)
expected: Field recovers (enabled + selectable) when the locked id can't be resolved; message clears once the user picks a valid replacement.
result: PASS, but only after a real fix — navigating to `?clienteId=00000000-0000-0000-0000-000000000000` showed the field correctly re-enabled, but the "cliente já não está disponível" message never rendered. Root-caused live: `cliente_id`/`clienteId` are `register()`-based uncontrolled RHF fields, and nothing ever cleared the field's RHF-internal value when the locked id was confirmed missing — the native `<select>` fell back to its empty placeholder purely as a browser-visual artifact (no matching `<option>`), while `watch()` kept returning the original stale/non-existent id, so `lockedClienteMissingUnresolved` was always false. Fixed in both `processos/novo/page.tsx` and `pareceres/nova/page.tsx` (commit `ccd1b80`) by clearing the field via `setValue(..., "")` the moment `lockedClienteMissing` flips true. Re-tested live after the fix: message now renders, and clears correctly once a valid replacement client is picked. `pnpm build` + `tsc --noEmit` + `eslint` re-confirmed clean on both files.
