### Warnings

#### WR-01: Locked "Cliente" field has no recovery path when `?clienteId=` does not resolve to any client

**File:** `web/src/app/(dashboard)/processos/novo/page.tsx:66,91,111-115,322,332-336`
**Also affects:** `web/src/app/(dashboard)/pareceres/nova/page.tsx:49,60,78-82,141,149-153` (identical pattern)

**Issue:**

The CR-01 fix correctly re-syncs the locked `cliente_id`/`clienteId` once `clientes.data` loads *and contains a matching id*:

```tsx
React.useEffect(() => {
  if (lockedClienteId && clientes.data?.some((c) => c.id === lockedClienteId)) {
    intakeForm.setValue("cliente_id", lockedClienteId, { shouldValidate: true });
  }
}, [lockedClienteId, clientes.data, intakeForm]);
```

This guard is correct for the cold-cache race it was written to fix, but it has no `else`/fallback branch: if `lockedClienteId` is well-formed but simply **not present** in `clientes.data` once the query resolves — e.g. the client was deleted, or merged away into another client via the app's own cliente-merge feature (`ResourceController`'s cliente merge, per `CLAUDE.md`'s architecture notes), between the time the "Novo Processo"/"Novo Parecer" link was generated (or bookmarked/left open in a stale tab) and the time it's clicked — the effect's `.some(...)` condition is permanently false. The `<NativeSelect>` stays `disabled={clientes.isPending || clientes.isError || Boolean(lockedClienteId)}` (`processos/novo/page.tsx:322`, `pareceres/nova/page.tsx:141`) forever, showing only the empty placeholder option, while the helper text directly underneath continues to assert:

```tsx
{lockedClienteId ? (
  <p className="text-sm text-slate-500 dark:text-slate-400">
    Cliente pré-preenchido a partir da ficha de cliente — não pode ser alterado aqui.
  </p>
) : null}
```

which is now actively false (nothing was successfully pre-filled) and misleading. There is no separate messaging path distinguishing "still loading" from "id not found" — the only error message rendered (`clientes.isError`) covers a failed *fetch*, not a *not-found* id within an otherwise-successful fetch, so this specific failure mode surfaces no explanation at all. Since the field can never be manually re-enabled by the user, the only way out is to notice the contradiction unassisted and navigate away via the unrelated "Voltar"/"Cancelar" button — there is no in-context recovery.

Notably, `clientes/[id]/page.tsx` (touched by this same phase) already establishes the correct pattern for this exact class of problem one level up — `cliente.data ? (...) : (<div>Cliente não encontrado.</div>)` — but that fallback isn't mirrored for the locked-id case in either create form.

**Fix:** Add an explicit "not found" branch once the clientes query has actually settled, and stop asserting the "não pode ser alterado" copy in that case, e.g.:
```tsx
const lockedClienteMissing =
  Boolean(lockedClienteId) &&
  !clientes.isPending &&
  !clientes.isError &&
  !clientes.data?.some((c) => c.id === lockedClienteId);
```
```tsx
{lockedClienteMissing ? (
  <p className="text-sm text-red-600">
    O cliente associado a este link já não está disponível. Volte à ficha do cliente e tente novamente.
  </p>
) : lockedClienteId ? (
  <p className="text-sm text-slate-500 dark:text-slate-400">
    Cliente pré-preenchido a partir da ficha de cliente — não pode ser alterado aqui.
  </p>
) : null}
```
and consider re-enabling the field (or providing a "limpar" affordance) when `lockedClienteMissing` is true, so the user isn't left in a dead-end disabled state.

**File:** `web/src/app/(dashboard)/processos/novo/page.tsx:562-567`
