### Summary

Reviewed the three areas of this phase: (1) RBAC-gated "Novo Processo"/"Novo Parecer" deep-link buttons on the cliente ficha plus the corresponding locked-cliente-field treatment on `/processos/novo` and `/pareceres/nova`; (2) the webpage's `getLoginUrl()` helper and its four call sites; (3) the Pareceres list page's `Select` → `NativeSelect` filter conversion.

Area 2 (webpage login redirect) and Area 3 (Pareceres filter alignment) are clean — mechanical, low-risk changes, and I found no defects in either. Area 1 has one real functional bug in the new "locked cliente field" pattern: it depends on `useForm`'s `defaultValues` matching an `<option>` that is populated from an asynchronous, un-prefetched query, with no re-sync once that query resolves. I traced this through React Hook Form's actual (minified) source rather than assuming from memory, and through the phase's own artifacts, which confirm the runtime scenario has not yet been manually exercised (`115.1-01-SUMMARY.md`: "Manual/UAT verification ... remains for the phase verifier"). I also verified the build (`pnpm build`) and lint (`pnpm exec eslint`) both pass, and used that verified-clean baseline to isolate genuinely new issues from pre-existing tech debt already logged in `115.1-01-deferred-items.md` (which I did not re-report).

Beyond the blocker, there's one pre-existing-but-relevant data-completeness gap that this phase's new "Novo Parecer" entry point makes more consequential (WR-01), and one minor pre-existing consistency nit (IN-01).

### Critical Issues

#### CR-01: Locked "Cliente" field can desync from `?clienteId=` on cold navigation, contradicting its own "cannot be changed" hint

**File:** `web/src/app/(dashboard)/processos/novo/page.tsx:65-66,91,201-203,306-324,710`
**Also affects:** `web/src/app/(dashboard)/pareceres/nova/page.tsx:48-49,60,131-143` (identical pattern)

**Issue:**

Both create forms now read `lockedClienteId` from `?clienteId=` (set by the new "Novo Processo"/"Novo Parecer" buttons added to `clientes/[id]/page.tsx`) and seed it as a **one-shot** `useForm` default:

```tsx
// processos/novo/page.tsx
const searchParams = useSearchParams();
const lockedClienteId = searchParams.get("clienteId");
...
const intakeForm = useForm<ProcessoIntakeFormValues>({
  resolver: zodResolver(processoIntakeFormSchema),
  defaultValues: { cliente_id: lockedClienteId ?? "", ... },
});
...
<NativeSelect
  id="cliente_id"
  disabled={clientes.isPending || clientes.isError || Boolean(lockedClienteId)}
  {...intakeForm.register("cliente_id")}
>
  <option value="">{clientes.isPending ? "A carregar..." : "Selecionar cliente"}</option>
  {(clientes.data ?? []).map((c) => <option key={c.id} value={c.id}>{c.nome}</option>)}
</NativeSelect>
{lockedClienteId ? <p>Cliente pré-preenchido a partir da ficha de cliente — não pode ser alterado aqui.</p> : null}
```

`clientes.data` comes from `useClientes({})`, an async, un-prefetched TanStack Query (no `prefetchQuery` exists anywhere in `web/src`). On the primary flow this phase ships — clicking "Novo Processo"/"Novo Parecer" directly from a client's own ficha (`/clientes/[id]`, which never itself calls `useClientes`) — that query is cold on first render. At the moment this `<select>` mounts, only the placeholder `<option value="">` exists; the `<option value={lockedClienteId}>` is not in the DOM yet, so there is nothing for RHF's uncontrolled-field mount to select.

I confirmed via React Hook Form's own source (`node_modules/react-hook-form/dist/index.cjs.js`, function `de`/`getFieldValue`) that `getValues()` for a plain single-select reads the **live DOM `.value`**, not a cached JS value:
```js
function de(e){const r=e.ref;return G(r)?r.files:X(r)?ue(e.refs).value:Q(r)?[...r.selectedOptions].map(...):t(r)?ne(e.refs).value:oe(c(r.value)?e.ref.value:r.value,e)}
```
Concretely provable consequence: `processos/novo/page.tsx`'s Step 3 review screen computes
```tsx
const intakeFormValues = intakeForm.getValues();
const selectedClienteName = (clientes.data ?? []).find((c) => c.id === intakeFormValues.cliente_id)?.nome ?? "";
```
and renders `{selectedClienteName || "—"}` (line 710) — on a cold-cache run, this will show **"Cliente: —"** for a process that is in fact tied to a specific client. The field is simultaneously `disabled` for the entire "locked" lifetime, so the user cannot fix it by re-selecting, while the helper text right below it insists "não pode ser alterado aqui" (pre-filled, cannot be changed) — a direct, visible contradiction. Because `cliente_id`/`clienteId` are required (`z.string().trim().min(1, ...)` in `web/src/schemas/processos.ts:10` and `web/src/schemas/pareceres.ts:14`), this can also surface as a blocking "O cliente é obrigatório" / "Selecione um cliente." validation error the user cannot resolve, since the one field that would fix it is disabled.

This is not a hypothetical: the sibling file touched by this exact phase (`clientes/[id]/page.tsx`) already demonstrates the *correct* pattern for this exact class of problem — seed `defaultValues` empty, then explicitly `form.reset(buildDefaultValues(cliente.data))` inside a `useEffect` once the async data arrives (see `clientes/[id]/page.tsx:295-301`). That re-sync step is missing from both `processos/novo/page.tsx` and `pareceres/nova/page.tsx`. The phase's own `115.1-01-SUMMARY.md` confirms this exact runtime path was never exercised: only `pnpm build`/`pnpm lint` were run; "Manual/UAT verification ... remains for the phase verifier."

**Fix:** Add an effect that re-applies the locked value once the list resolves and confirms the id exists, mirroring the established `clientes/[id]/page.tsx` pattern:

```tsx
// processos/novo/page.tsx — after `const clientes = useClientes({});`
React.useEffect(() => {
  if (lockedClienteId && clientes.data?.some((c) => c.id === lockedClienteId)) {
    intakeForm.setValue("cliente_id", lockedClienteId, { shouldValidate: true });
  }
}, [lockedClienteId, clientes.data, intakeForm]);
```
```tsx
// pareceres/nova/page.tsx — after `const clientes = useClientes({});`
React.useEffect(() => {
  if (lockedClienteId && clientes.data?.some((c) => c.id === lockedClienteId)) {
    form.setValue("clienteId", lockedClienteId, { shouldValidate: true });
  }
}, [lockedClienteId, clientes.data, form]);
```
Alternatively (more robust, avoids the timing dependency entirely), render a read-only `Input` showing the resolved client name instead of a disabled `<select>` when `lockedClienteId` is set, and pass `lockedClienteId` straight through in the submit payload instead of round-tripping it through the `<select>`'s DOM value.

Either way, this needs a real manual check (cold cache, i.e. reload before clicking "Novo Processo") before shipping — `pnpm build`/`pnpm lint` cannot catch this class of bug since it's a runtime data-timing issue, not a type or lint error.

### Warnings

#### WR-01: "Advogado Responsável" is silently blank for non-ADMIN users across all three Pareceres surfaces touched by this phase

**File:** `web/src/app/(dashboard)/clientes/[id]/page.tsx:1211-1217,1273`
**Issue:**

`ClienteParecerTab` (extended by this phase with the new `canCreatePareceres`-gated "Novo Parecer" button) resolves each row's "Advogado Responsável" via:
```tsx
const isAdmin = Boolean(permissions.data?.roles?.includes("ADMIN"));
const adminUsers = useAdminUsers({ enabled: isAdmin });
const advogados = React.useMemo(() => (adminUsers.data ?? []).filter((u) => u.roles?.includes("ADVOGADO")), [adminUsers.data]);
const advogadoNomeById = React.useMemo(() => new Map(advogados.map((u) => [u.id, u.nome] as const)), [advogados]);
...
{advogadoNomeById.get(s.advogadoId ?? "") ?? "—"}
```
`useAdminUsers` calls `GET /api/v1/admin/users` (`web/src/hooks/use-admin.ts:7-16`), which is restricted to ADMIN at the class level in the backend (`backend/src/main/java/com/lexcv/controllers/AdminController.java:24-25`: `@PreAuthorize("hasRole('ADMIN')")`). Because the fetch here is explicitly gated on `isAdmin`, **any non-ADMIN user permitted to view pareceres (e.g. an ADVOGADO with `pareceres:view`) sees "—" in every row's "Advogado Responsável" column**, even for pareceres assigned to them.

The identical root cause recurs, unmitigated, in two more places this phase's diff touches or is adjacent to:
- `web/src/app/(dashboard)/pareceres/nova/page.tsx:72`: `const adminUsers = useAdminUsers();` — called unconditionally. For a non-ADMIN creator (gated only by `pareceres:create`, not `hasRole('ADMIN')`), the `/admin/users` call 403s, `apiFetch` swallows the toast for 401/403 (`web/src/lib/api.ts:43-45`) but still leaves `adminUsers.data` undefined — so the "Advogado responsável (opcional)" dropdown on the very form this phase's new CTA routes users to only ever offers "Atribuir mais tarde." Non-admin lawyers can never assign a specific advogado responsável at creation time.
- `web/src/app/(dashboard)/pareceres/page.tsx:84`: same unconditional call — the "Advogado" filter/pesquisa dropdowns are empty and the desktop table's advogado column is unresolvable for any non-ADMIN viewer of the list page.

This predates this diff (the `isAdmin` gate and the two unconditional calls are all pre-existing lines, untouched by the phase's edits), but this phase's own new CTA (`ClienteParecerTab`'s "Novo Parecer" button) actively funnels more non-admin, permission-holding users into this exact broken path, so it's worth fixing alongside this phase rather than carrying it forward silently.

**Fix:** Resolve advogado names via an endpoint scoped to a broader permission than `hasRole('ADMIN')` (e.g. a `pareceres:view`-gated "list advogados" lookup), or at minimum degrade gracefully instead of a bare "—"/empty dropdown — e.g. fall back to rendering `s.advogadoId` (or a short id) when the friendly-name map can't be populated, so non-admin users get some signal instead of silently-missing data.

#### IN-01: Conflict-check match links omit `encodeURIComponent`, inconsistent with the rest of the codebase

**File:** `web/src/app/(dashboard)/processos/novo/page.tsx:550-559`
**Issue:** Every other dynamic link in these reviewed files consistently wraps route params with `encodeURIComponent` (e.g. `/clientes/${encodeURIComponent(id)}/ficha`, `/processos/${encodeURIComponent(p.id)}`, `/pareceres/${encodeURIComponent(s.id)}`). The conflict-check "Ver registo" link is the one exception:
```tsx
<Link href={match.entidadeTipo === "cliente" ? `/clientes/${match.entidadeId}` : `/processos/${processoId}`}>
```
Pre-existing (not touched by this diff) and low practical risk since these ids are backend-generated UUIDs, but worth aligning for consistency/defense-in-depth next time this block is touched.
**Fix:** `` `/clientes/${encodeURIComponent(match.entidadeId)}` `` / `` `/processos/${encodeURIComponent(processoId ?? "")}` ``.
