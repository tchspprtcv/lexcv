### CR-01: Locked "Cliente" field can desync from `?clienteId=` on cold navigation, contradicting its own "cannot be changed" hint

**Status:** fixed: requires human verification
**Files modified:** `web/src/app/(dashboard)/processos/novo/page.tsx`, `web/src/app/(dashboard)/pareceres/nova/page.tsx`
**Commit:** a645f38
**Applied fix:** Added a `React.useEffect` in both create forms (placed after each form's `useForm(...)` declaration) that re-applies the locked `cliente_id`/`clienteId` value via `form.setValue(..., { shouldValidate: true })` once the initially-cold, un-prefetched `useClientes({})` query resolves and confirms the id is present in the returned list — mirroring the established re-sync pattern already used in `clientes/[id]/page.tsx` (`form.reset(buildDefaultValues(...))` inside a `useEffect` keyed on the async data, lines 295-301). This closes the race between the one-shot `useForm` `defaultValues` seed and the `<option>` elements that only exist in the DOM once `clientes.data` has loaded, which previously could leave the disabled Cliente `NativeSelect` showing its empty placeholder (and Step 3's review screen rendering "Cliente: —") on a cold-cache navigation from the cliente ficha's "Novo Processo"/"Novo Parecer" buttons. Applied the review's primary suggested fix (the `useEffect` re-sync) rather than its noted alternative (swapping the locked field for a read-only `Input`), since it is the smaller, more targeted change and matches an existing codebase precedent.

**Why flagged for human verification:** the review explicitly states this is "a runtime data-timing issue, not a type or lint error" and that `pnpm build`/`pnpm lint` cannot catch it — confirmed independently: `npx tsc --noEmit` (project-wide) and `npx eslint` on both modified files pass with zero new errors/warnings (only the same pre-existing findings already logged in `115.1-01-deferred-items.md`, confirmed via exact line-number-shift arithmetic), but neither tool can exercise the actual cold-cache race condition. A manual check (hard-reload, then click "Novo Processo"/"Novo Parecer" from a cliente ficha, confirm the Cliente field/Step-3 review show the correct pre-filled client) is still needed before this is considered fully verified.

### WR-01: "Advogado Responsável" is silently blank for non-ADMIN users across all three Pareceres surfaces touched by this phase

**Status:** fixed
**Files modified:** `web/src/app/(dashboard)/clientes/[id]/page.tsx`, `web/src/app/(dashboard)/pareceres/nova/page.tsx`, `web/src/app/(dashboard)/pareceres/page.tsx`
**Commit:** c4b8733
**Applied fix:** Applied the review's "at minimum" graceful-degradation option rather than its alternative (a new, broader-permission backend endpoint), since the latter is a backend/RBAC architecture decision (new `@PreAuthorize` scope, new endpoint/DTO, cross-layer wiring) out of proportion for an automated fix to this Warning-level finding.
- `clientes/[id]/page.tsx` (`ClienteParecerTab`): the "Advogado Responsável" table cell now falls back to the raw `s.advogadoId` when `advogadoNomeById` can't resolve a friendly name (e.g. because the viewer is non-ADMIN and `useAdminUsers` was never fetched, since it's gated `{ enabled: isAdmin }`), instead of collapsing indistinguishably to "—" for both "no advogado assigned" and "name unresolvable." Mirrors the pre-existing `clienteNomeById.get(...) ?? id` idiom already used in `pareceres/page.tsx` and `pareceres/columns.tsx`.
- `pareceres/nova/page.tsx`: added a muted helper line under the "Advogado responsável (opcional)" dropdown, shown when `adminUsers.isError` (the `/admin/users` call 403s for a non-ADMIN creator, confirmed via `apiFetch`'s throw-on-non-ok behavior in `web/src/lib/api.ts`), explaining the list couldn't be loaded and that the parecer can be assigned later.
- `pareceres/page.tsx`: added the same helper line under both the quick-filter and "Pesquisa Avançada" "Advogado" dropdowns when `adminUsers.isError`.

**Adaptation note:** the review's file citation also mentioned "the desktop table's advogado column is unresolvable," but the current `pareceres/columns.tsx` has no advogado-related column definition at all (only Estado, Cliente, Prioridade, Prazo, Criado, Ações) — this part of the finding's description does not match the current code, so no change was made there; only the two confirmed-empty filter dropdowns in `pareceres/page.tsx` were addressed.

**Residual gap (not fixed, by design):** this is a frontend-only mitigation. The underlying capability gap — non-ADMIN users still cannot select/assign a specific advogado when creating or filtering pareceres, only see "Atribuir mais tarde" / an empty filter — remains, since closing it fully requires a backend endpoint scoped to something broader than `hasRole('ADMIN')`. Recommend tracking the review's primary suggested fix (a `pareceres:view`- or `pareceres:create`-scoped "list advogados" lookup) as a follow-up item for a future phase.
