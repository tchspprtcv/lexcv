## Área 1 — Criar Processo/Parecer a partir da Ficha de Cliente

**Locked by `115.1-CONTEXT.md`:** "Novo Processo" button in `ClienteProcessosTab`'s header (same visual pattern as `ClienteDocumentosEntreguesTab`'s "Adicionar" button) → navigates to `/processos/novo?clienteId={id}`. "Novo Parecer" button in `ClienteParecerTab`'s header, same pattern → `/pareceres/nova?clienteId={id}`. Both target forms read `clienteId` via `useSearchParams`, pre-select the Cliente `NativeSelect`, and lock it against editing. RBAC: `processos:create` / `pareceres:create`.

### Reference pattern (byte-for-byte source of truth)

`ClienteDocumentosEntreguesTab`'s "Adicionar" button, `clientes/[id]/page.tsx:1337-1340`:

```tsx
<Button type="button" variant="outline" size="sm" className="">
  <Plus className="h-4 w-4" />
  Adicionar
</Button>
```

This exact `variant`/`size`/icon combination is what "mesmo padrão visual" locks — **not** the bigger, bold, primary-variant "Novo Processo"/"Nova Solicitação" CTA used on the standalone `/processos` and `/pareceres` list pages (`className="font-bold ... shadow-none"`, default variant). This is a deliberate visual de-emphasis: inside a cliente's tab, "Novo Processo"/"Novo Parecer" is a secondary, contextual action, not the page's primary CTA. Do not "upgrade" it to the bolder list-page style.

### Component contract — `ClienteProcessosTab` (currently `clientes/[id]/page.tsx:1094-1163`)

The tab currently has **no header row at all** — `CardContent className="p-0 ..."` goes straight into the loading/error/empty/table conditional. Add a new sibling wrapper **above** the existing `<Card>`, not inside its `p-0` `CardContent` (keeps the Table's flush-edge rendering completely untouched — zero risk to existing markup):

```tsx
function ClienteProcessosTab({
  clienteId,
  canCreateProcessos,
}: {
  clienteId: string;
  canCreateProcessos: boolean;
}) {
  const processos = useProcessos({ cliente_id: clienteId });

  return (
    <div className="space-y-2">
      {canCreateProcessos ? (
        <div className="flex items-center justify-end">
          <Button type="button" variant="outline" size="sm" asChild>
            <Link href={`/processos/novo?clienteId=${encodeURIComponent(clienteId)}`}>
              <Plus className="h-4 w-4" />
              Novo Processo
            </Link>
          </Button>
        </div>
      ) : null}
      <Card>
        <CardContent className="p-0 bg-white dark:bg-[#020617]">
          {/* existing loading/error/empty/Table content, unchanged */}
        </CardContent>
      </Card>
    </div>
  );
}
```

Apply the identical structure to `ClienteParecerTab` (`clientes/[id]/page.tsx:1184-1249`): wrapper `<div className="space-y-2">`, conditional `canCreatePareceres`-gated header row, `<Link href={\`/pareceres/nova?clienteId=${encodeURIComponent(clienteId)}\`}>`, label "Novo Parecer".

**Why `space-y-2` (8px) and not a larger gap:** matches the declared spacing scale's `sm` token ("compact element spacing") — this is a tight header-to-content relationship, the same visual weight as the gap already used between a filter bar and its table elsewhere in the app.

**No redundant `<h4>` title:** unlike `ClienteDocumentosEntreguesTab`/Documentos-a-Tratar/Deslocações (which each need an `<h4>` because several such cards are stacked together inside one shared tab), `ClienteProcessosTab`/`ClienteParecerTab` are each the **sole** content of their own `Tabs` panel — the `TabsTrigger` itself already reads "Processos"/"Pareceres". Repeating that as an `<h4>` directly below it would be redundant. Header row is button-only, right-aligned (`justify-end`).

### RBAC wiring (mirrors the existing `canEditDocumentos` prop-drilling pattern exactly)

`ClienteDetailContent` (`clientes/[id]/page.tsx:144-149`) already derives `canViewProcessos`/`canViewPareceres`/`canEditDocumentos` once and passes them down as props. Add two siblings the same way:

```tsx
const canCreateProcessos = permissions.can.create("processos");
const canCreatePareceres = permissions.can.create("pareceres");
```

Pass as new props: `<ClienteProcessosTab clienteId={id} canCreateProcessos={canCreateProcessos} />`, `<ClienteParecerTab clienteId={id} canCreatePareceres={canCreatePareceres} />`.

**Gate on RBAC only — explicitly not on the ficha's `isEditing` toggle.** `ClienteDocumentosEntreguesTab`'s "Adicionar" button is gated `editable && canEditDocumentos` because uploading a document IS an edit to cliente-owned data. Creating a Processo/Parecer is a distinct, independently-permissioned action unrelated to whether the cliente record itself is in edit mode — gating it behind "Editar" would hide it from a user who has `processos:create` but hasn't (or can't) toggle cliente edit mode, an incorrect coupling. `canViewProcessos`/`canViewPareceres` need no separate check here — the tab itself already only renders (`clientes/[id]/page.tsx:872-890`) when the corresponding `canView*` is true, so reaching this component already implies view access.

**`/pareceres/nova` (`pareceres/nova/page.tsx:54-64/128-145`):** identical treatment — add `useSearchParams` import, read `lockedClienteId`, seed `defaultValues.clienteId`, add `Boolean(lockedClienteId)` to the `disabled` expression, same helper `<p>` below the field (same copy, same classes).

**Precedent for `useSearchParams` safety:** this exact hook is already used for query-param seeding in this codebase (`pareceres/page.tsx:4/62-79` reads `?q=`/`?_seed=` the same way) — no `Suspense` boundary or other special wiring is needed beyond what these existing client-component pages already do.

**Integration note — param name vs. field name:** the query param is `clienteId` (camelCase) at both URLs per `115.1-CONTEXT.md`. Pareceres' form field is already named `clienteId` (direct match). Processos' form field is named `cliente_id` (snake_case, per `processoIntakeFormSchema`) — the executor maps `searchParams.get("clienteId")` to the `cliente_id` default value; the URL param name itself does not change to match the field name.

**Disabled-state visual (no new styling needed):** `NativeSelect`'s wrapper already carries `has-[select:disabled]:opacity-50` and the `<select>` itself carries `disabled:pointer-events-none disabled:cursor-not-allowed` (`native-select.tsx:18/27`) — reused as-is, zero new CSS.

**Confirmed side-effect, not a new requirement:** Pareceres' "Processo (opcional)" field already reactively depends on `clienteId` (`processos = useProcessos(clienteIdValue ? { cliente_id: clienteIdValue } : {})`, `pareceres/nova/page.tsx:68-69`). Once `clienteId` is pre-filled via `defaultValues`, this dropdown populates correctly with no additional wiring.

### Explicit non-goals (Área 1)

- **"Voltar" / breadcrumb / "Cancelar" targets are unchanged.** `/processos/novo`'s "Voltar" button and breadcrumb still hard-link to `/processos` (`processos/novo/page.tsx:212/226`); `/pareceres/nova`'s "Cancelar" still hard-links to `/pareceres` (`pareceres/nova/page.tsx:114`). `115.1-CONTEXT.md` only specifies reading `clienteId`, pre-selecting, and locking the field — it does not ask for a return-to-cliente-ficha navigation flow. Do not invent one.
- **No cliente name/number in the page `<h1>` or breadcrumb.** Both forms keep their existing static "Novo Processo"/"Nova Solicitação de Parecer" headings — no "Novo Processo para {cliente}" variant.
- **No new icon.** `Plus` is already imported in `clientes/[id]/page.tsx:6` — zero new `lucide-react` imports for this area.

## Área 2 — Redirect "Entrar" do Webpage → Login do Web

**Zero visual contract.** This is a routing/environment-variable correctness fix, not a UI change. All 4 call sites keep their exact current copy, variant, size, and icon — only the computed `href` changes, and only when `NEXT_PUBLIC_WEB_APP_URL` is set (local dev); production (where it's left unset) renders byte-identical output to today.

| Call site | Current JSX (unchanged variant/copy/icon) |
|---|---|
| `site-header.tsx:48-50` (desktop) | `<Button asChild variant="secondary" className="hidden md:inline-flex"><a href="/login">Entrar</a></Button>` |
| `site-header.tsx:74-78` (mobile sheet) | `<Button asChild variant="secondary" className="mt-4"><a href="/login" onClick={...}>Entrar</a></Button>` |
| `hero-section.tsx:28-30` | `<Button asChild variant="secondary" className=""><a href="/login">Entrar</a></Button>` |
| `site-footer.tsx:12-14` | `<Button asChild size="lg" className=""><a href="/login">Entrar<ArrowRight className="h-4 w-4" /></a></Button>` |

Each `<a href="/login">` becomes `<a href={getLoginUrl()}>` (or equivalent call) — the `<Button>` wrapper, its variant/size/className, the visible text "Entrar", and `site-footer.tsx`'s trailing `ArrowRight` icon are all **untouched**.

**Helper resolution (`115.1-CONTEXT.md`'s "Claude's Discretion" item — researcher default):** following the exact one-function-per-file convention already established by `webpage/src/lib/backend-origin.ts`/`setup.ts`/`branding.ts` (each exports one `getX()` function, JSDoc explaining the fail-mode), add `webpage/src/lib/get-login-url.ts` exporting `getLoginUrl(): string`:

```ts
export function getLoginUrl(): string {
  const configured = process.env.NEXT_PUBLIC_WEB_APP_URL;
  return configured ? configured.replace(/\/+$/, "") + "/login" : "/login";
}
```

This is a pure client-safe read (unlike `backend-origin.ts`'s `getBackendOrigin()`, it does **not** throw when unset — an unset `NEXT_PUBLIC_WEB_APP_URL` is the expected, correct production case per `115.1-CONTEXT.md`, not a config error). Document `NEXT_PUBLIC_WEB_APP_URL` in `webpage/.env.example` alongside the existing `BACKEND_API_ORIGIN`/`NEXT_PUBLIC_API_BASE_PATH` entries, left empty/commented (production doesn't set it).

**No loading/error/empty state applies.** `NEXT_PUBLIC_*` variables are inlined at build time — this is a synchronous string computation, not a fetch. No new UI state of any kind is introduced by this area.

## Área 3 — Alinhamento Visual dos Filtros de Pareceres

**Locked by `115.1-CONTEXT.md`:** "Filtros" panel: `Select`/`SelectItem` → `NativeSelect`. "Pesquisa Avançada" panel: raw `<input>`/`<label>` → `Input`/`Label` primitives, no behavior change. Aplicar/Limpar buttons **keep their text** — icon-only conversion is explicitly out of scope (already excluded for Pareceres by Phase 115's own `115-CONTEXT.md`, reaffirmed here). Container structure (`Card > CardContent p-4 > form flex flex-wrap`) is already identical to Processos — no change. The dual "Filtros"/"Pesquisa Avançada" toggle stays — do not remove it.

Pareceres (`pareceres/page.tsx`) has **two** filter `Card`s today; `115.1-CONTEXT.md` names them separately:

1. **"Filtros" panel** — the primary `Card` (toggle buttons + Aplicar/Limpar + a collapsible `advancedOpen` grid with 3 `Select`s: Estado L204-215, Advogado L223-235, Cliente L243-255).
2. **"Pesquisa Avançada" panel** — a *separate* `Card` below (`pesquisaOpen`-gated, L264-396), unique to Pareceres (Processos has no equivalent second panel). Contains raw `<input>`/`<label>` (Pesquisar L277-284, Data Início/Fim L353-369) **and** 3 more `Select`s of its own (Cliente L292, Advogado L312, Estado L332).

### Researcher-resolved ambiguity: `Select`→`NativeSelect` applies to **both** panels (6 fields total)

`115.1-CONTEXT.md`'s bullet names only the "Filtros" panel for the `Select`→`NativeSelect` swap; the "Pesquisa Avançada" bullet is silent on `Select` (it only calls out the raw-HTML gap). Read literally, this could leave `NativeSelect` in one panel and `Select` in the other **on the same page** — directly contradicting the area's own stated goal ("alinhar o padrão visual dos filtros"). Processos, the alignment target, uses zero `Select` anywhere. The current `pareceres/page.tsx` import (`import { Select, SelectContent, SelectItem, SelectTrigger, SelectValue } from "@/components/ui/select";`) is a single block feeding all 6 fields — after full conversion it is deleted outright and replaced with `import { NativeSelect } from "@/components/ui/native-select";` (already imported at the top for other reasons is not the case here — this becomes a fresh import), which is a cleaner, more likely-intended full refactor than a mixed half-state requiring both imports simultaneously. **Decision: convert all 6 (Estado/Advogado/Cliente × 2 panels).**

**Visual delta of this swap, confirmed by direct component comparison (`select.tsx` vs `native-select.tsx`):** the focus ring color does **not** change — both already use the neutral `focus-visible:ring-ring/50` (`--ring` token), never blue. Height is unchanged (`h-9` default, `h-8` for `size="sm"`, identical in both components). The real, intended change is the **dropdown interaction pattern**: Radix's custom-styled popover-with-checkmark list becomes the browser's native OS `<select>` dropdown — exactly what "align with Processos" means, since Processos never uses the custom popover pattern.

**Mechanical event-handler change (implementation note, not a visual one):** `Select`'s `value`/`onValueChange={(v) => setX(v)}` becomes `NativeSelect`'s `value`/`onChange={(e) => setX(e.target.value)}` — same `"todos"` sentinel convention already used by every draft/pesquisa state variable, no value-shape change.

**"Filtros" panel option markup** (per field, e.g. Estado — same conversion shape for Advogado/Cliente in both panels):

```tsx
<div className="lg:col-span-4">
  <div className="text-[11px] font-bold tracking-wider uppercase text-slate-500 dark:text-slate-400">
    Estado
  </div>
  <div className="mt-2">
    <NativeSelect value={draftStatus} onChange={(e) => setDraftStatus(e.target.value)} size="default" className="w-full">
      <option value="todos">Todos</option>
      <option value="PENDENTE">Pendente</option>
      <option value="EM_ELABORACAO">Em elaboração</option>
      <option value="EM_REVISAO">Em revisão</option>
      <option value="CONCLUIDO">Concluído</option>
    </NativeSelect>
  </div>
</div>
```

The `<div className="text-[11px] font-bold tracking-wider uppercase ...">` micro-label wrapper is **already** correct in this panel (matches Processos byte-for-byte) — only the `Select` block inside it changes.

### "Pesquisa Avançada" panel — `Input`/`Label` swap

Raw `<input>`/`<label>` → shadcn primitives, **preserving the exact current visual classes via `className` override** (this bullet is a component-primitive swap, not a restyle — the panel's own label typography, `text-[11px] font-bold tracking-wider uppercase text-slate-500 dark:text-slate-400` for the 5 main labels and `text-xs font-medium text-slate-500 dark:text-slate-400` for the Data Início/Data Fim sub-labels, is unchanged):

```tsx
<Label htmlFor="pesquisa-texto" className="text-[11px] font-bold tracking-wider uppercase text-slate-500 dark:text-slate-400">
  Pesquisar
</Label>
<div className="mt-2">
  <Input
    id="pesquisa-texto"
    type="text"
    value={pesquisaTexto}
    onChange={(e) => setPesquisaTexto(e.target.value)}
    placeholder="Pesquisar por conteúdo do parecer..."
    className="bg-white dark:bg-[#020617] border-slate-300 dark:border-slate-700 focus-visible:ring-blue-500"
  />
</div>
```

Same pattern for `pesquisa-data-inicio`/`pesquisa-data-fim` (`type="date"`, same className override, `text-xs font-medium ...` `Label`).

**Visual delta of the `Input` swap (intended, matches Processos' own `Input` usage exactly):** height changes from the raw input's explicit `h-10` to `Input`'s own base `h-9` (`input.tsx:11`); border-radius now derives from the `--radius` token (`rounded-md`) instead of the raw input's implicit browser default; `shadow-sm` is added (`Input`'s base). The existing `focus-visible:ring-2 focus-visible:ring-blue-500` is **preserved** via the override className (same accent-blue ring the raw input already had — not a new color usage, a carried-over one), matching Processos' own `Input` override pattern verbatim (`processos/page.tsx:217-222`).

**Recommended, non-blocking addition — proper label association for Cliente/Advogado/Estado in this panel:** these 3 fields' `<label>` tags currently have no `htmlFor`/`id` pairing at all (`pareceres/page.tsx:288/308/328`). Since converting their sibling `Select`→`NativeSelect` (this area's own mandated change, above) gives each a real `<select>` capable of taking an `id`, and since `Label`'s entire purpose is proper `htmlFor` association, pairing them (e.g. `pesquisa-avancada-cliente`/`-advogado`/`-status`) is a near-zero-risk, zero-visual-change correctness improvement bundled into the swap already required. Recommended; not required to pass this phase — do not block on it if time-constrained.
