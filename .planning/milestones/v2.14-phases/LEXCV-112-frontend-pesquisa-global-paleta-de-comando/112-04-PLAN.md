## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL `?q=` param → filter state → rendered `<Input value>` + backend query param | An attacker can craft `/clientes?q=<payload>`; the value is reflected into an input and sent to the backend `q` filter |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-112-10 | Tampering / reflected XSS | `?q=` seeded into `draftQuery` → `<Input value={draftQuery}>` | mitigate | The value flows into a controlled React `<Input value>` (text node / attribute — React auto-escapes; no `dangerouslySetInnerHTML` anywhere on these pages). No script execution path from the reflected `q` |
| T-112-11 | Information Disclosure / injection | seeded `q` sent to GET /clientes?q= and GET /processos?q= | accept | These are the SAME existing, already-shipped server-side `q` filters the manual search box uses; the backend applies its own tenant scoping and ILIKE metacharacter escaping (Phase 111 WR-02). Seeding introduces no new query surface — only a new way to populate an existing one |
| T-112-SC | Tampering (supply chain) | package installs | accept (N/A) | Zero new dependencies (`useSearchParams` is part of the already-installed `next`). No npm install; package-legitimacy gate does not apply |
</threat_model>
