    Create `ParecerVersaoConcorrenciaIT` in package `com.lexcv.repositories` under backend/src/test/java. Reuse the exact Testcontainers wiring established in 91-01: `@DataJpaTest`, `@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)`, `@Testcontainers`, and a `static @Container @ServiceConnection PostgreSQLContainer<>("postgres:16-alpine")`. `@Autowired` `ParecerSolicitacaoRepository`, `ParecerVersaoRepository`, and `PlatformTransactionManager`.

    Test method A — lock serializes concurrent increments (the primary TEST-02 assertion):
    - Annotate this test method with `@Transactional(propagation = Propagation.NOT_SUPPORTED)` so @DataJpaTest does NOT wrap it in a single auto-rollback transaction — genuine concurrency needs two real, independently-committing transactions.
    - Persist one `ParecerSolicitacao` fixture (tenantId, clienteId, descricao) inside its own committed transaction via a `TransactionTemplate` built from the injected `PlatformTransactionManager`; capture its id.
    - Build a `Runnable` that, inside a `TransactionTemplate.execute(...)` (its own transaction), performs the createVersao sequence: `findByIdForUpdate(solicitacaoId)` (acquires the row lock), `int next = findMaxNumeroVersaoBySolicitacaoId(id).orElse(0) + 1`, then `save(ParecerVersao.builder().tenantId(...).solicitacaoId(id).numeroVersao(next).build())`.
    - Run two of these on an `ExecutorService` (2 threads). Use a `CountDownLatch` so both threads are released as simultaneously as possible to maximize contention. Collect both `Future`s and call `get()` with a bounded timeout (e.g. 20s) so a deadlock/hang fails fast rather than hanging the suite.
    - After both complete, assert via `findBySolicitacaoId(id)` that exactly TWO versions exist and their `numeroVersao` values are exactly the set {1, 2} — sequential and distinct, never a duplicate {1, 1}. This is the observable proof the PESSIMISTIC_WRITE lock (not a JVM monitor) made the increment-and-insert atomic across transactions.

    Test method B — DB unique-constraint backstop:
    - CRITICAL flush requirement: this method runs under @DataJpaTest's default ambient (rollback-only) transaction with Hibernate FlushMode.AUTO. A plain `.save()` only registers the entity in the persistence context — Hibernate DEFERS the INSERT and never sends SQL to Postgres before the assertion runs, so the unique-constraint violation would never surface and `assertThrows` would fail with "expected exception but none was thrown." To force the INSERT synchronously, use `parecerVersaoRepository.saveAndFlush(...)` for the colliding insert (technique (a) from ARCHITECTURE.md — NOT a bare `.save()`).
    - Persist a solicitacao fixture (via `parecerSolicitacaoRepository.save(...)`) plus a first `ParecerVersao` with numeroVersao=1 using `parecerVersaoRepository.saveAndFlush(...)` so the first row is actually written to the container DB before the collision attempt.
    - Attempt to persist a second `ParecerVersao` for the SAME solicitacaoId with numeroVersao=1 via `parecerVersaoRepository.saveAndFlush(...)` (again, NOT a bare `.save()`), and assert — with the `saveAndFlush` call INSIDE the `assertThrows(...)` lambda so the flush fires synchronously — that it throws `org.springframework.dao.DataIntegrityViolationException` (Hibernate surfaces the Postgres unique-violation this way). This proves the `(solicitacao_id, numero_versao)` constraint declared on the @Entity actually materializes in the container schema (via ddl-auto=create-drop from 91-01) and fires as the defense-in-depth backstop.

    Use fresh random ids / distinct solicitacoes per test method so committed rows from one method never interfere with the other (the container is shared static across methods and NOT_SUPPORTED means real commits persist).
