# Phase 73.1: Code Review Report

## Summary

This phase correctly closes both audit BLOCKERs it set out to close. The frontend NIF-sync overwrite is fully removed from both `novo/page.tsx` and `editar/page.tsx` — `payload.nif` is now sourced exclusively from the Zod-validated `...values` spread, with no post-build overwrite anywhere in either onSubmit function. The backend adds `@NotBlank` + `@Pattern(regexp = "^\\d{9}$")` to `Cliente.nif`, adds `@Valid` to both `createCliente` and `updateCliente` `@RequestBody Cliente` parameters, and removes the server-side sync in both methods; `updateCliente` now applies `nif` unconditionally from `payload.getNif()`. `createCliente` correctly enforces the field for both Particular and Empresa client types (the Bean Validation constraint on `Cliente.nif` is type-agnostic). The edit form's `form.reset()` correctly seeds `nif: cliente.data.nif ?? ""`, so a legacy record with a null NIF loads an empty string that Zod's `.regex()` will reject on save, forcing correction through the `updateCliente` `@Valid` path — that specific flow was verified end-to-end and works correctly.

However, the fix has an unaddressed side effect the plan's threat model did not consider: Jakarta/Hibernate Bean Validation is not scoped to `@Valid @RequestBody` — by default (`javax.persistence.validation.mode=AUTO`, unmodified anywhere in this codebase, and `spring-boot-starter-validation`/Hibernate Validator is on the classpath) it also fires on every JPA `persist`/`merge` via `@PrePersist`/`@PreUpdate` listeners, i.e. on every `clienteRepository.save(...)` call site — not just the two annotated endpoints. Three other call sites in `ResourceController.java` (`uploadProcuracao`, `deleteProcuracao`, `mergeClientes`) fetch an existing `Cliente` from the DB and call `clienteRepository.save(cliente)` without ever touching the `nif` field. If that fetched entity has a null or non-9-digit `nif` (fully plausible: the audit itself documents that pre-fix code silently persisted unvalidated NIFs for an unknown period), the new `@Pattern`/`@NotBlank` constraints will now throw `ConstraintViolationException` at save time in those unrelated endpoints. There is zero `@ExceptionHandler`/`@ControllerAdvice` anywhere in the backend, so this surfaces as an unhandled HTTP 500 — meaning any tenant with even one pre-existing invalid-NIF client can no longer upload/delete a procuração or merge that client, with an opaque failure. This is a real regression introduced by this phase, not a pre-existing condition, because the constraint that triggers it did not exist before this phase.

Additionally, no automated tests were added despite the plan's `<behavior>` section specifying four explicit HTTP-status scenarios (missing NIF → 400, malformed NIF → 400, valid NIF → 201/200, never re-derived from documentoNumero) — the SUMMARY only reports a passing `mvn -DskipTests package`/`tsc --noEmit`, i.e. compilation, not behavioral verification.

## Critical Issues

### CR-01: New Bean Validation on Cliente.nif breaks unrelated save() paths for pre-existing invalid-NIF records

**File:** `backend/src/main/java/com/lexcv/models/Cliente.java:37-39`
**Also affects:** `backend/src/main/java/com/lexcv/controllers/ResourceController.java:320` (`uploadProcuracao`), `:370` (`deleteProcuracao`), `:755` (`mergeClientes`)

**Issue:** `@NotBlank`/`@Pattern(regexp = "^\\d{9}$")` on `Cliente.nif` is JPA-lifecycle-scoped, not just `@Valid @RequestBody`-scoped. Hibernate Validator's default `javax.persistence.validation.mode=AUTO` (not overridden anywhere in `application.yml`/`application-prod.yml`) means these constraints are also checked via `@PrePersist`/`@PreUpdate` on every `EntityManager` persist/merge — i.e. on every `clienteRepository.save(...)` call, not only the two endpoints this phase intentionally hardened.

Three other controller methods fetch an existing `Cliente` and call `clienteRepository.save(cliente)` without setting `nif`:
- `uploadProcuracao` (line 320) — sets `procuracaoKey`, then saves
- `deleteProcuracao` (line 370) — clears `procuracaoKey`, then saves
- `mergeClientes` (line 755) — merges non-blank fields from `secondary` into `primary`, then saves `primary`

If the fetched `Cliente` entity carries a `nif` that is `null`, blank, or not exactly 9 digits — a realistic state given the exact pre-fix bug this phase is closing (the audit confirms the legacy sync path silently persisted unvalidated `documento_numero` values into `nif` for an unknown period before this fix), or any client created before Phase 71 introduced the dedicated `nif` field at all — the `save()` call in any of these three endpoints will now throw `ConstraintViolationException`. There is no `@ExceptionHandler`/`@ControllerAdvice` anywhere in the backend (confirmed via search — zero matches), so this exception is unhandled and surfaces as an opaque HTTP 500, silently blocking procuração upload/delete and client merge for any tenant with even one legacy invalid-NIF client. This is a functional regression introduced by this phase (the constraint didn't exist before), and it directly contradicts one of the plan's own `must_haves` truths — "Existing seed data ... still loads without validation failure" implicitly assumed only seed data mattered, but any *non-seed* pre-existing record with an invalid NIF is now broken for unrelated operations.

**Fix:** Either (a) scope the validation to the request-body boundary only, by removing the constraint from the entity and instead validating on a separate create/update DTO (larger refactor, likely out of this phase's stated scope), or (b) at minimum, add a global `@RestControllerAdvice` handling `ConstraintViolationException` so JPA-level violations degrade to a structured 400/409 instead of an unhandled 500, and separately run a one-time data-remediation pass (or backfill migration) to normalize/flag existing invalid-NIF clients before this constraint ships to production. A minimal in-scope mitigation:

```java
@RestControllerAdvice
public class ValidationExceptionHandler {
    @ExceptionHandler(jakarta.validation.ConstraintViolationException.class)
    public ResponseEntity<?> handleConstraintViolation(jakarta.validation.ConstraintViolationException ex) {
        return ResponseEntity.badRequest().body(Map.of("message", "Dados inválidos: " + ex.getMessage()));
    }
}
```
This does not fix the underlying data problem but prevents an unhandled 500 from leaking a stack trace and blocking unrelated procuração/merge operations. Confirm with the plan owner whether pre-existing invalid-NIF records exist in production before shipping this constraint as JPA-scoped.

## Warnings

### WR-01: No automated tests cover the four behavior scenarios the plan specified

**File:** `backend/src/main/java/com/lexcv/controllers/ResourceController.java:220,256`; `backend/src/main/java/com/lexcv/models/Cliente.java:37-39`
**Issue:** The plan's Task 2 `<behavior>` block specifies four explicit, testable scenarios (POST with null/blank nif → 400; POST with `"12345"`/`"12345678a"` → 400; POST with valid 9-digit nif → 201 with nif persisted as-is; PUT with invalid nif → 400, valid nif → 200 persisted as-is, never re-derived from documentoNumero). None of these are covered by an automated test — `backend/src/test/` has zero references to `nif`. The SUMMARY's verification evidence is limited to `mvn -DskipTests package` (compiles) and `tsc --noEmit` (typechecks), which proves the code compiles but not that the validation behaves as specified. A regression in the regex escaping, the `@Valid` placement, or the unconditional `cliente.setNif(payload.getNif())` line would not be caught by any existing test suite.
**Fix:** Add a `@WebMvcTest`/`@SpringBootTest` integration test (or at minimum a focused `MockMvc` test) asserting: POST with missing/invalid nif → 400; POST with valid nif → 201; PUT with invalid nif on an existing client → 400 (payload unchanged in DB); PUT with valid nif → 200 and persisted value matches request body exactly (not re-derived from `documentoNumero` even when `documentoTipo=NIF` and `documentoNumero` differs from `nif`).

### WR-02: `updateCliente`'s partial-update pattern is inconsistent for `nif` vs. other optional fields, silently allowing null-out on well-formed requests that omit `nif`

**File:** `backend/src/main/java/com/lexcv/controllers/ResourceController.java:262-281`
**Issue:** Most fields in `updateCliente` are unconditionally overwritten from `payload` (`cliente.setNome(payload.getNome())`, `cliente.setEmail(payload.getEmail())`, etc.), while a few (`descricaoCaso`, `documentosEntregues`, `documentosATratar`, `deslocacoes`, `honorariosPropostos`) are guarded with `if (payload.getX() != null)` to preserve existing values when the client omits them. `nif` was moved to the unconditional-overwrite group by this phase, which is correct per the plan's intent ("never re-derived from documentoNumero") — but it means any `PUT` request that constructs its `Cliente` payload without an explicit `nif` field (e.g. a partial-update API client, or a future frontend feature that PATCHes a subset of fields) will send `nif: null`, and because `@Valid` on the JSON body triggers `@NotBlank` before the field even reaches `cliente.setNif(...)`, this specific case is now correctly rejected with 400 at the `@Valid` boundary — so functionally this is fine for `updateCliente`'s own endpoint. This is flagged as a warning only because the pattern the endpoint now uses (unconditional overwrite for `nif`, conditional preserve for other fields) makes the endpoint harder to reason about and is undocumented — a future maintainer extending `updateCliente` might miss that `nif` behaves differently from adjacent fields for a reason that isn't self-evident from reading the method alone.
**Fix:** No functional change required for this phase's scope. Consider a one-line comment above `cliente.setNif(payload.getNif())` explaining why it's unconditional (i.e., "nif is always required in the payload — @Valid rejects null/blank before this line executes"), to prevent a future edit from "fixing" it into a conditional pattern that would silently reopen the BLOCKER 1/2 defect class.

## Info

### IN-01: `nif` is not trimmed server-side before Bean Validation

**File:** `backend/src/main/java/com/lexcv/models/Cliente.java:37-39`
**Issue:** The frontend Zod schema trims `nif` (`z.string().trim().regex(...)`) before validation, but `Cliente.nif`'s `@Pattern(regexp = "^\\d{9}$")` has no equivalent server-side trim. A direct API caller (the exact threat this phase's `T-73.1-01` targets) sending `nif: " 123456789 "` (with leading/trailing whitespace) would fail `@Pattern` with a 400, which is arguably correct/strict behavior, but is inconsistent with the browser path where Zod's `.trim()` would silently normalize the same input and successfully submit `"123456789"`. This is a minor inconsistency between the two validation layers described as needing to "mirror" each other in the plan's interfaces block, not a security or data-integrity issue (fails closed, doesn't corrupt data), so it's Info rather than Warning.
**Fix:** If exact parity between the two validation layers is desired, add a `@PrePersist`/setter-level trim, or accept the intentional stricter server-side behavior as-is (recommended — failing closed on untrimmed input from non-browser callers is arguably safer and requires no code change).
