# Phase 101 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 101 is infrastructure-only. Its own ROADMAP.md goal is explicit: *"sem que nenhuma página visível mude ainda"* (no visible page changes). All 5 success criteria (FND-01 to FND-08) are technical facts — a file exists, a component compiles, a version is pinned, a `<Toaster/>` is mounted — none describe new user-facing screens or interactions. Per CONTEXT.md, this entire phase is Claude's Discretion at the implementation level, with the technical shape already locked by `.planning/research/STACK.md` / `ARCHITECTURE.md` / `PITFALLS.md`.

Consequently, most sections below (Spacing, Typography, Copywriting) are marked **not exercised this phase** rather than filled with a freshly-invented contract — inventing one here would misrepresent what Phase 101 actually ships and would give the checker/executor false confidence about pages that are not being touched. The one section that IS load-bearing and visually observable is **Color** — specifically the exact `--background`/`--foreground`/`--radius`/`--primary` values that must be *restored/set deliberately* after `shadcn init` runs, per the CONTEXT.md decision and the corruption risk documented in PITFALLS.md Pitfall 1 and ARCHITECTURE.md Pattern 3. Registry Safety is also load-bearing (which primitives get added, from where).

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (official CLI, package `shadcn`, current `4.13.0`) |
| Preset | `init -b radix` — explicit `-b radix` flag required in both `web/` and `webpage/` (the CLI's July-2026 default is now Base UI; plain `init` would silently scaffold an incompatible second primitives library). Non-interactive flags: `style=new-york` (legacy value, resolves internally to `radix-vega`), `baseColor=neutral`, `cssVariables=true`, `iconLibrary=lucide` |
| Component library | Radix (`@radix-ui/react-*`, matches the 9 packages already installed and every one of the 14 hand-rolled `web/src/components/ui/*` files). `shadcn migrate radix` is run in this phase per CONTEXT.md decision, unifying existing scoped-package imports and all newly-added components onto the single `radix-ui` package — no dual-package bridge state left at phase close |
| Icon library | `lucide-react` (already installed, `^0.543.0`) — unchanged |
| Font | Geist Sans (`--font-geist-sans`, body/UI) + Geist Mono (`--font-geist-mono`, monospace), wired via `next/font/google` in `web/src/app/layout.tsx` — **unchanged by this phase**, not touched by `shadcn init` |

`components.json` does not exist yet in either app (verified: absent in `web/` and `webpage/`). `webpage/components.json` is created by manually copying `web/`'s resolved answers per FND-02 / CONTEXT.md decision — never a second independent `init` wizard run, to prevent the two apps' design systems forking silently (PITFALLS.md Pitfall 5).

`components.json` `tailwind.config` field must be left as `""` (empty string) in both apps — both are Tailwind v4 CSS-first with zero `tailwind.config.{js,ts}` today (verified absent); do not let a stray config file get created during this phase (PITFALLS.md Pitfall 4).

## Typography

**Not exercised this phase** — no page visibly changes, so no new typography is introduced or enforced here. The values below document the existing baseline (verified in `web/src/app/(dashboard)/dashboard/page.tsx` and sibling pages) that Phase 101 leaves untouched — they are descriptive of current state, not a new rule this phase's executor must apply anywhere.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`) | 600 semibold | 1.4 |
| Heading | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display | 30px (`text-3xl`) | 600 semibold | 1.2 |

Known pre-existing debt (not addressed by Phase 101): several pages use `font-bold` (700) ad hoc for KPI numbers and uppercase labels (e.g. `dashboard/page.tsx` lines 91/140/147/167/187/207) alongside `font-semibold`/`font-medium` elsewhere — a real inconsistency already flagged in `.planning/research/PITFALLS.md`. Phase 101 does not touch any of these files; consolidating to the 2-weight system above is left to whichever future module UI-SPEC first touches that page's typography.

## Color

This is the one section with real visual-identity impact this phase. All values below are sourced directly from the current codebase (`web/src/app/globals.css`, `web/src/components/ui/{card,badge}.tsx`, `web/src/components/shared/dashboard-shell.tsx`) — not invented — and must survive `shadcn init`'s token merge unchanged, per CONTEXT.md's explicit decision and PITFALLS.md Pitfall 1 (silent theme corruption via a second `:root`/`.dark` block).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background: #f8fafc` (light) / `#020617` (dark); `--foreground: #020617` (light) / `#f8fafc` (dark) | Page background + default text. **Must be restored to these exact hex values immediately after `shadcn init`** if the CLI's `neutral` baseColor overwrites them — verify via `git diff` before committing the init, in both `web/` and `webpage/` |
| Secondary (30%) | `bg-slate-950` / `dark:bg-[#04091a]` (sidebar), `bg-slate-900/50` (nav/user-card surface), `bg-white` / `dark:bg-neutral-950` (cards, per `card.tsx`) | Sidebar (`dashboard-shell.tsx`), topbar nav surfaces, card backgrounds. Not touched by this phase's token merge — these remain hardcoded Tailwind literals in `components/shared/*` until a future module phase deliberately migrates them to semantic tokens (`--card`, `--sidebar` etc.), per ARCHITECTURE.md's "normalize only when a module phase explicitly touches that file" rule |
| Accent (10%) | `--primary: #2563eb` (Tailwind `blue-600`) light / `#3b82f6` (`blue-500`)-toned dark-mode variants | Reserved **exclusively** for: (1) the active sidebar nav item's left-edge indicator + icon + label tint (`bg-blue-600/10 text-blue-400`, `dashboard-shell.tsx` lines 98-99/117-118/178-179/197-198), (2) the user-avatar gradient badge (`from-blue-600 to-indigo-500`, line 288), (3) the search-input focus ring (`focus-visible:ring-blue-500/50`, line 257) and its icon focus-within tint (line 254), (4) positive/urgent KPI number highlighting on the Dashboard. **Not** used for the default `Button` variant, which is `bg-neutral-900`/`bg-neutral-100` (neutral, not blue) — do not conflate the two |
| Destructive | `#dc2626` (Tailwind `red-600`) light / `#f87171` (`red-400`)-toned dark | Destructive actions only: delete/remove confirmations, "red" badge variant, overdue/vencido KPI figures (`dashboard/page.tsx` line 187) |
| `--radius` | `0rem` | Sharp corners — deliberate institutional identity, hardcoded today as `rounded-none` throughout `card.tsx`, `dialog.tsx`, badge usages, and Dashboard KPI tiles. **Must be set explicitly to `0rem`** immediately after `init`; the CLI's `nova`/`new-york` preset otherwise defaults to a non-zero rounded value that would visually clash the moment any newly-added primitive (Select, Tabs, etc.) renders next to the existing sharp-cornered components |

Additional shadcn semantic tokens introduced by `init` (`--secondary`, `--muted`, `--accent` [shadcn's own internal hover/subtle-surface token — distinct from the "Accent (10%)" institutional-blue role above, do not conflate the two], `--border`, `--input`, `--ring`, `--card`, `--popover`) are **net-new** — no existing value collides with them, so the CLI's `neutral` baseColor defaults are acceptable to keep as-is for this phase (per ARCHITECTURE.md: "every other token it adds is net-new"). Confirm exactly one `:root` block and one `.dark` block exists after merge (not two silently overlapping ones) before committing.

Accent reserved for (explicit, closed list — never "all interactive elements"):
- Sidebar active-nav-item indicator, icon tint, and label tint
- User-avatar gradient badge (topbar + sidebar footer)
- Global search input's focus ring and focus-within icon tint
- Dashboard KPI positive/urgent number highlighting
