# Phase 106 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 106 covers AGD-36 (`Calendar` in the criar/editar Evento date fields) and AGD-37 (`Select` in the Agenda list filters). Per `106-CONTEXT.md`'s locked scope, the actual files are the `Evento` module — `agenda/novo/page.tsx`, `agenda/[id]/editar/page.tsx` (forms) and `agenda/page.tsx` (filters + monthly grid). The existing monthly calendar grid (CSS grid + drag-and-drop, `buildMonthGrid`/`dayKey`/`cursorMonth`) is **not touched** — it is a distinct visual surface from the filters/forms this phase changes. The literal "Prazo" entity's Dialog in `processos/[id]/page.tsx` is explicitly out of scope (different module, deferred).

**This is the first `Popover`+`Calendar` composition in the project.** Unlike Phase 105's `NativeSelect`/`Select` work (which inherited an established visual precedent), there is no prior date-picker composition anywhere in the codebase to diff against — `popover.tsx` has so far only wrapped a notifications list and a `RadioGroup`. This UI-SPEC is therefore more prescriptive than usual on the composition's exact anatomy (trigger button variant/size/icon, placeholder copy, popover content sizing, locale) precisely because there is no existing pattern to inherit and no room for silent per-call-site drift between the 3 places this composition is used.

**Verified-against-source findings (load-bearing for planning):**

1. **`agenda/[id]/editar/page.tsx` has no `recurrenceRule`/`recurrenceEndDate` fields in its JSX today**, even though its `defaultValues`/`form.reset` carry `recurrenceRule: "NONE"` and the loaded `evento.data` may contain both. Only `agenda/novo/page.tsx` renders the Recorrência `<select>` and the conditional `recurrenceEndDate` date input. This means the **date-only** Popover+Calendar+Button composition (for `recurrenceEndDate`) is needed in exactly **one** file (`agenda/novo/page.tsx`); the **date+time** composition (for `dataInicio`/`dataFim`) is needed in **both** form files (`agenda/novo/page.tsx`, `agenda/[id]/editar/page.tsx`). Do not add recurrence fields to the editar form as a side effect of this phase — building an edit path for recurrence is explicitly deferred (`106-CONTEXT.md` Deferred Ideas).
2. **`Select` (Radix combobox) is already imported exactly once in the codebase** (`web/src/components/shared/data-table/data-table-pagination.tsx`, the rows-per-page control) — confirmed by grep. This phase is the first use of `Select` for an actual **list filter**, matching `106-CONTEXT.md`'s framing. `select.tsx` itself needs no changes; its shipped defaults (`SelectTrigger` `h-9`/`data-[size=sm]:h-8`, `text-sm`, `border-input`) are used as-is.
3. **The 3 Agenda list filters (`agenda/page.tsx`) use hardcoded `text-xs font-bold text-slate-700` (12px/700) native `<select>`s** inside a non-tokenized filter bar (`bg-white dark:bg-[#020617] border-slate-300`, `rounded-none`). `font-bold` (700) here is a 3rd type weight beyond this project's declared 400/600 pair — migrating to `SelectTrigger`'s own shipped `text-sm` (14px, unweighted → inherits Body's 400) is a deliberate typography-contract correction, not a preservation requirement, matching the precedent Phase 105 set for allowing primitive defaults to override legacy off-scale styling during migration. The filter bar's own container styling (`bg-white dark:bg-[#020617]`, `rounded-none`, `slate-*` borders) is **not** retokenized by this phase — out of scope, same treatment Phase 104/105 gave to page-level chrome surrounding a migrated primitive.
4. **Radix `Select.Item` cannot take an empty-string `value`** (throws at runtime) — unlike the native `<select><option value="">`. The Processo filter's current sentinel is literally `""` (`useState<string>("")`, compared as `selectedProcessoId === ""`/`e.processoId !== selectedProcessoId`). This must change to a non-empty sentinel (e.g. `"todos"`, matching the Categoria/Estado filters' existing `"todos"` convention) as part of the `Select` migration — a required logic change, not just a template swap, called out here so the planner doesn't scope it as a pure JSX swap.
5. **`agenda/novo/page.tsx` and `agenda/[id]/editar/page.tsx` both declare a local `const selectClassName = "..."`** (identical string, `rounded-md border-neutral-200 ... focus-visible:ring-neutral-950`) for their ~7 combined native `<select>`s (4 in novo: Processo/Categoria/Prioridade/Recorrência; 3 in editar: Processo/Categoria/Prioridade). `106-CONTEXT.md` locks these onto `NativeSelect` (not `Select`), matching Phase 105's RHF-bound-field convention. Both `selectClassName` declarations are eliminated entirely, same as Phase 105's CLP-03 resolution.
6. **`Button` (`h-9`, size `default`) and `Input` (`h-9`) already share the same height** in this codebase (confirmed by direct read of `button.tsx`/`input.tsx`) — the new date-picker trigger `Button` and its adjacent `Input type="time"` will align in height with zero extra work, and also match `NativeSelect`'s own `h-9` default on the same form row (Prioridade sits in the same `grid gap-4 sm:grid-cols-3` row as Início/Fim).
7. **Neither `date-fns`'s `format()`/`locale` helpers nor `lucide-react`'s `CalendarIcon` are imported anywhere in the codebase today** (confirmed by grep) — this phase introduces both for the first time. `date-fns` (`^4.4.0`) is already an installed, Phase-101-vetted dependency (a `react-day-picker` peer dependency), so importing `date-fns/locale`'s `pt` export is not a new-package decision, just a first real use of an existing one.

## Visual Hierarchy

No new page-level focal point. The monthly calendar grid (`agenda/page.tsx`'s `Card`/CSS grid) is visually untouched and remains the dominant element on the Agenda list page. The 3 filter `<select>`s sit in the exact same filter-bar slot they occupy today (`bg-white dark:bg-[#020617] border-slate-200 p-4` row, unchanged container) — only the control itself changes from native `<select>` to `SelectTrigger`, same position, same `flex flex-col gap-1.5` label-above-control layout, same fixed per-filter widths. In the two form pages, each date-only/date+time field keeps its existing grid slot (`grid gap-4 sm:grid-cols-3` for Prioridade/Início/Fim; standalone `space-y-2` block for `recurrenceEndDate`) — the `Input type="datetime-local"`/`type="date"` is replaced by a composed control (trigger `Button` [+ `Input type="time"` for the two datetime fields]) of equivalent height (`h-9`), not a redesign of the form's layout rhythm.

## Component Inventory

### AGD-36 — Popover + Calendar (Date Picker composition, first in project)

Two distinct variants are needed — do not conflate them:

| Variant | Fields | Files |
|---------|--------|-------|
| Date-only | `recurrenceEndDate` | `agenda/novo/page.tsx` only (see Scope note #1 — editar has no recurrence UI today) |
| Date + time | `dataInicio`, `dataFim` | `agenda/novo/page.tsx` **and** `agenda/[id]/editar/page.tsx` |

**Shared trigger anatomy (both variants):**

| Element | Value |
|---------|-------|
| Trigger | `<PopoverTrigger asChild><Button type="button" variant="outline" className="w-full justify-start text-left font-normal">` — `variant="outline"` matches the existing "Voltar"/"Cancelar" buttons already on both pages, giving the new composed control the same visual weight as other secondary actions on the same screen |
| Leading icon | `<CalendarIcon className="mr-2 h-4 w-4 opacity-50" />` (new import, first use in project) |
| Label — has value | `date.toLocaleDateString("pt-CV", { day: "2-digit", month: "2-digit", year: "numeric" })` — reuses the exact `Intl`/`toLocaleDateString("pt-CV", …)` pattern already used elsewhere on `agenda/page.tsx` (`monthLabel`, event time chips) instead of introducing a `date-fns` `format()` call site; keeps one locale-formatting idiom project-wide |
| Label — empty | `"Selecionar data"` in `text-muted-foreground` (matches the shadcn official Date Picker demo's `!date && "text-muted-foreground"` idiom) |
| Trigger size | Default (`h-9`) — matches `Input`'s own `h-9` and `NativeSelect`'s own `h-9`, so the composed control lines up with sibling fields on the same row (Scope note #6) |
| Popover content | `<PopoverContent className="w-auto p-0" align="start">` — `align="start"` (not the component's own `align="end"` default) so the calendar opens under the left edge of the trigger, matching the official shadcn Date Picker pattern; `p-0` because `Calendar` supplies its own `p-3` |
| Calendar | `<Calendar mode="single" selected={fieldValueAsDate} onSelect={(d) => { ...update RHF field...; setOpen(false); }} locale={pt}` (`import { pt } from "date-fns/locale"`) `weekStartsOn={0}` `initialFocus />` |
| Close behavior | Popover closes immediately on day selection (single click = select + close), no separate "Aplicar" button — matches the official pattern's implicit UX, does not require a form submit |

**Locale requirement (new, first-of-its-kind — do not skip):** pass `locale={pt}` (`date-fns/locale`'s Portugal-Portuguese export — Cape Verde has no dedicated `date-fns` locale, `pt` is the closest available and matches this project's Portuguese domain language, per `CLAUDE.md`) so month/weekday names render in Portuguese, not react-day-picker's English default. Additionally pass `weekStartsOn={0}` explicitly — `pt`'s own default is Monday-first, but the existing monthly grid on the same page (`Dom, Seg, Ter, Qua, Qui, Sex, Sáb`) is Sunday-first; without this override the new date-picker widget would silently disagree with the monthly view's week orientation on the same screen.

**Date+time variant specifics (`dataInicio`/`dataFim`):**

| Element | Value |
|---------|-------|
| Layout | `<div className="flex gap-2"><Popover>…trigger flex-1 min-w-0…</Popover><Input type="time" className="w-24 shrink-0" value={timePart} onChange={syncTime} /></div>` inside the field's existing `space-y-2` wrapper (unchanged position in the `grid gap-4 sm:grid-cols-3` row) |
| Time input width | `w-24` (96px, on the 4px spacing scale) — fits `HH:mm` with padding |
| Sync contract | Selecting a day in `Calendar` OR changing the `time` input recomputes a single combined value and calls `form.setValue("dataInicio"/"dataFim", combined, { shouldValidate: true })` — internal wiring detail, exact helper/state shape is Claude's discretion (per `106-CONTEXT.md`), but the **visual contract is fixed**: one trigger button (date) + one native `Input type="time"` (time), side-by-side, never a single freeform text field |
| Fallback if cramped at implementation | If real rendering at `sm:` (640px) breakpoint shows the trigger label truncating unacceptably next to the time input, switch the same two elements from `flex-row` to `flex-col gap-2` inside the field's own wrapper — this does not change the outer 3-column parent grid or any sibling field's position, so it is a safe, contained fallback Claude may choose at implementation without re-opening this contract |

**Date-only variant specifics (`recurrenceEndDate`):**

Follows the shared trigger anatomy verbatim, with no adjacent time input — this is the literal shadcn official "Date Picker" pattern (`Popover`+`Button`+`Calendar`), unmodified.

**Reusability recommendation (Claude's discretion, per `106-CONTEXT.md` — recommendation, not a mandate):** because this exact composition is needed at 3 call sites (`dataInicio` ×2 files, `dataFim` ×2 files, `recurrenceEndDate` ×1 file) with zero prior precedent to keep them visually aligned, building one shared composed component (e.g. `web/src/components/shared/date-picker-field.tsx`, parameterized by an optional `withTime` prop) is strongly recommended over 5 inline duplications — this is the same anti-drift rationale Phase 104 used to justify a single shared `DataTable` pattern instead of 5 per-module reimplementations. Final naming/shape is Claude's call.

## Typography

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`/`105-UI-SPEC.md`, unchanged base scale. No new type role introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`) | 600 semibold | 1.4 |
| Heading | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display | 30px (`text-3xl`) | 600 semibold | 1.2 |

Component-specific notes:

- `SelectTrigger`/`SelectItem` render at `text-sm` (14px, Body), unweighted (inherits 400) — this **replaces** the 3 filter native `<select>`s' current `text-xs font-bold` (12px/700, a 3rd weight value outside this project's declared pair). This is a deliberate typography-contract correction during migration, not a preservation requirement (Scope note #3) — matches the precedent Phase 105 set for the same kind of primitive-default-corrects-legacy-violation move.
- `NativeSelect` in the two form files renders at its own shipped `text-sm` (14px), unweighted — the legacy `selectClassName` const it replaces was already `text-sm` with no weight override, so this is a like-for-like typography match, zero visible change.
- The date-picker trigger `Button` uses `font-normal` explicitly (`className="... font-normal"`, per the shared trigger anatomy table) — overriding `buttonVariants`' own default `font-medium` (500), matching the shadcn official Date Picker demo's own choice to keep the date label visually calm (Body-weight-adjacent, not button-emphasis weight). This introduces no new declared weight value — 400 is already Body's weight.
- The filter label chips ("Processo"/"Categoria"/"Estado", `text-[10px] font-bold`) are a pre-existing 10px/700 styling **not part of this phase's scope** (Scope note left them explicitly untouched) — flagged so the checker does not read this as a new violation introduced by AGD-37; it predates this phase and `106-CONTEXT.md` does not authorize touching it.
