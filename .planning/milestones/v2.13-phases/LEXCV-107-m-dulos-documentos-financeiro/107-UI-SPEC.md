# Phase 107 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Phase 107 covers DOF-01 (`Progress` for the upload bar, 3 duplicated call sites) and DOF-02 (`Select`/`NativeSelect` for tipo/honorário/pagamento forms — resolved per `107-CONTEXT.md`'s locked scope note below). Per the same document, the phase is expanded with a deliberate, user-approved scope addition: a brand-new **`Combobox`** composition (`Popover`+`Command`, the first `Command` consumer in the project) covering 4 call sites — 2 upgrading an existing `datalist` (free-typeable, not a closed list) for `Documento.tipo`, and 2 upgrading a free-text UUID `Input` filter (Processo/Cliente) on the Documentos list page to a searchable-by-name dropdown.

**Locked scope boundary (from `107-CONTEXT.md`, do not re-litigate):**
- `Pagamento.metodo` stays free text — no enum exists in any layer, inventing one needs a product decision not made here. Out of scope.
- `Documento.tipo` in `documentos/novo/page.tsx` (the standalone upload form) stays a plain `Input`, **not** upgraded to `Combobox` — there is no processo/cliente context yet at that point in the flow to source suggestions from.
- The financeiro edit-honorário Dialog (`financeiro/[id]/page.tsx:270-329`) has zero select-worthy fields (`valorTotal`/`dataAcordo`/`descricao`, all `Input`) — confirmed by direct read, nothing to migrate there.
- RBAC `isFetched` fix bundled into this phase (6 gates: `documentos/page.tsx:35`, `documentos/novo/page.tsx:120`, `documentos/[id]/page.tsx:25`, `financeiro/page.tsx:103`, `financeiro/novo/page.tsx:28`, `financeiro/[id]/page.tsx:80`) is a functional/non-visual correction, not part of this visual contract — flagged here only so the checker doesn't expect a UI-SPEC entry for it.

**Verified-against-source findings (load-bearing for planning — re-verified directly against current source, some correct or sharpen `107-CONTEXT.md`'s own line numbers/assumptions):**

1. **Global `--radius` is `0rem`, confirmed at `web/src/app/globals.css:75` (`:root` block)** — this is project-wide, not a Clientes/Processos-only scoped override as `106-UI-SPEC.md` stated (`--radius: 0.5rem`/`radius-vega` default claim was inaccurate; superseded here by direct source read). Every `rounded-md`/`rounded-lg`/`rounded-xl`/`rounded-2xl` class computes to a visual `0` site-wide already (`--radius-md: calc(var(--radius) * 0.8)` etc., all zero when `--radius: 0`). The explicit `rounded-none` classNames littered through the Processo/Cliente ficha Dialogs (e.g. `processos/[id]/page.tsx:2571`, `:2596`, `:2628`, `:2638`) are therefore visually redundant with the token today, kept only for literal-class consistency with sibling elements in the same dialog. New Combobox trigger buttons at those 2 call sites should still carry an explicit `rounded-none` class to match that literal-class convention (zero visual difference either way, but consistent with the file's existing pattern) — see Component Inventory.
2. **Both Financeiro list filters (`financeiro/page.tsx`), not just one, use an empty-string `""` sentinel** (`filtroProcesso` defaults to `useState("")`, line ~142; `filtroStatus` defaults to `useState<"" | "Pendente" | "Parcialmente Pago" | "Pago">("")`, line ~143; both filters' first `<option value="">Todos</option>`, lines ~217/~233). Radix `Select.Item` cannot take `value=""` (throws at runtime, same restriction `106-UI-SPEC.md` scope note #4 already documented for Agenda). **Both** filters need a non-empty sentinel (e.g. `"todos"`) and an updated truthy-check → `!== "todos"` comparison in the filter predicates (lines ~150-151) — this is a required logic change for **2** filters here, not 1 like Agenda's case (where Categoria/Estado already used `"todos"` and only Processo needed the fix). Do not scope this as a pure template swap.
3. **All 3 upload-progress duplicates are byte-identical**: outer `<div className="h-2 w-full rounded-full bg-neutral-200 dark:bg-neutral-700">` wrapping an inner `<div className="h-2 rounded-full bg-blue-600 transition-all" style={{ width: \`${progresso}%\` }} />`, preceded by a `flex justify-between text-xs` "A enviar... / {progresso}%" label row — confirmed identical across `documentos/novo/page.tsx:179-192`, `processos/[id]/page.tsx:2608-2621` (inside `ProcessoDocumentosTab`'s upload Dialog), `clientes/[id]/page.tsx:1340-1353` (inside `ClienteDocumentosEntreguesTab`'s upload Dialog). Tailwind's `blue-600` is `#2563eb` — **byte-identical** to `--primary` in light mode. Today's hardcoded fill has **no** dark-mode variant (same `bg-blue-600` renders in both themes); `Progress`'s shipped `bg-primary` indicator **does** shift in dark mode (`--primary: #3b82f6`, blue-500) — a small, deliberate tokenization delta, not a regression. See Color section for the accent-reservation update this causes.
4. **`command.tsx`'s `CommandItem` already auto-renders a trailing `CheckIcon`**, gated on a `data-checked` attribute the *consumer* must pass explicitly (`group-data-[checked=true]/command-item:opacity-100`) — this is distinct from cmdk's own built-in `data-selected` (keyboard/mouse hover highlight, unrelated to "is this the chosen value"). This is **not** the classic public shadcn combobox demo's pattern of manually rendering `<Check className={cn("ml-auto", value === x.value ? "opacity-100" : "opacity-0")} />` as a child — do not add a second manual check icon, or a double-checkmark bug results. Pass `data-checked={value === option.value}` on `<CommandItem>` and render **only** the item's label as children.
5. **`CommandInput` is pre-wrapped in `InputGroup`/`InputGroupAddon`** (`command.tsx:65-86`), which already renders a leading `SearchIcon` (`align="inline-start"`, confirmed default in `input-group.tsx:41`) and force-sets `h-8`. Do not pass a `className="h-9"`-style height override to `CommandInput` the way the classic public demo does — this project's version doesn't need it and the height is already fixed internally.
6. **`useProcessos()`/`useClientes({})` already fetch the full, unfiltered list client-side** (confirmed: no server-side search-as-you-type parameter is used anywhere in the app for these two hooks) — both Documentos-list filter Comboboxes and the existing `processoById`/`clienteNomeById` maps on the same page already rely on this. The new Combobox filters do **not** need debounced server search; filter the already-fetched array client-side, matching the pattern already used elsewhere on the same page.
7. **Radix's Popover-content-matches-trigger-width CSS variable was not independently confirmed against this exact `radix-ui` package build** (attempted a source grep, inconclusive against the minified bundle). Rather than depend on an unverified variable, this spec prescribes a fixed comfortable width (`w-80`, see Component Inventory) for the 2 filter Comboboxes' `PopoverContent` instead of trigger-width-matching — safe, on-scale, and independent of the trigger's own responsive width in the 3-column filter grid.

### Combobox (Popover + Command) — new composition, first `Command` consumer in the project

**Two distinct behavioral modes — do not conflate them:**

| Mode | Call sites | Behavior |
|------|-----------|----------|
| **Creatable** (open list, can type a brand-new value) | `Documento.tipo` in `processos/[id]/page.tsx` `ProcessoDocumentosTab` (`:2592-2606`); `Documento.tipo` in `clientes/[id]/page.tsx` `ClienteDocumentosEntreguesTab` (`:1324-1338`) | Suggestions come from `tipoOptions` (already-used tipos scoped to that processo/cliente); the user can also type any value not in the list and commit it directly |
| **Closed, searchable** (must pick an existing entity) | Processo filter in `documentos/page.tsx` (`:112-118`); Cliente filter in `documentos/page.tsx` (`:120-126`) | Options come from `useProcessos()`/`useClientes({})` (full list, already fetched elsewhere on the same page); the user can only select an existing processo/cliente or clear the field — no "create new" affordance |

**Shared trigger anatomy (both modes):**

| Element | Value |
|---------|-------|
| Trigger | `<PopoverTrigger asChild><Button type="button" variant="outline" role="combobox" aria-expanded={open} className="w-full justify-between font-normal">` |
| Trigger label | `<span className={cn(!selected && "text-muted-foreground")}>{selected ? selected.label : placeholder}</span>` — selected-value text at Body weight; placeholder in `text-muted-foreground` |
| Trailing icon | `<ChevronsUpDown className="ml-2 h-4 w-4 shrink-0 opacity-50" />` (new import, first use in project) — trailing, not leading, distinguishing this composition's anatomy from `DatePickerField`'s leading `CalendarIcon` |
| `font-normal` override | Explicit, same rationale `DatePickerField` established (Phase 106): the trigger displays a chosen **data value**, not a button-action label, so it should not inherit `buttonVariants`' own `font-medium` (500) default — keeps both of this project's composed Popover-trigger patterns visually consistent with each other |
| Popover content | `<PopoverContent className="w-80 p-0" align="start">` — fixed `w-80` (320px, on the 4px/8pt scale), **not** trigger-width-matching (see Verified-against-source finding #7); `p-0` because `Command` supplies its own `p-1` |
| Command | `<Command shouldFilter={false}>` — **manual filtering required**, do not rely on cmdk's built-in fuzzy filter (needed for the creatable mode's synthetic "create" item to always render regardless of cmdk's own match logic; kept identical for the closed-list mode for one consistent implementation) |
| Search input | `<CommandInput placeholder={...} value={query} onValueChange={setQuery} />` — leading `SearchIcon` and `h-8` sizing are already baked in (finding #5), do not override |
| List | `<CommandList><CommandGroup>{filtered.map(...)}</CommandGroup></CommandList>` |
| Selected-item indicator | `data-checked={option.value === value}` on `<CommandItem>`, **children = label text only** — do not manually render a `Check` icon (finding #4) |
| Close-on-select | `onSelect={() => { onChange(option.value); setOpen(false); setQuery(""); }}` — matches `DatePickerField`'s immediate-close-on-selection UX, no separate "Aplicar" step |

**Creatable-mode specifics (`Documento.tipo`, ×2):**

| Element | Value |
|---------|-------|
| Trigger placeholder | `"Selecionar ou escrever tipo..."` |
| Search placeholder | `"Pesquisar ou escrever novo tipo..."` |

| Element | Value |
|---------|-------|

## Typography

Inherited from `101-UI-SPEC.md`/`102-UI-SPEC.md`/`104-UI-SPEC.md`/`105-UI-SPEC.md`/`106-UI-SPEC.md`, unchanged base scale. No new type role introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`) | 600 semibold | 1.4 |
| Heading | 24px (`text-2xl`) | 600 semibold | 1.2 |
| Display | 30px (`text-3xl`) | 600 semibold | 1.2 |

Component-specific notes:

- `SelectTrigger`/`SelectItem`/`NativeSelect`/`CommandInput`/`CommandItem` all render at `text-sm` (14px, Body), unweighted (inherits 400) — a like-for-like match with the legacy raw `<select>`/`<input>` styling they replace, zero visible type-scale change.
- The Combobox trigger `Button` uses `font-normal` explicitly (see Component Inventory), overriding `buttonVariants`' own default `font-medium` (500) — matching `DatePickerField`'s established precedent (Phase 106) for composed Popover-trigger controls that display a chosen data value rather than an action label. This introduces no new declared weight value — 400 is already Body's weight.
- **Pre-existing, out-of-scope note:** the Financeiro filter label chips ("Processo"/"Estado"/"Data de"/"Data até", `text-xs font-medium text-neutral-500 dark:text-neutral-400`) use `font-medium` (500) — a 3rd weight value outside this project's declared 400/600 pair, the same class of issue `106-UI-SPEC.md` flagged for Agenda's `font-bold` (700) filter labels. This predates this phase, is not touched by DOF-01/DOF-02 (only the *control*, not its label, is in scope), and is flagged here purely so the checker does not misattribute it as a new violation this phase introduces.
- `CommandGroup`'s own `**:[[cmdk-group-heading]]:text-xs font-medium` styling only applies if a `CommandGroup` uses a `heading` prop — none of the 4 Combobox call sites in this phase use one (single flat group each), so this styling path is never exercised.
