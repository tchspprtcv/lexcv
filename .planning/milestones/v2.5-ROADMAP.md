# Milestone v2.5: Módulo de Parecer Jurídico

**Status:** ✅ SHIPPED 2026-06-30 (backend-only — ver Scope Note)
**Phases:** 61-64
**Total Plans:** 7

## Overview

Gerir o ciclo completo de pareceres jurídicos (solicitação → elaboração com versionamento → aprovação opcional → entrega), com auditoria automática e pesquisa avançada, reutilizando as entidades e padrões já existentes no LexCV (`Cliente`, `User`+role `ADVOGADO`, `AuditLog`, `StorageService`). A especificação original genérica foi adaptada ao domínio real do LexCV para evitar duplicação de entidades já existentes.

**Scope Note:** Esta milestone entregou apenas a camada de API backend — sem UI frontend. Decisão explícita e repetidamente confirmada durante o discuss de cada uma das 4 fases (ver `*-CONTEXT.md` de cada fase). O texto de `REQUIREMENTS.md` usa a fraseologia "Utilizador pode..." que, tomada literalmente, só é verdade a nível de chamada API direta neste momento — não através da aplicação web LexCV. A frontend UI ficou planeada para uma milestone futura (v2.6).

## Phases

### Phase 61: Data Layer + Backend CRUD

**Goal**: Existe uma base de dados e API funcionais para criar, atribuir e listar solicitações de parecer, com RBAC dedicado
**Depends on**: Nothing (first phase of milestone)
**Requirements**: PARC-01, PARC-02, PARC-03, PARC-04, PARC-05, PARC-06, PARC-10
**Plans**: 2 plans

Plans:

- [x] 61-01: Entidade ParecerSolicitacao, repositório e seeding RBAC pareceres:*
- [x] 61-02: ParecerController CRUD + atribuição de advogado com validação de papel ADVOGADO

**Details:**
Novo controller dedicado `ParecerController.java` (não adicionado ao `ResourceController.java` já com ~2300 linhas). Base path `/api/v1/pareceres/solicitacoes`. UUID interno, sem numeração sequencial visível. Status livre (`PENDENTE`/`EM_ELABORACAO`/`EM_REVISAO`/`CONCLUIDO`), transição automática para `EM_ELABORACAO` ao atribuir advogado. Scopes `pareceres:view/create/edit/manage` seedados por role e mirrorados em `web/src/lib/permissions.ts`. Code review: 2 iterações — CR-01/CR-02 (IDOR cross-tenant em `clienteId`/`processoId`), WR-01..04 (allowlist de criação, case-sensitivity, mensagens de erro, guarda de null em PUT parcial).

### Phase 62: Elaboração e Versionamento

**Goal**: O advogado responsável consegue elaborar o parecer em versões sucessivas, cada uma com conteúdo, anexo opcional e histórico rastreável
**Depends on**: Phase 61
**Requirements**: PARV-01, PARV-02, PARV-03, PARV-04
**Plans**: 2 plans

Plans:

- [x] 62-01: Entidade ParecerVersao + repositório (numeração sequencial por solicitação)
- [x] 62-02: Endpoints /versoes no ParecerController (criar com multipart, listar, detalhe, download de anexo via StorageService)

**Details:**
`ParecerVersao` imutável (sem endpoint UPDATE), `numeroVersao` via `synchronized` MAX+1 por solicitação (mesmo padrão de `Cliente.numeroSequencial`). Anexo reutiliza `StorageService`/`Documento` já existentes. Criação restrita ao advogado responsável ou ADMIN. Code review: 1 iteração — CR-01 (race condition no `synchronized` block só cobria a leitura, não o save), WR-01 (unique constraint DB em falta), WR-02 (limpeza de upload órfão no MinIO em caso de falha).

### Phase 63: Aprovação e Entrega

**Goal**: O parecer pode ser revisto internamente antes de ser entregue, e uma vez entregue fica disponível para consulta pela equipa/cliente
**Depends on**: Phase 62
**Requirements**: PARC-07, PARC-08, PARC-09
**Plans**: 1 plan

Plans:

- [x] 63-01: Campos aprovado/versaoFinalId nas entidades + endpoints /aprovar e /entregar no ParecerController

**Details:**
Aprovação restrita a ADMIN (`pareceres:manage` — não existe role SUPERVISOR no LexCV). Entrega permitida ao advogado responsável ou ADMIN (`pareceres:edit`). Entrega é irreversível — sem endpoint para reverter `CONCLUIDO`. Code review: 1 iteração — CR-01 (o `@PreAuthorize` de `/entregar` exigia `pareceres:manage`, tornando o ramo de código do advogado responsável inalcançável; corrigido para `pareceres:edit` mantendo a verificação de ownership em método), WR-01 (ordem das guardas).

### Phase 64: Auditoria e Pesquisa Avançada

**Goal**: Todas as ações relevantes sobre pareceres ficam auditadas automaticamente e qualquer parecer pode ser encontrado por texto livre combinado com filtros
**Depends on**: Phase 63
**Requirements**: PARA-01, PARS-01, PARS-02
**Plans**: 2 plans

Plans:

- [x] 64-01: Auditoria automática nos 5 endpoints de transição do ParecerController (AuditLog.save)
- [x] 64-02: Endpoint GET /pareceres/pesquisa + método de repositório (ILIKE texto livre + filtros combinados)

**Details:**
Reutiliza `AuditLog`/`AuditLogRepository` existentes sem alteração de schema. Pesquisa via `ILIKE` nativo do Postgres sobre `ParecerVersao.conteudo` (versão mais recente apenas, via subquery `MAX(numeroVersao)`), sem motor de busca externo nem índice full-text dedicado nesta v1. Code review: 1 iteração — CR-01 (JOIN interno excluía indevidamente solicitações sem versões de todos os resultados de pesquisa, não só de pesquisas por texto; corrigido para LEFT JOIN), WR-02 (`@Transactional` em falta nos 5 endpoints de transição para atomicidade entre save principal e save de auditoria).

## Milestone Summary

**Key Decisions:**

- Adaptar a especificação técnica genérica anexada ao domínio real do LexCV, reutilizando `Cliente`, `User`+`Role`, `AuditLog` em vez de duplicar entidades — evita deriva de dados e duplicação de RBAC
- Novo `ParecerController.java` dedicado em vez de expandir o já grande `ResourceController.java`
- Backend-only nesta milestone — UI frontend deliberadamente adiada, decisão confirmada em todas as 4 fases
- Sem workflow de aprovação multi-nível — aprovação interna é um passo simples (um único supervisor/ADMIN aprova/não aprova)
- Sem motor de busca externo — `ILIKE` nativo do Postgres é suficiente para o volume atual

**Issues Resolved:**

- 2 IDOR cross-tenant críticos (Fase 61)
- 1 race condition em numeração de versão (Fase 62)
- 1 mismatch de permissão que tornava inalcançável a lógica de autorização do advogado responsável (Fase 63)
- 1 bug de JOIN que excluía solicitações sem versões de toda a pesquisa (Fase 64)

**Issues Deferred:**

- UI frontend do módulo de pareceres — candidata a v2.6
- Comparação visual (diff) entre versões
- Índice full-text dedicado (tsvector/trigram) para pesquisa, se o volume justificar
- Numeração sequencial visível para pareceres (tipo PAR-0001), se necessidade legal formal surgir

**Technical Debt Incurred:**

- Nenhum endpoint `/pareceres/*` tem consumidor frontend — API funcional mas inacessível via produto até UI ser construída
- `versaoFinalId` (Fase 63) só é visível no JSON genérico das respostas GET existentes, sem vista dedicada "parecer entregue"
