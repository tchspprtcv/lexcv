## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → PUT /clientes/{id} | Edit-mode form submits an untrusted ClienteUpdateRequest payload; backend must remain the authoritative validator |
| client UI edit gate → server authorization | The new `isEditing` boolean and the existing `canEditClientes` RBAC flag are UX gates only; the backend `@PreAuthorize("hasAuthority('clientes:edit')")` on updateCliente is the real authorization boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-75-01 | Elevation of Privilege | `isEditing` toggle in [id]/page.tsx | accept | `isEditing` is a pure UX/visual state and is NOT an authorization mechanism. The Editar toggle is already gated on `canEditClientes` (view-permission gates the page, edit-permission gates the toggle), and the actual PUT is authorized server-side by the unchanged `@PreAuthorize` on updateCliente. A user forcing `isEditing=true` in devtools still cannot save without `clientes:edit`. No new authorization surface is introduced by this plan. |
| T-75-02 | Tampering | ClienteUpdateRequest payload | mitigate | Payload shape and Zod validation (`buildClienteFormSchema`) are reused verbatim from the existing edit page — no relaxation of client-side validation; backend Bean Validation remains the enforcement layer (unchanged). |
| T-75-03 | Information Disclosure | view-mode page-level gate | mitigate | View-permission gate (`canViewClientes` → AccessDeniedState) is preserved verbatim from the current detail page; the dropped standalone edit-route AccessDeniedState is redundant now (no separate route to guard). |
| T-75-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages installed by this plan (pure merge of existing code); nothing to audit. |
