# Phase 75 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

This phase is a **structural/interaction merge, not a redesign**. Per 75-CONTEXT.md (`<specifics>`): "o resultado final deve ser visualmente idêntico ao que existe hoje em ambos os modos (leitura = página atual `[id]/page.tsx`; edição = formulário atual `[id]/editar/page.tsx`), apenas unificados numa única página com toggle."

Both source pages were read in full:
- `web/src/app/(dashboard)/clientes/[id]/page.tsx` (902 lines) — read-only view: `dl`/`dd` 3-col grid for "Dados"/"Informações Adicionais", `Card`-wrapped `ClienteContactosCard`/`ClienteNotasCard`/`ProcuracaoCard`/`ResponsaveisCard`.
- `web/src/app/(dashboard)/clientes/[id]/editar/page.tsx` (740 lines) — edit form: same `Card` shell, react-hook-form + Zod (`buildClienteFormSchema`), native `<select>`s styled via shared `selectClassName`/`textareaClassName` constants, 3 staged intake lists (Documentos Entregues/a Tratar, Deslocações) with `Dialog`-based "Adicionar" modals.

No new screens, no new component library additions, no new color/typography/spacing tokens. Following the Phase 74 precedent (`74-UI-SPEC.md`), this spec stays narrow and points at existing code as the literal visual source of truth rather than re-describing it.

**Design System detected:** No `components.json` in `web/` — no shadcn CLI. Hand-rolled Radix-based primitives under `web/src/components/ui/` (`Button`, `Card`, `Dialog`, `Input`, `Label`, `RadioGroup`, `Switch`, `Badge`), flat/`rounded-none` convention for form inputs and staged-list items, `rounded-md` convention (from CVA `buttonVariants`) for `Button`/`Card`. Shared `selectClassName`/`textareaClassName` string constants already exist in `editar/page.tsx` and should move with the merged logic (or be extracted) rather than be re-authored. The shadcn initialization gate is **not applicable** — this phase introduces zero new UI primitives, only a new boolean-gated rendering mode over two already-built pages.

## Typography

No new typography introduced. Verified directly against both source files (`grep -n "font-semibold\|font-medium\|font-normal\|font-bold"` across `[id]/page.tsx` and `[id]/editar/page.tsx`): across all headings, section sub-headings, and emphasized field values, exactly **two** distinct weight utility classes are declared — `font-semibold` (600) and `font-medium` (500). Everything else (breadcrumbs, `dt` labels, plain `dd` values, muted/secondary text) carries **no weight class at all** and simply inherits the base/unstyled body weight — it is not a third *declared* weight, it is the absence of one. (Badge-only `font-bold`/`font-normal` micro-uses on the `numero_cliente`/status badges are pre-existing, out of scope for this phase, and not part of the page's text-role hierarchy.)

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Page H1 ("Cliente" / section sub-headings "Informações Adicionais", "Intake do Caso") | 24px (`text-2xl`) for H1, 18px (`text-lg`) / 14px (`text-sm`) for sub-headings | 600 (`font-semibold`) for H1; 500 (`font-medium`) for sub-headings | default (existing, unchanged) |
| Emphasized value (Nome `dd`, contact/responsável name values) | 14px (`text-sm`) | 500 (`font-medium`) | 1.5 (existing, unchanged) |
| Body / `dl`/`dd` plain values, breadcrumb, muted labels | 14px (`text-sm`, `text-sm text-neutral-500`) | no weight class declared — inherits base/unstyled weight (existing, unchanged) | 1.5 (existing, unchanged) |
| Card title (`CardTitle`) | existing `CardTitle` component default (unchanged) | existing default (unchanged) | existing default |

Declared weights for this phase: **2** — `font-semibold` (600) and `font-medium` (500). No third weight is introduced or relied upon.

## Interaction Contract (the actual new design surface)

This is the real scope of Phase 75's UI work. The checker/executor should validate against this section more than the boilerplate sections above.

### 1. Header button cluster state machine

Three mutually exclusive states, driven by local `isEditing` boolean (per CONTEXT.md — not URL-reflected):

| State | Buttons rendered (left to right) | Variants |
|-------|-----------------------------------|----------|
| View mode (`isEditing === false`) | `Voltar` · `Imprimir Ficha` · `Editar` (only if `canEditClientes`) | `outline` · `outline` · `default` |
| Edit mode (`isEditing === true`) | `Voltar` · `Imprimir Ficha` · `Cancelar` · `Guardar` | `outline` · `outline` · `outline` · `default` |
| Saving (`isEditing === true`, mutation pending) | same as edit mode, `Guardar` disabled with `A guardar...` label, `Cancelar` disabled | same, `Guardar` shows loading text per existing pattern |

`Voltar` and `Imprimir Ficha` never change position or behavior — they are outside the toggle's blast radius (CONTEXT.md: these sit "junto a" the toggled buttons in the header, not replaced by them).

### 2. Per-field read/edit rendering

For every field currently shown as `dl`/`dt`/`dd` in view mode and as `Label`+`Input`/`select`/`RadioGroup`/`Switch` in edit mode: render conditionally on `isEditing`. CONTEXT.md gives explicit discretion on the exact conditional structure (inline-per-field vs. larger blocks) — **not prescribed here** — but the rendered output for each mode must be pixel-identical to the current standalone pages:
- View mode: `dl className="grid grid-cols-3 gap-x-4 gap-y-3 text-sm"` pattern, unchanged.
- Edit mode: existing form field markup (`Label` + `Input rounded-none` / `selectClassName` / `RadioGroup` / `Switch`), unchanged.

### 3. Sub-component edit-gating (new prop required)

`ClienteContactosCard`, `ClienteNotasCard`, `ResponsaveisCard`, and the procuração `FileDropZone` block currently gate their inline CRUD affordances on `canEditClientes` (an RBAC/permission flag) alone. Per CONTEXT.md, add a second, independent gate for the page-level edit-mode toggle:

- **Naming:** use `editable: boolean` (or `readOnly: boolean` — pick one convention and apply consistently across all four; do not mix). Recommendation: `editable` (positive framing matches existing `canEditClientes` positive framing already used everywhere else in this codebase).
- **Semantics:** an affordance renders only when **both** `canEditClientes === true` AND the new `editable === true` (i.e., `isEditing` from the parent). This is an AND, not an OR/replace — RBAC still fully applies inside edit mode.
- **Affected affordances per component:**
  - `ClienteContactosCard` / `ClienteNotasCard`: the "Adicionar" input row + `Adicionar`/`Adicionar nota` button, and per-item `Editar`/`Remover`/`Guardar`/`Cancelar` buttons.
  - `ResponsaveisCard`: the "Adicionar" button (opens modal) and per-item `Remover` button.
  - Procuração `FileDropZone` block: the upload dropzone (both "no procuração yet" and "substituir ficheiro" variants) and the `Remover` button. The `Ver / Download` button stays visible in both modes (it's a read action, not an edit action).
- **Visual result when `editable === false`:** identical to today's `canEditClientes === false` rendering — these affordances are already implemented as conditionally-hidden (`{condition ? <Button/> : null}`), not disabled-in-place. Keep that same hide-not-disable pattern for consistency; do not introduce a new disabled/grayed-out visual state.

### 4. Cancel behavior

`Cancelar` (edit mode only) performs, in order: `form.reset(defaultValues)` → discard staged intake-list local state (documentosEntregues/documentosATratar/deslocacoes revert to last-loaded `cliente.data` values) → `setIsEditing(false)`. No confirmation dialog (explicit CONTEXT.md decision). No navigation occurs — stays on `/clientes/[id]`.

### 5. Save behavior

On successful `Guardar`: `useUpdateCliente(id).mutateAsync(payload)` (unchanged hook/payload shape) → toast success → TanStack Query invalidation (existing pattern) → `setIsEditing(false)` → remain on `/clientes/[id]`. No `router.push` (the old edit page's redirect-after-save is removed; CONTEXT.md: "fica na mesma página... sem navegação/redirect").

### 6. Route removal

`web/src/app/(dashboard)/clientes/[id]/editar/page.tsx` is deleted outright — no redirect shim, no compatibility route. Any remaining internal links pointing to `/clientes/[id]/editar` (e.g., from a clientes list or elsewhere) must be updated to just link to `/clientes/[id]` (this phase's `Editar` action is a state toggle, not a route).
