```java
@Transactional
@PreAuthorize("hasAuthority('processos:manage')")
@PostMapping("/processos/{id}/formalizar")
public ResponseEntity<?> formalizarProcesso(@PathVariable UUID id) {
    UUID tenantId = getTenantId();
    Processo processo = processoRepository.findById(id).orElse(null);
    if (processo == null || !processo.getTenantId().equals(tenantId)) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(Map.of("message", "Processo não encontrado"));
    }

    // (0) BLOQUEIO POR ESTADO — só processos em TRIAGEM podem ser formalizados
    if (!"TRIAGEM".equalsIgnoreCase(processo.getEstado())) {
        return ResponseEntity.status(HttpStatus.CONFLICT).body(Map.of(
                "message", "Não é possível formalizar: o processo não está em estado de TRIAGEM"
        ));
    }

    // (a) BLOQUEIO POR CAMPOS MÍNIMOS
    String tipoProcesso = processo.getTipoProcesso() != null ? processo.getTipoProcesso().toLowerCase() : null;
    List<String> camposObrigatorios = CAMPOS_MINIMOS_POR_TIPO.getOrDefault(tipoProcesso,
            CAMPOS_MINIMOS_POR_TIPO.get("default"));
    List<String> camposEmFalta = new ArrayList<>();
    for (String campo : camposObrigatorios) {
        switch (campo) {
            case "clienteId" -> { if (processo.getClienteId() == null) camposEmFalta.add(campo); }
            case "numeroProcesso" -> { if (processo.getNumeroProcesso() == null || processo.getNumeroProcesso().isBlank()) camposEmFalta.add(campo); }
            case "tipoProcesso" -> { if (processo.getTipoProcesso() == null || processo.getTipoProcesso().isBlank()) camposEmFalta.add(campo); }
            case "areaJuridica" -> { if (processo.getAreaJuridica() == null || processo.getAreaJuridica().isBlank()) camposEmFalta.add(campo); }
            case "tribunal" -> { if (processo.getTribunal() == null || processo.getTribunal().isBlank()) camposEmFalta.add(campo); }
            case "dataInicio" -> { if (processo.getDataInicio() == null) camposEmFalta.add(campo); }
            case "descricao" -> { if (processo.getDescricao() == null || processo.getDescricao().isBlank()) camposEmFalta.add(campo); }
            case "origem" -> { if (processo.getOrigem() == null) camposEmFalta.add(campo); }
        }
    }
    if (!camposEmFalta.isEmpty()) {
        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY).body(Map.of(
                "message", "Não é possível formalizar: faltam campos mínimos obrigatórios para este tipo de processo",
                "camposEmFalta", camposEmFalta
        ));
    }

    // (b) BLOQUEIO POR DECISÃO DE CONFLITO
    ConflictCheckDecisao decisao = conflictCheckDecisaoRepository
            .findByTenantIdAndProcessoId(tenantId, id).orElse(null);
    if (decisao == null) {
        return ResponseEntity.status(HttpStatus.CONFLICT).body(Map.of(
                "message", "Não é possível formalizar: o conflict check ainda não tem uma decisão registada"
        ));
    }
    if ("impeditivo".equals(decisao.getNivel())) {
        return ResponseEntity.status(HttpStatus.CONFLICT).body(Map.of(
                "message", "Não é possível formalizar: existe um conflito impeditivo registado"
        ));
    }

    // Transition TRIAGEM -> ATIVO
    processo.setEstado("ATIVO");
    return ResponseEntity.ok(processoRepository.save(processo));
}
```

```java
@Getter

public class Honorario {
    @Id

    private Integer id;

    @Column(name = "processo_id", nullable = false)

    @Column(name = "data_acordo")

}
```

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client (authenticated user with `processos:manage`) → `POST /processos/{id}/formalizar` | Already-authenticated, tenant-scoped request; this plan adds a side-effect (Honorario row creation) triggered by a permission scope (`processos:manage`) that is NOT the same scope that gates direct financial writes (`financeiro:edit`, per `createHonorario`/`updateHonorario`) |
| `formalizarProcesso` → `Honorario` persistence | Server-side only -- no client-supplied field flows into the created `Honorario` row; `processoId` comes from the already-validated path variable, `dataAcordo` is server-computed (`LocalDate.now()`), `valorTotal` is a hardcoded `null` literal, never derived from request body or `Cliente.honorariosPropostos` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-82-01 | Tampering / Repudiation | `formalizarProcesso` Honorario creation | mitigate | `honorarioRepository.findByProcessoId(id).isEmpty()` existence check runs before every creation, independent of the `estado != TRIAGEM` guard -- protects against retries/replays that reach the transaction more than once (network retry, double-submit racing ahead of the estado guard's own commit); verified explicitly by Task 2's double-formalize live test and the `GROUP BY ... HAVING COUNT(*) > 1` SQL detection query |
| T-82-02 | Tampering | `Honorario.valorTotal` on auto-creation | mitigate | `valorTotal` is hardcoded to the literal `null` inside `formalizarProcesso` -- no code path in this plan reads `Cliente.honorariosPropostos` or any client-supplied numeric value; a real `valorTotal` can only be set afterward via the pre-existing `PUT /honorarios/{id}` (`updateHonorario`), which requires the separate `financeiro:edit` scope. Verified by Task 1's acceptance criteria (zero matches for `honorariosPropostos` inside the method) and Task 2's live test using a cliente with `honorariosPropostos` filled in |
| T-82-03 | Elevation of Privilege | RBAC scope mismatch: `processos:manage` side-effect creates a row in the financial domain | accept | The auto-created `Honorario` carries no monetary value (`valorTotal=null`, `descricao=null`) -- it is an empty placeholder row establishing the `processo_id` linkage only. A user holding `processos:manage` but not `financeiro:edit` can cause this empty row to exist, but cannot set or view a real fee amount through this path (`financeiro:edit` remains the sole gate for writing `valorTotal`). Accepted because no financial value or capability is actually granted; a future milestone could add a stricter check if empty-Honorario visibility itself becomes a concern, but that is out of this phase's scope (PROC-14 only) |
| T-82-04 | Information Disclosure | `Honorario` row visible via existing `GET /honorarios` (`financeiro:view`) after auto-creation | accept | `Honorario` has no `tenant_id` column; isolation is already transitive via the parent `Processo` (unchanged pattern, same as Decisão/Facto/Testemunha in Phase 80/81) -- `listHonorarios` already iterates `processoRepository.findByTenantId(tenantId)` before resolving each processo's honorarios, so the auto-created row is exposed under the exact same tenant boundary as every manually-created `Honorario` today. No new exposure surface introduced by this plan |
