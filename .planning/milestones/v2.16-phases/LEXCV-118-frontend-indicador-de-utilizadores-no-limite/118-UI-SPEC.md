## Interaction Notes

Concrete implementation contract points that fell out of reading the current code — not covered by the tables above but load-bearing for the executor:

1. **Disabled-button + Tooltip is a new pattern in this codebase.** `buttonVariants` bakes in `disabled:pointer-events-none` (`components/ui/button.tsx:8`), which means a Radix `TooltipTrigger asChild` wrapping a natively-`disabled` `<Button>` will never fire. No existing "disabled + explanatory tooltip" precedent exists elsewhere in this app to copy verbatim (only pending-state `disabled` on transient mutations, which don't need a tooltip). Wrap the `Button` in a focusable, non-disabled element as the actual `TooltipTrigger` target (e.g. `<TooltipTrigger asChild><span tabIndex={0}>` around the `Button`), so hover/focus still reaches the tooltip while the inner `<button>` itself stays natively `disabled` (submission is still blocked at the DOM level, independent of the tooltip).
2. **Fetch `Y` via `useMe()`/`usePermissions()` called inside `UserManagementTab` itself**, not prop-drilled from `SettingsPage`. This matches the sub-component's existing self-fetching convention (it already calls its own `useAdminUsers()` and `useAdminRbac()` rather than receiving them as props). TanStack Query dedupes on the shared `["auth", "me"]` query key/cache — calling `useMe()` again here is not a parallel network fetch.
3. **`me` is guaranteed already loaded by the time `UserManagementTab` mounts.** The "Utilizadores" tab button in the parent is itself gated behind `hasUsersManage`, which is derived from `me` (`usePermissions()`), so no additional loading-state branch is needed for `Y` — it cannot be in a pending state at the point this component renders.
4. **`X` uses a strict truthy filter, not the table's display convention.** CONTEXT.md locks `X = users.filter(u => u.ativo).length` (strict `ativo === true`), matching the backend's `countByTenantIdAndAtivoTrue` semantics exactly. This is deliberately different from the existing table row's display logic (`user.ativo !== false`, which treats `undefined` as active for the "Ativo" badge). Do not "fix" this into consistency with the table — the two serve different purposes (display default vs. authoritative count).
5. **Toast prefix must be generalized for the 409 case to read as "clear."** `handleFormSubmit`'s catch block (`settings/page.tsx:292-299`) currently only strips `"API 400: "` (`err.message.replace("API 400: ", "")`). A 409 would otherwise render its local toast as `"API 409: Limite de utilizadores atingido..."`. Generalize the strip to any status code, e.g. `msg.replace(/^API \d{3}: /, "")`, so both the automatic `apiFetch` toast and this component's own local toast render the clean backend sentence.
6. **Layout:** counter text sits directly above the "Novo Utilizador" button, right-aligned, inside the existing `CardHeader` row (`flex flex-row items-center justify-between`, `settings/page.tsx:351`) — replace the bare `<Button>` with a `flex flex-col items-end gap-2` wrapper containing the counter `<span>` then the (tooltip-wrapped) `Button`.
