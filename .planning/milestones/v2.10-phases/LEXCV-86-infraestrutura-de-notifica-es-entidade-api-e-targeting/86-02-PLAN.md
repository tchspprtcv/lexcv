<objective>
Create `NotificacaoService` — the single write choke point through which every notification row is ever persisted OR mutated: `criar(...)` for creation, `marcarLida(...)`/`marcarTodasLidas(...)` for status mutation (called by Plan 86-03's `NotificacaoController` instead of the repository directly) — plus the ADMIN fan-out helper that resolves recipients per the "+ADMIN, never mass-broadcast" targeting rule (NOTF-14). Add `NotificacaoServiceTest` (this backend's first Mockito test) that proves, automatically, the two isolation guarantees the ROADMAP requires — independent rows per recipient (Success Criterion 2, write side) and one independent row per current ADMIN (Success Criterion 3) — plus the scoped mark-read mutation contract the controller depends on.

Purpose: NOTF-14 is a systemic guarantee — "each notification goes only to the directly-linked entity plus ADMIN, never in bulk by view-permission." That guarantee lives here, in recipient resolution + fan-out, and is verifiable now (two test recipients) before any real business trigger exists (those are Phase 87/88). Centralizing status mutation here too (not just creation) keeps the "sole write path" guarantee true for the whole notification lifecycle, not just creation.

Output: `NotificacaoService.java`, `NotificacaoServiceTest.java`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| trigger caller → NotificacaoService | Future callers (Phase 87 controllers, Phase 88 job, Plan 86-03's controller) pass a resolved recipient; the service must never widen distribution beyond the explicit recipient + ADMIN fan-out (the NOTF-14 anti-broadcast rule). |
| recipient A ↔ recipient B / ADMIN rows | Each recipient (including each ADMIN) must own a physically separate row, so one recipient's read/mark-read (`marcarLida`/`marcarTodasLidas`) can never mutate another's state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-86-04 | Information Disclosure | ADMIN fan-out (`notificarAdmins`) + `criar` | mitigate | Fan-out writes ONE independent row per recipient/ADMIN (each with its own `destinatario_id`, its own `lida=false`), never a shared row with a visibility flag — so no recipient can ever read or clear another's notification. Enforced-by-test: `notificarComFanOutAdmin_...` asserts one save per admin; `criar_doisDestinatariosDistintos_...` asserts two distinct-recipient rows. |
| T-86-05 | Tampering | write choke point | mitigate | `NotificacaoService` is the sole path to `notificacaoRepository.save(...)`/`saveAll(...)` — `criar(...)` for creation, `marcarLida(...)`/`marcarTodasLidas(...)` for status mutation (Plan 86-03's controller calls these instead of the repository). Centralizing ALL writes, not just creation, prevents a future caller from persisting a notification without an explicit `destinatarioId`, or flipping `lida` on a row it doesn't own — the anti-mass-broadcast AND anti-cross-recipient-mutation guarantee of NOTF-14. Enforced-by-test: `marcarLida_naoPertenceAoDestinatarioOuInexistente_...` asserts `save(...)` is never called for a foreign/non-existent row. |
| T-86-06 | Repudiation / Elevation | recipient resolution source | accept | Recipient/ADMIN resolution uses the existing `findByTenantIdAndRoleName(tenantId, "ADMIN")` scoped to the caller-supplied tenant; the service never queries across tenants. No new privilege path introduced; risk equivalent to existing role-scoped reads. |
| T-86-SC | Tampering | Mockito test dependency | accept | Mockito is already on the classpath transitively via `spring-boot-starter-test` (backend/pom.xml line 108) with no exclusion — no new package is installed. Supply-chain surface unchanged; no legitimacy checkpoint required. |
