<objective>
Create the persistence foundation for the notifications subsystem: the `Notificacao` JPA entity (one row per event-recipient pair), the `NotificacaoRepository` (whose every method is scoped by BOTH tenant and recipient), and the required manual production migration script that creates `t_notificacao` with the composite read index.

Purpose: This is the contract layer every other Phase 86 plan builds on. It establishes — structurally, before any service or controller exists — the project's first per-recipient-private resource, where isolation depends on a second scoping dimension (`destinatario_id`) that no other entity in this codebase has ever needed.

Output: `Notificacao.java`, `NotificacaoRepository.java`, `backend/migrations/86-create-notificacao-table.sql`.
</objective>

Optional-filter native query idiom — from backend/src/main/java/com/lexcv/repositories/ParecerSolicitacaoRepository.java (lines 24-41).
Every nullable @Param is wrapped in CAST(:param AS type): PostgreSQL cannot infer the type of a bare null bind inside "(:param IS NULL OR ...)" and fails at runtime with "could not determine data type of parameter". nativeQuery=true is required because this idiom is Postgres-specific, not portable JPQL:
```java
@Query(value = "SELECT s.* FROM t_parecer_solicitacao s " +
        "WHERE s.tenant_id = :tenantId " +
        "AND (CAST(:status AS text) IS NULL OR s.status = CAST(:status AS text)) ",
        nativeQuery = true)
List<ParecerSolicitacao> pesquisar(@Param("tenantId") UUID tenantId, @Param("status") String status);
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| service/controller → DB | Downstream callers (Plan 2 service, Plan 3 controller) read/write notifications; the repository is the last line that can enforce dual scoping in SQL. |
| recipient A ↔ recipient B (same tenant) | First-ever intra-tenant per-user privacy boundary in this codebase — the entity/schema must make cross-recipient access structurally impossible, not merely discouraged. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-86-01 | Information Disclosure | NotificacaoRepository finders | mitigate | Every finder signature carries BOTH tenant and destinatario params (`findByIdAndTenantIdAndDestinatarioId`, `countByTenantIdAndDestinatarioIdAndLidaFalse`, `findByTenantIdAndDestinatarioIdAndLidaFalse`); the native `buscarPorFiltros` hard-codes both as non-optional predicates. No tenant-only finder is declared — cross-recipient reads are impossible to express. |
| T-86-02 | Information Disclosure | buscarPorFiltros optional filters | mitigate | `tenant_id`/`destinatario_id` predicates sit BEFORE the optional `categoria`/`lida` CAST filters and are never null-guarded, so a caller cannot widen scope by omitting query params. |
| T-86-03 | Tampering | entity/DDL nullability | mitigate | `destinatario_id` and `tenant_id` are `NOT NULL` at both JPA (`@Column(nullable=false)`) and DDL level; `lida` defaults false via `@Builder.Default` + `DEFAULT FALSE` — no unowned or ambiguous-read-state row can be persisted. |
| T-86-SC | Tampering | dependency installs | accept | No npm/pip/cargo installs in this plan — pure Java + SQL against existing dependencies. Supply-chain surface unchanged; no legitimacy checkpoint required. |
</threat_model>
