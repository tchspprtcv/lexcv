## Gap Closure Record

**Gap:** CLI-05 unsatisfied (first audit pass) — NIF field could be silently overwritten by an unvalidated legacy field (frontend + backend), and NIF validity was enforced only client-side.

**Closure:** Phase 73.1 inserted after Phase 73 (decimal numbering, urgent insertion). Removed the legacy NIF-sync overwrite block from both `novo/page.tsx` and `editar/page.tsx`; removed the server-side twin of the same bug in `ResourceController.createCliente`/`updateCliente`; added `@NotBlank`/`@Pattern(regexp = "^\\d{9}$")` to `Cliente.nif` and `@Valid` to both endpoints.

**Review-caught regression:** Code review on 73.1 found that Hibernate's default JPA-lifecycle Bean Validation (`jakarta.persistence.validation.mode=AUTO`) would also fire the new constraints on every `clienteRepository.save()` call — including three unrelated endpoints (`uploadProcuracao`, `deleteProcuracao`, `mergeClientes`) that fetch and re-save existing `Cliente` entities without touching `nif`. For any pre-existing client with a legacy invalid NIF, this would throw an unhandled `ConstraintViolationException` (no global exception handler exists) — a 500 blocking unrelated operations. Fixed by setting `jakarta.persistence.validation.mode: none` in `application.yml`, which disables only the JPA-lifecycle validation layer while leaving Spring MVC's `@Valid` controller-boundary enforcement (the actual CLI-05 mechanism) fully intact — confirmed architecturally independent by the re-audit.

**Re-audit verdict:** Both original BLOCKERs confirmed genuinely closed. The regression fix confirmed correctly scoped with no side effects. Full create-client and edit-client E2E flows re-traced end-to-end with no breaks.
